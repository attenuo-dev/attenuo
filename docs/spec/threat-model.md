# Threat model

- Status: draft
- Date: 2026-10-22
- Related: [RFC-0001](rfc-0001-attenuo.md), [incident list](../research/incidents-2025-2026.md), [ADR-0001](../decisions/0001-separate-enforcement-layer.md)

## Assets

1. **Originating-user identity and consent**: which human a run acts for, and what they allowed.
2. **Capabilities**: the set of (server, tool, argument constraints) each hop may exercise.
3. **Data reachable through tools**: private repos, mailboxes, tenant records.
4. **The decision log**: the only record that distinguishes agent actions from user actions.
5. **Signing keys and lease state** inside attenuo.

## Trust boundaries

```
 [IdP] ──creds──▶ [agent client] ──MCP + token──▶ [attenuo proxy/PDP] ──MCP──▶ [MCP server] ──▶ [upstream API]
   trusted          UNTRUSTED                      TRUSTED (reference monitor)    UNTRUSTED
```

- **Agent client (and the LLM driving it): untrusted.** It may be prompt-injected, buggy, or malicious. It can send any MCP message and any token it holds.
- **Sub-agents: untrusted.** Each is a separate workload with its own credential; a parent cannot vouch for a child's behaviour, only bound its authority.
- **MCP server: untrusted.** It may be a typosquat, a poisoned tool description, or a legitimate server with a vulnerability. It receives only what the proxy forwards.
- **attenuo: trusted reference monitor.** Its correctness is the security argument. It must be small, fail closed, and have its invariants property-tested.
- **IdP: trusted for authentication only.** It is not trusted to express per-tool or per-argument authorization.
- **Policy author and log verifier: trusted.** Policies are code; they get review and tests.
- **A gateway that uses attenuo as its external authorizer: trusted, when one is configured.** With an `[[ext_authz]]` entry, agentgateway asks attenuo about each request and enforces the answer itself ([design](../design/agentgateway-ext-authz.md)). attenuo decides on the method, headers and body the gateway shows it and cannot see what the gateway then sends. So the gateway is trusted to forward exactly that body, once, only after a 2xx answer, to fail closed when attenuo is down, not to cache answers, and to keep the MCP server out of the agent's reach. It authenticates with a shared secret per server (`X-Attenuo-Gateway-Secret`); anyone holding that secret and an agent's token can obtain decisions in that agent's name, each recorded and charged as a real call. Bodies that parsers could read differently, batches and cut bodies are refused, so that what is decided is what an honest gateway forwards. The tool's answer never passes attenuo on this path, so output labelling does not apply to it.

## Attacker capabilities

An attacker may do any of the following; attenuo's guarantees must hold anyway.

- A1. Inject instructions into any content the agent reads (issues, emails, web pages, tool descriptions, tool results).
- A2. Control a sub-agent fully, including crafting arbitrary exchange requests.
- A3. Publish or compromise an MCP server the client connects to.
- A4. Replay or forward any token observed on the wire or in logs.
- A5. Request capabilities broader than the parent holds, or deeper chains than allowed.
- A6. Keep a run alive after the user has withdrawn consent.
- A7. Read the audit log after the fact and attempt to alter or truncate it.
- A8. Be a careless or malicious operator of attenuo, or hold an operator's admin token. Mitigated: each operator has a token of its own and one of three roles (ADR-0016), so a `viewer` cannot revoke, decide approvals, reload policy, refund budgets or mint roots, and an `operator` cannot do the last three; every admin action and every operator approval is in the signed audit log under the operator's name (`urn:attenuo:admin:<name>`), which A7's protections cover; the config holds only token digests, compared in constant time; a stolen operator token can be withdrawn without a restart (remove its entry or expire it, then `POST /admin/operators/reload`, which is audited and refused if it would leave no `admin`), and an entry can carry an `expires_at` after which its token is refused (ADR-0016, update of 2026-11-13). Not mitigated: an operator acting within its role (an `admin` can do everything, and anyone sharing `[admin] token` is recorded only as `urn:attenuo:admin`); a stolen token until someone notices and withdraws it, or until its `expires_at` (expiry is optional, and the server's clock decides it); a stolen `[admin] token`, which has no expiry and is withdrawn only by changing it and restarting; no rotation workflow beyond adding a new entry and reloading, no login with a second factor and no per-operator rate limit; and anyone who can edit the config file or the server's environment, who can add an `admin`. Reads are not audited, so what a `viewer` looked at is not recorded.

Out of scope: compromise of attenuo's host or signing keys, compromise of the IdP, side channels, denial of service against attenuo itself.

Denial of service stays out of scope as a security property: attenuo fails closed, so a swamped server refuses calls rather than letting them through, and nothing here claims it stays available under attack. The server does have basic protections against one caller or a burst taking the process down ([`[limits]`](../reference/config.md#limits), single replica, all in-process): a cap on requests in flight that answers `503` at once instead of queueing (never on `/healthz` or `/readyz`), header, body and handler deadlines, optional per-run (`/mcp`), per-agent and per-peer-address (`POST /token`) rate limits answering `429`, and bounded queues and deadlines behind them (the audit writer's queue and append timeout, upstream connect and response deadlines, key-fetch timeouts, the session registry). A flood beyond these, or from many addresses, is for the network in front of attenuo.

| **mcp-remote RCE** (CVE-2025-6514, Jul 2025, CVSS 9.6, 437,000+ downloads): malicious server URL executed commands on the client | Client-side parsing bug | Nothing directly. | **MCP Inspector unauthenticated RCE** (CVE-2025-49596, Jun 2025) and **nginx-ui MCP endpoint skipped auth** (CVE-2026-33032, Mar 2026) | Missing authentication on an endpoint | Not applicable: these are servers exposed without any auth. attenuo requires a verified token on every call it proxies (**P1**) but cannot protect endpoints reached around it | Direct access to the vulnerable endpoint |
| **MCP STDIO transport design flaw** (Apr 2026, 10 CVEs, 150M+ downloads): configuration became OS commands | Local process model | Not applicable. STDIO servers run in the client's process tree; attenuo's proxy covers streamable HTTP | Local command execution |

## What attenuo does not prevent

Stated plainly so nobody relies on it for these.

- **Legitimate-but-harmful reads.** If policy permits an agent to read a document, attenuo cannot stop the server, or the agent, from sending that content somewhere else through a channel attenuo does not mediate. Exfiltration of permitted data needs egress control and information-flow labels.
- **Server-internal misbehaviour.** A server that receives a clean request and then does something extra (BCC, extra API calls, logging to a third party) is invisible to argument-level policy. That is the sandbox layer's job, which is a stated non-goal ([ADR-0001](../decisions/0001-separate-enforcement-layer.md)).
- **Prompt injection.** attenuo does not detect injected instructions. It assumes the agent is compromised and bounds the damage.
- **Over-permissive policy.** If the policy author permits everything, every property still holds and nothing is protected. The attenuation rule bounds children relative to parents; it does not bound the root.
- **Bypass routes.** Tools reached without going through the proxy (local STDIO servers the agent starts itself, direct API keys in the agent's environment, 79% of servers pass keys via environment variables per [Practical DevSecOps](https://www.practical-devsecops.com/mcp-security-statistics-2026-report/)) are outside the monitor. A STDIO server that the operator runs behind `attenuo stdio-bridge`, out of the agent's reach, is an upstream like any other ([STDIO MCP servers](../guides/stdio-servers.md)); the bridge has no authentication, so anything that can reach its port bypasses the proxy.
- **Compromise of attenuo.** Keys, lease store and log live in the trusted base. Hash chaining detects tampering after the fact. An attacker who holds the host and the issuer key can rewrite the log and sign new checkpoints over it; only checkpoints that left the host earlier catch that. With `[audit.sink]` each checkpoint is shipped when it is signed, and `audit verify --file --checkpoints` reports any one signed again after shipping (SR-21). What remains: entries after the last shipped checkpoint, checkpoints still queued when the host is taken (the queue is bounded and the sink can be down), and a sink whose credentials allow overwriting or deleting. A prune of the log (`[audit.retention]`, off by default) is signed with the same key, so the same attacker can make one that looks like the operator's; the anchors and checkpoints shipped before it, and the operator's own record of when they pruned, are what show it ([ADR-0015](../decisions/0015-audit-retention.md)). With `prune = "auto"` the operator keeps no record of each prune, so a prune made with the key looks like one the timer made; only the shipped anchors (each one's time and boundary, which should trail it by at least `keep_seconds`) show what was pruned when. With `archive_dir` the automatic prune keeps the pruned entries as files on the same host; an attacker who holds the host can delete or replace them, so they count only once copied off the host, and the `archive_sha256` in the shipped anchor is what proves a kept copy is the real one. Without `archive_dir` the pruned entries are not kept at all. The automatic prune trusts the host's clock. Its cutoff is `keep_seconds` before the earliest of now, the newest entry that is not a prune record, and the wall time at start plus the monotonic time since. Inside one process, a clock jump cannot speed pruning up, with or without new entries. Across a restart the server cannot tell a jumped clock from real downtime, so after a restart with a wrong clock the cutoff starts from the wrong time. Entries written while the clock was behind carry old timestamps, and once the clock is set right they can be pruned early by up to that error. On an idle server the last `keep_seconds` before the newest entry are kept. A run is also skipped (`clock_jump`) when the wall clock and the monotonic clock move more than an hour apart, as a signal. `archive_dir`, once copied off the host, is what protects the content. An archive file is signed only when its bytes are the export of its range made again from the log, so a planted file with extra fields or lines is refused. Without the key, deleting the first rows of the log fails `audit verify` as truncation does. Someone who can write the file but holds no key can still insert an anchor row: every read (`GET /admin/audit`, entries, export) starts after the newest anchor row without checking its signature, so a forged row hides the rows below it from reads until it is removed. `audit verify` checks the signature and reports the forged row in `bad_anchors` with `ok: false`, and walks the rows from genesis. Only the signed verify authenticates where the log starts.

## Residual risks to track

- Deployment posture the server enforces at startup. attenuo assumes TLS in front of it, or on its main listener with `[server.tls]` (ADR-0018; the admin, console and metrics listeners have none): an `http://` `[server] public_url` whose host is not loopback refuses to start unless `[server] allow_insecure_http = true`, because tokens and the admin bearer would cross the network in cleartext (A4). The key fetches that decide whose ID and actor tokens verify (`[[idps]]` discovery and JWKS, `[[actor_trust]]` JWKS and SPIFFE bundles) use `https://` only, with plain `http://` accepted only to a loopback host, and follow no redirects, so a network attacker cannot inject keys that would forge an originating user or an actor. Their server certificates are checked against the web PKI roots built into attenuo, plus, for an entry that sets `ca_pem_path`, the CA certificates in that file: an operator-supplied trust input. Whoever can write that file, or the CA it names, can issue a certificate for that entry's key URL and so serve keys for it; the extra roots apply to that entry's fetches only, never to another entry or another outbound connection, and they add roots without turning off verification or the hostname check. The admin API (`/admin/*`: revoke, reload, approve, export) is not served on a main listener that is off loopback unless the operator says so: it goes on a listener of its own (`[admin] listen`), where the agent-facing port answers its paths as unknown ones, or the server refuses to start unless `[admin] serve_on_main_listener = true` (S-1, ADR-0013). That separates the admin plane from the agents' network by address; who may do what on it is A8 (named operators with roles, ADR-0016). The development root mint (`[dev] allow_root_mint`, which mints for a user nobody verified) refuses to start when the admin API's listener is off loopback; the demo-only `[dev] allow_root_mint_off_loopback` lifts that for a container behind a loopback-published port. What remains: an operator can still set any of these overrides, and a loopback listener reachable through a local reverse proxy is as exposed as that proxy makes it.
- TLS client certificates (ADR-0019). An agent or PEP can authenticate with a self-signed certificate pinned by its SHA-256. Whoever holds the certificate's private key is that client until the thumbprint is removed and the lists are reloaded, or the certificate expires: there is no CRL or OCSP check. The tokens it gets are bearer or DPoP-bound, not bound to the certificate. Without `[server.forwarded_client_cert]` only a certificate from attenuo's own handshake counts and forwarded-certificate headers are never read, so a TLS-terminating proxy in front hides the certificate rather than letting a caller forge one.
- TLS client certificates from a CA (ADR-0020). An entry can trust a CA file and one name (a SPIFFE ID or a DNS name). Whoever can write the CA file, or holds a CA key in it, can issue a certificate with any name and so become any client that trusts that CA. A CA that issues a certificate with another agent's name gives that agent's identity away. There is no CRL or OCSP check: a revoked certificate works until it expires or the CA or name leaves the entry and the lists are reloaded. Checking a chain takes longer than refusing an unknown id, so timing can show which ids use a CA. The chain check costs CPU before the client is authenticated, on certificates the client chose: it is bounded by at most 4 intermediates, one per subject and none self-issued, at most 16 CAs, rustls-webpki's limit of 100 signature checks and a per-connection cache of the answer. `[limits] token_unauthenticated_requests_per_minute` is off by default and does not cover the PEP endpoints, so a client that opens many connections is limited only by `[limits] max_in_flight` and the cost of its own handshakes. rustls-webpki does not read the client certificate's `keyUsage`. One certificate never authenticates two entries of one list; an agent and a PEP may share a name.
- Forwarded TLS client certificates (ADR-0021). With `[server.forwarded_client_cert]`, a proxy sends the client's certificate in `Client-Cert` and `Client-Cert-Chain` to a listener of its own. attenuo sees no proof of possession: anyone who can send those headers to that listener can claim any certificate and so be any agent or PEP that uses one. A proxy that passes on the client's own copy of the headers, or a compromised proxy, does the same. The fences: the headers are read only on that listener; it serves only TCP peers in `trusted_peers` (never decided by a header) and answers every other peer `403` before routing; every other listener refuses the headers with `400` while the section is set; that listener never speaks TLS and the TLS listener never reads the headers; only a listed set of routes is served there (not the admin API, not `/ext-authz/...`), and a test makes every new route a decision; the section cannot come from environment overrides. What is left: every process that can connect from a listed address (all of the host, for `127.0.0.1/32`) can claim any certificate; the proxy must run in HTTP mode and strip and set the headers, which attenuo cannot check (a proxy in TCP mode that ends TLS passes a client's forged header, and only a shared secret, which this design avoids, could tell), so the deploying guide's recipe file is run against HAProxy and its forged-header check is a required step; the hop from the proxy is plain HTTP; the unauthenticated `/token` limit counts in one bucket per proxy address there, and over it only a request whose sole credentials are a forwarded certificate and a client id still runs (and is refused unless it authenticates), so secret clients behind the proxy share a bucket and the proxy should limit by client address; HAProxy's TLS session resumption, which would keep a certificate without a new proof, is off in the recipe; and the CA check runs once per distinct certificate (a bounded shared cache), not once per connection. The header parser is strict and bounded (4 intermediates, 16 KiB per certificate, 64 KiB in all) and fuzzed (compiled; not run here).
- Checkpoint sink lag (SR-21). The window in which a host compromise can rewrite history undetected is the time from an entry to the delivery of the next checkpoint covering it: up to `checkpoint_every` entries or `checkpoint_interval_seconds`, plus queue and retry delay while the sink is down. Watch `audit_sink_oldest_undelivered_timestamp_seconds`, `audit_sink_dropped_total` and the `/readyz` `degraded` flag; set `fail_readiness = true` where a server must not run with its checkpoints stuck on the host.
- Token theft within a lease TTL window, for tokens that are not bound to a key. Bound tokens (DPoP, [RFC-0001 section 4.1](rfc-0001-attenuo.md#41-sender-constrained-tokens-dpop)) are useless without the holder's private key; an attacker who also takes the key is still in scope only up to the token's capabilities and lease.
- Replay of a DPoP proof. A proof is accepted once per server process: its `jti` is kept in memory, per process, and is not shared between replicas, so a proof captured with its token can be sent once to each replica on another database file within its `iat` window. A restart does not open that window again on one file: the new process refuses every proof the previous one could have accepted (the restart fence, [binding tokens to keys](../guides/binding-tokens-to-keys.md#limits)). A proof made before a restart is refused after it. The cost: right after a quick restart, proofs made then are refused too, for up to about 21 seconds with the defaults, and a marker the operator restores or deletes gives up the fence for that one start.
- The approval token is readable by every hop of its run. `GET /approvals/{id}` answers any delegation token of the same run whose leases are live (with a DPoP proof when bound; a revoked hop gets 404, SR-60), and every answer about a granted approval carries `approval_token`. A sub-agent that learns an approval id can therefore fetch the token, but cannot spend it: the token names the calling hop's lease and, for a bound hop, its key (`cnf.jkt`), the server consumes the approval once against that binding, and the call hash pins the exact arguments. What the channel does leak is that the call was approved, and by whom, to agents the operator may not have told. Keep approval TTLs short (default 120 s), and treat the approval id like the token.
- Who may approve. With `[approvals] client_id` unset, an ID token whose audience is the run's root agent's own client id decides at `POST /approvals/{id}`. Each ID token is used once and the one redeemed at hop 0 is refused, but a root agent that can get fresh ID tokens for its user (silent re-authentication, a refresh token) can approve its own gated calls, and the record says `by: user`. Set `client_id` to the approval page's own client wherever approvals matter. When a loaded policy carries `@obligation("approval")` and `client_id` is unset, the server warns at startup and after every policy reload, and refuses to start off a loopback listener unless `[approvals] allow_unset_client_id = true` (SR-64). A loopback server, or one with the override, still accepts the agent's own client.
- Run limits count JSON values, not what a tool makes of them. `calls_per`, `distinct` and the catalog `destination` compare the canonical JSON of a value: aliases of one recipient (case, whitespace, plus-addressing) are different values, and a comma-separated string, a nested list or an object is one value even when the tool fans it out. Aliases cannot get past `distinct` or a rule that asks on a new destination, but they do get past `calls_per` and rules that ask on a repeat. `"derive": "host"` follows the WHATWG URL parser and refuses strings with a backslash, whitespace or a control character, on which common HTTP clients disagree with it (SR-56), and finds a host only in a URL of a special scheme (`http`, `https`, `ws`, `wss`, `ftp`, `file`), since any other scheme has an opaque host that is not normalised (FZ2-2); subdomains of one domain are still different hosts. In run usage a value with no host counts as itself, wrapped so that it never equals a host, so each different unparseable value is a new destination (SR-63); a rule that asks on a repeat notices only an exact repeat of one. Pin argument formats with constraints where a limit depends on them (SR-65, SR-66).
- Refunds of `distinct` charges. A refund frees a value only when no other unrefunded decision used it, so refunding the call that first reached a value does not reopen it while a later call that also reached it stands (SR-62). Charge rows written before that fix do not record later uses of a seen value, so on a store upgraded mid-run a refund can still free such a value once.
- Policy limits over run usage are exact within one server process: a per-run lock covers the read of `context.usage` and `context.budget` through the charge (SR-55). Two servers on one store would not share it. With `[policy] track_usage = "auto"`, usage is kept only while a loaded policy can read it, so a usage policy loaded mid-run counts only the calls made since; set `track_usage = true` where usage policies may be added to live runs (SR-68).
- Other processes on the store. The server's SQLite file may be read by other processes (an operator's `sqlite3`, a backup tool) only through SQLite, which coordinates through file locks; nothing in the server may open and close the database file itself, since that drops the process's locks (SR-58). Copy a live store with SQLite's backup API, not `cp`.
- Audit volume from revoked tokens. A request refused for a revoked, expired or unknown lease is a `deny` record even when it carries no per-call decision (`initialize`, `tools/list`, `GET`). These refusals are bounded: the first per delegation chain, tool (a fixed name: the allowlisted method or `http.POST`, `http.GET`, `http.DELETE`) and reason within the record window (`[proxy] record_window_seconds`, default 60 s) is recorded, and repeats in the window are refused the same way (their 401 names the first record) but only logged and counted in `audit_records_suppressed_total{tool,reason}`. A holder of a revoked but unexpired token retrying undecided requests therefore adds at most one record per window for each of the eleven tool names until the token's `exp`; a reader of the log must take one such record to stand for possibly many refused requests of that chain in the following window, whose count is in the metric alone. A `tools/call` with that token is a decision and is still recorded every time, as are refused token exchanges and renewals, so whoever holds such a token can still add one record per decided request; there is no per-token rate limit on those. Tokens that fail verification add nothing (SR-18), so the volume is bounded by tokens attenuo issued and their lifetimes. Watch `decisions_total{decision="deny",reason="lease_revoked"}` and `audit_records_suppressed_total`.
- Audit volume from refused exchanges. A token exchange refused after its subject token (and DPoP proof) verified is a `deny` record against the parent's chain (`token.exchange`, reasons `exchange_*` or the parent's lease reason), so the holder of a valid parent token, together with credentials for some agent where actor authentication is on, can add one record per refused request until the parent expires, as a `tools/call` denial with that token always could. Malformed requests, failed client or actor-token authentication and subject tokens that fail verification add nothing (SR-18). A refused exchange does not use up the parent's one delegation per actor, so it can be retried. Watch `decisions_total{decision="deny",reason=~"exchange_.*"}`.
- Audit volume from refused renewals. A `POST /token/renew` refused after its token (and DPoP proof) verified is a `deny` record against the token's chain (`lease.renew`, reason `lease_revoked`, `lease_expired` or `lease_unknown`), so whoever holds a revoked but unexpired token can add one record per renewal attempt until the token's `exp`, as with the proxy refusals above. An agent that keeps renewing after a revocation shows up instead of failing silently. Tokens or DPoP proofs that fail verification add nothing (SR-18); there is no per-token rate limit on the log. Watch `decisions_total{decision="deny",reason=~"lease_.*"}`.
- Stream endings (SR-28). Open response streams (the `GET` listen stream, a streamed `POST` answer) are re-checked every `[proxy] stream_recheck_seconds`, so after a revocation or token expiry a stream keeps relaying for up to one interval (default 2 s). When the proxy ends a stream for a lease or token reason it writes one `deny` record of tool `stream.end` with the reason and the session's hash tag, so the log tells a stream cut by revocation from one that was dropped. A client disconnect or an upstream that ends the stream is only a log line (`info` and `debug`, with server, session hash tag, subject and `chain_id`) and a count in `proxy_streams_ended_total{cause}` (`client_disconnect`, `upstream_eof`, `upstream_error`, besides the re-check causes, for `GET` listen streams), so the audit log does not show how long a session's listen stream stayed open or when it was dropped; correlate with proxy logs for that. Each stream adds at most one record, and only for a token that verified when the stream opened (SR-18). On the `GET` listen stream the records are bounded further: at most one `stream.end` per delegation chain and reason per record window (default 60 s), the first. Later ends in that window end their stream the same way but are only logged and counted in `audit_records_suppressed_total{tool="stream.end",reason}`. A reader of the log must therefore take one listen-stream `stream.end` record to stand for possibly many streams of that chain ended for that reason within the next window; it names the server and session of the first one only, and the record has no field for the count, which is in the metric alone. Among stream endings the bound covers only `stream.end` on the listen stream: the `stream.end` of a streamed `POST` answer is written each time. The `http.GET` refusals of a client that keeps reopening a stream on a revoked lease have their own window of the same shape (see the audit-volume entry above); every tool-call decision is written each time. Reopening with an expired token is refused before any lease check and never recorded. Watch `decisions_total{decision="deny",reason=~"lease_.*|token_expired"}` and `audit_records_suppressed_total`.

- Look-alike stream ends. An upstream could send a message in the shape of the proxy's stream-end event (a response with `id` `null` or absent and error `-32001`) so that a client reports its call as cut by the proxy, naming a decision id that is in no record. The proxy rewrites every such message it relays, on any SSE stream and in a JSON answer it reads, to error `-32005` with `data.reason` `upstream_stream_end_shape` and the upstream's error in `data.upstream_error`; the proxy's own final event is appended after the rewrite. On a stream without a list filter, an event is parsed for this only when a byte scan finds a number in it that could have the value `-32001` in any spelling (`guard::may_hold_stream_end_code`), so the scan never lets a message of the shape through. What remains: the upstream can still end the call (it could anyway), an upstream `-32001` that answers the request by its id is relayed as is (the SDKs read it as `Unauthorized`), and a plain JSON answer to a method the proxy neither filters nor labels (`initialize`, `ping`) is relayed unread.
- `resources/unsubscribe` is allowlisted: it needs a live lease and no capability or decision, and an allowed one is not recorded. Giving up a subscription never widens what the agent can do, and the session it acts on is bound to the run (SR-11), so it cannot end another principal's subscription; a policy cannot forbid it, and the log shows it only when it is refused for the lease. `resources/subscribe` stays decided.
- Revoking by user (`POST /admin/leases/revoke` with `user`) matches the leases whose originating subject the server recorded at issue. Leases issued before it recorded subjects are not matched, the subject is compared under every issuer, and leases issued after the call are not covered; an operator revokes by `chain_id` for older runs and disables the user at the IdP to stop new root tokens. Revoking by MCP session (`session`) finds the chain through a binding the server writes when the proxy binds a new session for a verified token, so an unauthenticated caller cannot write one (SR-18). The binding is keyed by the session id's full SHA-256, never the raw id, and is write-once per session and upstream: if an upstream reused a session id for another principal after the first binding expired, the selector would still name the first chain. Sessions opened before the server recorded bindings, or through a server on another store, are not found; revoke those by `chain_id`. Bindings are pruned once their chain's root lease is revoked, or has been expired for longer than `[leases] session_retention_seconds` (default a day): an expired lease can be renewed while its token is valid, so a retention shorter than the longest token lifetime the server issues would let a renewed chain's sessions drop out of revoke-by-session (they can still be revoked by `chain_id` or user). A pruned session matches nothing, like an unknown one. Lease rows and recorded subjects follow the lease retention below: revoke-by-user deliberately matches expired but unrevoked leases so that a renewal cannot bring them back, which needs their subjects for as long as a renewal is possible.
- Lease retention. A run (a root lease and everything delegated from it) is deleted whole from the registry once every lease in it is revoked or expired and the last ended longer ago than `[leases] retention_seconds` (default a week), with its recorded subjects, chain bindings, session bindings, hop limits and run labels. It is never deleted in part, so no surviving lease has a missing parent, and a deleted run's token reads as unknown, which is refused (`lease_unknown`) and audited like any unknown lease, on calls, session requests, renewals and exchanges. Safety does not depend on the setting: a retention shorter than a token's lifetime can only turn a renewable run into a refused one. What the operator loses for a pruned run: revoke-by-user, by chain and by session no longer match it (nothing is left to revoke), the console's lease tree no longer shows it, and its refusals say `lease_unknown` rather than `lease_revoked` or `lease_expired`, so telling a pruned run from a forged lease id takes the audit log, which keeps every decision, issuance and revocation unless pruned (`[audit.retention]`, off by default; a prune only reaches entries older than `min_age_seconds`, which may not be below this run-state retention). Run-limit counters, their charge log and approvals of a pruned run follow their own retention, which starts only once the run's leases are gone: nothing of a run whose leases are in the registry is deleted, whatever its age, so a granted approval not yet used, or a counter a live hop charges, is never touched; after that a charge-log entry goes once its charge and any refund are older than `[leases] run_state_retention_seconds` (default 30 days), a counter once no charge under its lease is left, an approval once its creation, decision and expiry are older. Deleting a counter cannot reopen a budget: the hops it counted are unknown to the registry, so every call they make is refused as `lease_unknown` first. What the operator loses there: the refund of such a decision answers 410 `charge_pruned` (the server reads the decision's audit record to tell it from one that charged nothing, which stays 404 `not_found`), so a late refund request cannot be honoured, nor told from a duplicate without reading the refund records, and its approvals leave `GET /admin/approvals` and the console. The audit log keeps every decision record with its `budget` member, every refund record and every approval request and grant, unless pruned (`[audit.retention]`).
- What a response is. The proxy finds an upstream's answers (for output labelling and the list filter) as messages without a string `method` whose `id` matches a call it forwarded; a `method` that is `null` or not a string does not make a request, since clients such as the Python MCP SDK read such a message as the response (SR-69). A message with a string `method` and a `result` is left alone, as clients read it as a request. An answer to an earlier call that arrives in the body of a later `POST` of the same session and run is labelled like one on the listen stream (SR-85). An answer on the listen stream, or in a later `POST` body, that arrives after `AWAITED_RESULT_TTL` (10 minutes) still passes unlabelled (SR-89).
- What the proxy reads of an SSE body. Output labelling, the list filter and the look-alike rewrite act on the events the proxy parses, so a client must not act on an event the proxy could not read. The proxy drops a byte order mark that opens a stream and ends a stream at a non-UTF-8 event (SR-77), reads a lone surrogate escape as U+FFFD as `JSON.parse` does (SR-78), and drops an event whose data it still cannot parse (deeper nesting than `serde_json` allows, for one) on a labelled stream, on a list-filtered stream and when the event may hold the stream-end code (SR-79, SR-80). What remains: on a stream it neither labels nor filters (a `DELETE` answer, an answer to `initialize`) an event is relayed unread, and a new parser differential on a field the proxy does not inspect (one that parses on both sides) is not detected.
- AuthZEN batches and authentication failures. An entry that fails with 401 or 403 refuses the whole batch after the entries before it were decided, audited and charged; the caller does not see those decisions (SR-84). Each is a real decision under the caller's token, so the log hides nothing, and a charge the caller did not see only tightens its own budget.
- Record windows and failed appends. A lease-refusal or `stream.end` window opens only on a record that was written (SR-81, fixed): when the append fails, the refusal names no decision id and the next occurrence is recorded again, carrying the count suppressed meanwhile. Occurrences suppressed in the moment between the first occurrence and its failed append are in `audit_records_suppressed_total` and the proxy log only. A custom `Authorizer` that does not override `record_rejection_checked` is taken to have written every record.
- Argument strings and URL parsers. Policy patterns and `prefix` constraints compare strings, and a tool may resolve one differently: WHATWG URL parsers (Node's `fetch`, Rust's `url` crate) read `\` as `/`, `%2e%2e` as `..` and drop tabs and line breaks, so `acme/..\evil\api` leaves `acme/` once it is put into a URL path. The starter policy's repository rules refuse `\`, `%`, `?`, `#`, tab, line feed and carriage return (SR-70); a `prefix` constraint does not (SR-73), so for a whole repository name prefer `equals` or `one_of`, and for a file path `path_prefix`, which refuses `..`, `.` and empty segments, `\`, control characters and `%2e`, `%2f` and `%5c` instead of comparing strings; and custom policies that put a value into a URL need the same guards.
- A `GET` an upstream answers with a success status but no `text/event-stream` body is refused with `502` `upstream_not_event_stream` instead of relayed: MCP allows only an SSE listen stream or `405` there, and that body would have reached the client without the list filter or result labelling. What remains on the listen stream is what the filter cannot know: list answers are recognised by shape (a response whose `result` holds `tools`, `resources`, `resourceTemplates` or `prompts` as an array), so a list result that an upstream wrapped in some other shape would pass unfiltered, as it would on a `POST`; and `405` or error bodies on `GET` are relayed as they are.
- Two findings of security review pass 12, both Info, fixed after the pass ([report](../research/security-review-2026-11-13-pass12.md)), with what remains. With `[limits] token_unauthenticated_requests_per_minute` on, one unauthenticated `POST /token` from each of `rate_limit_max_keys` addresses (an IPv6 address counts by its /64) within a minute fills the per-peer table, and every agent used to be refused `429` before it could authenticate, because agents never enter that table (SR-109). Now a new address on a full table is let through when it carries client credentials and no actor token, served if it authenticates an agent and refused with the same `429` if not ([ADR-0014 update](../decisions/0014-request-limits.md#update-2026-11-13-a-full-peer-table-lets-agents-authenticate-sr-109)). What remains: during such a flood an agent that sends an actor token is still refused, and from addresses beyond the table's size the flood gets one client authentication per request, bounded by `max_in_flight` in concurrency but not in rate; a flood from many addresses is for the network in front of attenuo, as above. SR-110, where a refused client assertion told an unauthenticated caller which agent and PEP ids use keys, is fixed: every refusal before the signature verifies is one answer, `client_authentication_failed`, and costs one signature verification ([ADR-0017 update](../decisions/0017-private-key-jwt.md#update-2026-11-13-one-answer-until-the-signature-verifies-sr-110)). What timing still shows: an RS256 probe against an entry whose RSA key is larger than 2048 bits verifies more slowly than one against an unknown id.
- Redirects from the server URL (SR-112, Low, fixed in [security review pass 13](../research/security-review-2026-11-13-pass13.md)). A followed `307` or `308` sends the request body again to wherever `Location` names; on `POST /token` that is the agent's `client_secret`, `client_assertion` or `actor_token` with the subject token and a `DPoP` proof the server has not seen. The CLI, both SDKs (`mcpFetch` included) and the server's own outbound clients follow no redirect, and the CLI and SDKs report a 3xx as an error naming its `Location`. What remains: HTTP code of your own, or an MCP client library given its own `fetch` rather than `mcpFetch`, follows whatever its HTTP client does; `fetch` and most clients follow `307` and `308` with the body. Give such clients the final URL and do not put a redirect rule for `/token` in front of attenuo.
- AuthZEN action search ([security review pass 14](../research/security-review-2026-11-14-pass14.md)). The caller chooses `context.input`, so an agent can try argument values against the policy (which recipient, path or amount a rule lets through). Each search writes one `search` audit record for the request, with the chain, the server, the digest of `context.input` and how many tools it evaluated and permitted, as the same attempts through `POST /access/v1/evaluation` each write a `deny` record. A search refused before it evaluates anything writes none. `[limits] authzen_search_requests_per_minute` bounds the rate per run (the chain's root lease, also for a PEP's unsigned chain), counted after authentication and before anything is evaluated, but it is off by default, like every rate limit: unset, only `max_in_flight` and `request_timeout_seconds` apply. One request evaluates at most `[authzen] max_batch` tools. Evaluation and batch evaluation are not counted by it. Nothing found this way is allowed without a decision, which is audited and charged. The record is not a decision and charges nothing (SR-117, Info, fixed after the pass). Fixed on that branch: a newline in a search's `server` forged log lines (SR-115, Low), and paging counted catalogued tools outside the token's capabilities (SR-116, Info); the candidates are now the catalogued tools the capabilities name.
- What the CLI prints, and the S3 sink endpoint ([security review pass 15](../research/security-review-2026-11-14-pass15.md)). The CLI prints what the server and, through the proxy, an upstream MCP server send (tool names, descriptions and results, JSON-RPC error messages, a refusal's `error`, `code` and `detail`) with control characters escaped, keeping a tool text's and a description's line breaks and tabs, so an upstream cannot hide text from the reader with escape sequences or drive the terminal (SR-118, Low, fixed). What remains is what such text says: a description written to mislead is printed as any MCP client shows it, and `--json` is JSON for a program, which must do its own escaping. An `[audit.sink]` S3 `endpoint` is checked as the HTTP client parses it, so a bare `http://` no longer sends the PUT to the host the bucket names (SR-119, Info, fixed). The live smoke scripts under `scripts/` keep their per-run credentials in a `0700` directory and pass container passwords through docker's environment (SR-120, Info, fixed); `mc`, `kcadm.sh` and curl in them still take some secrets as arguments, so run them on a machine you do not share.
- Hop-0 limits and the ID-JAG ceiling ([security review pass 16](../research/security-review-2026-11-14-pass16.md)). A limit in `[[root_grants]]`, or in an ID-JAG claim under `[idps.id_jag_ceiling]`, is copied into the requested capability it covers, and hop 0 has no parent hop to charge, so a limit copied into several capabilities would bound each of them, not the run. Hop 0 refuses a request in which two capabilities fall under the same limited capability, one that covers the calls of both (`limit_split_at_root`; before SR-128's fix, the one both took their limits from), so an agent cannot split its first request by recipient, URL or amount range to get the figure once per capability (SR-121, Medium, fixed after the pass). Limits set at an exchange were never affected, and run usage policies count per tool. The ceiling applies to ID-JAGs only, so an agent that can present the issuer's ID tokens gets the root grant without it; `[[idps]] credentials = ["id-jag"]` makes the entry refuse its ID tokens at hop 0 (`credential_type_not_accepted`), and the server warns at start about an entry with a ceiling that accepts them. The default still accepts both kinds, so the gap stays open until the operator sets the key (SR-122, Low, fixed after the pass). An ID-JAG claim naming more than 256 capabilities names nothing, which bounds the cost of attenuating a request against the ceiling (SR-123, Low). A request, and so each hop of a token, holds at most 1,024 capabilities and a `one_of` at most 1,024 values (`too_many_capabilities`, `one_of_too_long`), as do `[[root_grants]]` and `scopes`. A request also holds at most 1,024 argument constraints and 1,024 `one_of` values in all (`too_many_constraints`, `too_many_one_of_values`), and a `one_of` implies another through a set of canonical keys, so attenuation no longer costs the product of the two lists: the slowest shape within the bounds took 51 ms in a release build, and a root token of 400 lists of 1,024 values, which took 19.8 s, is refused at reading in 73 ms (SR-123, fixed after the pass). Hop 0's attenuation, the ceiling's meet and the split checks run on the blocking pool, as the exchange's do, so a worst-case intake no longer holds a runtime worker. The root token record of an intake under the ceiling has an `id_jag_ceiling` member: the names of the claims that narrowed the grant and a SHA-256 digest of their full values, so a holder of the ID-JAG can check it against the record. The values themselves are only on the info line of the intake, cut to 512 bytes each. A refused intake writes no record (SR-126, Info, fixed after the pass).
- Limits that reach hop 0 by more than one path ([security review pass 17](../research/security-review-2026-11-14-pass17.md)). The split check of SR-121 looked at the root grant and at the final ceiling. A limit that a `[idps.id_jag_ceiling] scopes` entry carries was copied by the claim's `authorization_details` into one ceiling capability per capability the claim names, so a request split along them got the figure once per capability (SR-127, Medium, fixed after the pass: the check is also made against each step of the ceiling that holds limits). Two limited capabilities of one root grant entry, one within the other, were not combined: a root token capability took the limits of one of them, and calls under the other were not charged to it, so "100 in all, at most 30 to alice" let 130 through, and a tighter `calls: 1` on one tool under a wider limited `bank:*` bounded nothing unless the request asked for the entry as it is (SR-128, Low, fixed after the pass: a root token capability carries the limits of every limited capability of the grant or ceiling that covers its calls, and the split check applies to each; a limited capability that only overlaps a requested one, without covering its calls, still bounds nothing at hop 0). Under the ceiling, a limited `scopes` capability over two limited capabilities of the root grant bounded neither, since the ceiling kept the grant's two with their own figures (SR-131, Low, found while fixing SR-128, fixed after the pass: hop 0 also checks the request against what each claim that holds limits named). A `scope` or `resource` claim that repeats one value is expanded once (SR-129, Low, fixed). A start-up refusal of a `[[root_grants]]` entry leaves its subject out under `[logging] redact_subjects` (SR-130, Info, fixed).
- The hop-0 limit rule after its fixes ([security review pass 18](../research/security-review-2026-11-15-pass18.md)). Through the whole server and a generated budget check (every limited capability of the grant and of each claim, against what the issued token can spend, charging every limited token capability that permits a call), in the shapes tried no request got more than a configured limit allows, except through a token capability that only overlaps the limited one or is wider than it, which hop 0 does not bound (stated since SR-128). A refusal names only capabilities as requested. A request whose own limit is on another argument than a limited capability over it is refused with `scope_exceeds_grant` (or `scope_exceeds_id_jag`) or with `limit_conflict_at_root` depending on the rest of the entry (SR-132, Info, documented, and the detail's wording corrected).
- Upstream decoders and the STDIO bridge ([security review pass 19](../research/security-review-2026-11-15-pass19.md)). An upstream that matches JSON member names without regard to case (Go's `encoding/json`) read `Method`, `params.Name` or a second argument name in another case as the member the proxy decided on (SR-133, High, fixed): the proxy and the agentgateway adapter now refuse a message with two member names that differ only in case, or with a JSON-RPC or MCP name of the message or its `params` in another case. A single argument name in another case (`Path` alone) is refused too when the decision knows the name for the tool (`argument_case_mismatch`, fixed after the pass): it differs only in case from a name in the tool's catalog entry (`inputs`, `amount`, `destination`, `outbound`), in a constraint or run limit of a capability that covers the tool, or read by a loaded policy under `context.input` or compared with `context.untrusted_args`. What remains: the proxy has no schema of the tool, so a name nothing in the decision reads passes in any case, and the upstream may read it as a field the operator never named; an argument whose meaning depends on a name no catalog entry, capability or policy names cannot be checked. A policy that tests a name some other way than those is not read for names (see pass 20 below). Declare in the catalog the inputs the policies and limits are about. `attenuo stdio-bridge` removes every `ATTENUO_*` variable from its child's environment (SR-134, fixed), but not secrets under names the operator chose, and on stop it stops the child's whole process group, so a launcher's child goes with it (SR-135, Info, fixed after the pass); a process that left the group is not reached.
- Argument names and the fold ([security review pass 20](../research/security-review-2026-11-16-pass20.md)). The fold that tells two names apart now joins every pair of names Go's `encoding/json` joins: Go compares names rune by rune under Unicode simple case folding, which joins `ß` with the capital `ẞ`, and upper then lower case had given those two different keys, so `straẞe` passed where `straße` was known (SR-137, Low, fixed). The fold still joins more than Go does (`ß` with `ss`, a ligature with its letters, the dotless `ı` with `i`), which can only refuse more; for characters added to Unicode after the version Go's tables carry, the two may differ either way. The names a policy reads are collected from its text, so only a read the text names counts: `context.input.<name>`, `context.input["<name>"]`, `context.input has <name>` and `context has input.<name>`, inside any expression, and a string literal compared with `context.untrusted_args` itself or passed to one of its set methods. Not collected (SR-138, Info, documented): a record literal compared with `context.input` whole; a read through an expression that yields the record or the set (`(if ... then context.input else context.input) has path`, `{"r": context.input}.r`, `(if ... then context.untrusted_args else []).contains("path")`); and a name computed at evaluation time (`context.untrusted_args.contains(principal.arg)`). A `forbid` written in one of these forms can be passed by an argument name in another case against an upstream that ignores case; write such reads in the direct forms, or declare the name in the catalog.
- External enforcement points and revocation. A PEP that uses the AuthZEN endpoint, or a gateway on `[[ext_authz]]`, enforces revocation only when it asks. One that caches an allow, or holds a stream open, keeps letting a revoked agent through until it asks again. `[leases.notify]` narrows that window: after each revocation the server `POST`s a signed `lease.revoked` notice naming the top leases revoked and their chains, and the PEP can refuse tokens whose chain contains a listed lease and drop cached allows for the listed chains. It is a hint, not enforcement. An attacker who can drop or delay traffic between the server and the receiver can suppress it. A full queue or a receiver that is down past `max_attempts` loses it. A server that stops between the revocation and storing its notice loses it too, since the notice goes into the outbox in a separate, later write. Either way the PEP is back to asking, so nothing is lost but time. A forged notice cannot be made without the HMAC secret, and a receiver that skips the check can only be made to drop cached allows or refuse tokens, which fails closed. A receiver that checks the timestamp and `event_id` refuses a replayed notice. The body tells the receiver lease ids, the operator's name and subject, the reason the operator typed and, for a revocation by user, that user's subject; no token and no raw session id. Lease expiry sends no notice, since the PEP has the token's `exp`.
- Policy-cache or lease-cache staleness longer than one TTL under partition (fail closed when the lease store is unreachable).
- Constraint-algebra gaps that let an argument slip past `⊑` (property tests over the attenuation rule; fuzz the matcher).
- Audit loss on power failure at the default `[audit] durability = "normal"`. A decision is answered (and an allowed call forwarded) once its record is committed, but a `normal` commit is not synced, so a power failure or kernel crash can lose the newest records of calls that did run. The surviving log is a clean prefix and verifies. A process crash loses nothing, and revocations are always synced. Use `durability = "full"` where the audit trail must cover every executed call (SR-48, [deploy guide](../guides/deploying.md)).
