# Status

What has been tested, reviewed and proven, and what has not. The README carries a short version of this page.

attenuo is pre-alpha and has not been used in production. Release 0.1.0 is prepared but not tagged; its draft notes, upgrade notes and known limitations are in [docs/release/0.1.0.md](release/0.1.0.md).

- **Tests and fuzzing.** The Rust workspace has unit, property and integration tests (`cargo test --workspace`), and both SDKs have unit tests and integration tests against a real server; [CONTRIBUTING](https://github.com/attenuo-dev/attenuo/blob/main/CONTRIBUTING.md#running-the-checks-locally) says how to run them, and `scripts/release-check.sh` runs every check a release needs, the injection suite's included. There are [22 fuzz targets](design/fuzzing.md) (tokens, DPoP, chains, capability attenuation, the proxy, SSE, audit export, since round 2 run-limit charges, budget plans, approval tokens, the usage walker and the server's HTTP routes, since round 3 the proxy's SSE framing and data parsing, and since 2026-11-15 the prepared implication, hop-0 attenuation and the ID-JAG ceiling). The [second campaign](design/fuzzing.md#second-campaign-10-minutes-per-target-2026-10-23-evening) ran the first twelve for 10 minutes each, about 282 million inputs in all, with no crash. Those campaigns found five bugs (three in token and proxy handling, two in audit verification), and [round 2](research/fuzzing-2026-10-24-round2.md#findings) found four more (FZ2-1 to FZ2-4, low or info), all fixed. [Round 3](research/fuzz-round-3-2026-10-25.md) (300 s per target over the pass 7 SSE parsing) found none.
- **Machine-checked proof.** A Lean model of the covering rule proves that, in the model, delegation never widens authority; the Rust code is not verified against it, though a differential test finds the model, run as a program, and the Rust code in agreement on 31,500 generated cases ([proofs/lean](https://github.com/attenuo-dev/attenuo/blob/main/proofs/lean/README.md#differential-test)).
- **Security review.** Eighteen review passes have been done in this repository, between 2026-10-22 and 2026-11-15: [pass 1](research/security-review-2026-10-22.md), [3](research/security-review-2026-10-23.md), [4](research/security-review-2026-10-23-pass4.md), [5](research/security-review-2026-10-24-pass5.md), [6](research/security-review-2026-10-25-pass6.md), [7](research/security-review-2026-10-25-pass7.md), [8](research/security-review-2026-11-05-pass8.md), [9](research/security-review-2026-11-06-pass9.md), [10](research/security-review-2026-11-06-pass10.md), [11](research/security-review-2026-11-12-pass11.md), [12](research/security-review-2026-11-13-pass12.md), [13](research/security-review-2026-11-13-pass13.md), [14](research/security-review-2026-11-14-pass14.md), [15](research/security-review-2026-11-14-pass15.md), [16](research/security-review-2026-11-14-pass16.md), [17](research/security-review-2026-11-14-pass17.md) and [18](research/security-review-2026-11-15-pass18.md). Pass 2 was the fix round for pass 1. Together they recorded 132 findings, SR-01 to SR-132: none Critical, 5 High (all in pass 1), 21 Medium, 57 Low and 49 Info. Every finding but two is fixed or accepted with its reasoning in its report. Open: SR-117 (Info: AuthZEN action search writes no audit record, so an agent can try argument values against the policy without a record; an optional per-run rate limit, `[limits] authzen_search_requests_per_minute`, off by default, bounds how fast; whether a search should also write an audit record is a design choice left to the maintainer), and one of pass 16, proposed with a recommendation: SR-126 (Info: what the ceiling was is not in the audit record; the intake's log line now has it). The one of pass 18 was fixed on its branch: SR-132 (Info: a hop-0 request whose own limit is on another argument than a limited capability over it is refused with `scope_exceeds_grant` or with `limit_conflict_at_root` depending on the rest of the entry, which the configuration reference now says, and the refusal's wording is corrected; nothing is granted either way). The three of pass 13 (SR-112, Low: the CLI and the TypeScript SDK followed a redirect from the server URL with the token request body; SR-113 and SR-114, Info) and two of pass 14 (SR-115, Low: a newline in an action search's server name forged log lines; SR-116, Info) and the three of pass 15 (SR-118, Low: the CLI printed text from the server or an upstream MCP server with its control characters; SR-119 and SR-120, Info) and two of pass 16 (SR-124 and SR-125, Info; SR-123 in part) and two of pass 17 (SR-129, Low: a repeated `scope` token or `resource` value was expanded once per repeat; SR-130, Info: a `[[root_grants]]` start-up refusal named the subject under `[logging] redact_subjects`) were fixed on the branch that recorded them. SR-121 (Medium, pass 16: a limit in a root grant or an ID-JAG claim bounded each requested capability at hop 0, not the run) was fixed after its pass: hop 0 refuses a request that splits a limited capability (`limit_split_at_root`). So was the rest of SR-123 (Low, pass 16: attenuation cost the product of both sides' `one_of` values): a `one_of` now implies another through a set of canonical keys, and a request holds at most 1,024 argument constraints and 1,024 `one_of` values in all. So was SR-127 (Medium, pass 17: an ID-JAG's `authorization_details` copied a limit of a `[idps.id_jag_ceiling] scopes` entry into one ceiling capability per recipient, so the hop-0 split check did not see the split): the check is now made against each step of the ceiling that holds limits. So was SR-128 (Low, pass 17: two limited capabilities of one root grant entry, one within the other, were not combined, so "100 in all, at most 30 to alice" let 130 through): a root token capability now carries the limits of every limited capability of the entry or ceiling that covers its calls, and the split check applies to each. So was SR-131 (Low, found while fixing SR-128: under `[idps.id_jag_ceiling]`, a limited `scopes` capability over two limited capabilities of the root grant bounded neither): hop 0 now also checks the request against what each claim that holds limits named. So was SR-122 (Low, pass 16: an ID token got past `[idps.id_jag_ceiling]`), in that the operator can now close it: `[[idps]] credentials = ["id-jag"]` refuses the entry's ID tokens at hop 0, and the default still accepts both. The project did all eighteen passes itself; there has been no outside audit.
- **Not tested.** The identity-provider recipes for Auth0, Okta, Entra ID and Google, and ID-JAG, are untested against a real provider; the server's tests use assertions it signs itself. The Keycloak recipe was run once, against Keycloak 26.8.2 in dev mode on loopback (`scripts/live-keycloak-smoke.sh`, not part of CI): hop 0 from a real login with curl, both SDKs and the CLI, then a delegation and proxied calls. A production Keycloak was not. The S3 checkpoint sink was run against MinIO over HTTP and HTTPS, with static credentials and with temporary ones from MinIO's STS (`scripts/live-minio-smoke.sh`, `scripts/live-minio-tls-sts-smoke.sh`), not AWS S3 or AWS STS, and `[[actor_trust]]` against SPIRE 1.16.0 with a join-token attestor on loopback (`scripts/live-spire-smoke.sh`), not a production SPIRE; none of these scripts is part of CI. Trace export was run through OpenTelemetry Collector 0.165.0 into Jaeger 2.23.0 (`scripts/live-collector-smoke.sh` and `scripts/live-otel-backend-smoke.sh`, also not part of CI), not into another backend and not over TLS. The Docker image and the compose demo have a smoke test (`scripts/compose-smoke.sh`, a CI job) that builds them and plays the demo through them, but the release workflow that pushes the multi-arch image has never run, and there is no Helm chart or Kubernetes manifest. The agentgateway adapter (`/ext-authz/v1/mcp/{server}`) is tested only against a fake gateway written from agentgateway's source; it has not been run with agentgateway itself, and the agentgateway configuration in its guide has not been loaded. There has been no production use and no load test on reference hardware.
