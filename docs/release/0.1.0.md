# Release 0.1.0

Draft release notes for the first tagged release, and the steps that cut it. Nothing here has been tagged or published yet. GitHub Actions have not run for this repository, so every check below was run locally with [`scripts/release-check.sh`](https://github.com/attenuo-dev/attenuo/blob/main/scripts/release-check.sh). When the tag is pushed, paste the [release notes](#release-notes) section into the draft GitHub release in place of the git-cliff text (see [step 4](#4-review-the-draft-release-and-publish-it)).

## Release notes

### Highlights

Attenuo is an authorization layer for AI agents that call tools over MCP. A user's authority reaches an agent, and every sub-agent it hands work to, as a signed delegation chain that can only narrow at each hop (RFC 8693 token exchange), and an enforcing proxy checks every `tools/call` against that chain and Cedar policies before anything reaches the upstream server.

0.1.0 is the first release. It ships one server process with token exchange, an AuthZEN decision endpoint, the MCP proxy and a hash-chained audit log with signed checkpoints. Leases revoke a delegation and everything below it: the next call on a revoked lease is refused, and streams already open are cut within the stream re-check interval (2 s by default). A call already forwarded to the upstream cannot be recalled. Tokens can be bound to the agent's key with DPoP. Output labelling marks untrusted tool results and sends later risky calls to an operator for approval. Run limits cap call counts, amounts and destinations per delegation. The `attenuo` CLI, an admin console and Python and TypeScript SDKs cover the same API.

Landed in the last day before the cut:

- Proxy record windows you can set: `[proxy] record_window_seconds` and `record_window_max_keys`, defaults unchanged (#121).
- The SDKs treat a stream-end event as a proxy cut only with a reason the proxy sends and a UUID decision id; anything else of that shape is an `RpcError` (#123).
- Security review pass 7 (#124): SR-77 to SR-80 fixed in the proxy's SSE handling, SR-81 fixed in #128, SR-82 fixed in #125 and #126, SR-83 open, SR-84 accepted.
- The Python SDK's SSE parser reads a long line in linear time: a 1 MiB line in 1 KiB reads went from about 4 s to about 10 ms (#125).
- An optional total deadline on a streamed call, Python `deadline=` and TypeScript `deadlineMs`, so keep-alive comments cannot hold a call open (#126).
- `Authorizer::record_rejection_checked`, a default trait method, lets the proxy open a record window only on a record that was written (#128).

The injection-suite figures in the docs come from synthetic, model-free cases written alongside the policies they test, so they show what the mechanisms can block, not how a real agent under attack fares.

attenuo is pre-alpha and has not been used in production. See the [README status section](https://github.com/attenuo-dev/attenuo#status).

### What is in it

The complete list, 290 entries, is the [0.1.0 section of the changelog](../project/changelog.md). By group:

- **Added (116 entries).** The server (`attenuo-server`): RFC 8693 `POST /token` with hop-0 intake from an OIDC ID token or ID-JAG and hop n+1 exchange with authenticated actors (client secret or an `actor_token` from a trusted issuer), `may_act`, lease renewal, the AuthZEN evaluation and batch endpoints, and the MCP proxy for `tools/call`, resources, prompts and completions with list filtering. DPoP sender-constrained tokens with server nonces. A hash-chained SQLite audit log with signed checkpoints, JSON Lines export, offline verification and a webhook sink. Output labelling (ADR-0009): untrusted results, argument-level taint and operator approvals with a signed approval token. Run limits (ADR-0010): `calls`, `sum`, `calls_per` and `distinct` budgets per hop, run usage as a Cedar input, and refunds. An opt-in admin console on its own loopback listener and the read-only admin API behind it. The `attenuo` CLI for tokens, calls, leases, audit, policies, approvals and budgets, with a Cedar policy test harness and linter. Python (`attenuo`) and TypeScript (`@attenuo/sdk`) SDKs with token refresh, approvals and offline audit verification. Configurable proxy record windows and an optional total deadline on streamed SDK calls. Fuzz targets, the injection suite and `attenuo-bench`.
- **Changed (43 entries).** The project rename from `onbehalf`, server-scoped Cedar actions, default-deny for tools missing from the catalog, mandatory actor authentication, the bundled SQLite at 3.53.2, `[policy] track_usage`, the SDKs' stricter reading of a stream cut, and the MSRV at Rust 1.89.
- **Deprecated (1 entry).** `[policy] legacy_bare_actions`.
- **Fixed (20 entries).** SQLite lease-store open races, audit WAL growth under sustained load, `audit tail` record rendering, `policy lint` false reports, a flaky test, and the injection suite reading another deployment's `ATTENUO_*` variables.
- **Security (68 entries).** Fixes for every finding of seven security review passes except the accepted Info and Low findings (SR-52, SR-54, SR-65 to SR-68, SR-73 to SR-76, SR-84) and the open SR-83 (release workflow toolchain not hash-pinned), and for the bugs the two fuzzing campaigns found.
- **Performance (22 entries).** WAL mode, group commit, a verified-token cache, a Cedar translation cache, checkpoints off the writer, a byte scan before parsing SSE events for the stream-end shape, the Python SDK's linear SSE parser, and measurements: 0.4 to 0.8 ms added at the median per proxied call on the test VM ([performance](../design/performance.md)).
- **Evaluation (9 entries)** and **Documentation (11 entries).** Injection-suite runs for the labelling and limits arms, new case sets, the run-limits design and ADR-0010, the guides and this documentation site.

Entries marked BREAKING are breaking against earlier builds from `main`. 0.1.0 is the first release, so nobody upgrades from a published version, but anyone who ran `main` before should read them; 24 entries carry it.

### Upgrade notes

From the [deploy guide](../guides/deploying.md#upgrades):

- Until 1.0, minor versions can change the config, the token format and the database layout. Read the changelog before every upgrade, and back up the database and the issuer key first. Tokens issued by one version may not verify on the next: plan to re-mint.
- Run limits need every server on 0.1.0 or later. Older builds accept a `limits` block and ignore it, without an error or a log line. Until every replica and every external PEP that reads `limits` runs 0.1.0, do not rely on a limit for safety: back it with a Cedar `forbid` or an approval. A `decision` record in `attenuo audit tail --json` for a limited capability without a `budget` member came from an old server.
- Coming from a build of `main` from before the rename: names, environment variables, headers and signing contexts changed from `onbehalf` to `attenuo`, so tokens need re-minting and configs, scripts and log filters need the new names (see the BREAKING rename entry and `docs/design/rename-plan.md`).
- The SQLite file now carries a schema version (SQLite's `user_version`). The first start of 0.1.0 on a file from an earlier build adopts it at version 1 in one transaction, adding what is missing (such as the `approvals` table's `jkt` column). There is no downgrade: back the file up first ([the database schema](../guides/deploying.md#the-database-schema)).
- Behaviour change (SR-77): an upstream SSE stream with an event that is not UTF-8 now ends with an error at that event, since a lenient client would read what the proxy could not label; the call's answer does not reach the client. A UTF-8 byte order mark that opens a stream is dropped.

### Known limitations

- Pre-alpha, with no production use and no load test on reference hardware. Benchmarks ran on a shared 4 vCPU VM.
- Every identity-provider recipe (Keycloak, Auth0, Okta, Entra ID, Google, ID-JAG with Okta) is untested against a live tenant; the tests use assertions the server signs itself.
- The Dockerfile and `docker-compose.yml` are untested, and the release workflow has never run.
- Admin authentication is one static bearer token; hop-0 agents authenticate with a static client secret only (no `private_key_jwt` or mTLS).
- The ID-token, ID-JAG and DPoP replay caches are in memory: they do not survive a restart and are not shared between replicas.
- No push channel for revocation: an external PEP using AuthZEN learns of a revocation only by asking.
- Checkpoints are signed with the key the server holds; ship them off the host (`[audit.sink]`) to detect tampering by whoever controls the server.
- `[audit] durability = "normal"` can lose the newest records, including those of forwarded calls, on a power failure.
- List filtering is by capability by default. Filtering by Cedar policy is built and opt-in (`[proxy] list_filter = "policy"`, [ADR-0011](../decisions/0011-cedar-aware-list-filtering.md)), covers `tools/list` only, and is advisory: a hidden tool that is called is still decided as usual.
- attenuo sees only calls that go through it. It is not a prompt-injection detector or a sandbox: in the injection suite's dev split, 15 of 77 attack calls still went through the base `attenuo` arm because they used a tool and arguments the task needed. Output labelling and run limits reduce that only by asking a person or through a limit set for the task ([run limits, section 7](../design/run-limits.md#7-measured)).
- The injection suite is synthetic and model-free, and its cases were written by the same project as its policies. The AgentDojo runs with a model in the loop are small (attenuo enforcing on the workspace suite only, with grants derived from each task's known solution), and no attack succeeded with or without attenuo, so they measure the cost of enforcement and not its benefit ([technical report](../report/attenuo-2026-11.md), section 5.2).
- The SDK integration tests run against a server from the same commit; no SDK is tested against a server of another version.

The full list of server gaps is in [design/server.md](../design/server.md#known-limits-v0), and open findings are on the [task board](../tasks/board.md).

## Maintainer steps

### What is ready

Every published artifact says 0.1.0: the Cargo workspace (and the `version = "0.1.0"` on each intra-workspace dependency that `cargo publish` needs), the Python package `attenuo`, and the npm package `@attenuo/sdk` with both lockfiles regenerated. The seven publishable crates (`attenuo-core`, `attenuo-token`, `attenuo-audit`, `attenuo-policy`, `attenuo-proxy`, `attenuo-cli`, `attenuo-server`) carry a description, licence, repository, homepage, readme (each crate's own `README.md`), keywords and categories, and ship a `LICENSE` (a symlink to the top-level file that `cargo package` resolves). `attenuo-bench` has `publish = false`. Both SDKs ship `LICENSE`, and their READMEs use absolute links so they render on PyPI and npm. The SDKs publish through `.github/workflows/release-packages.yml` with one dispatch each ([step 6](#6-publish-the-sdks)).

### 1. Run the local checks on the commit you will tag

```sh
git switch main && git pull
python3 -m venv /tmp/rel && /tmp/rel/bin/pip install -e 'sdk/python[dev]' -r evaluation/injection-suite/requirements.txt mcp build twine
PYTHON=/tmp/rel/bin/python scripts/release-check.sh
```

It runs, in order and stopping at the first failure: version consistency, `cargo fmt`, clippy with `-D warnings`, rustdoc with `-D warnings`, `cargo test --workspace --locked`, the link check, the mdBook build (skipped if `mdbook` is not installed), the demo policy tests, the injection suite's pytest run, the Python SDK's ruff, mypy and pytest, the TypeScript SDK's lint, build, tests and CJS/ESM smoke test, `cargo publish --dry-run --workspace --locked`, `python -m build` with `twine check --strict`, and `npm pack --dry-run`. `--from <step>` resumes after a fix; `--list` prints the steps. The crates dry run needs a clean tree (or `ALLOW_DIRTY=1`).

Per-crate dry runs (`cargo publish --dry-run -p attenuo-token`) fail with `no matching package named attenuo-core found` until the crates below it are on crates.io. `--workspace` (Cargo 1.90 or later) avoids that: it packages every crate and verifies each one against the others through a temporary local registry, so no crate needs `--no-verify`.

### 2. Settle the names

Before anything is public, check that these names are free or already yours: the seven crate names on crates.io, `attenuo` on PyPI, the `@attenuo` scope on npm, and `ghcr.io/attenuo-dev/attenuo`.

### 3. Tag

The release workflow (`.github/workflows/release.yml`) runs on any pushed tag matching `v*`, and git-cliff reads tags matching `v[0-9].*`. Use `v0.1.0`, annotated, on the merge commit of this preparation branch:

```sh
git tag -a v0.1.0 -m "attenuo 0.1.0"     # or -s to sign
git push origin v0.1.0
```

A tag with a `-` (for example `v0.1.0-rc.1`) makes a pre-release and does not move the image's `latest` tag.

The workflow produces:

- four archives, `attenuo-v0.1.0-<target>.tar.gz` for `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `aarch64-apple-darwin` and `x86_64-apple-darwin`, each holding `attenuo`, `attenuo-server`, `LICENSE`, `README.md` and `CHANGELOG.md`;
- a multi-arch (amd64, arm64) image `ghcr.io/attenuo-dev/attenuo:0.1.0` and `:latest`, signed with cosign (keyless, GitHub OIDC), with an SPDX SBOM attested to it;
- `SHA256SUMS` over the archives and the SBOM;
- a draft GitHub release with all of the above and a git-cliff changelog section.

Secrets: none beyond the automatic `GITHUB_TOKEN`. The workflow asks for `packages: write` (GHCR) and `id-token: write` (keyless signing) itself. Actions must be enabled for the repository. The workflow does not publish crates, the Python package or the npm package. The same tag also starts `release-packages.yml`, which builds, tests and checks both SDKs as a dry run and uploads nothing.

### 4. Review the draft release and publish it

Replace the git-cliff body with the [release notes](#release-notes) above (git-cliff renders commit subjects, not the changelog), check the four archives against `SHA256SUMS`, run `attenuo --help` from one of them, verify the image signature, then publish the draft. Set the GHCR package to public after the first push.

### 5. Publish the crates

This is manual in any case. Run it from the tagged commit, after `scripts/release-check.sh` passed, with a crates.io token from `cargo login`:

```sh
cargo publish --workspace --locked        # Cargo 1.90+: publishes in dependency order, waiting for each
```

or one at a time, in this order, waiting for each to appear on crates.io before the next:

```sh
cargo publish --locked -p attenuo-core
cargo publish --locked -p attenuo-token
cargo publish --locked -p attenuo-audit
cargo publish --locked -p attenuo-policy
cargo publish --locked -p attenuo-proxy
cargo publish --locked -p attenuo-cli
cargo publish --locked -p attenuo-server
```

### 6. Publish the SDKs

The Python package `attenuo` goes to PyPI and `@attenuo/sdk` to npm through [`.github/workflows/release-packages.yml`](https://github.com/attenuo-dev/attenuo/blob/main/.github/workflows/release-packages.yml). Pushing the `v0.1.0` tag runs it as a dry run: it builds, tests and checks both packages (ruff, mypy, pytest, `python -m build`, `twine check --strict`, a check that the wheel holds only the package; `npm ci`, lint, build, tests, `npm pack --dry-run`) and uploads nothing. Only a manual dispatch with `dry_run=false` publishes, and only from a `v*` tag that equals the package's version.

One-time setup, before the first publish:

1. **GitHub environments.** In the repository's Settings, Environments, create `pypi` and `npm`. Add yourself as a required reviewer on both if you want a confirmation click before each upload, and limit their deployment refs to tags `v*`.
2. **PyPI trusted publisher.** On PyPI, add a trusted publisher for the project `attenuo` (a "pending publisher" under your account's Publishing page if the project does not exist yet): owner `attenuo-dev`, repository `attenuo`, workflow `release-packages.yml`, environment `pypi`. No API token is stored anywhere.
3. **npm scope and token.** Create the `@attenuo` organisation on npm (the free plan publishes public packages) with two-factor authentication on for every member. Create a granular access token with read and write on `@attenuo` packages, allowed to publish without an OTP (the workflow cannot type one), and store it as the secret `NPM_TOKEN` of the `npm` environment. npm's trusted publishing (OIDC, no token) can replace the secret: configure `attenuo-dev/attenuo`, `release-packages.yml` and environment `npm` as the package's trusted publisher, then delete the secret. It needs an npm CLI recent enough to support it in the publish job and the package to exist already; this was not tried.

Publish, from the tagged commit after the tag's dry run (or `scripts/release-check.sh`) passed:

```sh
gh workflow run release-packages.yml --ref v0.1.0 -f package=python -f dry_run=false
gh workflow run release-packages.yml --ref v0.1.0 -f package=typescript -f dry_run=false
# or both at once:
gh workflow run release-packages.yml --ref v0.1.0 -f package=both -f dry_run=false
gh run watch
```

Without `--ref` the dispatch runs on the default branch, and the publish jobs refuse to start because the ref is not the version's tag. `-f dry_run=true` (the default) repeats the checks without uploading. The PyPI upload carries PEP 740 attestations, and the npm package a provenance statement linking it to the workflow run; the npm package page shows it. Check afterwards with `pip install attenuo==0.1.0` and `npm view @attenuo/sdk@0.1.0`.

Manual fallback, if Actions stay blocked or the workflow fails. Python, with a PyPI API token (user `__token__`):

```sh
python -m build --outdir dist-py sdk/python
twine check --strict dist-py/*
twine upload dist-py/*
```

TypeScript, after `npm login` as an owner of the `@attenuo` scope (npm asks for the 2FA code):

```sh
cd sdk/typescript && npm ci && npm publish --access public --provenance=false
```

`prepack` builds `dist/` before packing. Provenance needs a supported CI provider, so a publish from a laptop must turn it off (`publishConfig.provenance` is `true` for the workflow); `npm publish --provenance --access public` works only in CI. A version once uploaded to PyPI or npm cannot be uploaded again, even after deleting it, so fix and bump the version rather than retry.

### If Actions stay blocked

Step 5 and the manual fallback of step 6 are unaffected. For the binaries and image, build locally and attach them to a release created by hand:

```sh
cargo build --release --locked -p attenuo-server -p attenuo-cli
docker buildx build --platform linux/amd64,linux/arm64 -t ghcr.io/attenuo-dev/attenuo:0.1.0 --push .
gh release create v0.1.0 --draft --title v0.1.0 --notes-file notes.md attenuo-v0.1.0-*.tar.gz SHA256SUMS
```

Package each archive as the workflow's Package step does (the two binaries plus `LICENSE`, `README.md` and `CHANGELOG.md`), put the release notes section in `notes.md`, and write `SHA256SUMS` with `sha256sum`. A hand-built image is not signed by the workflow identity, so the cosign command above will not verify it; say so in the notes, or leave the image out until Actions run.
