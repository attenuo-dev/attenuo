# Release 0.2.1

Release notes for 0.2.1, the upgrade from 0.1.0, and the steps that cut it. This page was written on 2026-11-24, before the tag. Nothing here has been tagged or published yet. When the tag is pushed, paste the [release notes](#release-notes) section into the draft GitHub release in place of the git-cliff text, and change its relative links to full `https://github.com/attenuo-dev/attenuo/blob/v0.2.1/docs/...` links, because relative links do not work on a release page (see [step 5](#5-review-the-draft-release-and-publish-it)).

## Why 0.2.1 and not 0.2.0

The tag `v0.2.0` was pushed on 2026-11-22, but the release workflow's container image job failed twice. The first run failed because the amd64 and arm64 builds shared their build caches (fixed in #403). The second run hit the job's 60 minute limit (fixed in #404). The draft release job waits for the image job, so there is no GitHub release and no container image for 0.2.0. The binaries and the Python and npm package builds passed, but nothing was published.

The tag `v0.2.0` stays where it is and is not moved. 0.2.1 is the first complete release after 0.1.0.

## Release notes

### Highlights

0.2.1 is the second release of attenuo, an authorization layer for AI agents that call tools over MCP. It has everything prepared for 0.2.0 (tagged, never released) and the changes made since.

From 0.2.0 (the full list is in the [0.2.0 release notes](0.2.0.md#release-notes)):

- **Audit retention.** You can prune the oldest audit entries behind a signed anchor, by hand with `attenuo audit prune` or on a timer with `[audit.retention] prune = "auto"`. Pruning is off by default.
- **Changes without a restart.** You can reload agents and PEPs and rotate the token signing key without a restart. A client can also publish its `private_key_jwt` keys at a URL (`jwks_url`).
- **DPoP across restarts.** A DPoP proof made before a restart is refused after it, and a proof may be at most 10 seconds ahead of the server's clock by default.
- **Revocation notices.** A signed webhook after each revocation (`[leases.notify]`). It is a hint, not enforcement.
- **Easier to start.** `scripts/install.sh`, a Helm chart, `attenuo init`, `attenuo connect`, and the leak demo from the published image.
- **Security fixes.** SR-117, SR-126, SR-135, and `url` 2.5.9 for RUSTSEC-2026-0592.

New in 0.2.1:

- **`attenuo audit compact`** (#402). Pruning removes rows but does not make the database file smaller. This new command shrinks the file. Run it with the server stopped. It checks the audit chain before and after, and `--dry-run` only reports what it would do ([guide](../guides/deploying.md#bounding-the-audit-log)).
- **Admin console: Reload page** (#401). It reloads the admin operators, the agents and PEPs, and the issuer keys, each after a confirmation, with every safety option off until you tick it. It needs the `admin` role and `[admin_ui] allow_write` ([guide](../guides/admin-console.md#reload)).
- **Admin console: automatic prune panel** (#401). With `prune = "auto"`, the Verify page shows the prune settings and the last run to the `admin` role. To serve it, the console listener now mounts `GET /admin/audit/prune/plan` (a read, `admin` role only).
- **Release build fixes.** Each image architecture has its own build caches (#403), and the image job may run for 180 minutes (#404).

The upgrade from 0.1.0 changes the database in a way that cannot be undone, and some requests that worked before are now refused. Read the [upgrade notes](#upgrade-from-010) before you upgrade.

attenuo is pre-alpha and has not been used in production. See the [status page](../status.md).

### What is in it

The complete list is the [0.2.1 and 0.2.0 sections of the changelog](../project/changelog.md). The 0.2.0 entries are summed up in [what is in 0.2.0](0.2.0.md#what-is-in-it). The 0.2.1 section adds:

- **Added (4 entries).** The `attenuo audit compact` command, the console's Reload page, the automatic prune panel on the Verify page, and the `console` member of `GET /admin/whoami` on the console listener.
- **Fixed (2 entries).** Separate build caches per architecture in the Docker image build, and the 180 minute limit for the image job.

No entry in the 0.2.1 section is marked BREAKING. The database schema is still version 5, and no config key was added, renamed or removed since 0.2.0.

### Upgrade from 0.1.0

Follow the [0.2.0 upgrade notes](0.2.0.md#upgrade-from-010), with 0.2.1 in place of 0.2.0. Nothing else is needed. The database migration, the DPoP and AuthZEN changes and the `ca_pem_path` rule are the same.

There is no upgrade from 0.2.0, since 0.2.0 was never released. If you built the server yourself from the `v0.2.0` tag, 0.2.1 reads the same database file and the same config.

### Known limitations

The [0.2.0 list](0.2.0.md#known-limitations) still applies, with these changes:

- The Helm chart is installed from a checkout of the `v0.2.1` tag. It is still not published to a chart repository.
- The release workflow has not finished a full run yet. For 0.1.0 the draft release job failed. For 0.2.0 the image job failed. This tag is the first run with #403 and #404.
- The arm64 image still builds under emulation, so the image job is slow. It may now run for up to 180 minutes.

## Maintainer steps

### What is ready

Every place the `versions` step of `scripts/release-check.sh` compares says 0.2.1: the Cargo workspace and the `version` of each `attenuo-*` entry under `[workspace.dependencies]`, `sdk/python/pyproject.toml`, `sdk/typescript/package.json` and its lockfile, and the `## [0.2.1] - 2026-11-24` heading of the changelog. `Cargo.lock` and `fuzz/Cargo.lock` were regenerated with `cargo update --workspace`. The step does not check these, and they say 0.2.1 too: the Helm chart's `version` and `appVersion`, `CITATION.cff` (with `date-released: "2026-11-24"`), and the lockfile of `examples/typescript-agent`.

What still names 0.1.0 on purpose, because no 0.2.x image or release exists until this tag is pushed: the CI `install-script` job (it installs the published `v0.1.0`), the CI `helm chart` job (`ATTENUO_IMAGE_TAG: "0.1.0"`), the leak demo's image (`examples/github-leak-demo/compose.image.yml`, `run-docker.sh` and its README), the deploy guide's Helm section, and the README. Move them in a change after the release ([after the release](#after-the-release)).

The release date in the changelog heading and in `CITATION.cff` is 2026-11-24. If the tag is pushed on a later day, change both in the release PR before it is merged.

Do not move or delete the `v0.2.0` tag.

### 1. Merge the release PR

Merge the `chore(release): v0.2.1` PR once CI is green. Do not push anything else to `main` until the tag is pushed.

### 2. Run the local checks on the merged commit

Run them on `main` after the merge, so they check the commit you will tag:

```sh
git switch main && git pull
git log -1 --format='%H %s'    # the commit the release PR made on main; note the hash
python3 -m venv /tmp/rel && /tmp/rel/bin/pip install -e 'sdk/python[dev]' -r evaluation/injection-suite/requirements.txt mcp build twine
PYTHON=/tmp/rel/bin/python scripts/release-check.sh
```

The `versions` step fails if `main` does not say 0.2.1 yet. The steps and `--from <step>` are described in [step 2 of the 0.2.0 page](0.2.0.md#2-run-the-local-checks-on-the-merged-commit). Leave `ALLOW_DIRTY` unset for this run. If a check fails, fix it in a new PR and start again at step 2 on the new commit.

### 3. Tag the commit the checks ran on and push the tag

From a machine with push rights to `attenuo-dev/attenuo`, tag the commit whose hash you noted in step 2. Check first that `main` has not moved:

```sh
git log -1 --format='%H %s'                    # the same hash as in step 2
git tag -a v0.2.1 -m "attenuo 0.2.1" <hash>   # or -s to sign
git push origin v0.2.1
```

The tag must be `v0.2.1`: `release.yml` runs on any pushed tag that matches `v*`, git-cliff reads tags that match `v[0-9].*`, and the `release-packages.yml` jobs check that the tag equals the package versions.

### 4. Watch the release workflows

```sh
gh run list --workflow release.yml --limit 1
gh run watch
```

`release.yml` does what [step 4 of the 0.2.0 page](0.2.0.md#4-watch-the-release-workflows) says, with `v0.2.1` and `0.2.1` in place of `v0.2.0` and `0.2.0`: the four binary builds, the multi-arch image (pushed as `0.2.1` and `latest`, signed, with an SBOM), then the draft release.

The image job can now take up to 180 minutes, because the arm64 half builds under emulation. The draft release job starts only after it. If a job fails, fix the cause and run only the failed jobs again with `gh run rerun <run-id> --failed`.

The same tag starts `release-packages.yml` as a dry run. It uploads nothing.

**Open item: cosign.** If PR #223 (Dependabot, `sigstore/cosign-installer` to v4.1.3) is still open, decide before you tag whether to merge it, as the 0.2.0 page says.

### 5. Review the draft release and publish it

1. Replace the git-cliff body with the [release notes](#release-notes) section of this page. The git-cliff text covers only the commits since `v0.2.0`, so it leaves out everything listed under 0.2.0.
2. Download the four archives, the SBOM `attenuo-image.spdx.json` and `SHA256SUMS` into one directory, and check them there with `sha256sum -c SHA256SUMS`.
3. Unpack one archive, for example `tar -xzf attenuo-v0.2.1-x86_64-unknown-linux-musl.tar.gz`, `cd` into `attenuo-v0.2.1-<target>/`, and run `./attenuo --version` and `./attenuo-server --version`. Both print 0.2.1.
4. Verify the image signature with the command [above](#verifying-the-container-image).
5. Publish the draft.

Leave the GHCR package settings as they are.

### 6. Crates and SDK packages, if you publish them

Neither the crates nor the SDKs are on a registry yet. Publishing them is not needed for this release. If you do, follow [step 5](0.1.0.md#5-publish-the-crates) and [step 6](0.1.0.md#6-publish-the-sdks) of the 0.1.0 page with `v0.2.1` in place of `v0.1.0`:

### 7. Check the published artifacts

Install script, against the new tag and as "latest":

```sh
ATTENUO_VERSION=v0.2.1 ATTENUO_INSTALL_DIR=/tmp/a2 sh scripts/install.sh
/tmp/a2/attenuo --version && /tmp/a2/attenuo-server --version
ATTENUO_INSTALL_DIR=/tmp/a3 sh scripts/install.sh    # no version: the latest release, now v0.2.1
/tmp/a3/attenuo --version
```

Image:

```sh
docker pull ghcr.io/attenuo-dev/attenuo:0.2.1
docker run --rm ghcr.io/attenuo-dev/attenuo:0.2.1 --version
cosign verify ghcr.io/attenuo-dev/attenuo:0.2.1 \
  --certificate-identity-regexp '^https://github.com/attenuo-dev/attenuo/\.github/workflows/release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify ghcr.io/attenuo-dev/attenuo:latest \
  --certificate-identity-regexp '^https://github.com/attenuo-dev/attenuo/\.github/workflows/release\.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Check that `docker manifest inspect ghcr.io/attenuo-dev/attenuo:0.2.1` lists `linux/amd64` and `linux/arm64`.

Then check that each platform holds binaries for its own architecture. `--version` is not enough for this: with emulation installed, an arm64 binary also runs on an amd64 host. Read the ELF header of both binaries from each platform instead:

```sh
img=ghcr.io/attenuo-dev/attenuo:0.2.1
out=$(mktemp -d)
for arch in amd64 arm64; do
  docker pull --platform "linux/$arch" "$img"
  id=$(docker create --platform "linux/$arch" "$img")
  docker cp "$id:/usr/local/bin/attenuo-server" "$out/attenuo-server-$arch"
  docker cp "$id:/usr/local/bin/attenuo" "$out/attenuo-$arch"
  docker rm "$id"
done
file "$out"/*
```

The `amd64` files must say `x86-64` and the `arm64` files must say `ARM aarch64`.

Helm chart, from a checkout of the tag, with its default image (the chart's `appVersion`, now 0.2.1), in a kind cluster:

```sh
git switch --detach v0.2.1
kind create cluster --wait 180s
bash scripts/helm-smoke.sh
```

Without `ATTENUO_IMAGE_TAG`, the smoke test installs `ghcr.io/attenuo-dev/attenuo:0.2.1`.

The leak demo from the new image: `ATTENUO_IMAGE=ghcr.io/attenuo-dev/attenuo:0.2.1 examples/github-leak-demo/run-docker.sh`.
