# Release 0.2.0

Release notes for the second tagged release, the upgrade from 0.1.0, and the steps that cut it. This page was written on 2026-11-22, before the tag. Nothing here has been tagged or published yet. When the tag is pushed, paste the [release notes](#release-notes) section into the draft GitHub release in place of the git-cliff text (see [step 5](#5-review-the-draft-release-and-publish-it)).

## Release notes

### Highlights

0.2.0 is the second release of attenuo, an authorization layer for AI agents that call tools over MCP. It adds:

- **Audit retention.** You can prune the oldest audit entries behind a signed anchor, by hand with `attenuo audit prune` or on a timer with `[audit.retention] prune = "auto"`. The archives and the kept log verify as one log, with the CLI and with both SDKs. Pruning is off by default.
- **Changes without a restart.** `POST /admin/agents/reload` puts changed `[[agents]]` and `[[peps]]` in force. `POST /admin/keys/reload` rotates the token signing key. An agent or PEP can publish its `private_key_jwt` keys at a URL (`jwks_url`) and rotate them with no change to the server's config.
- **DPoP across restarts.** A DPoP proof made before a restart is refused after it. A proof may now be at most 10 seconds ahead of the server's clock by default.
- **Revocation notices.** With `[leases.notify]`, the server sends a signed webhook after each revocation, so an enforcement point outside the server can learn of it sooner. It is a hint, not enforcement.
- **Easier to start.** A one-line install of the release binaries (`scripts/install.sh`), a Helm chart (`deploy/helm/attenuo`), `attenuo init` to write a starter configuration for one MCP server, `attenuo connect` for desktop MCP clients, and the leak demo from the published image with no Rust toolchain.
- **Security fixes.** SR-117 (an AuthZEN action search now writes an audit record), SR-126 (the ID-JAG ceiling is readable in the root token record), SR-135 (`attenuo stdio-bridge` stops what its child started), and `url` 2.5.9 for RUSTSEC-2026-0592.

The upgrade from 0.1.0 changes the database in a way that cannot be undone, and some requests that worked before are now refused. Read the [upgrade notes](#upgrade-from-010) before you upgrade.

attenuo is pre-alpha and has not been used in production. See the [status page](../status.md).

### What is in it

The complete list is the [0.2.0 section of the changelog](../project/changelog.md). By group:

- **Added (16 entries).** Audit retention in four steps (the server and the store, the CLI and the SDKs, the console, and the automatic prune), the agents and keys reloads, client keys from a URL, `[leases.notify]`, the SDK admin calls for the new routes and the anchor check in the SDK cross-check, `attenuo connect`, `attenuo init`, the Helm chart, the install script and the leak demo from the image.
- **Changed (10 entries).** The database schema version 5, the AuthZEN `missing_token` order, the 1 MiB cap on `ca_pem_path`, the DPoP future skew, `/readyz` during the DPoP restart fence, the stricter SDK cross-check, the Rust API changes, the console's audit kinds, a newer container base image, and a 35 second shutdown grace in the examples.
- **Security (5 entries).** The DPoP restart fence, SR-117, SR-126, SR-135 and the `url` update.
- **Fixed (2 entries).** The SDK readers of exports and shipped files now take and refuse the same lines as the Rust ones, and the release workflow's draft job names the SBOM file before it writes `SHA256SUMS` (#375).
- **Documentation (2 entries).** A shorter README with a new [walkthrough](../guides/walkthrough.md), and a [STDIO servers](../guides/stdio-servers.md) walkthrough against a real server.

Seven entries are marked BREAKING and two are marked as behaviour changes. They are listed with what to do in the [upgrade notes](#upgrade-from-010). No metric and no admin API field was renamed or removed, and no existing config key became required. The token format did not change.

### Upgrade from 0.1.0

Do these in order. The general rules are in the deploy guide's [Upgrades](../guides/deploying.md#upgrades) section.

1. **Read the BREAKING entries** in the [changelog](../project/changelog.md). The ones an operator acts on are below.
2. **Check the clocks of DPoP clients.** A DPoP proof's `iat` may now be at most `[token] dpop_future_skew_seconds` ahead of the server's clock. The new key defaults to 10 seconds (or `dpop_max_age_seconds` when that is smaller). Before, it could be as far ahead as `dpop_max_age_seconds`, 300 seconds by default. A client whose clock runs more than 10 seconds fast gets 401 `invalid_dpop_proof`. Fix its clock, or set the key higher ([`[token]`](../reference/config.md#token)).
3. **Check every `ca_pem_path` file** in `[[idps]]`, `[[actor_trust]]` and `[audit.sink]`. The file must now be a regular file of at most 1 MiB, or the server refuses to start. (`ca_pem_path` in `[[agents]]` and `[[peps]]` is new in 0.2.0, and the same rule applies.) The built-in web PKI roots are trusted already, so the file needs only your private CA certificates.
4. **Check the PEPs that call AuthZEN.** While `[authzen] allow_unsigned_chain` is off, `/access/v1/evaluation`, `/access/v1/evaluations` and `/access/v1/search/action` now answer 401 `missing_token` to any request without a bearer, before they look at the PEP's credentials or the body. Some of these requests got 400, 401 `invalid_client` or a 200 with `decision: false` before. None was ever allowed. A PEP should send the agent's token as the bearer on every request, and treat 401 `missing_token` as the answer to a request without one ([Decision](../reference/http-api.md#decision)).
5. **Upgrade the readers of the audit log with the server.** 0.2.0 writes a `search` record for each AuthZEN action search, and an `id_jag_ceiling` member in root token records under `[idps.id_jag_ceiling]`. A 0.1.0 server or CLI reports a log that holds them as corrupt, so install the 0.2.0 CLI wherever `attenuo audit verify` runs. The 0.1.0 SDK verifiers still verify such a log. Upgrade the SDKs anyway: once you prune, a shipped file holds anchor lines, and the 0.1.0 CLI and SDKs fail their cross-check on it. The 0.2.0 SDK `cross_check` / `crossCheck` is also stricter: `ok` is true only when the shipped anchors pass too.
6. **Stop the old server** and wait until it has exited. It holds the single-writer lock on the database file.
7. **Back up the database and the issuer key.** For example `sqlite3 attenuo.sqlite ".backup '/backups/attenuo-before-0.2.0.sqlite'"`, or copy `attenuo.sqlite` with its `-wal` and `-shm` files while nothing runs. This backup is the only way back.
8. **Start 0.2.0.** Before it serves anything, it migrates the file from schema version 4 to 5 in one transaction and logs `database schema migrated ... from=4 to=5`. Version 5 adds the empty `audit_anchors` table. No other table or row changes, so the audit chain and its checkpoints verify as before. A step that fails leaves the file at version 4 and the server does not start ([the database schema](../guides/deploying.md#the-database-schema)).
9. **There is no downgrade.** A 0.1.0 binary refuses the migrated file before it reads or writes anything: `the database has schema version 5, written by a newer attenuo; this build reads schema versions up to 4`. To go back, stop 0.2.0 and restore the backup from step 7. Whatever happened after the upgrade, decisions and revocations included, is not in that backup.
10. **Expect the DPoP restart fence on later restarts.** The first start of 0.2.0 on a file that 0.1.0 used is not fenced, because 0.1.0 wrote no liveness marker. From then on:
    - A DPoP proof made before a restart is refused after it with 401 `invalid_dpop_proof`, however long the restart took. (Once its `iat` is too old, it would be refused anyway.) The client must make a new proof.
    - After a quick restart, new proofs are refused for a short time too. The old server kept a marker in the file about 20 seconds ahead of its clock, and the new one refuses every proof whose `iat` is at or before that marker. With the default settings that is up to about 21 seconds after the start. A new proof made in that window is refused as well; only a proof made after the window has passed works. A restart more than about 20 seconds after the old server's last marker write costs nothing.
    - While the fence holds, `/readyz` answers 503 with `checks.dpop_restart_fence` set to `"fenced"`. This happens whatever `[token] dpop` is set to, because bound tokens are checked in every mode. So every deployment can be unready for up to about 21 seconds after a quick restart, the one-pod Helm chart included. A load balancer or Kubernetes sends the new server no traffic until then ([binding tokens to keys](../guides/binding-tokens-to-keys.md#limits)).
11. **Rust embedders only.** `AppState` no longer has `issuer`, `verifier`, `jwks` and `checkpoint_keys`: read them from `AppState::keys()`, one snapshot per task. `ProofCheck`, `DpopError`, `DecisionRecord` and `RecordKind` gained members; see the Rust API entry in the changelog.

Nothing else needs a config change. Every new setting is optional and off or unchanged by default: `[audit.retention]` (`prune = "off"`), `[leases.notify]`, `jwks_url`, `dpop_future_skew_seconds`. If you copied the shutdown grace from the 0.1.0 examples, raise it to 35 seconds: the server's worst case with the default timeouts is 32 seconds ([signals](../guides/deploying.md#docker-and-compose)).

Before you turn on pruning: a webhook `[audit.sink]` receiver must accept the anchor's body, or every later checkpoint queues behind it. Keep the keys that signed kept checkpoints and anchors in `[issuer] previous_key_paths`. The [guide](../guides/deploying.md#bounding-the-audit-log) has the details.

### Known limitations

What changed since the [0.1.0 list](0.1.0.md#known-limitations):

- There is now a Helm chart. It is not published to a chart repository: install it from a checkout of the `v0.2.0` tag. It is tested in a kind cluster only, not on a cloud provider's cluster, behind an ingress controller, or across chart upgrades.
- The release workflow has run once, for 0.1.0. Its builds and its image job passed; its draft release job failed on the SBOM file name. That is fixed (#375) but has not run since, so this tag is the first full run.
- The DPoP replay cache is still in memory, per process and not shared between replicas. The restart fence now covers a restart on the same file. It does not cover a new file, `sqlite_path = ":memory:"`, the first start of 0.2.0 on a 0.1.0 file, or a start on a restored backup.
- Audit retention: the server does not copy `archive_dir` off the host. Without `archive_dir`, an automatic prune deletes the entries with no copy. The console shows pruned logs but has no prune button and does not list anchors.
- Of the three desktop client configurations for `attenuo connect` in the [guide](../guides/integrating-mcp-clients.md), two were not run in their apps.

The rest of the 0.1.0 list still applies.

## Maintainer steps

### What is ready

The step does not check these, and they say 0.2.0 too: the Helm chart's `version` and `appVersion`, `CITATION.cff` (with `date-released: "2026-11-22"`), and the lockfile of `examples/typescript-agent`.

What still names 0.1.0 on purpose, because the 0.2.0 artifacts exist only once the tag is pushed: the CI `install-script` job (it installs the published `v0.1.0`), the CI `helm chart` job (`ATTENUO_IMAGE_TAG: "0.1.0"`), the leak demo's image (`examples/github-leak-demo/compose.image.yml`, `run-docker.sh` and its README), and the README. Move them in a change after the release ([after the release](#after-the-release)).

The release date in the changelog heading and in `CITATION.cff` is 2026-11-22. If the tag is pushed on a later day, change both in the release PR before it is merged.

### 1. Merge the release PR

Merge the `chore(release): v0.2.0` PR once CI is green. Do not push anything else to `main` until the tag is pushed.

### 2. Run the local checks on the merged commit

Run them on `main` after the merge, so they check the commit you will tag and not the last 0.1.0 commit:

```sh
git switch main && git pull
git log -1 --format='%H %s'    # the commit the release PR made on main; note the hash
python3 -m venv /tmp/rel && /tmp/rel/bin/pip install -e 'sdk/python[dev]' -r evaluation/injection-suite/requirements.txt mcp build twine
PYTHON=/tmp/rel/bin/python scripts/release-check.sh
```

The `versions` step fails if `main` does not say 0.2.0 yet. It runs, in order and stopping at the first failure: `versions`, `fmt`, `clippy`, `doc`, `test`, `links`, `book` (skipped without `mdbook`), `policy`, `suite`, `sdk-python`, `sdk-typescript`, `crates-dry-run`, `python-dist` and `npm-pack`. `--from <step>` resumes after a fix; `--list` prints the steps. Leave `ALLOW_DIRTY` unset for this run, so everything is packaged from committed files only. [Step 1 of the 0.1.0 page](0.1.0.md#1-run-the-local-checks-on-the-commit-you-will-tag) says more about each step. If a check fails, fix it in a new PR and start again at step 2 on the new commit.

### 3. Tag the commit the checks ran on and push the tag

From a machine with push rights to `attenuo-dev/attenuo`, tag the commit whose hash you noted in step 2. Check first that `main` has not moved:

```sh
git log -1 --format='%H %s'                    # the same hash as in step 2
git tag -a v0.2.0 -m "attenuo 0.2.0" <hash>   # or -s to sign
git push origin v0.2.0
```

The tag must be `v0.2.0`: `release.yml` runs on any pushed tag that matches `v*`, git-cliff reads tags that match `v[0-9].*`, and the `release-packages.yml` jobs check that the tag equals the package versions. A tag with a `-` makes a pre-release and does not move the image's `latest` tag.

### 4. Watch the release workflows

```sh
gh run list --workflow release.yml --limit 1
gh run watch
```

What `.github/workflows/release.yml` does today, on the pushed tag:

1. **Build**, one job per target: `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` (on a native arm64 runner), `aarch64-apple-darwin` and `x86_64-apple-darwin`. Each builds `attenuo` and `attenuo-server` with `cargo build --release --locked` and the toolchain pinned in `rust-toolchain.toml`, with no cache, and packs `attenuo-v0.2.0-<target>.tar.gz` with the two binaries, `LICENSE`, `README.md` and `CHANGELOG.md`.
2. **Container image.** Builds the `runtime` target of the Dockerfile for `linux/amd64` and `linux/arm64`, pushes it to `ghcr.io/attenuo-dev/attenuo` as `0.2.0` and `latest`, signs it with cosign (keyless, the job's GitHub OIDC token), makes an SPDX SBOM of it and attests the SBOM to the image with cosign.
3. **Draft GitHub release.** After both, downloads the archives and the SBOM, names the SBOM file `attenuo-image.spdx.json`, writes `SHA256SUMS` over the archives and the SBOM, renders the changelog section of the newest tag with git-cliff (from commit subjects, not from `CHANGELOG.md`), and creates a draft release `v0.2.0` with the archives, the SBOM and `SHA256SUMS`.

It needs only the automatic `GITHUB_TOKEN`; the jobs ask for `packages: write` and `id-token: write` themselves. It does not publish crates or SDK packages.

The first run of this workflow, for `v0.1.0`, failed in the draft release job: the SBOM file in the downloaded artifact did not end in `.spdx.json`. #375 fixed that, and this tag is the first run since. If the draft job fails again, the archives and the image are already done: fix the cause, then run only the failed job again with `gh run rerun <run-id> --failed`.

The same tag starts `.github/workflows/release-packages.yml` as a dry run. It checks that each package's version equals the tag, then lints, tests, builds and checks the Python package (with the hash-pinned tools of `sdk/python/release-requirements.txt`) and the npm package (`npm ci --ignore-scripts`, lint, build, tests, `npm pack --dry-run`). It uploads nothing.

**Open item: cosign.** PR #223 (Dependabot, `sigstore/cosign-installer` from the v3 pin to v4.1.3, which installs cosign v3) is open and is meant to be tried at this release. It changes only the installer pin in `release.yml`. It is not part of this release PR. Decide before you tag whether to merge it. If you merge it first, check `cosign verify` on the published image with the cosign version you expect users to run.

### 5. Review the draft release and publish it

1. Replace the git-cliff body with the [release notes](#release-notes) section of this page.
2. Download the four archives, the SBOM `attenuo-image.spdx.json` and `SHA256SUMS` into one directory, and check them there with `sha256sum -c SHA256SUMS`. The file covers the archives and the SBOM, so it fails if the SBOM is missing.
3. Unpack one archive, for example `tar -xzf attenuo-v0.2.0-x86_64-unknown-linux-musl.tar.gz`, `cd` into the directory it makes (`attenuo-v0.2.0-<target>/`), and run `./attenuo --version` and `./attenuo-server --version`. Both print 0.2.0.
4. Verify the image signature with the command [above](#verifying-the-container-image).
5. Publish the draft.

The GHCR package was made public after the 0.1.0 push, and the CI jobs pull it without logging in. Leave its settings as they are. Do not change the visibility of anything that is already public.
