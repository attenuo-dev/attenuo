# agentgateway external authorization: design

- Status: built, off by default (#349). Run once against agentgateway v1.7.0 on 2026-11-16, on one machine, on loopback ([section 6](#6-run-against-agentgateway-v170)).
- Date: 2026-11-15. Base: `main` at 18c6348.
- Related: [guide](../guides/agentgateway.md), [enforcement points](../concepts/enforcement-points.md), [server pipeline](server.md#the-decision-pipeline), [AuthZEN conformance](../reference/authzen.md), [output labelling](output-labelling.md), [threat model](../spec/threat-model.md).

## 1. Problem

[agentgateway](https://github.com/agentgateway/agentgateway) (Apache-2.0) is an MCP gateway. Its `extAuthz` policy asks an external authorizer about each request and forwards the request only when the authorizer says yes. attenuo could not be that authorizer: it speaks MCP (its proxy) and AuthZEN, and `extAuthz` speaks either Envoy's gRPC `envoy.service.auth.v3` or a plain HTTP mode. This note describes a small adapter for the HTTP mode that gives the gateway the same answer attenuo's own proxy would give for the same request.

## 2. What the gateway sends

First read from agentgateway's source at commit `18f83707118b3e2df500cc63299486958a0e86f5` (2026-11-13, `main`). Then checked against the v1.7.0 tag (commit `26f5aebe99a36a037fe54f8080a608aca5547e15`, 2026-10-27), by reading its source and by running it ([section 6](#6-run-against-agentgateway-v170)). Every point below holds for v1.7.0 except where it says otherwise. The two commits were not compared line by line: only the v1.7.0 source was at hand. Paths are relative to `crates/agentgateway/src/`.

- **When.** Route policies run on every HTTP request the agent sends, before the request reaches the MCP backend (`proxy/httpproxy.rs`, `apply_request_policies`, the `ext_authz` step). The policies under `mcp: policies:` become the route policies of the one generated route (`types/local.rs`, `convert_mcp_config`). So the check runs per HTTP request: per `POST` of a JSON-RPC message, and also for the `GET` listen stream and the `DELETE` of a session.
- **Method and path.** The check request has the agent's method. Its path is the result of the `protocol.http.path` CEL expression, or the agent's own path and query when that is unset (`http/ext_authz.rs`, `check_http`).
- **Headers.** Only `Authorization` by default. With `includeRequestHeaders`, exactly the listed ones (the list replaces the default, so `authorization` must be listed too). `addRequestHeaders` adds headers from CEL expressions; a string literal sets a fixed value. Nothing else the agent sent is copied.
- **Body.** Only with `includeRequestBody`: the agent's body as it arrived (before any decompression, `apply_request_policies`), buffered up to `maxRequestBytes` (default 8192). A larger body is refused by the gateway with 413 and attenuo is not called, unless `allowPartialMessage` is true; then the first `maxRequestBytes` bytes are sent. Whenever the body is included, the gateway sets `x-envoy-auth-partial-body` to `true` or `false` itself, after copying the agent's headers, so the agent cannot set it (`check_http`). A `protocol.http.body` CEL expression replaces the forwarded body and leaves that header out.
- **The answer.** A 2xx answer allows: the request goes on, with any headers named in `includeResponseHeaders` copied into it. Any other status denies: the gateway sends the authorizer's status, headers and body to the agent as its response (`check_http`, which in v1.7.0 returns the response as the policy's direct response; v1.7.0 has no `ProxyError::direct_response_from`). Only rate-limit errors are rewritten into JSON-RPC (`mcp/mod.rs`, `maybe_convert_mcp_error`).
- **Failure.** The check request has a 2 second timeout unless the authorizer's backend policies set another (`check_http`). A connection error or timeout goes to `failureMode` (`handle_auth_failure`): `deny` by default (403 to the agent, text body `authorization failed`), `denyWithStatus: <code>`, or `allow`, which lets the request through undecided. All four were seen in the run.
- **Caching.** Off unless `cache` is configured. A cached answer is replayed without calling the authorizer.
- **Forwarding.** After an allow, the gateway forwards the agent's request to the MCP server, including the agent's `Authorization` header unless a `requestHeaderModifier` removes it (`mcp/upstream/mod.rs`, test `apply_propagates_other_headers`). A route's `requestHeaderModifier` runs after its `extAuthz` (`apply_request_policies`), so removing the header there does not hide it from the authorizer. The gateway does not forward the agent's bytes: it parses the JSON-RPC message and sends its own encoding of it. In the run, v1.7.0 added `"_meta":{}` to `params`, moved `_meta` first, and kept the other members and the agent's `_meta` members. It also keeps its own MCP session: the agent gets a session id the gateway made, and the upstream's id stays with the gateway.
- **Tool names.** With one target and the default `prefixMode`, the tool name in the body is the name the upstream receives. With several targets, names carry a `<target>_` prefix that the gateway strips before forwarding (`mcp/mod.rs`, `mcp_request_name`).

Not found in the source read: how the gateway handles a JSON-RPC batch body. The adapter refuses batches (section 3). How the gateway reads JSON that parsers can read differently was tried in the run, through a v1.7.0 gateway without `extAuthz` (attenuo refuses these bodies first, so they never reach this step behind it): of two `arguments.repo` members it forwarded the last, as serde_json reads it; `1e3` and `1.50` were forwarded as `1000.0` and `1.5`; a `Name` next to `name` was dropped; two `name` members gave a JSON-RPC error (HTTP 500). So for those bodies v1.7.0 reads what attenuo reads, but that is one version, and the adapter still refuses them (section 3).

## 3. What attenuo answers

A new route, `/ext-authz/v1/mcp/{server}`, mounted only when at least one `[[ext_authz]]` entry is configured. It runs the proxy's own code for the request: the same authentication (`Authorizer::authenticate_request`), the same per-message screening (`screen_message` in `crates/attenuo-proxy/src/proxy.rs`, which calls `Authorizer::authorize_with` and so `Pipeline::decide`), the same lease check and lease-refusal record for undecided messages. There is no new decision logic.

- **Server name.** `{server}` names the decision's MCP server, the `server` of every `ToolCall`. It must match an `[[ext_authz]]` entry, and the gateway's shared secret must be that entry's. The gateway sets the path with a fixed `protocol.http.path` string per route. Because each entry has its own secret, a gateway route configured for `github` cannot get decisions for another server even if its path were built from something the agent controls.
- **Who may call.** The header `X-Attenuo-Gateway-Secret` must hash (SHA-256) to the entry's `secret_sha256`, compared in constant time. It is checked first, before the token, the DPoP proof or the body are read, so a caller without it cannot use the route as an oracle, charge run limits, write audit records or spend DPoP proofs. A missing or wrong secret is 403 `ext_authz_unauthenticated`. The route is off by default: with no entry it is not mounted and the path is unknown (404). It is on the main listener, next to `/mcp/{server}`, because the gateway needs to reach it like the proxy.
- **Body.** `x-envoy-auth-partial-body` must be exactly `false` on every request, which proves that `includeRequestBody` is configured and the body is whole. Missing, `true` or anything else is 403 `ext_authz_body_incomplete`, before the token is checked. The body is then read with the proxy's limit (`[proxy] max_request_body_bytes`, 413 `request_too_large`).
- **Ambiguous JSON.** The proxy forwards the message re-encoded from its own parse, so the upstream reads what was decided. Through the gateway the upstream gets the gateway's encoding of the gateway's own parse (section 2), not attenuo's, so a body that two parsers can read differently is refused with 400 `ext_authz_ambiguous_body` before any decision: an object with two members of one name (serde_json keeps the last, others keep the first; `crates/attenuo-proxy/tests/hardening.rs`), two members whose names differ only in case, or a member of the message or its `params` that is a JSON-RPC or MCP name in another case such as `Method` (Go's `encoding/json` matches names without regard to case and takes the last match; the proxy refuses these messages too, SR-133), and a number whose text is not exactly what serde_json reads (`0.10000000000000001`, an integer beyond 64 bits, `1e3`, `1.50`). The second rule is stricter than needed: a client that writes a number in a form serde_json would print differently is refused too.
- **POST.** A body that is not JSON is 400 `parse_error`, and one that is neither an object nor an array is 400 `invalid_request`, as at the proxy. A JSON array is 400 `ext_authz_batch_unsupported`, before anything is decided: the proxy answers the refused entries of a batch itself and forwards the rest, and the gateway can only forward all or nothing, so deciding entries that are then not forwarded would charge run limits for calls that never ran. One message is screened exactly as the proxy screens it:
  - `tools/call`, `resources/read`, `resources/subscribe`, `prompts/get`, `completion/complete` and unknown methods are decided by the pipeline and audited. Allow: 200. Deny, approval required, or invalid params: the proxy's JSON-RPC error body (`-32003`, `-32008`, `-32602`, with `data.reason` and `data.decision_id`), with HTTP 403 instead of the 200 the proxy uses inside a JSON-RPC answer.
  - `initialize`, `ping`, the list methods, `resources/unsubscribe`, `logging/setLevel`, notifications and responses without a method are forwarded by the proxy after a lease check. The adapter answers 200 when the lease check passes and 401 (`-32001`, recorded as the proxy records it) when it fails.
  - A token that does not verify is 401 with the proxy's body and `WWW-Authenticate`; over `[limits] mcp_requests_per_minute` is 429, and a full DPoP replay cache 503, as at the proxy.
- **GET and DELETE.** As the proxy: authenticate, check the lease (recorded under `http.GET` or `http.DELETE` when it fails), then 200. `HEAD` is answered as `GET` (axum routes it to the `GET` handler, as at `/mcp/{server}`). Any other method is 405 with no body and no code.
- **Allow answers** are 200 with no body. They carry `X-Attenuo-Decision-Id` when a call was decided, which the gateway can copy into the upstream request with `includeResponseHeaders`.
- **Sessions.** `Mcp-Session-Id` is ignored. The proxy binds a session id to the principal that opened it and rejects it from anyone else (SR-11); the adapter never sees the upstream's answer, so it cannot learn which session belongs to whom. To keep a client from naming another principal's session in a decision, the adapter puts no session in the `ToolCall`, so Cedar sees no `context.session_id`. Session binding is the gateway's job here.
- **DPoP.** A proof names the method and URL the agent called, which is the gateway's URL. An entry may set `dpop_url` to that URL (no query or fragment); the proof is then checked by the same code as at the proxy (`check_presented`: signature, `ath`, `htm` against the forwarded method, `htu` against `dpop_url`, `iat` window, server nonce when required, and the `jti` replay cache, so a proof is still accepted once). The URL comes from attenuo's config, never from the request. Without `dpop_url`, a request that carries a `DPoP` header is 401 `ext_authz_dpop_url_unset`, and a key-bound token without a proof is 401 `dpop_required` as anywhere else. The gateway must forward the header: `includeRequestHeaders: [authorization, dpop]`.
- **Run limits and audit.** A decision through the adapter is a call to `Pipeline::decide` like any other: it charges run limits and writes the same decision record, and a failed audit append denies. A charge is made when the call is allowed, before the gateway forwards it, as at the proxy.

## 4. What is not covered

attenuo sees the request, never the answer: the gateway forwards to the MCP server and relays the result. So, compared with the proxy:

- **No output labelling.** Results are not recorded (`tool_result` records), not labelled untrusted, and do not taint the run (ADR-0009). Policies that ask for approval after untrusted output never see such output. The AuthZEN endpoint has the same limit: the server "sees results only through its own proxy" ([output labelling, section 5](output-labelling.md#5-interoperability)).
- **No list filtering.** `tools/list` and the other list answers reach the agent unfiltered, and `require_listed_tools` only knows the tools in `[policy.catalog]` (the adapter never sees a `tools/list` answer), so with it on, a tool missing from the catalog is denied `tool_not_listed`.
- **No stream re-check.** The proxy ends a long-lived stream when the lease is revoked (SR-28). Through the gateway, a stream that was allowed stays open; revocation is seen at the next request.
- **The approval token goes upstream.** The proxy removes `params._meta["dev.attenuo/approval"]` before forwarding; the gateway forwards the message with the agent's `_meta` members (section 2). The decision is unchanged (the token is taken out before the call hash, as at the proxy), but the upstream sees a token that has just been used.
- **The agent's token goes upstream** unless the gateway removes `Authorization` and `DPoP` (the guide shows how).
- **Trust.** attenuo decides on the body the gateway shows it and trusts the gateway to forward that same body, once, only after a 2xx, and to fail closed. That is a new trust assumption ([threat model](../spec/threat-model.md)).

What the operator must set on the gateway to fail closed: `includeRequestBody` with `allowPartialMessage` left false; `failureMode` left unset or `deny`, never `allow`; no `cache`; one target per route (or a fixed `prefixMode` and tool names the catalog uses); and the upstream reachable only through the gateway.

## 5. Alternatives rejected

- **agentgateway's CEL mapping onto the AuthZEN endpoint.** agentgateway's own example `examples/mcp-authzen/config.yaml` builds an AuthZEN request with a `body` CEL expression and enforces `decision` with an `authorization` rule. That works without code here, but an AuthZEN deny is a 200, so forgetting the extra rule lets every call through; the gateway decides which messages to send (`has(mcp.tool)` skips `resources/read`, `prompts/get` and anything it cannot parse); and each operator writes the mapping of arguments into `context.input` by hand. The adapter answers deny with a non-2xx status and classifies messages with the proxy's own code.
- **The gRPC `Check` service.** It carries the same information (headers and body) but needs protobuf and gRPC dependencies the server does not have. The HTTP mode is enough.
- **Accepting batches.** See section 3: an all-or-nothing gateway and a per-entry decision do not fit without charging for calls that never run.
- **A loopback-only or admin-listener route instead of a secret.** A gateway usually runs on another host, and the admin listener carries operator credentials the gateway should not hold.
- **Not needing an adapter at all: the gateway in front of attenuo's proxy.** Pointing the gateway's MCP target at attenuo's `/mcp/{server}` keeps everything in section 4. It needs no code, but has not been tried either, and a DPoP-bound token would not pass: the agent's proof names the gateway's URL, which the proxy does not accept. It is the better choice when the extra hop is acceptable; the adapter is for deployments where the gateway must talk to the MCP server directly.

## 6. Run against agentgateway v1.7.0

On 2026-11-16, on one Linux machine, all on 127.0.0.1: agentgateway v1.7.0 (commit `26f5aebe`), built from source without the UI, with the [guide](../guides/agentgateway.md)'s configuration; attenuo from this repository with one `[[ext_authz]]` entry; `fake_mcp` as the MCP server (the MCP Python SDK's server for the listen stream, which `fake_mcp` does not serve). The guide lists each case and what the agent got ([What was run](../guides/agentgateway.md#what-was-run)); `scripts/agentgateway-smoke.sh` repeats the allowed and the denied call.

What the gateway sent attenuo, recorded by a logging pass-through between them, matches section 2: the agent's method; the fixed path; `authorization` (the DPoP requests were not recorded this way, but attenuo checked their proofs, so `dpop` arrived too); `x-envoy-auth-partial-body: false`; the secret from `addRequestHeaders`; `host` and `content-length`; no `content-type`; the agent's body byte for byte; on `GET` and `DELETE` the same headers and no body. `x-envoy-auth-partial-body` was `true` only with `allowPartialMessage: true` and a body over `maxRequestBytes`, and absent without `includeRequestBody`. attenuo's answers needed no change: every case gave what section 3 says.

What differed from what this note and the guide said before the run:

- The upstream does not receive the agent's bytes (section 2, "Forwarding"). The refusal of ambiguous bodies stays; its reason is now that the gateway parses the message itself.
- `mcp.port`, which the guide used, is deprecated in v1.7.0 and listens on every interface; on a host without IPv6 the gateway did not start with it. The guide now uses `gateways` with `bindAddress`.
- v1.7.0 writes a generated session key into its config file on first start unless `SESSION_KEY` is set.
- A refusal by the gateway itself (a body over `maxRequestBytes`, `failureMode`) is plain text (`authorization failed`), not JSON-RPC.

Not run: other versions of agentgateway, among them commit `18f83707`; TLS; any component on another host; `cache`; several targets or another `prefixMode`; the gRPC mode; a batch through the gateway; an approval flow; load.
