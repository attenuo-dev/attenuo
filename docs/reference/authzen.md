# AuthZEN conformance

Attenuo's decision endpoint follows the [OpenID AuthZEN Authorization API 1.0](https://openid.net/specs/authorization-api-1_0-final.html) (final, January 2026). This page lists what of that specification the server implements, what it adds, and what it leaves out. It was checked against `crates/attenuo-server/src/routes/authzen.rs`, `crates/attenuo-server/src/authz/pipeline.rs` (`Pipeline::would_allow`), `crates/attenuo-policy/src/authzen.rs` and `crates/attenuo-server/src/routes/wellknown.rs`. Section numbers below are the specification's.

The conformance fixtures in `crates/attenuo-server/tests/fixtures/authzen/` exercise every row marked as implemented. Each fixture is a JSON request and the answer the server must give, with a `_note` naming the section it covers. `crates/attenuo-server/tests/authzen_conformance.rs` runs them all against one server. It compares the status and the whole answer exactly. The only tolerance is for values that are random or depend on the clock: `decision_id`, `approval_id`, `call_hash`, `expires_at`, and the server's own URL in discovery.

The endpoints and their configuration are also listed in the [HTTP API reference](http-api.md#decision) and the [configuration reference](config.md#authzen).

## Implemented

| Specification | Attenuo |
| --- | --- |
| 5.1 to 5.4, 6.1: request of `subject` (`type`, `id`, `properties`), `action` (`name`, `properties`), `resource` (`type`, `id`, `properties`) and an optional `context` | `POST /access/v1/evaluation`. `subject`, `action` and `resource` are required; if one is missing, or one of its required members is, the answer is 400 `invalid_request`. |
| 5.5, 6.2: answer of a boolean `decision` and an optional `context` object | Always `{"decision": <bool>, "context": {...}}`. A deny is 200 with `decision: false`, never an HTTP error. |
| 7.1, 7.1.1, 7.2: `POST /access/v1/evaluations` with an `evaluations` array; top-level `subject`, `action`, `resource` and `context` are defaults that each entry overrides, and may be left out when every entry has them; answers come back in request order as `{"evaluations": [...]}` with no top-level `decision` | Implemented. At most `[authzen] max_batch` entries (default 64); more is 400 `batch_too_large` before anything is decided. |
| 7.1: a batch request with no `evaluations`, or an empty one, behaves like a single evaluation | Implemented: it is decided as one evaluation and answered as one, `{decision, context}`. |
| 7.1.2.1: `options.evaluations_semantic`, default `execute_all` | `execute_all` (sent or left out), `deny_on_first_deny` and `permit_on_first_permit`. See [batch semantics](#batch-semantics). Any other value, or one that is not a string, is 400 `invalid_request` before anything is decided. |
| 7.2.1: an entry that cannot be evaluated is closed (`decision: false`) and says why in its `context` | `{"decision": false, "context": {"error": {"status", "code", "message"}}}`, following the spec's non-normative `{status, message}` example with Attenuo's error code added. The other entries are still decided. A failed authentication refuses the whole request instead (401 or 403). |
| 8, 8.2, 8.3, 8.6: Action Search API, `POST /access/v1/search/action` with `subject`, `resource`, optional `context` and `page`, answered `{page, results}` | Implemented for one MCP server's catalogued tools, with no side effects and paged by `page.token` / `page.next_token`. See [action search](#action-search). Subject and resource search are not served. |
| 9, 9.1.1, 9.2: discovery at `GET /.well-known/authzen-configuration` | `policy_decision_point` and `access_evaluation_endpoint` (both required), `access_evaluations_endpoint` and `search_action_endpoint`, without authentication. See [discovery](#discovery). |
| 10.1: HTTPS `POST` with JSON bodies at the default paths `/access/v1/evaluation`, `/access/v1/evaluations` and `/access/v1/search/action` | Implemented. The server listens on plain HTTP and is expected behind TLS termination in production ([deploying](../guides/deploying.md)). |
| 10.1.2: 400, 401, 403 and 500 for failed requests | 400 for a malformed request, 401 for a missing or bad credential, 403 `chain_not_issued` for an unsigned body chain that this server did not issue, 500 for internal errors. 503 can also occur (a JWKS that cannot be fetched, a full DPoP replay cache). |
| 10.1.3: when the request carries `X-Request-ID`, the answer MUST carry the same value | Implemented on all three endpoints, for successful and refused requests alike. A request without one gets none. |

## Batch semantics

Section 7.1.2.1 defines three values for `options.evaluations_semantic` on `POST /access/v1/evaluations`:

- `execute_all` (the default): every entry is decided and answered, in request order.
- `deny_on_first_deny`: "deny on first denial (or failure)", short-circuiting like `&&`. Entries are decided in order and the batch stops after the first entry answered `decision: false`. An entry that cannot be evaluated (7.2.1, answered with `context.error`) is a failure and stops the batch too.
- `permit_on_first_permit`: the converse, like `||`. Entries are decided in order and the batch stops after the first entry answered `decision: true`. A failed entry is not a permit and does not stop it.

**Entries after the stop are left out, not answered as denied.** The specification's text does not say this in so many words, but its examples do: three requests under `deny_on_first_deny` get two answers (permit, then the deny), and three under `permit_on_first_permit` get one. Attenuo follows the examples, so `evaluations` in the answer holds exactly the entries that were decided, in request order, ending with the one that stopped the batch. The i-th answer still belongs to the i-th request (7.2). A PEP that gets fewer answers than it sent knows the batch stopped, and the last answer says why.

Entries that were not decided have no side effects: no audit record, no charge to the run's limits, no approval used. Each decided entry is audited exactly as under `execute_all`. Authentication failures still refuse the whole request (401 or 403) before or instead of any answer, and `[authzen] max_batch` counts the entries sent, not the ones decided.

The answer to the deciding entry keeps Attenuo's own `context` (`reason` such as `policy_deny`, `policy_ids`, `decision_id`, ...). The specification's non-normative example puts `"reason": "deny_on_first_deny"` there instead; Attenuo does not overwrite the policy reason, which is what the audit record says.

Fixtures: `evaluations-deny-on-first-deny.json`, `evaluations-permit-on-first-permit.json` and `evaluations-semantics.json`. `stopped_batch_audits_only_what_it_ran` in `authzen_conformance.rs` checks that a stopped batch leaves one audit record per answered entry, with the answer's `decision_id`, and none for the rest.

## Action search

`POST /access/v1/search/action` answers "which actions may this subject perform on this resource, in this context" (section 8.6). It maps onto the decision pipeline without a new decision path, which is why it is built and the other two searches are not.

- **Request.** `subject` and `context` as for an evaluation, and the same authentication: the agent's delegation token as bearer (with a DPoP proof for this URL when the token is bound), or with `[authzen] allow_unsigned_chain` a `[[peps]]` entry and an unsigned chain this server issued. `resource` is the MCP server: `resource.properties.server`, or else `resource.id`, which must then hold no `/` (`github`, not `github/read_file`; otherwise 400 `invalid_search_resource`). `resource.type` is not checked, as for evaluation; `mcp_server` is the suggested value. An `action` member is ignored: section 8.6 leaves it out of this request, and 10.1.1 says unknown members are ignored.
- **Candidates.** The tools the `[policy] catalog` lists for that server, in name order. A tool the catalog does not list is never a result, even under `[policy] unknown_tools = "allow"`, because there is nothing to enumerate it from.
- **Results.** The candidates the pipeline would allow now, each as `{"name": <tool>, "properties": {"server": <server>}}`. "Would allow" is `Pipeline::would_allow`: the lease check, the run's taint labels, run-limit counters, run usage and per-user windows read from the store, argument taint, then the capability stage and Cedar, on one policy snapshot, which are the stages `POST /access/v1/evaluation` runs. So a result sent back as the `action` of an evaluation with the same subject, resource and context is decided `true` while the run's state is unchanged (8.1's SHOULD); the server and the request's `properties.server` make that request unambiguous. `context.input` and `context.session_id` apply to every candidate, as they would to each evaluation: a tool whose permit needs an argument is a result only when the context carries it. A revoked or expired lease gives an empty `results`, not an error, as each evaluation would be `decision: false`.
- **What a caller learns.** No `reason`, `policy_ids` or `diagnostics`, only the names that evaluation would answer `true` for. Evaluating each catalogued tool one at a time with the same body tells the caller the same set; `action_search_agrees_with_evaluation` in `authzen_conformance.rs` checks that the two agree, for several capability sets and contexts. The names a search can return are a subset of the tools the proxy already lists to the same token.
- **No side effects, and no audit record.** A search writes nothing: no audit record, no charge to run limits or run usage, no approval taken, no pending approval created, no decision metrics. This is the choice the admin dry run (`POST /admin/policies/evaluate`) and the list screen (`[proxy] list_filter = "policy"`, [ADR-0011](../decisions/0011-cedar-aware-list-filtering.md)) already made: the audit log records decisions that let something happen, and a search lets nothing happen. A PEP that acts on a result still has to call the evaluation endpoint or the proxy, and that decision is audited and charged as always. The server logs one `info` line per search (`AuthZEN action search`, with `chain_id`, `server`, how many candidates were evaluated and how many were permitted). The cost of this choice is the one ADR-0011 names for the list screen: a caller can ask without leaving a record in the hash-chained log.
- **Approvals.** No approval is looked up or taken, so Cedar sees `context.approval.present = false` and an approval-gated tool is never a result, even when a granted approval for the exact call is waiting (an evaluation would take it). `context.approval_token` is 400 `approval_token_not_accepted`: an approval token is spent by the one decision it names, so it has no meaning for a search. Results are therefore sound (each would be allowed) but not complete.
- **Bounds and paging (8.2).** One request evaluates at most `[authzen] max_batch` candidates (default 64), the bound of a batch. `page.limit` is how many candidates one page evaluates: default and maximum `max_batch`, a larger value is clamped (a generic AuthZEN client cannot know the maximum), and 0 or a value that is not an integer is 400 `invalid_page`. So a page holds at most `limit` results and can hold fewer, even none, while more remain. The answer always has `page`, first: `next_token` is the token of the next page or `""` after the last (8.2.2), and `count` is the number of results in this answer. `total` is left out, because knowing it would mean evaluating every candidate. Send `next_token` back as `page.token`; a token this route did not issue is 400 `invalid_cursor`, and `""` asks for the first page.
- **Deviations.** The token is the server's ordinary paging cursor ([paging](http-api.md#paging)) holding an offset into the candidate list: it carries no digest of the request, so a request whose `subject`, `resource`, `context` or `limit` changed between pages is not refused (8.2 says a PDP SHOULD return an error) but continues at that offset. A forged token can only start the caller's own search at another offset. A policy or catalog reload between pages can repeat or skip a tool, which 8.2 allows. `page.properties` is ignored.

Fixtures: `search-action-paged.json` (two pages, then the evaluation of a result), `search-action-context.json`, `search-action-budget.json` (two searches charge nothing; after the evaluation spends the run's one call, the search no longer returns the tool), `search-action-lease-revoked.json`, `search-action-missing-bearer.json` and `search-action-errors.json`. `action_search_writes_nothing` checks that repeated searches over an approval-gated and a limited tool leave the audit log and the approval store as they were, and `action_search_needs_a_proof_for_its_own_url` in `dpop.rs` that a bound token needs a DPoP proof made for the search URL. `unsigned_authzen_chains_can_search_actions_from_a_pep` in `e2e.rs` covers the `[[peps]]` path under `allow_unsigned_chain`: an issued chain from an authenticated PEP is searched, and a PEP without or with wrong credentials (401 `invalid_client`) or a chain the server did not issue (403 `chain_not_issued`) is refused, with no audit record either way.

Clients: Python `Client.authzen_search_action` and `authzen_search_action_iter`, TypeScript `authzenSearchAction` and `authzenSearchActionIter`, and `attenuo authzen search` ([CLI](cli.md#authzen-search)).

## Discovery

`GET /.well-known/authzen-configuration` serves the PDP metadata document of section 9, at the well-known path of 9.2, answering a `GET` (9.2.1) with 200 and `Content-Type: application/json` (9.2.2):

```json
{
  "policy_decision_point": "https://attenuo.example",
  "access_evaluation_endpoint": "https://attenuo.example/access/v1/evaluation",
  "access_evaluations_endpoint": "https://attenuo.example/access/v1/evaluations",
  "search_action_endpoint": "https://attenuo.example/access/v1/search/action"
}
```

- **Members (9.1.1).** `policy_decision_point` and `access_evaluation_endpoint` are required; `access_evaluations_endpoint` and `search_action_endpoint` are optional and present because those endpoints are served. `search_subject_endpoint` and `search_resource_endpoint` are left out because those APIs are not served: an absent parameter tells the PEP the PDP does not support that API. Nothing else is in the document.
- **No `capabilities` (9.1.2).** The member is "a list of registered IANA URNs referencing PDP specific capabilities", from the AuthZEN Policy Decision Point Capabilities registry, whose registration policy is Specification Required. The specification registers no capability itself, and none of what Attenuo adds (delegation tokens as PEP credentials, approval tokens, run limits in `context`) has a registered URN. Publishing a URN of our own under the `authzen` namespace would claim a registration that does not exist, and an empty array is not allowed either (9.2.2: a parameter with no values MUST be omitted). So the member stays absent until a registered capability applies. Paging uses no extra `page` keys, which 8.2.1 would tie to a declared capability.
- **No `signed_metadata` (9.1.3).** Nothing signs the document; it holds only public URLs, and 11.8 lets unsigned metadata rely on TLS.
- **Base URL.** `[server] public_url`, so `policy_decision_point` is the identifier a PEP configured and 9.2.3's identity check passes. Without it, which is allowed only on a loopback listener, the base is `http://<Host>` and `Host` must be `localhost`, `127.0.0.1` or `[::1]` (400 `invalid_host` otherwise), so a forged `Host` cannot end up in a document a shared cache serves to others (SR-19).
- **No authentication, by decision.** The specification does not protect the metadata endpoint: its 9.2.1 example request carries no credential, and 11.8 relies on TLS at the hosting site for the integrity of unsigned metadata. A PEP also needs the document before it can know where to send credentials. So discovery is public like `/.well-known/jwks.json`: it takes no credential and ignores an `Authorization` header (an invalid bearer gets the same document, not a 401). That is safe because the document holds only the server's public base URL and the three fixed endpoint paths, all of which any caller of the API already knows: no policy, tenant, lease, key, configuration or version information, and it does not vary with the caller.

Fixture: `metadata.json` (no credential, and an invalid bearer; the comparison is exact, so an extra member fails it). The `Host` checks are tested in `crates/attenuo-server/tests/hardening.rs`.

## Extensions

These are allowed by the specification (5.5.1 lets the answer's `context` hold any object), but a generic AuthZEN client will not know them.

- **Who may call.** The specification leaves PEP authentication open (11.2). Attenuo requires the agent's delegation token as the bearer (`Authorization: Bearer <token>`, or `DPoP <token>` with a proof for a key-bound token) and decides for that token's chain. The body may repeat the chain in `subject.properties.chain`; if it does, it must equal the token's chain (400 `chain_mismatch`). With `[authzen] allow_unsigned_chain = true`, a `[[peps]]` entry may instead send an unsigned chain in the body, authenticating with HTTP Basic or `pep_id` and `pep_secret` in the body, and every hop must match a lease this server issued (403 `chain_not_issued` otherwise).
- **Subject.** `subject.type` must be `agent`; any other type is 400 `invalid_request`. An empty `subject.id` is filled in with the chain's current agent. A non-empty one must be that agent (400 otherwise).
- **Action and resource.** `action.name` is the tool. The MCP server comes from `action.properties.server`, else `resource.properties.server`, else the part of `resource.id` before `/<tool>`. `resource.type` is not checked; the convention is `tool`, with `resource.id` set to `<server>/<tool>`.
- **Request context.** `context.input` holds the tool's arguments and becomes Cedar's `context.input`. `context.session_id` becomes Cedar's `context.session_id`. `context.approval_token` carries a signed approval token ([approval tokens](http-api.md#approval-tokens)); anything other than a string is 400. No other member reaches Cedar: the server takes run usage, budgets and labels from its own state, and ignores what a PEP sends under `context.usage` or `context.budget`.
- **Answer context.** Always `reason` (an Attenuo reason code such as `policy_allow`, `policy_deny`, `capability_denied`, `lease_revoked`, `budget_exhausted`, `approval_required`, `approval_invalid`, `tool_not_in_catalog`), `policy_ids` (the Cedar policies that decided), `diagnostics` (empty unless `[authzen] diagnostics` allows the caller) and `decision_id` (the id of the audit record). Depending on the call, also `call_hash`, `approval_id` and `expires_at` (approval required), `approval` (an approval was used), `budget`, `charged` and `limit` (run limits), `usage` (destructive tools) and `untrusted_args` (output labelling). The [HTTP API reference](http-api.md#decision) describes each one.
- **Side effects.** An evaluation is a real decision, the same as a call through the proxy. It is written to the audit log, an allowed evaluation is charged to the run's limits and counted in its usage, and a granted approval is used up. Use the admin dry run `POST /admin/policies/evaluate` to ask without these effects.
- **Error bodies.** Refused requests answer with a JSON object, `{"error": "<error>", "code": "<code>", "detail": "<text>"}`, and add `error_description` on a 401; `code` is the stable code ([Errors](http-api.md#errors)). This differs from the specification's table; see [the open decision](#open-decision-error-bodies).

## Open decision: error bodies

Section 10.1.2's table gives the body of a 400, 401, 403 and 500 as "an error message string". Attenuo answers every refused request on the AuthZEN routes as it does on every other REST route, with a JSON object (`Content-Type: application/json`):

```json
{"error": "unauthorized", "code": "missing_token", "detail": "missing_token", "error_description": "missing_token"}
```

This is a known difference, left as it is until the owner decides.

- **What the specification says.** The table says "an error message string" and nothing more: no media type, and no statement whether that is a plain-text body or a JSON string value. 10.1.1 says the top-level element of all request and response bodies MUST be a JSON object, which a bare JSON string is not; the table and that rule are hard to satisfy together. The specification's own per-entry error example in 7.2.1 is an object (`{"status": 404, "message": "..."}`).
- **What changing it would break.** `code` is the stable, documented identifier of every refusal (`missing_token`, `dpop_required`, `batch_too_large`, `chain_not_issued`, `invalid_cursor`, ...), listed in [Errors](http-api.md#errors) and promised never to be reworded ([API compatibility](api-compatibility.md)). The CLI, the Python and TypeScript SDKs and the console read `code` from these answers, including on the AuthZEN routes, and PEPs written against Attenuo can match on it. A string body would drop `code` on these three routes only, so a client would need a second error parser for them, and the guard tests that check every refusal's `code` would have to exempt them. It would be a breaking change under the compatibility policy.
- **What a generic AuthZEN client sees today.** The status code, which is what 10.1.2 asks it to act on, and `WWW-Authenticate` on a 401 (11.3). A client that shows the body as a message shows the JSON text, which still holds `detail`.
- **Recommendation.** Keep the object. It meets 10.1.1, carries the status semantics 10.1.2 requires, and keeps one error shape across the API. If strict conformance to the table becomes a requirement, the least disruptive change is opt-in (for example, a plain-text `detail` when the request's `Accept` prefers `text/plain`), not a change of the default. Raising the table's wording with the AuthZEN working group would settle which reading is meant.

## Not implemented

- **Subject and resource search (8.4, 8.5).** `/access/v1/search/subject` and `/access/v1/search/resource` are not served, and discovery leaves out their endpoint parameters, which signals that they are not supported (9.1.1). Both need a set to enumerate that Attenuo does not hold: subjects are agents and users named in delegation tokens, and the server keeps no directory of them (an issued token's chain is in the audit log, but "every agent that may call this tool" would mean inventing agents and chains that were never issued); resources are tools, and a tool is already the action here, so resource search would be action search under another name. Note that 10.1 also says a client SHOULD fall back to the default path when a parameter is absent; such a client gets 404 from Attenuo.
- **Discovery `capabilities` (9.1.2).** Not published, because no registered capability applies ([why](#discovery)).
- **Signed metadata (9.1.3).** `signed_metadata` is not published: nothing signs the document.
- **`Content-Type` (10.1).** Requests are not refused for a missing or different `Content-Type`; the body is parsed as JSON whatever the header says.
- **HTTPS-only identifiers (9).** On a loopback listener without `[server] public_url`, `policy_decision_point` is an `http://` URL. That is meant for local development only.
