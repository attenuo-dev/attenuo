# Configuration keys

The server reads one TOML file: `attenuo-server --config <file>` or `ATTENUO_CONFIG=<file>`. Unknown keys are rejected at start-up. Relative paths resolve against the working directory. `ATTENUO__<SECTION>__<KEY>` environment variables override single keys of the file; see [Environment overrides](#environment-overrides).

The annotated source of truth is [config/example.toml](https://github.com/attenuo-dev/attenuo/blob/main/config/example.toml). Never use its example agent secrets for anything real; it ships no admin token. [Deploying](../guides/deploying.md) covers what to change before you expose a server.

## `[server]`

| Key | Default | Meaning |
| --- | --- | --- |
| `listen` | `127.0.0.1:8080` | Address to bind. |
| `public_url` | none | Externally visible base URL (`https://attenuo.example.com`), the only source of the URLs in `/.well-known/authzen-configuration`. **Required** when `listen` is not a loopback address: the server refuses to start without it. On loopback it may be left out; discovery then uses `http://<Host>` and answers 400 `invalid_host` unless `Host` is `localhost`, `127.0.0.1` or `[::1]` (with an optional port). Must be `http(s)://host[:port][/path]`, without query or fragment. A plain `http://` URL whose host is not loopback (`localhost`, `127.0.0.0/8`, `[::1]`) is refused unless `allow_insecure_http = true`. With TLS at a reverse proxy, give the proxy's `https://` URL; nothing else is needed. With `[server.tls]` it is required, even on loopback, and must be `https://`. |
| `allow_insecure_http` | `false` | Accept an `http://` `public_url` whose host is not loopback. Tokens and the admin bearer then cross the network in cleartext; set it only when that hop is on a network you trust. The server logs a warning when it is used. Refused together with `[server.tls]`. |

### `[server.tls]`

TLS on the main listener (`[server] listen`). Off by default. The admin (`[admin] listen`), console (`[admin_ui]`) and metrics (`[metrics]`) listeners always speak plain HTTP. The listener speaks TLS 1.3 only, offers ALPN `http/1.1` only, keeps no sessions for resumption, and asks for a client certificate only with `client_certificates = "optional"`. The handshake must finish within `[limits] header_read_timeout_seconds`. Both files are read once, at start: a renewed certificate needs a restart. No key of this section can be set from an environment override, also when the file has the section: every TLS setting is in the reviewed file. With it, health checks must use `https://`: the image's `HEALTHCHECK` and the Helm chart's probes speak plain HTTP and fail ([health checks](../guides/deploying.md#health-checks-the-image-and-the-cli)). See [TLS in attenuo itself](../guides/deploying.md#tls-in-attenuo-itself) and [ADR-0018](../decisions/0018-native-tls-listener.md).

| Key | Default | Meaning |
| --- | --- | --- |
| `cert_pem_path` | required | PEM file with the server certificate first, then any intermediate certificates. At most 1 MiB, a regular file. The server refuses to start when the file has no certificate, or holds a private key, encrypted or not (unless it is also `key_pem_path`). The server does not check the certificate's dates. |
| `key_pem_path` | required | PEM file with exactly one private key (`PRIVATE KEY`, `EC PRIVATE KEY` or `RSA PRIVATE KEY`; RSA, ECDSA P-256 or P-384, or Ed25519; not encrypted). At most 64 KiB, a regular file. The server refuses to start when the key does not belong to the first certificate of `cert_pem_path`, and, on Unix, when its owner or mode breaks PostgreSQL's `ssl_key_file` rule: owned by the server's effective user or root, no access for others, no group write or execute, and group read only when root owns the file (so `0600` or `0400` owned by the server's user, or `0640` or `0440` owned by root). For Kubernetes and Docker secrets see [the key file's mode](../guides/deploying.md#the-key-files-mode). |
| `client_certificates` | `"off"` | `"off"`: the handshake asks for no client certificate. `"optional"`: it asks for one and never requires one, so a client without one connects as before. It proves only that the client holds the private key of the certificate it sent: no chain, no issuer, no dates, no revocation. Whether the certificate authenticates anyone is decided per request, by the `tls_client_cert_sha256` or `tls_client_ca_pem_path` of the entry the request names ([TLS client certificates](#tls-client-certificates), [from a CA](#tls-client-certificates-from-a-ca)). A `tls_client_cert_sha256` or `tls_client_ca_pem_path` on any `[[agents]]` or `[[peps]]` entry refuses to start unless this is `"optional"`. There is no `"required"`. A proxy that ends TLS in front of attenuo hides the client's certificate: this needs clients that connect to attenuo directly, or a TCP (layer 4) pass-through. Any other value refuses to start. |

The names reserved for the server's own audit records are refused at start: `attenuo` as a server name (`[[upstreams]]`, the catalog, `[[root_grants]]` capabilities) and as an agent id (`[[agents]]`, `[[peps]]`, `[[root_grants]] agent`). User subjects starting with `urn:attenuo:` are refused at IdP intake and by the dev root mint; admin actions are audited as `urn:attenuo:admin`.

## `[issuer]`

| Key | Default | Meaning |
| --- | --- | --- |
| `issuer` | `http://127.0.0.1:8080` | The `iss` of tokens. Also the `aud` an ID-JAG must carry. |
| `audience` | `attenuo` | The `aud` of issued tokens. |
| `max_depth` | `8` | Longest allowed delegation chain. |
| `default_ttl_seconds` | `900` | Token lifetime when the exchange does not ask for one. Must be positive. |
| `lease_interval_seconds` | `300` | How long a lease lives after issuance or renewal. Must be positive. |
| `private_key_pem_path` | ephemeral key | Ed25519 PKCS#8 key. Created with mode 0600 on first start if missing. |
| `previous_key_paths` | none | Retired keys (PEM) that stay trusted for verification and in the JWKS. They never sign. |

`POST /admin/keys/reload` (`attenuo admin key reload`) re-reads these two keys from the config file and the key files they name, and swaps in the new signing key and verifying keys without a restart. The other keys of `[issuer]` take a restart. A reload is stricter than startup: it never generates a key, so `private_key_pem_path` must be set and the file must exist, and each key may be listed once. It refuses to drop the current signing key, or a key that signed the audit log, unless asked. See [Keys reload](http-api.md#keys-reload) and [Key rotation](../guides/deploying.md#key-rotation).

## `[policy]`

| Key | Default | Meaning |
| --- | --- | --- |
| `policies_path` | none | Cedar policy file. `POST /admin/policies/reload` re-reads it. Unset, the policy set is empty, so every call is denied, and reload is unavailable. |
| `catalog_path` | none | JSON tool catalog. Can be combined with `[policy.catalog]`. |
| `schema_path` | none | Cedar schema file (Cedar schema syntax) replacing the built-in base schema, the entity types policies are validated against. Actions, context types and `UserAttributes` are still generated. It must declare `User`, `Agent in [User, Agent]`, `Server` and `Tool in [Server]` with every attribute of the default, required and of the same type, or the server refuses to start and says what is missing; it may add entity types and optional attributes. Read once at start (a policy reload keeps it). A relative path is resolved against the working directory; `attenuo policy test` and `policy lint --config` resolve it against the config file, as they do `catalog_path`. |
| `user_attributes` | none | Extra `originating_user.attributes` for the Cedar schema, as `{ name = "type" }`. Types: `string`, `long`, `bool`, `set<string>`. A value of another type is denied with `attribute_type_mismatch`. `decimal` is a catalog input type only and is refused here. |
| `unknown_tools` | `"deny"` | A call to a `(server, tool)` pair missing from the catalog: `"deny"` (reason `tool_not_in_catalog`), `"sensitive"` (evaluated with `resource.sensitive = true`) or `"allow"` (default attributes). |
| `import_annotations` | `"never"` | What MCP tool annotations from `tools/list` may change in the catalog: `"never"`, or `"narrowing"`, where an explicit `readOnlyHint: false` clears `readonly` and `destructiveHint: true` sets `destructive` for a catalog tool. Nothing an annotation says makes a tool less restricted, and tools missing from the catalog are not affected. `openWorldHint` is not imported: a tool's `outbound` inputs come from the catalog only. |
| `track_usage` | `"auto"` | Whether run usage (`context.usage`, [run limits](../design/run-limits.md#usage-kept-only-when-something-can-read-it-2026-10-24)) is kept for calls to destructive tools. `"auto"` keeps it only when some loaded policy reads `context.usage` or some catalog entry names `amount` or `destination`, and decides again on every policy reload; otherwise allowed destructive calls make no usage write and their records carry no `usage`. `true` always keeps it, for example to watch the counters before writing a policy over them. `false` is refused: usage a policy reads is always kept. Per-user windows (`context.usage.user_window.hour` and `.day`) have no setting: a kind is kept exactly when some loaded policy reads it, decided again on every reload. |
| `legacy_bare_actions` | `false` | **Deprecated.** Evaluate with the pre-2026-10-23 action ids, `Action::"<tool>"`, instead of `Action::"<server>/<tool>"`. A bare action matches that tool on every server (SR-13). Logged as a warning at start; `attenuo policy lint` lists bare actions. |

The built-in user attributes `mfa` (bool), `roles` (set of string), `tenant` and `email` are always declared.

### `[policy.catalog.<server>.<tool>]`

| Key | Meaning |
| --- | --- |
| `readonly` | Boolean. Tests as `resource.readonly` in policies. |
| `sensitive` | Boolean. Tests as `resource.sensitive` in policies. |
| `destructive` | Boolean, default `true` unless `readonly = true`. Tests as `resource.destructive` in policies. |
| `output` | `"untrusted"` (default) or `"trusted"`. A result of an untrusted tool taints the delegation run (`context.session.tainted`); a trusted tool's result is recorded but taints nothing. |
| `inputs` | Table of argument name to type: `"string"`, `"long"`, `"bool"`, `"decimal"` or `{ set = "<type>" }`. Used to validate `context.input.*` in policies, and checked on every call before Cedar: a present, non-null argument of another type is denied with reason `input_type_mismatch`. Undeclared arguments are not checked. `long` is a whole number (`5.0` counts). `decimal` is a JSON number with at most 4 fractional digits and a magnitude of at most 922337203685477, as Cedar's `decimal` type: `12.5` and `100` reach Cedar as `decimal("12.5")` and `decimal("100.0")`, and `12.34567` is refused, never rounded. The one rounding is the JSON parse's: a number written with more digits than a double holds (more than 15 significant digits) is read as the nearest double, so `1000000000000.00001` arrives as `decimal("1000000000000.0")`, and the upstream is sent that same double. Compare it with the decimal methods: `context.input.amount.lessThan(decimal("100.0"))`. |
| `amount` | Name of the input whose value run usage sums for this tool, as `context.usage.amount` ([run limits](../design/run-limits.md#35-policy)). Only destructive tools and tools with an `outbound` input keep usage, and naming `amount` or `destination` on any tool makes the server keep it (see `track_usage`). A value that is not a non-negative integer adds 0. If `inputs` declares it, it must be `long` (not `decimal`; usage and `sum` limits count integers, so send a float amount in minor units). |
| `destination` | Name of the input that says where the call goes (payee, recipient), for `context.usage.destination_seen`. A list counts each element. Only keyed hashes of the values are stored, per run. `"<input>#host"` (for example `destination = "url#host"`) counts the host of a URL input instead of the whole value, so pages of one site are one destination. Only a URL of a special scheme (`http`, `https`, `ws`, `wss`, `ftp`, `file`) has a host; any other scheme (`ssh://`, `git://`) has an opaque host that is not normalised, so it has none. A value with no scheme is a bare host and is read as `http://` followed by the value (`www.example.com/x` has host `www.example.com`). A value with no host counts as itself (wrapped as `{"raw": value}`, so it never equals a host), so each different unparseable value is a new destination. A `#` followed by anything but `host` is refused at load. |
| `outbound` | The inputs whose values are delivered to a party they name (a fetch's URL, a callback): `outbound = "url#host"` for one, `outbound = ["url", "callback#host"]` for several. Each entry is an input name with an optional `#host`, as for `destination`. An outbound input is a destination for run usage whatever `destructive` says, so a read-only fetch keeps `context.usage` and a rule over `context.usage.destination_seen` (such as `ask_on_a_new_site`) applies to it. With `destination` set too, `destination` stays the input it was and the outbound values (hosts, with `#host`) count as further destinations of the same tool: `destination_seen` is true when any of the call's values was seen before, as for a list. Usage is kept only when something reads it (`track_usage`): naming `outbound` alone does not turn it on. On a tainted run, an argument that matched an untrusted result and is outbound sets `context.untrusted_outbound` (an `unreadable` match, when the span index cannot be read or the call carries more than 8,000 fingerprints, counts). Cedar sees `resource.outbound`, true when the entry names at least one. Refused at load: an empty entry, an input named twice, a `#` followed by anything but `host`, and `#host` on an input `inputs` declares as anything but `string` or a set of strings. An entry naming an input that `inputs` does not declare (when it declares some) loads with a warning. A custom `schema_path` base that does not declare `outbound: Bool` on `Tool` still loads, but a policy that reads `resource.outbound` then fails validation. |

Every action a policy names must be in the catalog: the table `[policy.catalog.github.read_file]` declares `Action::"github/read_file"`.

Argument names are compared exactly, and a call argument whose name differs only in case from one the entry names (`inputs`, `amount`, `destination`, `outbound`), from one a capability constraint or limit names for the tool, or from one a loaded policy reads under `context.input` or tests in `context.untrusted_args`, is denied with reason `argument_case_mismatch` before the capability stage, because an upstream that ignores case (Go's `encoding/json`) would read it as that name. Write the names as the tool's input schema spells them.

Server and tool names follow one rule everywhere (catalog, `[[upstreams]]`, capabilities, `tools/call`): 1 to 128 ASCII letters, digits, `_`, `.` or `-`, compared case-sensitively and never normalized. A tool key may also be an MCP method name made of such segments joined by `/` (`"resources/read"`), which is how the proxy authorizes methods other than `tools/call`. The server refuses to start with a catalog or grant that breaks the rule.

## `[audit]`

| Key | Default | Meaning |
| --- | --- | --- |
| `sqlite_path` | `":memory:"` | Audit log and lease registry. `:memory:` keeps both in memory and loses them on exit. For a file, the server takes an exclusive lock on `<sqlite_path>.lock` in the same directory before it opens the database, and refuses to start while another process holds it (see [single-writer fence](#single-writer-fence)). |
| `checkpoint_every` | 1000 | Sign a checkpoint every this many entries. 0 turns the count trigger off. |
| `checkpoint_interval_seconds` | 300 | Also sign one this often, if entries arrived since the last. 0 turns the timer off. Whichever trigger fires first writes the checkpoint. |
| `durability` | `"normal"` | `"normal"` or `"full"`: SQLite `synchronous` for a file-backed store, which always runs in WAL mode. `normal` does not sync on commit; `full` syncs every commit. Lease revocations always sync. Ignored for `:memory:`. See below. |
| `wal_checkpoint_seconds` | 5 | How often a background thread copies SQLite's write-ahead log into the database file (`PRAGMA wal_checkpoint(PASSIVE)`), so audit appends do not wait while a checkpoint copies and syncs. It also runs after every 256 commits, keeps the WAL from growing under continuous load with a short catch-up pass (appends pause for it) once the WAL passes 64 MB, truncates the WAL when no append is in progress, and runs once more at shutdown. 0 leaves checkpoints to SQLite on the writer (every 1,000 pages). Not the signed checkpoints above. Ignored for `:memory:`. |
| `append_queue_max` | 1024 | Most audit appends that may wait for the writer thread at once. One more fails at once: the decision is denied with `audit_error` and counted in `audit_append_shed_total{cause="queue_full"}`. Under the default it is never reached by load alone, since the requests that append run on a blocking pool of 512 threads; it bounds memory when the writer stops draining. Between 16 and 1000000; anything else refuses to start. |
| `allow_network_filesystem` | `false` | Start even when the directory holding `sqlite_path` is on a network filesystem (NFS, SMB/CIFS, 9p, CephFS, Lustre, AFS, ...). By default the server refuses to start there, because SQLite's WAL mode and the single-writer lock are not reliable on one; with `true` it starts and logs a warning at every start. FUSE is never refused, only warned about, and a filesystem the server cannot identify is not refused. See [deploying](../guides/deploying.md#not-on-a-network-filesystem). Ignored for `:memory:`. |
| `append_timeout_seconds` | 10 | How long an audit append waits for the writer thread to take it. Past it the record is withdrawn and never written, the decision is denied with `audit_error` and counted in `audit_append_shed_total{cause="timeout"}`, so a hung disk denies calls instead of holding a thread per request for as long as it hangs. The writer takes a batch only once it holds the database connection; the requests in that one batch (at most 256) wait for its commit however long it takes, so a denied decision is never in the log, and its budget charge and approval are given back. Between 1 and 300; anything else refuses to start. |

**Durability.** With `"normal"` a decision that was answered survives the server process crashing or being killed, because the commit is in the operating system's page cache. If the machine loses power or the kernel crashes before SQLite's next sync (at a WAL checkpoint, normally no more than `wal_checkpoint_seconds` or 256 commits apart), the newest decisions can be lost. What survives is always a prefix of the log: an entry is never half-written, the database is never corrupt, and `audit verify` still passes, with the head at an earlier `seq`. A signed checkpoint you shipped off the host for a lost entry will then show the truncation, as it should. Lease revocations are always committed with `synchronous=FULL`, so a revoked lease cannot come back after a power failure; lease registrations and renewals follow the setting. Choose `"full"` when losing the last moments of the record on power failure is not acceptable; it costs one `fsync` per audit commit (see [performance](../design/performance.md)).

Checkpoints are signed with the issuer key and verified against the JWKS; see [Audit log](../concepts/audit-log.md#signed-checkpoints).

### Single-writer fence

One server process owns a database file. With a file `sqlite_path`, the server creates `<sqlite_path>.lock` next to it (for `/var/lib/attenuo/audit.sqlite`, `/var/lib/attenuo/audit.sqlite.lock`), takes an exclusive advisory lock on it (`flock` on Unix) and writes its process id into it. A second server on the same file stops at start-up with `/var/lib/attenuo/audit.sqlite.lock is locked by another process: one server process per database file; stop the other instance first (in Kubernetes, use strategy: Recreate). The lock file records pid 1234, the last attenuo server that took it; ...`. The pid is the last server that took the fence, not necessarily the holder, since any process that can open the file can lock it. On Unix the lock file is created `0600` (and an existing one owned by the server is narrowed to `0600`), a new database file and its `-wal` and `-shm` files `0600`, and a data directory the server creates `0700`; an existing database file or directory keeps its mode (SR-103). The lock belongs to the open file, so the operating system releases it when the process exits, crashes or is killed; a lock file left on disk does not block the next start, and should not be deleted by hand while a server runs. Path spellings are resolved first, so a symbolic link to the same file meets the same lock. The fence is advisory: it keeps out other attenuo servers, not other programs. `attenuo` (the CLI) never opens the database: `audit verify` and `audit export` read the log over the admin API or from an export file, so they work while the server runs. Opening the file read-only with `sqlite3` for offline inspection is not fenced either; stop the server first for anything that writes. `flock` is reliable on a local filesystem and a `ReadWriteOnce` volume, not across hosts on NFS, where SQLite in WAL mode does not work anyway; before the lock the server refuses a network filesystem unless `allow_network_filesystem` is set. Why one process: the run lock, the DPoP replay cache and the loaded policy set live in the process, and the credential replay markers in the file are checked by one writer at a time ([multi-replica readiness](../design/multi-replica.md)). An in-memory store takes no lock.

### `[audit.sink]`

Ships every signed checkpoint off the host as it is created (SR-21); see [Shipping checkpoints off the host](../concepts/audit-log.md#shipping-checkpoints-off-the-host). Unset by default. Only the keys of the chosen `kind` may be set; a missing required key fails startup.

| Key | Default | Meaning |
| --- | --- | --- |
| `kind` | required | `"webhook"`, `"file"` or `"s3"`. |
| `url` | required for webhook | URL to `POST` each checkpoint to (`http://` or `https://`). Any 2xx is success; redirects are not followed. |
| `bearer_token` | `ATTENUO_AUDIT_SINK_TOKEN` | webhook: sent as `Authorization: Bearer <token>`. |
| `path` | required for file | JSON Lines file to append to; created if missing, synced after each line. Put it on another mount than `sqlite_path` (a warning at startup otherwise). |
| `endpoint` | required for s3 | Base URL without a path, e.g. `https://s3.eu-west-1.amazonaws.com` or `http://minio:9000`. Requests are path-style (`<endpoint>/<bucket>/<key>`); an endpoint with the bucket in its host name (virtual-hosted style) is not supported. It is checked as the HTTP client parses it: one without a host (`http://`), with a path, query or fragment, or holding a backslash, whitespace or a control character refuses to start (SR-119). Run against MinIO, not AWS S3 ([tested against MinIO](../concepts/audit-log.md#tested-against-minio)). |
| `bucket` | required for s3 | Bucket name. Each PutObject carries `x-amz-sdk-checksum-algorithm: SHA256` and `x-amz-checksum-sha256`, which AWS requires for a bucket with an Object Lock retention period (a `Content-MD5` would also do; the sink sends none). |
| `region` | `us-east-1` | s3: SigV4 signing region. |
| `prefix` | `attenuo/checkpoints/` | s3: object key prefix; keys are `<prefix><seq, 20 digits>-<16 hex of checkpoint_sha256>.json`. |
| `access_key_id`, `secret_access_key`, `session_token` | `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` | s3 credentials. Give them `PutObject` only. With `session_token` (temporary STS credentials) each PUT also sends `x-amz-security-token`, signed. All three are read once at start and never refreshed: when temporary credentials expire, every PUT is refused (403; the log names S3's error code: MinIO answers `InvalidAccessKeyId`, AWS documents `ExpiredToken`) and checkpoints queue until the server is restarted with new ones. |
| `ca_pem_path` | unset | webhook and s3: PEM file of CA certificates that the sink's requests trust in addition to the web PKI roots built into attenuo (not the system trust store), for a receiver or an S3-compatible store (MinIO, Ceph, Garage) whose certificate a private CA issued. Only the sink uses it; every other outbound connection keeps the built-in roots alone. It adds roots and changes nothing else: the certificate must still be valid for the URL's host. Every `CERTIFICATE` block of the file is used, other blocks are ignored. A file that is missing, unreadable or empty, holds no certificate, or holds one that cannot be used as a root refuses to start. Read once at start: a new file needs a restart. A relative path is resolved against the working directory. With an `http://` URL it is not used, and a warning says so at start. A refused TLS connection is logged with its cause (`invalid peer certificate: UnknownIssuer`). The file may be at most 1 MiB. |
| `queue_capacity` | 1024 | Checkpoints waiting for delivery, at most. When full, the oldest queued checkpoint is dropped and `attenuo_audit_sink_dropped_total` counts it. A prune's anchor is never dropped: with only anchors queued the queue grows past this. |
| `max_lag_seconds` | 300 | `/readyz` reports the sink degraded once the oldest undelivered checkpoint is older than this, or the queue is full. |
| `fail_readiness` | `false` | Make a degraded sink fail `/readyz` (503). Off by default: the server keeps serving and reports `"degraded": true`. |
| `timeout_seconds` | 10 | Per-request timeout (webhook, s3). |
| `initial_backoff_ms` | 500 | First retry delay; doubles per attempt up to `max_backoff_seconds`, each wait drawn between half and all of it. Failed deliveries are retried until they succeed. |
| `max_backoff_seconds` | 60 | Longest retry delay. |

`queue_capacity`, `max_lag_seconds`, `timeout_seconds`, `initial_backoff_ms` and `max_backoff_seconds` must each be at least 1. A webhook `url` and an s3 `endpoint` must start with `http://` or `https://`.

A prune of the log (`[audit.retention]` below) also ships its signed anchor through the sink, in the format `attenuo-shipped-anchor-v1`: one more webhook `POST` (with `x-attenuo-anchor-through-seq` and `x-attenuo-anchor-sha256` in place of the checkpoint headers), one more line of the file (told apart by its `anchor` member), or one more S3 object, `<prefix>anchor-<through_seq, 20 digits>-<16 hex of anchor_sha256>.json`. The anchor is retried until it is delivered, like a checkpoint, and is never dropped or given up. Two things follow for what reads the sink:

- A webhook receiver must accept the anchor's body (status 2xx). One that refuses it holds every later checkpoint behind it in the queue, and the sink goes degraded (`/readyz`) until the receiver accepts it.
- An older `attenuo audit verify --checkpoints`, or an older Python or TypeScript SDK `cross_check`, fails on a shipped file that holds an anchor line: it reads the line as a malformed checkpoint. Upgrade the CLI and the SDKs before the first prune. This release checks the anchor lines: `attenuo audit verify --checkpoints` and the SDKs' `cross_check` / `crossCheck` compare them with the export.

### `[audit.retention]`

Whether the oldest part of the audit log may be pruned, behind a signed anchor that the retained log verifies from ([ADR-0015](../decisions/0015-audit-retention.md), [design](../design/audit-retention.md)). Off by default: with `prune = "off"` the log is never pruned.

| Key | Default | Meaning |
| --- | --- | --- |
| `prune` | `"off"` | `"off"`, `"manual"` or `"auto"`. With `"manual"` the admin prunes through `GET /admin/audit/prune/plan` and `POST /admin/audit/prune` ([HTTP API](http-api.md#audit-retention)); with `"off"` both answer 409 `prune_disabled`. With `"auto"` the server also prunes on its own, every `interval_seconds`, what is older than `keep_seconds` (see below), and the admin may still prune by hand. |
| `min_age_seconds` | 7776000 (90 days) | Nothing younger is pruned: the entry at the boundary must be older than this (409 `prune_too_recent`). At most 3153600000 (100 years); a larger value refuses to start, whatever `prune` is. |
| `batch_rows` | 10000 | Rows deleted per transaction once a prune is committed. The maintenance task runs the batches (at most `[leases] maintenance_max_passes` per run, every `maintenance_interval_seconds`), and appends wait for each one: on a 200,000-row file a batch of 10000 took about 0.35 s. Between 1 and 1000000. |
| `keep_seconds` | none | With `prune = "auto"` only, and required there. The server prunes entries older than this, in seconds. At least `min_age_seconds` and at least 86400 (a day), at most 3153600000 (100 years). |
| `interval_seconds` | 3600 | With `prune = "auto"` only. Seconds between two checks for something to prune. The first check is one interval after start. Between 1 and 86400. |
| `archive_dir` | none | With `prune = "auto"` only. A directory where each automatic prune first writes the entries it removes, as an export file. It must exist and be writable when the server starts. A relative path is taken from the server's working directory. The server warns at start if the directory is writable by its group or by everyone. Unset: the entries are deleted and no copy is kept, and the server logs a warning at start. |
| `max_entries_per_run` | 1000000 | With `prune = "auto"` only. At most this many entries per automatic prune, so the first prune of a large old log is split into several smaller ones. The boundary must still be a checkpoint: when no checkpoint falls inside the limit, the run prunes to the first allowed checkpoint above it. At least 1. |

With `prune` other than `"off"` the server refuses to start when `sqlite_path` is `":memory:"`, when `[audit.sink]` is not set (the anchor must leave the host), or when `min_age_seconds` is below the run-state retention of `[leases]`: below `retention_seconds + run_state_retention_seconds` (each term only when it is not 0) or below `user_window_retention_seconds`. With the defaults that floor is 37 days (3196800 seconds).

`keep_seconds`, `interval_seconds`, `archive_dir` and `max_entries_per_run` refuse to start with `prune` other than `"auto"`, so a typo in `prune` cannot turn into a log that is never pruned without a word. `"auto"` without `keep_seconds` refuses to start too, and so does an `archive_dir` that does not exist, is not a directory, or where the server cannot create a file (it writes and removes a small probe file to check).

**What `prune = "auto"` does.** Every `interval_seconds` the server runs the same plan and the same prune as the admin's routes, with `keep_seconds` in place of `min_age_seconds`. Only entries older than the run's cutoff count as old enough. The cutoff is not simply now minus `keep_seconds` (see **The clock** below). It picks the newest signed checkpoint whose entry is that much older and that every guard allows: no live run at or below it, and `[audit.sink]` caught up (not degraded, a checkpoint at or past it delivered since the server started, and the anchor of the last prune delivered). Then it verifies the entries it would prune, from the log's start to that checkpoint, as `GET /admin/audit/verify` does. With `archive_dir` set, it then writes those entries to an archive file (see below) and checks the file. Only when all of this passes does it prune. Its prune record has the subject `urn:attenuo:retention`, so it can be told from an operator's. Its anchor carries the archive file's SHA-256 in `archive_sha256`, or no digest without `archive_dir`. The rows are then deleted by the maintenance task, as for a manual prune.

- **With `archive_dir`.** Each prune first writes `audit-<from>-<through>.jsonl` into the directory (both numbers padded to 20 digits, so the names sort). The file is the export `attenuo audit export --from <from> --to <through>` would give, so `attenuo audit verify --file <archive> ... --file <retained> --checkpoints <shipped>` checks it with no other tool. The server writes a temporary file, flushes it to disk, links it into place and flushes the directory. It then reads the file back and verifies it, from the start of the log or the last prune's anchor to the boundary. It never replaces a file. If a file of that name is already there, the server checks it the same way, and then makes the export of the range again with the file's own `exported_at` (which must be a time in the form the server writes) and compares the bytes. If it is exactly this prefix's archive, byte for byte, it is used, and its own SHA-256 goes into the anchor; if not, the run fails (`archive_exists`), nothing is pruned, and the file is left alone. The file is mode 0600.
- **The archive stays on the host.** The server does not ship or back up `archive_dir`. Copy its files off the host yourself, and delete old ones when your own policy says so. Someone who controls the host can delete the files. The anchor shipped by `[audit.sink]` carries each file's SHA-256, and that digest is what proves that a kept copy is the real one. The shipped anchors name the real archives: a file in `archive_dir` that matches no anchor is not part of the log. The server removes a file it wrote itself when its prune was refused. After a store error the prune may have committed, so the file stays and the next run checks it and uses it. The server never removes any other file; it warns once per file about one that no prune used.
- **No archive.** Without `archive_dir` the server keeps no copy of what it prunes, and says so in a warning at start. `[audit.sink]` holds the signed checkpoints and the anchor, which prove how long the pruned prefix was and its last hash, but not the records themselves. To keep the records without `archive_dir`, export them yourself, well before they pass `keep_seconds`: on a schedule, run `attenuo audit export --from <seq after the last archive> --to <a checkpoint seq> --out <file>`. Entries that pass `keep_seconds` before you export them are gone.
- **Fail closed.** A run that finds nothing allowed prunes nothing and is counted as skipped, with the guard that stopped it. A run whose entries do not verify prunes nothing and is counted as failed (`verify_failed`); run `attenuo audit verify` to see why. An archive that cannot be written (a missing or read-only directory, a full disk) fails the run with `archive_write_failed`, one that does not verify when read back with `archive_verify_failed`. If another prune moved the boundary while the archive was written, or just before this run's prune, the run is skipped as `concurrent_prune`. A run that fails (a store error) is logged and counted, and the next interval tries again. Nothing here stops the server or changes `/readyz`.
- **After a crash.** A crash while a file is written leaves only a temporary file, `.audit-<from>-<through>.jsonl.<pid>.tmp`. The next run removes regular files with exactly that name pattern, and nothing else. A crash after the file is in place but before the prune leaves the file, and the next run prunes to that file's boundary and uses it, once it passes the check.
- **The clock.** The cutoff of a run is `keep_seconds` before the earliest of three times: now; the newest entry that is not a prune record; and the wall time when the server started plus the time its monotonic clock counted since. Inside one process, a clock jump cannot speed pruning up: the cutoff moves at most as fast as the monotonic clock, with or without new entries. Across a restart the server cannot tell a jumped clock from real downtime, so after a restart with a wrong clock the cutoff starts from the wrong time. Entries written while the clock was behind carry old timestamps, and once the clock is set right they can be pruned early by up to that error. On an idle server the last `keep_seconds` before the newest entry are kept. `archive_dir` is what protects the content. Before each run the server also compares the wall clock with its monotonic clock. If they moved more than an hour apart since the last run, forward or back (NTP stepping the clock, a bad hardware clock, a restored VM), the run is skipped as `clock_jump` with a warning, and the next run goes on. That is a signal, not the protection. On Linux the monotonic clock does not count a suspend or a VM pause. That only makes pruning later, and it can make a run report a `clock_jump` that was none.
- **The first run on a large log.** A run verifies, and with `archive_dir` writes, every entry it prunes, so its time grows with the prefix. `max_entries_per_run` bounds that: a log with years of entries is pruned over several runs, one interval apart.
- **With a manual prune.** A manual prune and an automatic one cannot both commit: the store checks the guards again inside the prune's write transaction, so the second one is refused (and an automatic run counts it as skipped).
- **After a restart.** The sink's progress is counted from the start, so the first automatic prune after a restart waits until the sink has delivered a new checkpoint at or past the boundary.
- **Watching it.** `audit_auto_prune_runs_total{outcome, reason}`, `audit_auto_prune_last_run_timestamp_seconds` and `audit_prune_last_timestamp_seconds` ([metrics](http-api.md#metrics)), and `auto` in `GET /admin/audit/prune/plan`, which shows the settings and the last run with its archive file. `attenuo audit prune --dry-run` prints the same.

With `[leases] retention_seconds = 0` lease trees are never pruned from the registry, so every chain ever issued counts as live and `prune_live_run` refuses any boundary at or above its first record: in practice almost nothing can be pruned. The server starts, with a warning that says so.

Anchors, and the checkpoint at the newest boundary, are never pruned. A key that signed one must stay in the JWKS after a key rotation (`[issuer] previous_key_paths`), or `audit verify` reports the anchor as signed by an unknown key and the log as broken.

### `[approvals.notify]`

`POST`s a small signed JSON document to a webhook when an approval becomes pending, and again when it is decided or expires, so an operator does not have to watch the console. Unset by default. Delivery is best effort and never holds up a call or a decision; see [the server design](../design/server.md#approvals).

| Key | Default | Meaning |
| --- | --- | --- |
| `url` | required | URL to `POST` to: `https://` or `http://`, with a host and no user info or fragment. Any 2xx is success; redirects are not followed. Log lines name only its host. |
| `headers` | none | Extra request headers, as header name to the name of the environment variable holding the value, e.g. `{ authorization = "ATTENUO_NOTIFY_AUTH" }`. Read at startup; an unset or empty variable fails startup. `content-type`, `content-length`, `host`, `transfer-encoding` and `x-attenuo-*` are refused. |
| `secret_env` | `"ATTENUO_APPROVAL_NOTIFY_SECRET"` | Environment variable holding the HMAC signing secret, at least 32 bytes. Required: startup fails without it. |
| `timeout_seconds` | 5 | Per-request timeout. |
| `queue_capacity` | 256 | Notifications waiting for delivery, at most. When full, the oldest queued one is dropped and `attenuo_approval_notify_dropped_total` counts it. One run has at most 32 approvals pending at once (see `[approvals] ttl_seconds`), so it cannot fill the queue by itself. |
| `max_attempts` | 5 | Attempts per notification. After the last one fails it is dropped and counted in `attenuo_approval_notify_dropped_total`. |
| `initial_backoff_ms` | 500 | First retry delay; doubles per attempt up to `max_backoff_seconds`, each wait drawn between half and all of it. |
| `max_backoff_seconds` | 30 | Longest retry delay. |
| `max_lag_seconds` | 300 | `/readyz` shows `checks.approval_notifier: "degraded"` once the oldest undelivered notification, or the current run of failed deliveries, is older than this, or the queue is full. A degraded notifier never makes `/readyz` fail. |
| `outbox_retention_seconds` | 604800 | How long a notification stays in the outbox table after it was delivered or given up (7 days by default). Within this window a restart never sends it again. An approval that expired longer ago than this gets no `approval.expired` notice when the server starts. |

Every limit must be at least 1.

**The document.** `type` (`approval.pending`, `approval.decided` or `approval.expired`), `event_id` (a UUID, the same on every retry of one notification), `approval_id`, `decision_id` (the gated decision), `chain_id`, `server`, `tool`, `call_hash` (SHA-256 over the server, tool and arguments, as in `-32008`), `subject` and `issuer` of the originating user, `agent` (the last hop's agent), `chain_depth` (hops), `requested_at`, `expires_at` (RFC 3339) and `reason`, a one-line summary naming the sources of the run's untrusted results. An `approval.decided` document adds `decision` (`grant` or `decline`), `decided_by: {subject, by}` and `decided_at`. No token and no argument values are sent. The call hash of an argument with few possible values can be confirmed by guessing, so treat the receiver as able to learn what a guessable call was.

**Headers and signature.** `Content-Type: application/json`, `X-Attenuo-Event` (the `type`), `X-Attenuo-Event-Id` and `X-Attenuo-Signature: t=<unix seconds>,v1=<hex>`, where `<hex>` is HMAC-SHA-256 under the secret of the bytes `<t>.` followed by the body exactly as received. The timestamp is the time of the attempt, so a receiver can refuse old requests (five minutes is a reasonable window) and should compare signatures in constant time. A receiver may see one notification twice, if an answer was lost or the server stopped between the delivery and recording it; deduplicate by `event_id`.

**Across restarts.** Every notification is stored in the server's SQLite database (table `notice_outbox`, next to the approvals) before it is queued, and marked when it is delivered or given up. A server that starts on the same database first delivers what was left undelivered, oldest first, counting the attempts already made towards `max_attempts`. It reads those notifications from the table half a `queue_capacity` at a time as the queue empties, so a backlog longer than the queue is delivered whole. Notifications that arrive meanwhile are stored and wait in the table behind it, so everything goes out in the order it was stored, and the notices of one approval always arrive in their order (`approval.pending` before its `approval.expired` or `approval.decided`), across a restart too; once the backlog is through, notifications are queued as they come again. It also watches the approvals still pending again, so one that expired while the server was down gets its `approval.expired` notice at start, after its `approval.pending` if that was still undelivered. `event_id` is derived from the approval id and the type, so it is the same on every attempt and after any restart, and each approval gets at most one notice of each type. With `sqlite_path = ":memory:"` nothing survives a restart. The queue is still bounded: a notification dropped from a full queue is not retried after a restart.

## `[leases]`

Retention of the lease registry and what it records beside the leases (see [Leases and revocation](../concepts/leases-and-revocation.md)). One background task runs every `maintenance_interval_seconds` (a minute by default) when any of the three retentions is on: a session pass, then a lease pass, then a run-state pass, each in passes of `maintenance_batch_rows` rows (1,000 by default, one short write transaction each) and at most `maintenance_max_passes` passes of each kind per run (100 by default). The figures below for the retentions are those defaults.

| Key | Default | Meaning |
| --- | --- | --- |
| `retention_seconds` | 604800 | How long a run's leases are kept once all of them have ended. An expired lease can still be renewed while its token is valid, so keep this above the longest token lifetime the server issues; the server warns at startup when it is below `[issuer] default_ttl_seconds`. Too short a value fails closed: a pruned run's renewal is refused as `lease_unknown`. The default, a week, is far above the default token lifetime (900 s) and the usual IdP credential lifetime, and leaves a week to investigate an ended run in the console. 0 keeps every lease. Run-limit counters, their charge log and approvals follow `run_state_retention_seconds`, which starts counting only once a run's leases are gone. |
| `session_retention_seconds` | 86400 | How long the record of an MCP session (revoke by session, SQLite table `lease_sessions`) is kept after its run's root lease expired. An expired lease can still be renewed while its token is valid, so keep this above the longest token lifetime the server issues (a root token never outlives the IdP credential it came from); a shorter value lets a renewed run's sessions drop out of revoke-by-session, though `chain_id` and `user` still reach it. A pruned session resolves to no run, as an unknown one does. 0 keeps every record. Lease rows and recorded users follow `retention_seconds`. |
| `run_state_retention_seconds` | 2592000 | How long a run's run-limit counters, charge log and approvals (SQLite tables `budget_counters`, `budget_charges`, `approvals`) are kept once the leases they belong to are gone from the registry. Nothing is deleted while a lease it belongs to is still there, whatever its age, so for a run this starts only after `retention_seconds` has pruned it (state under a lease the registry never knew follows the same rule). Then a charged decision's log entry goes once its charge and any refund are older than this, a counter once no charge under its lease is left, and an approval once its creation, decision and expiry are all older than this (a pending or granted approval of a pruned run can no longer be used, since its lease is unknown). Same task, after the lease pass, 1,000 rows per pass, counted in `run_state_pruned_total{kind}`. What goes with it: an operator refund of the decision answers 410 `charge_pruned` (a decision that charged nothing stays 404 `not_found`; the server tells them apart from the audit record), and `GET /admin/approvals` and the console no longer list the run's approvals. The audit log keeps every decision record with its `budget` member, every `admin.budget.refund` record and every `approval_request` and `approval_grant` record, unless pruned (`[audit.retention]`). The default, 30 days on top of the week of lease retention, leaves a month for refunds that follow billing or incident processes; the rows are small. 0 keeps everything. |
| `user_window_retention_seconds` | 3024000 | How long a per-user window (`context.usage.user_window`, run limits phase 3; SQLite tables `user_windows` and `user_window_charges`) and the charges logged against it are kept after the window ended: 35 days by default, a month of refunds after the longest window. Counted from the window's end, never from the leases, so revoking or pruning a run does not reset a user's window, and an open window is never pruned. Same maintenance task, after the run-state pass, under `maintenance_batch_rows` and `maintenance_max_passes`, counted in `run_state_pruned_total{kind="user_window"}`. After that, an operator refund of a decision whose only charge left was a window answers 410 `charge_pruned`. A value from 1 to 86399 (below a day, the longest window) is refused at start. 0 keeps every window. |
| `maintenance_interval_seconds` | 60 | Seconds between runs of the maintenance task. At least 1. A shorter interval prunes sooner after a row becomes prunable; it does not change what is pruned. |
| `maintenance_batch_rows` | 1000 | Rows one pass looks at (session records, leases, or run-state rows), each pass one write transaction. Between 1 and 100000. A lease pass also reads and deletes the whole tree of every prunable run among its rows, whatever this says. |
| `maintenance_max_passes` | 100 | Most passes of each kind in one run of the task; what is left waits for the next run, which continues where this one stopped. Between 1 and 10000. One run looks at no more than `maintenance_batch_rows * maintenance_max_passes` rows of each table (100,000 by default). |

| `max_backoff_seconds` | 30 | Longest retry delay. |
| `max_lag_seconds` | 300 | `/readyz` shows `checks.lease_notifier: "degraded"` on the same rule as the approval notifier. It never makes `/readyz` fail. |
| `outbox_retention_seconds` | 604800 | How long a notice stays in the outbox table after it was delivered or given up (7 days by default). |

Every limit must be at least 1.

**When a notice is sent.** One notice per revocation request that changed at least one lease: `POST /admin/leases/{lease_id}/revoke` (the cascade included) and `POST /admin/leases/revoke` by `user`, `chain_id` or `session`. The CLI's `attenuo lease revoke` and the console's revoke button use these routes, so they send it too. It is stored after the revocation and its `lease_revoke` audit record are written. A request that changes nothing (the lease was already revoked, an unknown lease answered 404, a selector that matched nothing, any `?preview=true`) sends nothing. A lease that expires sends nothing: the enforcement point already has its `exp`. A lease the server revokes itself because the audit record of its own issuance could not be written (reason `audit_error`) sends nothing either: its token was never handed out.

**The document.** `type` (`lease.revoked`), `event_id` (a UUID derived from the audit record's id, the same on every retry and after a restart; if that record could not be written, it is derived from a random value stored with the notice), `lease_ids`, `chain_ids`, `truncated`, `selector`, `revoked`, `reason`, `revoked_at` (RFC 3339, the record's time), `audit_record_id` (the id of the `lease_revoke` record, `null` if it could not be written: the revocation stands and the notice still goes), `by` (the operator's name, `admin` for `[admin] token`) and `by_subject` (the record's `originating_subject`, such as `urn:attenuo:admin:alice`).

- `lease_ids` are the tops of what was revoked. For a revocation by id it is the lease named. For a selector it is each matched lease whose parent this request did not revoke too, ordered by id. Every lease the request revoked is one of them or delegated from one.
- `chain_ids` are the root leases of the chains those leases are in, de-duplicated, in the order they are first reached. The list is not aligned with `lease_ids` by position. A chain id is what an AuthZEN request's chain and an audit record call `chain_id`.
- At most 100 ids are listed. `truncated` is `true` when more top leases matched.
- `selector` is `null` for a revocation by id, and otherwise the selector as the response shows it: `{"user": ...}`, `{"chain_id": ...}`, or `{"session_tag": ..., "chain_ids": [...]}`. A raw session id is never sent.
- `revoked` counts every lease that changed, descendants included. The descendants are not listed, since there can be any number of them. A receiver that needs them calls `GET /admin/leases/{lease_id}/tree`.
- `reason`, and the `user` and `chain_id` strings of `selector`, are cut to 1024 bytes at a character boundary and end in `…` when cut. The audit record and the HTTP response keep the full text. With the 100-id cap, a notice is about 10 KB at most for plain text, and under 21 KB even if every byte of that text needs JSON escaping, plus the operator's configured name and, for a session, one chain per upstream.

**What a revoked token is.** A token is revoked when its chain contains a listed `lease_id`. A listed `chain_id` does not mean the whole chain is revoked. When a lease in the middle of a chain is revoked, the root and its other branches stay valid. A `chain_id` only tells the receiver which runs to ask about again: drop cached allows for that run, and ask on the next request. Do not close streams or refuse tokens on `chain_id` alone. A receiver may choose to do so to fail closed, but it then refuses valid tokens of the other branches until they ask again.

No token, no secret and no argument values are sent. A revocation of one lease with one lease below it, from a test run:

```json
{"type":"lease.revoked","event_id":"2e11a466-9fd8-831f-acc0-417b80941b76","lease_ids":["c0f3caef-3fec-439d-b740-2990c5922840"],"chain_ids":["03f6ed85-4b48-460b-b35b-260591c1ddd8"],"truncated":false,"selector":null,"revoked":2,"reason":"incident 42","revoked_at":"2026-11-21T22:50:34.268272897Z","audit_record_id":"2371d366-6b7d-4383-8563-f0b48be96421","by":"admin","by_subject":"urn:attenuo:admin"}
```

**It is a hint, not enforcement.** The revocation is in force in the server whether or not the notice arrives. A notice can be late, lost or arrive twice. It is lost when the queue is full, when the receiver is down for `max_attempts` tries, or when the server stops between the revocation and storing its notice: the notice goes into the outbox in a separate, later write, so a stop in between leaves the revocation in force and no notice stored. A lost notice loses nothing but time: the next question the enforcement point asks is answered `false`, and the lease's `exp` ends it anyway. An enforcement point that must be sure keeps asking, or caches an allow for no longer than it is willing to leave a revoked agent running. See [using the notice](authzen.md#revocation-notices).

## `[[actor_trust]]`

Issuers of workload identities whose JWTs are accepted as the RFC 8693 `actor_token` of an exchange. Give each entry exactly one key source: `jwks_url` (with `issuer`), or `spiffe_trust_domain` with `spiffe_bundle_url`. Neither is discovered. The URL must be `https://`; plain `http://` is accepted only for a loopback host (`localhost`, `127.0.0.0/8`, `[::1]`), for local development and tests, and anything else refuses to start. Redirects are not followed: a 3xx answer fails the fetch, so give the final URL. The server certificate is checked against the web PKI roots built into attenuo (not the system trust store), plus the entry's `ca_pem_path` when set. The same entries authenticate the agent at hop 0 (IdP intake) when `[token] actor_auth` accepts actor tokens.

| Key | Default | Meaning |
| --- | --- | --- |
| `issuer` | | Exact `iss` the token must carry. Required with `jwks_url`. Optional with `spiffe_trust_domain`, because JWT-SVIDs often have no `iss`; when set, it is required and checked. |
| `jwks_url` | | JWKS of a generic JWT issuer. |
| `spiffe_trust_domain` | | SPIFFE trust domain, for example `example.org`. The token's `sub` must be a SPIFFE ID in it. |
| `spiffe_bundle_url` | | The trust domain's bundle endpoint (SPIRE server `federation.bundle_endpoint`). It serves a JWKS; keys with `use` = `jwt-svid` verify JWT-SVIDs, `x509-svid` keys are ignored. |
| `ca_pem_path` | unset | PEM file of CA certificates that this entry's key fetches trust in addition to the built-in web PKI roots, for a `jwks_url` or bundle endpoint whose certificate a private CA issued (SPIRE's `https_web` profile with `serving_cert_file`, say). Only this entry's fetches use it; other entries and every other outbound connection keep the built-in roots alone. It adds roots and changes nothing else: the certificate must still be valid for the URL's host, the `https://` rule and the refusal of redirects stay. Every `CERTIFICATE` block of the file is used, other blocks are ignored. A file that is missing, unreadable or empty, holds no certificate, or holds one that cannot be used as a root refuses to start. Not for SPIRE's `https_spiffe` profile, whose certificate is an X.509-SVID checked against the SPIFFE bundle, which attenuo does not do. The file may be at most 1 MiB. |
| `audience` | | The `aud` the token must carry, as a string or in an array. Use a value no other service accepts, such as the attenuo server's URL. |
| `subject_to_agent` | `"sub"` | How `sub` becomes an agent id. `"sub"`: `sub` itself (a whole SPIFFE ID). `"spiffe_path"`: the SPIFFE ID's path without the leading `/` (`spiffe://example.org/agents/coder` is `agents/coder`); needs `spiffe_trust_domain`. A table `{ "<sub>" = "<agent id>" }`: only listed subjects are accepted. The result must equal the exchange's `actor`. |
| `allowed_algs` | `RS256`, `ES256`, `EdDSA` | Accepted signature algorithms. HMAC is refused. |
| `jwks_ttl_seconds` | `300` | How long a fetched key set is used. An unknown `kid` triggers one refetch, at most every 30 seconds. |
| `clock_skew_seconds` | `60` | Leeway for `exp`, `nbf` and `iat`. |

An actor token authenticates one exchange: its `jti` (or, without one, its signed content) goes through the replay cache until `exp`. The child token never outlives the actor token's `exp`.

## `[admin]`

The admin API (`/admin/*`: revoke, reload, approve, export, the dev root mint) and where it is served. By default it is on the main listener. Off a loopback `[server] listen` it needs a listener of its own (`listen`) or the explicit `serve_on_main_listener`, so it is not reachable on the port agents use by accident ([ADR-0013](../decisions/0013-admin-api-listener.md)).

| Key | Default | Meaning |
| --- | --- | --- |
| `token` | unset | Static bearer for `/admin/*`: the operator named `admin`, with role `admin`, recorded in the audit log as `urn:attenuo:admin`. `ATTENUO_ADMIN_TOKEN`, when set, replaces it (setting it together with `ATTENUO__ADMIN__TOKEN` refuses to start). With no token and no `operators` configured, admin routes answer 403 `admin_disabled`. When `[server] listen`, `[admin] listen` or an enabled `[admin_ui] listen` is not a loopback address, the server refuses to start if there is no admin credential at all (neither `token` nor `operators`), or if `token` is set and is shorter than 32 bytes or a published placeholder (`change-me`, `admin`, ...); on loopback it only warns. Generate one with `openssl rand -hex 32`. Do not expose `/admin` publicly. |
| `listen` | unset | Serve the admin API on a listener of its own at this address (suggested `127.0.0.1:9102`), behind the same `token`, and not on `[server] listen`. The main listener then answers `/admin/*` exactly as it answers any unknown path (404, empty body). `/healthz`, `/readyz`, discovery and everything agents call stay on the main listener; the admin listener serves `/admin/*` only. It is drained and stopped with the main listener on shutdown. Off loopback the server logs a warning: keep it on a network only operators reach. Point the CLI's `--admin-server` (or `ATTENUO_ADMIN_SERVER`) and the SDKs' `AdminClient` at it. `[dev] allow_root_mint` is then judged by this address, not by `[server] listen`. Must differ from `[server] listen`. |
| `serve_on_main_listener` | `false` | Keep the admin API on `[server] listen` although that address is not loopback. Without it (and without `listen`) the server refuses to start off loopback. Set it only when something in front of the server keeps `/admin/` away from agents and the internet (a reverse proxy that does not forward `/admin/`, or a container that binds `0.0.0.0` behind a loopback-only published port); the server logs a warning. Cannot be combined with `listen`. No effect on loopback, where the admin API is on the main listener anyway. |

### `[[admin.operators]]`

Named admin credentials, each with a role ([ADR-0016](../decisions/0016-admin-operators.md)), next to `token` or instead of it. The file holds only the SHA-256 of each operator's token; `attenuo admin operator new --name alice --role operator` generates a token and prints the entry ([CLI](cli.md#admin-operator-new---name-name---role-role--admin-operator-hash)).

```toml
[[admin.operators]]
name = "alice"
token_sha256 = "<64 lowercase hex characters>"
role = "operator"
expires_at = "2026-12-31T23:59:59Z"   # optional
```

| Key | Meaning |
| --- | --- |
| `name` | `[a-z0-9_-]{1,64}`, unique, not `admin` (the name of `token`). The audit log records the operator's actions with `originating_subject` `urn:attenuo:admin:<name>`, and an approval it decides with that subject as approver. |
| `token_sha256` | SHA-256 of the operator's bearer token, 64 lowercase hex characters (`attenuo admin operator hash` computes it from a token on stdin). |
| `role` | `viewer`: read-only routes (lease state and tree, the audit log, its checkpoints and export, the loaded policies and their check, the `POST /admin/policies/evaluate` dry run, approvals, `GET /admin/whoami`). `operator`: a viewer that may also revoke leases (by id, user, chain or session, the preview included) and decide approvals. `admin`: every admin route (also policy reload, operators reload, agents reload, budget refunds and the dev root mint). The route table is in the [HTTP reference](http-api.md#admin). |
| `expires_at` | Optional. When the token stops working: an RFC 3339 time with an offset, quoted (`"2026-12-31T23:59:59Z"`) or as a TOML offset date-time. From that time on the token is answered 401 `admin_credential_expired`; `GET /admin/whoami` shows it. A time without an offset, or one that does not parse, refuses the file. An entry that has already expired when the server starts is accepted, with a warning that names it, and its token is refused. `attenuo admin operator new --expires-in 90d` (or `--expires-at`) writes it. |

The server refuses to start on a name that breaks the rules or appears twice, a `token_sha256` that is not 64 lowercase hex characters, two operators with the same `token_sha256`, and an operator whose `token_sha256` is the SHA-256 of `token`. Operators are read from the file at startup, and again by `POST /admin/operators/reload` (`attenuo admin operator reload`, role `admin`), which re-reads this array and nothing else from the file the server was started with, checks it with the rules above (against the `[admin] token` in force, which is not reloaded) and swaps it in at once; on any error the operators in force stay as they were. A reload that would leave no unexpired credential with role `admin` (no `token` and no such operator) is refused, so that a typo cannot lock everyone out. They cannot be set from the environment, as no `[[...]]` entry can ([environment overrides](#environment-overrides)); to keep tokens out of the file, keep only their digests in it, which is all it holds. A bearer is compared against every credential's digest in constant time, and only then is the matched entry's `expires_at` checked. To withdraw an operator's access, remove its entry (or set an `expires_at` in the past) and reload: its next request is refused.

## `[[idps]]`

Trusted identity providers for hop 0. Only these issuers are accepted at `POST /token`.

Every key fetch (`jwks_url`, or the discovery document at `issuer` and the `jwks_uri` it names) must be `https://`; plain `http://` is accepted only for a loopback host (`localhost`, `127.0.0.0/8`, `[::1]`), for local development and tests. Key fetches connect the name `localhost` to `127.0.0.1` or `[::1]` without asking the system resolver, so a resolver that sends `localhost` to DNS (no `localhost` line in `/etc/hosts`, say) cannot move a fetch off the machine (SR-107). A configured `jwks_url`, or the `issuer` when there is none, that breaks this rule refuses to start; a discovered `jwks_uri` that breaks it fails the fetch, and the ID token is refused. Redirects are never followed: a 3xx answer fails the fetch with an error naming the `Location`, so configure the final URL. The server certificate is checked against the web PKI roots built into attenuo (not the system trust store), plus the entry's `ca_pem_path` when set.

| Key | Default | Meaning |
| --- | --- | --- |
| `issuer` | | The IdP issuer URL. |
| `client_ids` | `{}` | Table of agent id to the client id registered for it at the IdP. An ID token must have that value in `aud` (and in `azp` when `aud` has several values or `azp` is present), or it is refused with `credential_audience_mismatch`. An agent with no entry must have a client id equal to its agent id; the server logs a warning at startup for each such agent. |
| `tenant` | unset | For a multi-tenant issuer, the tenant whose users this entry trusts. An ID-JAG must carry a `tenant` claim equal to it, else it is refused with `missing_claim` or `tenant_mismatch` (draft-ietf-oauth-identity-assertion-authz-grant-06 §4.4.1). ID tokens are not affected. Unset: `tenant` is not checked. An empty value is refused at startup. |
| `audience` | | Deprecated and ignored for ID tokens. Parsed so old configs load; a warning is logged when set. |
| `jwks_url` | discovery | JWKS location. Otherwise `jwks_uri` from `<issuer>/.well-known/openid-configuration`. |
| `ca_pem_path` | unset | PEM file of CA certificates that this entry's key fetches (the discovery document, the JWKS and the refetch on an unknown `kid`) trust in addition to the built-in web PKI roots, for an IdP whose certificate a private CA issued. Only this entry uses it. It adds roots and changes nothing else: the certificate must still be valid for the host, the `https://` rule and the refusal of redirects stay. A file that is missing, unreadable or empty, holds no certificate, or holds one that cannot be used as a root refuses to start. Read once at start: no reload re-reads it, so a new file needs a restart. A relative path is resolved against the working directory. Same rules as [`[[actor_trust]] ca_pem_path`](#actortrust). The file may be at most 1 MiB. |
| `allowed_algs` | `RS256`, `ES256`, `EdDSA` | Accepted signature algorithms. HMAC is refused. |
| `attribute_claims` | `email`, `groups`, `amr` | Claims copied into `originating_user.attributes`. `mfa` is always derived from `amr`. |
| `jwks_ttl_seconds` | `300` | How long a fetched key set is used. |
| `clock_skew_seconds` | `60` | Leeway for `exp`, `iat` and `nbf`. |
| `credentials` | `["id_token", "id-jag"]` | The credentials this issuer's users may be brought in with at hop 0: `"id_token"` (an OIDC ID token), `"id-jag"` (an ID-JAG), or both. The names are the audit record's `credential` values (`id_token` with an underscore, although the CLI's `--subject-token-type` spells it `id-token`). A credential of a kind not listed is refused with `400 invalid_grant` / `credential_type_not_accepted`, at the step that refuses an unknown issuer: before any key fetch, before its signature or claims are checked, and without using it up. An empty list or another name refuses to start. With [`[idps.id_jag_ceiling]`](#idpsidjagceiling), `["id-jag"]` makes the ceiling hold for every agent (SR-122). Approval ID tokens (`[approvals]`) are not affected. |

### `[idps.id_jag_ceiling]`

Optional, per `[[idps]]` entry, off by default. With it, the root token minted from one of this issuer's ID-JAGs carries no more than both the [`[[root_grants]]`](#rootgrants) entry and the ID-JAG's own `resource`, `scope` and `authorization_details` claims allow (draft-ietf-oauth-identity-assertion-authz-grant-06 §4.4.1). Without it those claims are ignored and nothing changes. ID tokens are never affected: an ID token from the same issuer, presented by an agent its `aud` names ([`client_ids`](#idps)), still gets the root grant as it is. So with the ceiling on and the default [`credentials`](#idps), which accepts both kinds, the ceiling holds only for agents that cannot present this issuer's ID tokens, and the server logs a warning at start for each such entry. Set `credentials = ["id-jag"]` on the entry to refuse its ID tokens at hop 0 and make the ceiling hold for every agent (SR-122). An empty table (`[idps.id_jag_ceiling]` with no keys) turns the ceiling on with only `authorization_details` able to name anything.

| Key | Default | Meaning |
| --- | --- | --- |
| `resources` | `{}` | Table of resource identifier (an exact `resource` value, RFC 8707) to a list of `[[upstreams]]` server names. Each server stands for `<server>:*`. Compared as strings: no URL normalisation, so `https://mcp.example/github` and `https://mcp.example/github/` are two identifiers. |
| `scopes` | `{}` | Table of scope token to a list of capabilities, written as in `[[root_grants]] capabilities` (`"server:tool"` with globs, or a full table with `constraints` and `limits`). |

How each claim names capabilities:

- `authorization_details`: the `capabilities` of every entry of type `attenuo_capabilities` (attenuo's own type, the one `POST /token` requests use), read as the token's capability objects but strictly: a capability with an unknown member (a misspelt `constraint`, say), an invalid name or limits no token may carry names nothing. An entry of any other type names nothing. A claim whose entries hold more than 256 capabilities, or more than 1,024 argument constraints or `one_of` values in all, names nothing at all, and a capability with a `one_of` of more than 1,024 values names nothing (SR-123).
- `resource` (a string or an array of strings): the servers `resources` maps each value to. An unmapped value names nothing.
- `scope` (a space-separated string): the capabilities `scopes` maps each token to. An unmapped token names nothing.

A claim of the wrong JSON type names nothing; a claim that is absent or `null` is not used. Each claim that is present narrows the root grant further, in the order `resource`, `scope`, `authorization_details`, so the result is within the grant and within every claim used. A claim can only narrow: naming something the grant does not give adds nothing. An ID-JAG with none of the three claims gets the root grant as it is. The request is then attenuated against the result. When nothing is left, the request is refused with `400 invalid_scope` / `id_jag_ceiling_empty`; a request within the root grant but beyond the ceiling is refused with `400 invalid_scope` / `scope_exceeds_id_jag` (beyond the root grant itself it is `scope_exceeds_grant`, as without the ceiling). Neither refusal uses the ID-JAG up.

A capability is kept when a single capability of the other side covers it (`⊑`, RFC-0001), after its limits are clamped to the grant's as at a delegation hop. This is not the full intersection: two capabilities that only overlap (`github:read_*` against `github:*_file`) give nothing, never a new capability built from both. See the [standards note](../research/standards.md#the-id-jags-claims-as-a-ceiling).

A limit in a claim, as in the root grant, is copied into the requested capability it covers. Hop 0 has no parent hop to charge, so a limit copied into several capabilities would bound each of them, not the run: a request in which two capabilities fall under the same limited capability of the ceiling (`send_money` once per recipient under `sum` 100) is refused with `invalid_scope` / `limit_split_at_root` (SR-121). Ask for one capability instead, with a `one_of` or wider constraint (`to` in `["alice", "bob", "carol"]`), which then carries the figure once. A capability of the ceiling without limits may be split as before. Limits set at an exchange are not affected, since every call is also charged against the parent hop. The check is made against the root grant, against the ceiling after each claim that holds limits, and against the final ceiling: each step copies the limits of the one before into each capability it keeps, so a limit carried by a `scopes` capability would otherwise be copied into each capability the ID-JAG's `authorization_details` names under it. A request for `send_money` to `alice` and to `bob` under a `scopes` capability with `sum` 100 is therefore refused with `limit_split_at_root` even when `authorization_details` names the two recipients separately, and also when it gives each a lower figure of its own (50 and 50); have the claim name one capability for both (`to` in `["alice", "bob"]`) and ask for that (SR-127). The check is also made against what each claim that holds limits names, as the claim names it: the ceiling keeps a capability of the root grant that a claim's capability covers as it is, with the grant's own limits, so a `scopes` capability with `sum` 60 over a root grant with `send_money` to `alice` under `sum` 50 and to `bob` under `sum` 50 would otherwise bound neither. A request for both is refused with `limit_split_at_root`, also when the claim's figure would hold both, and a request for one of them gets the grant's 50 (SR-131). A limit given only in `authorization_details` is the last step, so each capability the claim names with its own limit is its own budget, as before. Each of these checks also gives every requested capability the limits of every limited capability of that set (the grant, a step, the final ceiling, what a claim named) that covers its calls, as under `[[root_grants]]`, and the root token carries them all (SR-128): a `scopes` entry with `banking:*` under `calls` 10 and `banking:send_money` under `calls` 1 gives a request for `send_money` `calls` 1, whether or not `authorization_details` names `send_money` (when it does, the final ceiling holds `send_money` with the 10 copied from `banking:*`, and the step before it lowers it). Two of them with one kind of limit on different arguments refuse the request with `invalid_scope` / `limit_conflict_at_root`. A limited capability that only overlaps a requested capability, without covering its calls, bounds nothing here either.

The audit record of an intake under the ceiling has an `id_jag_ceiling` member: `claims`, the names of the claims used, and `claims_digest`, the SHA-256 of their full values in the verified ID-JAG ([audit log](../concepts/audit-log.md#the-id-jag-ceiling), SR-126). The values themselves are not stored. The claim names are also in the record's arguments, and so in its arguments digest, as before. The info line `root token issued from IdP credential` names them too (`id_jag_ceiling`) and gives their values (`id_jag_claims`, compact JSON, each cut to 512 bytes, Debug-formatted), so the log says what the ceiling was. Without the ceiling, and for an ID token, the record has no such member and the line has neither field. A refused intake writes no record.

The server refuses to start on an empty resource identifier, a resource mapped to no server or to a name that is not a valid server name (or is `attenuo`), a scope token that is empty or holds whitespace, a scope mapped to no capability, or a capability that does not parse or whose limits no token may carry (for example an empty `arg`, a `derive` on a `sum`, a `max` above 2^63 - 1), and on a scope mapped to more than 1,024 capabilities, more than 1,024 argument constraints or `one_of` values in all, or a `one_of` of more than 1,024 values.

```toml
[[idps]]
issuer = "https://idp.example.com"
credentials = ["id-jag"]

[idps.id_jag_ceiling]
resources = { "https://mcp.example.com/github" = ["github"] }
scopes = { "repo.read" = ["github:read_file", "github:list_*"] }
```

## `[[agents]]`

Agents (OAuth clients) that may present user credentials at `POST /token`, and that authenticate as the `actor` of an exchange with client credentials. With none configured, every request that authenticates with client credentials is rejected (`no_agents_configured`); an agent that authenticates with an `actor_token` from `[[actor_trust]]` needs no entry here.

An entry holds a secret, public keys (`jwks` or `jwks_url`), TLS client certificate settings (`tls_client_cert_sha256`, or `tls_client_ca_pem_path` with a name), or several of them; the server refuses to start with an entry that has none. The agent can only authenticate with what its entry holds: a secret sent for a key-only agent, an assertion for a secret-only agent, or a certificate for an entry without certificate settings, is `client_authentication_failed`. One request uses one method; a secret and an assertion together are `multiple_client_auth`. A secret or an assertion in the request decides even when the connection also has a certificate.

| Key | Meaning |
| --- | --- |
| `id` | Client id. Must match the `actor` if one is sent. |
| `secret_sha256` | Optional. SHA-256 of the client secret, in hex. Make it with `printf %s "$SECRET" \| sha256sum`. |
| `jwks` | Optional. The agent's public keys for `private_key_jwt` (RFC 7523 §2.2) client assertions: a JWK Set as JSON text, usually in a TOML literal string (`jwks = '''{"keys": [...]}'''`). `attenuo key gen --client <path>` writes a new key and prints this line. Read at start and by an [agents reload](#reloading-agents-and-peps). See below. |
| `jwks_url` | Optional, instead of `jwks`. A URL where the agent publishes its public keys, as a JWK Set that `jwks` would accept. The agent can then rotate its keys itself, with no change here and no reload. See [keys from a URL](#keys-from-a-url). |
| `jwks_ttl_seconds` | Optional, default `300`, only with `jwks_url`. How long fetched keys are used before they are fetched again. Must be positive. |
| `ca_pem_path` | Optional, only with `jwks_url`. A PEM file of CA certificates trusted for this entry's `jwks_url` only, in addition to the built-in web PKI roots, as for [`[[idps]]`](#idps). Read at start and by an agents reload. The file may be at most 1 MiB. |
| `tls_client_cert_sha256` | Optional. 1 to 8 SHA-256 thumbprints of self-signed TLS client certificates that authenticate this agent (RFC 8705 `self_signed_tls_client_auth`), each 64 lowercase hex characters. Needs `[server.tls] client_certificates = "optional"`. See [TLS client certificates](#tls-client-certificates). |
| `tls_client_ca_pem_path` | Optional, not with `tls_client_cert_sha256`. A PEM file of the CA certificates that issue this agent's TLS client certificate (RFC 8705 `tls_client_auth`). Needs exactly one of the two keys below, and `[server.tls] client_certificates = "optional"`. Read at start and by an agents reload. See [TLS client certificates from a CA](#tls-client-certificates-from-a-ca). |
| `tls_client_auth_san_uri` | With `tls_client_ca_pem_path`, or the next key. The URI the certificate must carry as a subject alternative name, such as the agent's SPIFFE ID. Compared exactly. |
| `tls_client_auth_san_dns` | With `tls_client_ca_pem_path`, or the key above. The DNS name the certificate must carry as a subject alternative name. No wildcard. Compared without regard to upper and lower case. |

A `jwks` must hold 1 to 8 public signing keys: RSA (2048 bits or more; `RS256`), EC P-256 (`ES256`) or OKP Ed25519 (`EdDSA`), the asymmetric algorithms the server accepts from identity providers. A key's `alg`, if given, must be that of its type; `use`, if given, must be `sig`. With more than one key every key needs a distinct `kid`. The server refuses to start, naming the entry and the key, on: text that is not a JWK Set, an empty set, a key with a private member (`d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`; the message names the member, never its value), a symmetric (`oct`) key, another algorithm or curve, a short RSA modulus, or a `kid` listed twice. To rotate, add the new key with a new `kid` and reload (or restart), move the agent to it, then remove the old key and reload again.

### Keys from a URL

With `jwks_url` the agent's keys are fetched from the URL, by the same rules as the `[[idps]]` keys:

- The URL must be `https://`. Plain `http://` is accepted only for a loopback host (`localhost`, `127.0.0.0/8`, `[::1]`), for local development and tests. Redirects are not followed, so give the final URL. A URL that breaks the scheme rule refuses to start (and an agents reload).
- `jwks` and `jwks_url` together on one entry refuse to start, and a reload with them is refused (`agents_invalid`): an entry takes its keys from one place, so it is always clear which keys are in force. `jwks_ttl_seconds` or `ca_pem_path` without `jwks_url` is refused too.
- Nothing is fetched at start, and an unreachable URL does not stop the server from starting. The keys are fetched on the first assertion that names the entry, and only for an id that is configured with `jwks_url`.
- Fetched keys are used for `jwks_ttl_seconds`. An assertion whose `kid` is not in the set fetches it again at once, at most once per 30 seconds per entry. Anyone can send assertions with made-up `kid`s and so use up that allowance, so a new key works within 30 seconds at most, not always at once. Publish a new key at least 30 seconds before the agent first signs with it. A key removed from the set stops working at the latest `jwks_ttl_seconds` after the last fetch.
- The fetched set is checked by the rules of `jwks` above, with one difference: a key the server does not use is skipped, not refused, since a set published for several consumers may hold such keys. Skipped: a `use` other than `sig` (such as `enc`), a key type, curve or `alg` the server does not accept, and an RSA key under 2048 bits. Each skipped key gets one info line with its `kid` and the reason, never the key. Refused whole: a set with a private or symmetric key, a member that is not a JWK, more than 8 keys, a `kid` listed twice among the keys kept, no usable key at all, or a body that is not a JWK Set; also a body over 256 KiB or a fetch that takes over 5 seconds.
- A failed fetch of keys past their TTL drops them: no stale keys are used. A failed refetch for an unknown `kid` keeps the keys that are still within their TTL, so made-up `kid`s and a key host that fails now and then cannot lock the agent out; only the request with the unknown `kid` is refused. After any failed fetch the next one starts 5 seconds later at the earliest, and until then a request that needs a fetch is refused without one.
- A client whose keys cannot be fetched gets the same answer as an unknown client, 401 `client_authentication_failed`, so the answer does not tell which ids exist. The server logs the cause once per failed fetch at warn level, `client JWKS unavailable`, with the entry's id and the URL (a password in the URL is masked); never a key. The requests refused with that stored failure are logged at debug level only.
- An agents reload builds every entry's key cache anew: keys from before the reload are not used by a request that takes the lists after the reload has answered, also when the URL did not change. They are fetched again on next use. A request that took the lists before the reload is decided with them, as for every list.

A client assertion is checked as [the HTTP API](http-api.md#client-authentication) describes: signed by one of these keys, `iss` = `sub` = `id`, `aud` = `[issuer] issuer` and nothing else, a bounded `exp` (`[token] client_assertion_max_lifetime_seconds`), and a `jti` used once.

### TLS client certificates

With `tls_client_cert_sha256` an agent or PEP authenticates with a self-signed TLS client certificate (RFC 8705 §2.2, `self_signed_tls_client_auth`). The client sends the certificate in the TLS handshake and names itself with `client_id` (an agent) or `pep_id` (a PEP) in the body, with no secret, no Basic header and no assertion. [Identity providers](../guides/identity-providers.md#tls-client-certificates) shows how to make a certificate and its thumbprint.

- The value is the SHA-256 of the certificate's DER bytes, in lowercase hex: `openssl x509 -in client.crt -outform DER | sha256sum | cut -d' ' -f1`. List 1 to 8. Two values let a client move to a new certificate with no gap: add the new one, reload, switch the client, remove the old one, reload.
- A value listed twice in one entry, or by two entries of one list, refuses to start (and a reload). One certificate authenticates one client.
- The certificate must be usable as a client certificate, by the rules rustls-webpki applies with the certificate as its own trust anchor: within its `notBefore` and `notAfter`, not a CA certificate (`basicConstraints` `CA:TRUE` is refused, and `openssl req -x509` sets it unless told not to), `clientAuth` in its extended key usage if it has that extension, no unknown critical extension, and signed by its own key. A certificate a CA issued is refused. These are checked on every request, so an expired certificate stops working without a reload.
- Names in the certificate (subject, SAN, SPIFFE ID) are not read. There is no CRL or OCSP check: to revoke a certificate, remove its thumbprint and reload.
- Every refusal (an unknown id, no pin on the entry, another thumbprint, a certificate outside its dates or otherwise not usable) is the same `401` `client_authentication_failed`; the server logs the reason at debug level only.
- `Client-Cert`, `X-Forwarded-Client-Cert` and similar headers are never read. Only a certificate from attenuo's own handshake counts.
- Tokens issued this way are bearer or DPoP-bound as before. They are not bound to the certificate (no `cnf.x5t#S256`).

### TLS client certificates from a CA

With `tls_client_ca_pem_path` an agent or PEP authenticates with a TLS client certificate that a CA issued (RFC 8705 §2.1, `tls_client_auth`). The client sends the certificate, and any intermediate CA certificates, in the TLS handshake, and names itself with `client_id` (an agent) or `pep_id` (a PEP) in the body, with no secret, no Basic header and no assertion. The entry says which CA and which name. Many agents can share one CA: each entry names its own SAN, so one agent's certificate never authenticates as another. [Identity providers](../guides/identity-providers.md#tls-client-certificates-from-a-ca-spiffe) has a worked example.

```toml
[[agents]]
id = "coder"
tls_client_ca_pem_path = "/etc/attenuo/agents-ca.pem"
tls_client_auth_san_uri = "spiffe://example.org/ns/agents/sa/coder"
# or: tls_client_auth_san_dns = "coder.agents.internal"
```

- **The CA file.** PEM, CA certificates only: 1 to 16 `CERTIFICATE` blocks, each with `basicConstraints` `CA:TRUE`. At most 1 MiB, a regular file. A private key anywhere in the file, any other kind of PEM block, or a certificate that is not a CA refuses to start (and a reload). Errors name the file, never its content. The file is read at start and by every agents reload, once per path, so the agents and PEPs that name it see the same bytes.
- **One name.** Set exactly one of `tls_client_auth_san_uri` and `tls_client_auth_san_dns`. A CA file without a name, a name without a CA file, or both names refuse to start. So does `tls_client_cert_sha256` on the same entry: an entry checks certificates one way. The same name on two entries of one list is refused too.
- **One certificate, one client of a list.** A certificate that carries the name of another entry of the same list (`[[agents]]` or `[[peps]]`) is refused for every entry, even when its own name is there too. An agent and a PEP may share a name. Names that no entry uses do not matter.
- **The chain.** The certificate must chain to one of the file's CAs, through the intermediates the client sent (at most 4; a client that sends more is refused), as rustls-webpki checks it: every signature, the dates of every certificate in the chain, the client's certificate not a CA (`CA:TRUE` is refused), every issuer a CA, path lengths of intermediates, `clientAuth` in the extended key usage when the certificate has that extension, no unknown critical extension, and the CAs' name constraints. The dates are checked on every request, against the server's clock. The CA certificates in the file are trust anchors: their own dates and path length are not checked. A CA with URI name constraints cannot be used: rustls-webpki does not support them and refuses the certificate.
- **A URI** (`tls_client_auth_san_uri`) is compared exactly, byte for byte, with the certificate's URI SANs. A value that starts with `spiffe:` must be a valid SPIFFE ID (`spiffe://<trust domain>/<path>`, lowercase trust domain, no port, query or fragment), and the certificate must then carry exactly one URI SAN, as an X.509-SVID does. Other URIs may be any one of several URI SANs.
- **A DNS name** (`tls_client_auth_san_dns`) is one host name: no wildcard, no IP address, no trailing dot. It is compared with the certificate's DNS SANs without regard to upper and lower case. A wildcard SAN in the certificate (`*.agents.internal`) never matches.
- **Not matched:** the subject DN (and its common name), IP addresses and e-mail addresses. A CA that puts the identity only in the subject cannot be used.
- **No revocation.** There is no CRL or OCSP check. A revoked certificate works until it expires, or until you remove the CA or change the name on the entry and reload. Short-lived certificates, such as SPIRE's, keep this window small.
- Every refusal (an unknown id, an entry without certificate settings, another CA, a broken chain, a certificate outside its dates or otherwise not usable, a name that does not match) is the same `401` `client_authentication_failed` as for `tls_client_cert_sha256`. The server logs the reason at debug level only.
- A reload applies on the next request, also on a connection that is already open. A new content of the CA file counts as a change of every entry that names it.
- **Cost.** The chain check runs before the client is authenticated. It is bounded: at most 4 intermediates, of which only one per subject is used (copies of the client's certificate and self-issued ones are dropped), at most 16 CAs, and the answer is kept per connection while it holds. Because self-issued certificates are dropped, a key-rollover link certificate (the new root signed by the old one) that the client sends is ignored: put the new root in the CA file. See [threat model](../spec/threat-model.md).
- Everything else is as for [TLS client certificates](#tls-client-certificates): no forwarded-certificate headers, a body credential wins, tokens are not bound to the certificate.

## `[[root_grants]]`

The most a root token may carry.

| Key | Meaning |
| --- | --- |
| `issuer` | Issuer of the users this applies to. |
| `agent` | The agent that holds the root token. |
| `subject` | Optional. Pins the entry to one user. A pinned entry wins over an unpinned one. |
| `capabilities` | List of `server:tool` strings (globs such as `github:*` allowed) or full capability tables `{ server, tool, constraints }`. Requests are attenuated against this. At most 1,024 capabilities, 1,024 argument constraints and 1,024 `one_of` values in all, and at most 1,024 values in a `one_of`; more refuses to start (SR-123). |
| `attributes` | Used only by the development root mint. IdP intake takes attributes from the verified token. |
| `may_act` | Optional list of agent ids: the RFC 8693 `may_act` of root tokens minted under this grant, so only these agents may exchange them. A request may narrow it with its own `may_act`, never widen it (`may_act_exceeds_grant`). |

For the development root mint, an empty `[[root_grants]]` list lets the admin mint any capabilities.

A constraint's `op` is `equals`, `one_of`, `prefix`, `path_prefix` or `range` ([capabilities](../concepts/capabilities-and-attenuation.md)); a malformed `range` or `path_prefix` (`{ op = "path_prefix", value = "/workspace/../x" }`) refuses the config. A `prefix` on an argument that looks like a file path (named `path`, `file`, `filename`, `dir`, `directory` or `folder`, or ending in `_path`, `_dir` or `_file`, or a prefix starting with `/`, `./` or `~`) is logged as a warning at startup recommending `path_prefix`, and `attenuo policy lint --config` prints the same warning; neither refuses it.

With no matching entry, no root token is issued.

A capability table may also carry `limits`. A limit there is copied into the requested capability it covers, and is the run's budget because only one capability of the root token may take it: a request in which two capabilities fall under the same limited capability of the entry (it covers the calls of both), such as `send_money` once per recipient under `{ server = "banking", tool = "send_money", limits = { sum = { arg = "amount", max = 100 } } }`, is refused with `invalid_scope` / `limit_split_at_root`, also when each asks for a lower figure of its own (SR-121). Ask for one capability that covers them all instead: a `one_of` constraint (`to = { op = "one_of", value = ["alice", "bob"] }`), a wider constraint, or, for several tools under a limited `github:*`, a tool pattern (`github:*` itself) rather than one capability per tool; the agent can then narrow to single tools at its first exchange, where the parent's budget bounds the total. A capability of the entry without limits may be split as before. `POST /admin/root-token` applies the same rule when `[[root_grants]]` is set. Every limited capability of the entry that covers a requested capability's calls bounds it, not only the one it takes its limits from: the root token capability carries the limits of each of them, combined kind by kind (`calls` the lowest; `sum`, `calls_per` and `distinct` on one argument the lowest; a `calls_per` or `distinct` that the combined `calls` already implies is not added), and the split rule above applies to each of them (security review pass 17, SR-128). So an entry with `send_money` to alice, bob or carol under `sum` 100 and `send_money` to alice under `sum` 30 gives a request for alice alone `sum` 30 and one for bob or carol `sum` 100, and refuses a request for both with `limit_split_at_root`, since both are within the wide capability; `calls = 1` on `bank:send_money` beside `bank:*` with `calls = 10` gives a request for `bank:send_money` `calls` 1. When two such capabilities set one kind of limit on different arguments (`sum` over `amount` and `sum` over `fee`), one capability cannot carry both, and the request is refused with `invalid_scope` / `limit_conflict_at_root` rather than one limit dropped. A request whose own limit is on another argument than one of them is refused too, with one of two codes: the request is first clamped, as at an exchange, to one capability of the entry (the first that covers it with its limits, else the first that covers its calls, in the canonical order of the entry), and if that capability is one it conflicts with, the answer is `scope_exceeds_grant` (`scope_exceeds_id_jag` against an ID-JAG ceiling); otherwise it is `limit_conflict_at_root`. So `send_money` with its own `sum` over `amount` is `scope_exceeds_grant` under an entry whose only capability over it has `sum` over `fee`, and `limit_conflict_at_root` when an unlimited `banking:*` is beside it (security review pass 18, SR-132). The entry written out as the request is refused too when one of its limited capabilities is within another (a split of the wider one, or a conflict); omit `capabilities` to get the entry as it is, in which every call is charged to each capability that matches it. Out of scope: a limited capability that only overlaps a requested capability, without covering its calls, bounds nothing at hop 0. A request for `bank:*` under the entry above takes `calls` 10, and its `send_money` calls are not bounded by the 1. Write a tighter rule for some of a wider capability's calls as a policy over run usage, or leave the wider capability out of the entry. Limits no token may carry refuse to start, with a message naming the entry (its index from 0 in file order, its `issuer`, `agent` and `subject`), the capability, the limit and what is wrong with it, such as an empty `arg`, an `arg` with a control character or `#`, a `max` over the bound, a `derive` on a `sum`, or a `sum` over an argument whose constraint admits no non-negative integer. Such an entry used to start and then fail every mint under it with `invalid_capability`. The other refusals of an entry at start name it the same way, `[[root_grants]] entry <index> (issuer "...", agent "...", subject "..." or any subject): ` followed by the reason (under `[logging] redact_subjects` the subject is not written out, SR-130): an `agent` of `attenuo`, a capability that does not parse, a server or tool name that is not allowed (or the server `attenuo`), and an entry over the size bounds (SR-123). `[[root_grants]]` is read at start only; there is no reload. A policy over run usage (`context.usage`) counts the calls of a destructive tool per tool, not per capability ([run limits](../design/run-limits.md)).

## `[[peps]]`

Policy enforcement points that call the AuthZEN endpoints. Same shape as `[[agents]]`, including `jwks` or `jwks_url` for `private_key_jwt`; `attenuo` is reserved as an id.

| Key | Meaning |
| --- | --- |
| `id` | PEP id, sent as the HTTP Basic user or as `pep_id` in an evaluation body, or as the `sub` of a client assertion. |
| `secret_sha256` | Optional. SHA-256 of the PEP's secret, in hex. |
| `jwks` | Optional. The PEP's public keys for client assertions, as for `[[agents]]`. A PEP sends `client_assertion_type` and `client_assertion` at the top level of the evaluation body; one assertion authenticates one HTTP request (a whole batch). |
| `jwks_url`, `jwks_ttl_seconds`, `ca_pem_path` | Optional. The PEP's keys at a URL instead of `jwks`, as for `[[agents]]` ([keys from a URL](#keys-from-a-url)). |
| `tls_client_cert_sha256` | Optional. Thumbprints of the PEP's self-signed TLS client certificates, as for `[[agents]]` ([TLS client certificates](#tls-client-certificates)). The PEP names itself with `pep_id` in the body; with a bearer token in `Authorization` too, it gets the diagnostics a PEP gets. |
| `tls_client_ca_pem_path` | Optional, not with `tls_client_cert_sha256`. The CA file for the PEP's TLS client certificate, as for `[[agents]]` ([from a CA](#tls-client-certificates-from-a-ca)). |
| `tls_client_auth_san_uri`, `tls_client_auth_san_dns` | Exactly one, with `tls_client_ca_pem_path`. The name the PEP's certificate must carry, as for `[[agents]]`. |

A request that authenticates as a PEP gets `context.diagnostics` under `[authzen] diagnostics = "peps"`, and only such a request may send an unsigned chain when `[authzen] allow_unsigned_chain = true` (the server refuses to start with that set and no `[[peps]]`).

### Reloading agents and peps

`[[agents]]` and `[[peps]]` are read at start, and again by `POST /admin/agents/reload` (`attenuo admin agent reload`, role `admin`). It re-reads the config file the server was started with, checks both lists with the startup rules above, against the other settings in force (`[token]`, `[authzen]`, `[[idps]]`, `[[actor_trust]]`, `[issuer] issuer`), and swaps both in at once. On any error both lists stay as they were. The [HTTP reference](http-api.md#agents-reload) has the answer and the error codes.

- A new agent or PEP can authenticate with its next request. A removed one, an old secret, an old key, a removed certificate thumbprint, and a removed or changed CA file or certificate name are refused from the next request on, also on a TLS connection that was already open. Each request authenticates against one snapshot of both lists.
- Keys fetched from a `jwks_url` before the reload are dropped, so a changed URL takes effect for every request that starts after the reload answered, with no TTL to wait for. A request already under way (waiting for a key fetch, say) is decided with the lists it started with. Each entry's keys are fetched again on its next assertion.
- Removing an agent stops its secret and keys, not every way to a new token: with `[token] require_actor_auth = false` an exchange can still name it as the actor, and an `[[actor_trust]]` entry that maps a workload to its id still accepts its actor token. Both need a restart to change, and the reload answers a warning for each.
- A file that empties a list in force, or whose `[issuer]` or `[audit]` differs from the running config, is refused unless `allow_empty` or `allow_mismatch` is sent (`--allow-empty`, `--allow-mismatch`): it is most likely an empty, cut-off or wrong file.
- The lists are also checked against the file's own settings, as a restart would apply them. Lists those settings would refuse are reloaded (they pass the rules in force) and named in `restart_warnings`.
- Tokens and leases already issued are not revoked: a token issued to a removed agent keeps working, and keeps renewing, until it expires or its lease is revoked (`attenuo lease revoke <LEASE>`, or by user or chain). Revoke them too when you remove a compromised agent.
- Nothing else in the file is applied. The answer lists, in `restart_needed`, each other section that differs from the one in force (`[[admin.operators]]` excepted, which has [its own reload](#adminoperators)); those take effect at the next restart. So an agent that needs a new `[[root_grants]]` entry or a new `[[idps]] client_ids` key still needs a restart for that part. The comparison is of the values in the file (after the environment overrides), not of the files they name, such as the policy or a key file.
- `[limits] token_requests_per_minute` keeps counting per agent id across a reload, and a client assertion's `jti` stays used: a rotation does not reset either.

Expired ones are reclaimed as new ones arrive; when every slot is live, the response that would bind a new session is replaced by `503`, JSON-RPC `-32006`, reason `session_registry_full`, `Retry-After: 30`. Live bindings are never evicted (SR-36). At least 1. |
| `max_sessions_per_principal` | `64` | Most live session bindings one principal holds. The principal is the chain's root lease: one user's root grant, shared by every agent it delegates to. Only live bindings count (expired ones are reclaimed first; a `DELETE` frees one). One more gets `429`, JSON-RPC `-32007`, reason `too_many_sessions`, `Retry-After: 30`, while other principals keep opening sessions (SR-49). When the proxy refuses a session for this reason or for `max_sessions`, it sends the upstream an MCP `DELETE` for the session the upstream just created (best effort, logged on failure). At least 1. |
| `record_window_seconds` | `60` | The window bounding repeated audit records of one condition: after a record, further occurrences with the same delegation chain, tool name and reason within this many seconds are refused or ended the same way (their error names that record) but only logged and counted in `audit_records_suppressed_total{tool,reason}`. One key for both bounded kinds, the `stream.end` records of `GET` listen streams and the lease refusals of requests without a per-call decision (`initialize`, the list methods, notifications, `GET`, `DELETE`): there is no case yet for them to differ. Shorter means more records from a client that keeps retrying, longer means each record stands for more. Tool-call decisions, refused exchanges and renewals are never bounded. Between 1 and 3600; anything else refuses to start. |
| `upstream_connect_timeout_seconds` | `5` | How long the proxy waits for the TCP (and TLS) connection to an upstream. Not connected in time: `502`, JSON-RPC `-32005`, reason `upstream_unreachable`, as for a refused connection; nothing was sent, so a retry is safe. Between 1 and 300; anything else refuses to start. |
| `upstream_response_timeout_seconds` | `120` | How long the proxy waits, from sending a request, for the upstream's response headers, and for the rest of a body it buffers (a JSON answer it filters, labels or merges replies into). Past it: `504`, JSON-RPC `-32005`, reason `upstream_timeout`. The request was sent, so the upstream may have acted on it. A body relayed as it arrives (SSE, the `GET` listen stream, a JSON answer the proxy does not need to read) is not cut once its headers are in; `stream_recheck_seconds` and the client govern those. Raise it for tools that answer in JSON only after running longer; an upstream that answers over SSE is not affected by the run time. Between 1 and 3600; anything else refuses to start. |
| `record_window_max_keys` | `10000` | Most delegation chain, tool and reason windows each of the two kinds keeps open. When the table is full of open windows a further occurrence is recorded, not suppressed, so a smaller figure only means more records under a flood of distinct chains. Between 100 and 1000000; anything else refuses to start. |

## `[limits]`

Basic protection of one server process against too much work at once: a cap on requests in flight, request deadlines, and per-caller rate limits. Every figure is per process; attenuo runs as a single replica ([deploying](../guides/deploying.md)), so per process is per server. None of it is a security property: it keeps one busy or misbehaving caller from taking the process down for everyone. Refusals carry `Retry-After` (whole seconds) and the route's usual error shape: `{"error", "detail", "error_description"}` on the REST routes, a JSON-RPC error with `id: null` and `data.reason` on `/mcp/{server}`. They write no audit record. They are counted in `requests_shed_total`, `requests_rate_limited_total{limit,cause}` and `request_timeouts_total{kind}` ([metrics](http-api.md#metrics)).

| Key | Default | Meaning |
| --- | --- | --- |
| `max_in_flight` | `1024` | Most requests the main listener handles at once. One more is answered at once with `503`, `Retry-After: 1`, `error_description` `overloaded` (on `/mcp/{server}`: JSON-RPC `-32006`, reason `overloaded`) instead of waiting in a queue. `/healthz` and `/readyz` are never refused or counted. A request counts until its answer starts: a streamed answer (SSE, the `GET` listen stream) stops counting once its headers are sent, and long-lived streams are bounded by `[proxy] max_sessions` instead. The `[metrics]`, `[admin] listen` and `[admin_ui]` listeners are not counted, so with `[admin] listen` set an operator can still revoke while the main listener sheds. `0` turns the cap off. At most 1000000; anything else refuses to start. |
| `header_read_timeout_seconds` | `30` | How long a connection may take to send a request's headers, and how long a kept-alive connection may stay idle before its next request. Past it the connection is closed. Applies to every listener. Between 1 and 300; anything else refuses to start. |
| `request_body_timeout_seconds` | `30` | How long a request body may take to arrive once its headers are in. Past it: `408`, `error` `request_timeout` (on `/mcp/{server}`: `400`, JSON-RPC `-32600`, "request body could not be read"). Applies to every route of the main listener. Between 1 and 3600; anything else refuses to start. |
| `request_timeout_seconds` | `60` | How long a route of the main listener may take to answer, except `/mcp/{server}` and `/admin/*`. Past it: `503`, `Retry-After: 1`, `error_description` `request_timeout`; work already handed to the blocking pool (a token issuance, an AuthZEN decision and its audit record) may still finish. The proxy routes are bounded by the `[proxy]` upstream deadlines and keep their streams open; the admin routes are left out because an audit verify or export of a large log can take longer. Between 1 and 3600; anything else refuses to start. |
| `token_requests_per_minute` | `0` (off) | `POST /token` requests per minute per authenticated agent (the client of the client credentials, or the agent of the actor token). Counted once the agent has authenticated, before the subject token or IdP credential is verified and before any lease lookup, signing or audit append; a request refused later (a replay, a widening) still counts. One more: `429`, `error` `rate_limited`, `Retry-After` until the agent's minute ends. At most 1000000; anything else refuses to start. |
| `token_unauthenticated_requests_per_minute` | `0` (off) | `POST /token` requests per minute per peer address that authenticated no agent: refused before authentication (a malformed body), failed it, or sent no credentials where `[token] require_actor_auth = false` allows that. IPv6 peers are counted by /64. Once a peer has used up its minute, every `POST /token` from that address is refused (`429`, `rate_limited`) before any work, a correctly authenticating agent's too, until the minute ends. When the table of peers is full (`rate_limit_max_keys`) and the address is not in it, the request is not refused up front if it carries client credentials (a secret or a client assertion) and no actor token: it is authenticated, served if it authenticates an agent (and not counted), and otherwise answered with the same `429`, counted as `table_full`. A request without client credentials, or with an actor token, from such an address is refused before any work, so an agent that authenticates with an actor token alone is refused during such a flood. So on a full table a new address can cost one client authentication per request (a digest compare or one signature verification), bounded in concurrency by `max_in_flight` but not in rate. Behind a reverse proxy every caller has the proxy's address, so the limit is then shared by all callers' failed attempts; set it with that in mind or leave it off. Peer addresses are never logged. At most 1000000; anything else refuses to start. |
| `mcp_requests_per_minute` | `0` (off) | Requests per minute to `/mcp/{server}` per run: the delegation chain's root lease, shared by every agent the run delegates to. Counted once the token and its DPoP proof have verified (the token's verification is cached, so this is before any lease lookup, decision, audit append or upstream call); a request with a bad token is a `401` and counts against no one. One more: `429`, JSON-RPC `-32007`, reason `rate_limited`, `Retry-After` until the run's minute ends. Other runs, of the same user too, are not affected. At most 1000000; anything else refuses to start. |
| `authzen_search_requests_per_minute` | `0` (off) | AuthZEN action searches (`POST /access/v1/search/action`) per minute per run: the delegation chain's root lease, from the bearer token or, for a `[[peps]]` entry sending an unsigned chain under `[authzen] allow_unsigned_chain`, from that chain once the server has checked it issued every hop. Counted once the caller has authenticated (the token and its DPoP proof, or the PEP's credentials) and before any candidate is evaluated; a request that fails authentication is a `401` and counts against no one. One more: `429`, `error` `rate_limited`, `Retry-After` until the run's minute ends, and nothing is evaluated. Each admitted search writes one `search` audit record and a refused one writes none, so this limit bounds how fast a run can try argument values against the policy, and the records show that it did (SR-117). It is a table of its own: searches do not use up `mcp_requests_per_minute`, nor MCP requests the searches. `POST /access/v1/evaluation` and `/access/v1/evaluations` are not counted. At most 1000000; anything else refuses to start. |
| `rate_limit_max_keys` | `10000` | Most callers each of the four rate limits tracks at once. A caller whose minute has ended is dropped first. A caller inside its minute is never dropped, so dropping cannot reset a count; when every tracked caller is inside its minute, a new caller is refused (`429`, counted with `cause="table_full"`) until the oldest minute ends; for the per-peer table of `token_unauthenticated_requests_per_minute`, a new address with client credentials is first allowed to authenticate, and refused only if it does not (see that key). Between 100 and 1000000; anything else refuses to start. |

**How the rate limits count.** Each is a fixed window of one minute per caller, starting at the caller's first request: the caller gets N requests, every further one is refused and not counted, and at the end of the minute it gets N again. No caller gets more than N within one of its windows; across the boundary of two windows it can send up to 2N in less than a minute. The rate limits are off by default because a sensible figure depends on the workload: one agent run can make a few calls a minute or thousands, and a limit set too low is a denial the operator caused. A starting point is a few times the busiest legitimate run's rate. They live in the process: a restart forgets them, and they do not add up across replicas.

The log the server writes to standard output ([deploying guide](../guides/deploying.md#logging)). What is logged, and at which level, is `RUST_LOG`'s job, as before.

| --- | --- | --- |

## `[telemetry]`

## Environment overrides

Any scalar key of the file can be set from the environment, so one image and one config file serve several deployments, and a container can change a listen address or a path without a file of its own. The variable is `ATTENUO__`, the section, `__`, the key, with nested sections as more `__` segments:

| Variable | Sets |
| --- | --- |
| `ATTENUO__SERVER__LISTEN=0.0.0.0:8080` | `[server] listen` |
| `ATTENUO__SERVER__PUBLIC_URL=https://attenuo.example.com` | `[server] public_url` |
| `ATTENUO__ADMIN__LISTEN=0.0.0.0:9102` | `[admin] listen` |
| `ATTENUO__AUDIT__SQLITE_PATH=/var/lib/attenuo/attenuo.sqlite` | `[audit] sqlite_path` |
| `ATTENUO__METRICS__ENABLED=true` | `[metrics] enabled` |
| `ATTENUO__LIMITS__MCP_REQUESTS_PER_MINUTE=600` | `[limits] mcp_requests_per_minute` |
| `ATTENUO__TELEMETRY__TRACES__SAMPLE_RATIO=0.1` | `[telemetry.traces] sample_ratio` |
| `ATTENUO__AUDIT__SINK__MAX_LAG_SECONDS=60` | `[audit.sink] max_lag_seconds`, when the file has `[audit.sink]` |

The rules:

- **Two underscores.** The prefix is `ATTENUO__` and the separator is `__`. The variables with one underscore that the server, the CLI and the SDKs read (`ATTENUO_CONFIG`, `ATTENUO_ADMIN_TOKEN`, `ATTENUO_LOG_FORMAT`, `ATTENUO_SERVER`, `ATTENUO_TOKEN`, `ATTENUO_CLIENT_SECRET`, ...) are never read as overrides, and an override is never read by them. Section and key names are matched without regard to case (`ATTENUO__SERVER__LISTEN` and `attenuo__server__listen` are the same key; two variables for one key refuse to start).
- **When.** The overrides are applied after the file is read and before any startup check, so every check and range applies to the final value exactly as if it had been written in the file. The file must still exist (an empty file is a valid config of defaults), and it must parse on its own: an override does not repair a broken file.
- **Types.** The value is read as the type of the key it replaces: `true` or `false` (lower case) for a bool, a decimal integer for an integer, a number for a float, the text as it is for a string. Addresses, paths, URLs and choices such as `[token] dpop` are strings. The text is never parsed as TOML, so quotes are part of the value. An optional key that the file leaves unset (`public_url`, `[admin] listen`, `[admin] token`) takes the type the key takes.
- **Scalars only.** Lists (`allowed_algs`, `previous_key_paths`), tables of names (`[policy.catalog]`, `[policy] user_attributes`, `[telemetry] resource_attributes`, `[approvals.notify] headers`, `[leases.notify] headers`) and arrays of tables (`[[upstreams]]`, `[[agents]]`, `[[idps]]`, `[[root_grants]]`, `[[peps]]`, `[[actor_trust]]`) cannot be set; a variable that names one refuses to start. There is no encoding of a list in one variable that would not be ambiguous for some value, and entries of an array of tables have no stable name. An optional section that the file does not have (`[audit.sink]`, `[approvals.notify]`, `[leases.notify]`) is not created: put it in the file, and override its keys.
- **Strict.** A variable that starts with `ATTENUO__` and cannot be applied stops the server: it names no key, its value is empty or does not parse as the key's type, another variable sets the same key, or the key is one of the refused kinds above. Every such variable is listed in one error, by name; the value is never printed, since it may be a secret. A typo in the name of a security setting is an error, never a silently ignored variable.
- **`[dev]` is refused.** `ATTENUO__DEV__ALLOW_ROOT_MINT` and every other `[dev]` key refuse to start, whatever the value. The unverified root mint is switched on in the file, where a review sees it, and never by a variable that can come in from a shared environment file, an orchestrator default or a CI job.
- **`[server.tls]` is refused.** `ATTENUO__SERVER__TLS__CLIENT_CERTIFICATES` and every other `[server.tls]` key refuse to start, whatever the value, also when the file has the section. The certificate, the key and whether clients are asked for certificates are set in the file, where a review sees them.
- **The older variables.** `ATTENUO_ADMIN_TOKEN` keeps replacing `[admin] token` and `ATTENUO_LOG_FORMAT` keeps overriding `[logging] format`, as before. Setting one of them together with the matching override (`ATTENUO__ADMIN__TOKEN`, `ATTENUO__LOGGING__FORMAT`) refuses to start, so two sources never disagree silently. The `*_env` keys (`secret_env` and `headers` of `[approvals.notify]` and `[leases.notify]`), `ATTENUO_AUDIT_SINK_TOKEN`, the `AWS_*` fallbacks of an S3 sink and the `OTEL_*` variables of `[telemetry]` work as they did; they are applied after the overrides, to the values the overrides produced.
- **Logged by name.** At startup the server logs, at `info`, `config keys overridden from the environment` with the keys and variables (`[server] listen (ATTENUO__SERVER__LISTEN), ...`), never their values.

`attenuo policy lint --config` reads the file only: it runs in the operator's shell, whose environment is not the server's.
