## Findings

### SR-97: a child hop can fill its run's pending approvals (Low, proposed)

- **Component.** `attenuo-audit` `approval.rs` `rules::counts_as_pending` and `below_pending_cap`; `sqlite/approvals.rs` `pending_of_run`; `lease.rs` `MemoryLeaseStore::create_approval`.
- **Observation.** SR-92's cap counts every pending, unexpired approval whose `chain_id` is the run, whichever hop asked and whether that hop's lease is still live. Revoking a lease does not touch its approvals (no store method changes approvals on revocation), and an approval of a revoked hop can never be consumed, so it is dead weight until `expires_at`: `[approvals] ttl_seconds` (default 120, no upper bound) or the hop's lease expiry, whichever is first.
- **Measured.** Scratch test against both stores: hops `l1` (root), `l2`, `l3` (child of `l2`); `l3` creates 32 approvals with distinct call hashes, `l3` is revoked, then `l2` asks for an approval one second later. Both stores answer `TooManyPendingApprovals { chain_id: "l1", max: 32 }`; `l2` gets one only once `l3`'s approvals have expired.
- **Exploit path.** Attacker (a), a narrow child token whose capabilities include one tool its policy gates (for example `confirm_destructive_with_untrusted_args` on a tainted run), sends 32 gated calls with distinct arguments, and repeats every `ttl_seconds`. Every other hop of the run, the parent that delegated to it included, has every gated call answered `-32008` with no `approval_id` (`too many pending approvals for this run`), so no person can approve the parent's real work. The operator's answer to a misbehaving child, revoking it, does not end this for up to `ttl_seconds`; declining the 32 approvals one by one does. Low: availability of approvals within one run, to a hop that is part of that run; nothing is allowed that would not be, and the denials are recorded.
- **Proposed patch** (behaviour changes, so not applied):
  1. Count only approvals whose lease is live. SQLite: `SELECT a.expires_at FROM approvals a JOIN leases l ON l.id = a.lease WHERE a.chain_id = ?1 AND a.state = 'pending' AND l.revoked_at IS NULL` (the lease rows of a revoked subtree are all marked, so the join covers descendants); memory store: the same filter with the `rows` map, taken in the same lock order `create_approval` already uses. A revoked child then frees its places at once. Test: the scratch test above, with the parent's approval created after the revocation.
  2. Optionally, give the calling hop's path a share: count against the cap only the approvals of the calling lease, its ancestors and its descendants, and keep a run-wide ceiling of, say, `4 * 32` so that minting siblings cannot bring back SR-92. A child then cannot fill the places its parent counts, and the notice queue stays bounded per run. A design choice for the lead.

### SR-98: a backlog batch filled the notice queue (Info, fixed)

- **Component.** `attenuo-server` `sink.rs` `Shared::refill` and the delivery loop in `run`; `notify.rs` `OutboxSettle::next_backlog`.
- **Observation.** SR-93's fix reads the outbox backlog in batches of `queue_capacity` each time the queue runs empty. The delivery thread takes the first row of the batch as in flight and leaves `capacity - 1` queued, so the second new notice that arrives while that row is delivered finds a full queue and `QueueHandle::push` drops the oldest queued item, a backlog row, which `OutboxSettle` marks given up without one attempt. That is SR-93's outcome again, one row per new notice, for as long as the backlog lasts: after a restart the receiver is often the slow part, and new approvals keep arriving. The queue also reads as full (`SinkStatus::degraded`, `/readyz` degraded) from the first batch to the last. Info, as SR-93: notices are best effort and the approvals themselves are unaffected.
- **Measured.** Scratch run of the new test on `77cc0a4`: 10 open rows, `queue_capacity = 4`, the first delivery held, two new notices pushed: 11 of the 12 notices delivered, the second backlog row given up unsent.
- **Fix and evidence.** The delivery thread asks `Settle::refill` for at most half the capacity (`refill_room`, at least 1), so a batch leaves half the queue for notices that arrive while it is delivered; the module docs, `docs/design/server.md` and `docs/reference/config.md` say so. With capacity 1 nothing changes. Test `notify::tests::notices_queued_while_a_backlog_batch_drains_drop_none_of_it_sr98`: the same 10 rows and two new notices, every row delivered once, in the order first batch, new notices, rest of the backlog, `dropped_total 0`, and the queue not full or degraded while the batch drains. It fails on `77cc0a4`. `a_notice_stored_while_the_backlog_drains_is_delivered_once_sr93` now expects a first batch of two.

### SR-99: arguments past `MAX_ARG_PROBES` are fingerprinted in full (Info, fixed in the docs)

- **Component.** `attenuo-server` `authz/pipeline.rs` `arg_probes` (142 on `77cc0a4`).
- **Observation.** The doc comment says that once the pairs pass the bound "the remaining arguments are only checked for having a fingerprint". The code calls `fingerprints(value)` on every remaining argument, as before the bound, and only stops keeping the results. So the bound limits the lookups under the store lock and the hits they expand to, which is what SR-91 asked, but not the CPU spent fingerprinting: that stays the cost of the body (each value at most `MAX_FINGERPRINTS_PER_VALUE` fingerprints from its first 1 MiB, the body at most `max_request_body_bytes`), on the blocking pool, outside every lock. The SR-91 test's own comment says so ("nearly all of it fingerprinting the 100,000 values"). Not exploitable beyond pass 9's figure (0.31 s for 3 MB of host tokens per call, not under a lock); the comment overstated how cheap a call past the bound is.
- **Fix.** The comment says what the code does. Test `authz::arg_taint_tests::arguments_past_the_bound_are_named_only_when_they_have_a_fingerprint_sr99` pins it: past the bound an argument with an entity is named and one with no fingerprint is not. It passes on `77cc0a4` as well: the change is the documentation.

### SR-100: IDNA deviation characters count a host that Python's stdlib does not reach (Info, proposed)

- **Component.** `attenuo-core` `limits.rs` `Derive::Host::apply`; for full URLs, and since #201 for bare hosts too.
- **Observation.** The `url` crate maps a host by UTS 46 non-transitional processing, as WHATWG does: `faß.example` is `xn--fa-hia.example` and `βόλος.example` is `xn--nxasmm1c.example`. Python's stdlib encodes a `str` host with its IDNA 2003 codec, which maps the four deviation characters (`ß` to `ss`, `ς` to `σ`, ZWJ and ZWNJ to nothing): `http.client`, `urllib.request` and `socket.getaddrinfo` connect to `fass.example` and `xn--nxasmq6b.example`. `requests`, `httpx`, Node and curl 8.5 with libidn2 agree with the crate (checked: `requests` prepares `http://xn--fa-hia.example/`, `httpx` `xn--fa-hia.example`). ZWJ and ZWNJ outside their joining context are refused by the crate (`CheckJoiners`), so `ß` and `ς` are what remains.
- **Exploit path.** Narrow. With an upstream built on `urllib.request`: the run has reached `https://xn--fa-hia.example/` (the punycode spelling), so host `xn--fa-hia.example` is counted and seen. The injected agent then sends `https://faß.example/?d=<secret>`: counted as `xn--fa-hia.example`, seen, no new host under `distinct` or `ask_on_a_new_site`; the tool connects to `fass.example`, which the attacker registered. Both names are registrable under TLDs that allow `ß` (`.de` since 2010). The other direction (Unicode spelling first) only over-counts.
- **Proposed patch.** As SR-56 did for backslashes, refuse to derive a host from a value whose host part holds `ß` (U+00DF) or `ς` (U+03C2), or ZWJ or ZWNJ (U+200D, U+200C); a host limit then answers `limit_arg_invalid` and run usage counts the value as itself. A refusal of inputs accepted today, so a behaviour change for the lead. Test: `https://faß.example/`, `faß.example`, `https://βόλος.example/` have no derived host; `https://xn--fa-hia.example/` keeps its host.

### SR-101: a bare value is counted as the host an `http://`-adding client reaches (Info, proposed)

- **Component.** `attenuo-core` `limits.rs` `parse_url_or_bare_host`, from `fix/derive-host-bare` (#201).
- **Observation.** Before the branch, a value with no scheme had no host, so a host limit refused it (`limit_arg_invalid`, fail closed). The branch counts it as `http://` plus the value. That is the host reached by an upstream that adds a scheme to a value without one, as curl does, as many fetch tools do (pass 5, SR-63) and as the AgentDojo tools need. An upstream that instead resolves the value as a relative reference against a base, a crawler's or a browser tool's current page (`urljoin`, `new URL(value, page)`, Scrapy's `response.follow`), reaches the base's host: `good.example/?d=x` on `evil.example`'s page goes to `evil.example/good.example/?d=x` and counts `good.example`. The branch already refuses `/…` and `//…`, the two relative forms that could name another host, so the host reached is always the base, which the run reached and counted before. What the value can do is spend another host's count instead of the base's: a `calls_per` limit on the base host is passed by choosing a different first label each time (each new label is a new host under `distinct`, which still bounds it).
- **Proposed patch.** No code change: one sentence in `Derive::Host`'s doc comment and in `docs/design/run-limits.md`: "A bare value counts the host a client reaches when it adds `http://` to it. For a tool that resolves its argument against a current page, give the argument as a full URL in the catalog's examples, or pair `calls_per` with `distinct`, since a bare value there reaches the page's host whatever it names."

## The `fix/derive-host-bare` branch (#201): safe to merge as is

Read at `origin/fix/derive-host-bare-main` (`2e8d59d`). Verdict: safe to merge as it stands, from a security point of view. It adds no way to make a host limit count a host other than the one a client reaches when it is given the value, beyond SR-100, which main already has for full URLs, and SR-101, a documented assumption. It has since merged as #201, and SR-101's sentence can follow it.

The ways a parser could split the host differently all fall on the safe side:

- **The SR-56 guard runs first.** `apply` refuses backslashes, whitespace and control characters before `parse_url_or_bare_host` is called, so WHATWG's stripping of leading C0 and space, and of tabs and newlines, never applies, and the scheme `Url::parse` reports starts at byte 0 of the value. The `raw.get(scheme.len() + 1..)` slice is therefore the text after the scheme's `:` (the scheme is ASCII and lowercasing keeps its length), and it returns `None` on a bad boundary instead of panicking.
- **User info.** `good.example@evil.example`, `good.example;@evil.example`, `a@b@evil.example`, `a.example%2f@evil.example` and the `%23` and `%3f` forms count `evil.example`, the host Node, curl, `urllib.parse` and `httpx` all reach. `a.example?@evil.example`, `a.example#@evil.example`, `a.example:80/@evil.example` and `a.example:80#@evil.example` count `a.example`, again the host every client reaches. Where the "scheme" is followed by anything other than digits (`a.example:80@evil.example`, `good.example:pw@evil.example`, `good.example:80:@evil.example`) the branch refuses the value while every client reaches `evil.example`: a refusal, never a wrong count. Only a password-free bare user info is read; with a password it is refused.
- **Ports.** The digits must run to the first `/`, `?` or `#` and be ASCII (`a.example:８０` is refused); leading zeros are a port (`a.example:00000000080` is `a.example`, as everywhere); an out-of-range port is refused.
- **Opaque look-alikes.** `tel:911`, `javascript:1` and `c:8080` count hosts `tel`, `javascript` and `c`, which is also what every client given `http://` plus the value reaches. It spends a count; it never reuses one. `mailto:`, `data:`, `javascript:alert(1)` and `a.example:/x` stay refused, and a special scheme always wins (`http:8080` is WHATWG's `0.0.31.144`, as on main).
- **IP literals.** `0x7f.1`, `127.1`, `2130706433` and `0177.0.0.1` count `127.0.0.1`. `urllib` and `httpx` pass the text through to `getaddrinfo`, which on glibc reads all four as 127.0.0.1, so the host reached is the same; Node and curl canonicalise as the crate does. `[::1]:8080/x` and `[::ffff:127.0.0.1]` count the bracketed address; `::1` and `[v1.x]` are refused.
- **Percent escapes and Unicode.** `%65vil.example` and `evil%2eexample` count `evil.example`; Node and curl reach `evil.example`, and the RFC 3986 parsers pass the escapes to DNS, where the name does not resolve. That is an over-count or a failed fetch, never a seen host reused. To reuse a seen host `good.example`, the escaped spelling would have to resolve under `good.example`'s own zone. `evil。example`, `ｅvil.example` and a trailing U+200B count `evil.example`, as every client that accepts them reaches. `ß` and `ς` are SR-100.
- **Paths.** `/a.example` and `//a.example/x` are refused, so the two relative forms that could name another host under a base-resolving tool are not read as bare hosts (SR-101 for the rest). `good.example/..//evil.example` counts `good.example` and every parser agrees. Dot segments cannot reach the authority.
- **Trailing dots.** `evil.example.:80` counts `evil.example`, and the clients keep the dot, which is the same DNS name.
- **What a host now counts against.** In run usage a bare value is now its host rather than `{"raw": value}` (SR-63), so `evil.example/?d=a` and `evil.example/?d=b` are one destination, as their full URLs are. That is the intended reading and matches the full-URL behaviour.

## Checked and found sound

- **SR-91 bounds (#193).** `arg_probes` counts `(argument, fingerprint)` pairs before deduplication and, past `MAX_ARG_PROBES` (8,000), clears the probes and owners, so `find_spans` is never called. Below the bound the owners expansion is at most `MAX_SEQS_PER_PROBE` (8) hits per probe times its owners, so at most 64,000 entries per call before the record keeps 64. The fail-closed path names every fingerprinted argument as `unreadable` and sets the diagnostic, and `ArgLabels` gives Cedar every name. Marking more arguments untrusted can only make a policy stricter, so this is a safe default for a policy that tests `args_contain_untrusted` or `untrusted_args.contains`. Both stores return the lowest `seq`s (`ORDER BY seq LIMIT 8`, and `take(8)` over an ordered set); the record and Cedar use only which arguments matched and the first `seq`s, so the truncation drops nothing a decision reads. `fingerprints` is per value, so a fingerprint repeated within one argument only repeats an owner, and the `BTreeSet` deduplicates it.
- **SR-92 cap (#195).** SQLite counts the run's pending rows and inserts inside one `IMMEDIATE` transaction under the write gate, and the memory store does both under the approvals lock, so two concurrent gated calls cannot both take the 32nd place. The reuse check runs first, so a repeated call is neither refused nor counted twice. Expiry is compared in Rust, the same rule as `reusable`. `pending_of_run` reads the run's rows through the `(chain_id, call_hash, state)` index prefix, so its cost grows with the run's stored approvals (pruned with the run), not with the table. The pipeline answers the refusal as a failed store does, with no `approval_id`, no `approval_request` record and no notice; only the diagnostic differs, and it names no other run. The 429 mapping carries only the cap (the `chain_id` stays in the log), and no route creates approvals, so it is reached by no request today.
- **SR-93 backlog (#195).** `through` is read before the queue starts and before any new notice is stored. SQLite gives a new row an id above the current maximum, and the row at `through` stays open until the backlog has read it, so it is never pruned while the backlog still needs it. A notice stored after start therefore always has an id above `through` and is never read twice. A failed outbox read ends the backlog and leaves the rows open for the next restart. An open row's notice found again by the watcher at start inserts nothing (`Ok(None)`) and is not queued in memory as well.
- **The notifier's clock (#196).** `main.rs` calls `serve`, `serve` calls `build`, and `build` and `AppState::from_config` pass `system_clock()`. `from_config_with_clock` is `pub(crate)`, and the only public ways to choose a clock are `build_with_clock` and `ApprovalNotifier::start`/`with_deliver`, which an embedder calls. No config key, header, route or environment variable reaches a clock, and `ManualClock::advance` is called only from tests. `clock_advanced` only wakes the watcher, which then reads the same clock again. `AppState::clock` is a public field, as it was before, so an embedder that replaces it after construction leaves the notifier on the old clock. That is embedder misuse with no request path. `Instant` subtraction in `next_due` saturates. `tokio`'s `test-util` is enabled only in `[dev-dependencies]`, and with resolver 2 it does not reach the shipped binaries.
- **Doc comments (#197, #199).** Each security claim in the added comments was checked against the code. "A bound token is refused until `with_dpop`" holds in both `authenticate` and `authenticate_request`. "Left out of `Debug`" holds for the S3 secret and session token (`finish_non_exhaustive`). Redirects are not followed by the webhook and S3 deliverers. "`None` answers every admin call 403" holds (`admin_disabled`). "Anything else is a 400 `invalid_request`" holds for the decision body. `ApiError::internal` sends `INTERNAL_DETAIL`. The dev root mint says the subject is "never verified". #199 changes visibility only.
