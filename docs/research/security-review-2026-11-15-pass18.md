## Findings

### SR-132: which code a conflict with the request's own limit gets depends on the entry (Info, fixed)

- **Confirmed by reading and reproduced.** `attenuate_root` runs `attenuate` first (its doc says so), and `attenuate_one` clamps each requested capability to one parent: the first capability that covers it with its limits, else the first that covers its calls. If clamping to that parent cannot give a capability it covers, the answer is `NotCovered`, which the server maps to `scope_exceeds_grant` (hop 0 against the root grant, and `POST /admin/root-token`) or `scope_exceeds_id_jag` (against the ceiling). Only when that step passes does `under_all` look at every limited capability over the request and return `LimitConflict` (`limit_conflict_at_root`). A request that carries its own limit of one kind on another argument than a limited capability over it therefore gets one code or the other according to what else the entry holds. The configuration reference (under `[[root_grants]]`) said such a request "is refused with `invalid_scope` / `limit_conflict_at_root`", and the HTTP reference listed "its own and theirs" under `limit_conflict_at_root` only.
- **Reproduced** through the whole server (throwaway test in `tests/oidc.rs`, the harness of `a_scopes_limit_over_several_grant_capabilities_is_one_budget_sr131`), an ID-JAG with no ceiling claims, the request in `authorization_details`:
  - root grant `banking:send_money` with `sum` over `fee` 5; request `banking:send_money` with its own `sum` over `amount` 10: `scope_exceeds_grant`, "is not covered by the parent capability set";
  - the same with an unlimited `banking:*` beside it: `limit_conflict_at_root`, "is under several limited capabilities of the [[root_grants]] entry", though one limited capability is involved;
  - root grant `send_money` with `sum` over `fee` 5 and `send_money` with `calls` 3; the request as above: `scope_exceeds_grant`; the request with `calls` 2 added: `limit_conflict_at_root`. Which of the two parents attenuation tries first follows the canonical order of the entry's capabilities (`calls` absent sorts first), not the order in the file or in the request;
  - under the ceiling, root grant `banking:*`, `scopes` `payments` = `send_money` with `sum` over `fee` 5, the request as above: `scope_exceeds_id_jag`.
- **Not affected.** Every one of these requests is refused, and the detail names the capability as requested, so nothing is granted and no limit figure is shown. Limits of the entry alone (two limited capabilities with one kind on different arguments, and a request without a limit of that kind) always give `limit_conflict_at_root`: the clamp to the first parent copies its limit and passes, and `under_all` then refuses. The answer does not depend on the order of anything the agent sends: the request, the grant and the claims are canonical sets.
- **Attacker.** None as such. An agent or a client reading the `code` to decide what to do next is told "not covered" for a capability that is covered, or "several" for one.
- **Severity.** Info: a refusal with a less precise code and wording than the documentation promised.
- **Options.** (1) In `attenuate_root`, when `attenuate` refuses a requested capability that a limited capability of `self` covers in its calls, return `LimitConflict` for it, so the code is `limit_conflict_at_root` whenever such a capability exists; and word the detail "under one or more limited capabilities". Changes the code (and the text) of answers given today, for requests that are refused either way. (2) Word the detail only. (3) Document the rule as it is. Under a covering limited parent, `attenuate` refuses only for such a conflict (clamping lowers every figure of the same kind and argument), so (1) does not hide a real widening. **Recommendation:** (3) now and (2) with the next change to the error mapping, since "several" is wrong for one. (1) is a judgement call: an exchange answers the same request `scope_exceeds_parent`, and hop 0 answering as an exchange does has value too. This branch does (3): the configuration reference, under `[[root_grants]]`, says which code each case gets. The HTTP reference's error table is generated from `attenuo_core::error_codes` (a guard test compares them), so its `limit_conflict_at_root` row, which says "or its own and theirs" and is not wrong but incomplete, was left as it was by the review itself.
- **Decided in review, on this branch.** Option 2 is done as well: the `limit_conflict_at_root` detail, the core error text, the fallback text at the ceiling and the reference rows say "one or more limited capabilities". The `code` values and which requests are refused are unchanged. Option 1 is not taken: hop 0 keeps answering a request its first parent cannot cover as an exchange answers it (`scope_exceeds_grant`, `scope_exceeds_id_jag`), and the configuration reference now says so.
- **Test.** None committed: the documentation change has none to guard, and a test pinning today's codes would pin what option 1 changes. The reproductions above were a throwaway test.

## Tried and held

- **Excess over a configured limit, by shape** (question 1), through the whole server with the `tests/oidc.rs` harness, each request in the token request's `authorization_details`:
  - Three claims at once: root grant `banking:*`, `resources` mapping a URI to `banking`, `scopes` `payments` = `send_money` with `sum` 100, and an ID-JAG with `resource`, `scope` and `authorization_details` naming `send_money` to `alice` and to `bob` without limits. A request for both: `limit_split_at_root`, both named as requested. Alice alone: `200`, `sum` 100.
  - A limit only in `authorization_details` over limited grant capabilities: root grant `send_money` to `alice` with `sum` 50 and to `bob` with `sum` 50, the claim naming `send_money` with `sum` 60. Both: `limit_split_at_root` (SR-131's check covers `authorization_details` too, since `apply` records any claim whose capabilities hold limits). Alice alone: `200`, 50.
  - Wildcard servers: root grant `*:*`, `scopes` = `*:*` with `calls` 5. `github:read_file` and `slack:post`: `limit_split_at_root`; `*:*`: `200` with `calls` 5. Under a root grant `banking:*` the same scope names nothing (`meet` keeps a capability only when one side covers the other), so `id_jag_ceiling_empty`.
  - A claim capability over a grant capability's calls with another kind of limit: root grant `send_money` with `calls` 10, `scopes` = `send_money` with `sum` 100. Alice: `200` with both `calls` 10 and `sum` 100; alice and bob: `limit_split_at_root` against the grant. The same kind on another argument (grant `sum` over `amount`, scope `sum` over `fee`), and a scope `sum` 100 over grant capabilities per recipient with `calls` 3, name nothing: `id_jag_ceiling_empty`. Both fail closed; the second is the documented incompleteness of `meet`, not an excess.
  - `calls` implying `calls_per` and `distinct`: root grant `send_money` with `calls_per` on `to` 1, scope `calls` 100: the token carries `calls` 100 and `calls_per` 1, because 100 does not imply 1; a request for `calls` 1 gets `calls` 1 alone, which bounds each recipient to one call. A scope `distinct` on `url#host` 2 under `web:*`, with `authorization_details` naming two URL prefixes: two fetches are `limit_split_at_root`; a request with its own `distinct` on `url` (no derivation) is refused (SR-132's case); one with `calls` 2 gets `calls` 2 alone, which bounds the hosts to two.
  - Equal after clamping: under a grant `send_money` with `sum` 100, `send_money` asked once without limits and once with `sum` 100 is one capability of the token with `sum` 100. With `calls` 1000000 added to the second, they differ, and the request is `limit_split_at_root`. Since the result is a set and two requested capabilities can only become equal when they have the same calls, a merge only drops a copy; it cannot hide a split.
  - `resources` maps to servers only and cannot carry a limit; `has_limits` keeps its step and its claim out of the extra checks, as it should.
- **A budget oracle over generated inputs** (question 1), a throwaway integration test with `--features fuzzing` driving `fuzzing::narrow`. A universe of four concrete calls (`s:a` and `s:b`, `to` `x` or `y`); root grants, `scopes` entries and `authorization_details` claims of one to three capabilities over server `s` or `*`, tool `a`, `b` or `*`, `to` unconstrained, `equals` or `one_of`, half of them with `calls`, `calls_per` on `to` or `distinct` on `to`; any subset of the three claims; requests of one to three capabilities, with or without limits of their own. For every token issued and every limited capability of the grant or of a claim used, the test computed by exhaustive search the most calls (per `to` value for `calls_per`, values for `distinct`) the token allows within that capability's calls, charging every limited token capability that permits a call, as `charges_for` does. Three seeds of 300,000 inputs (two with `*` servers in the request and the claim) issued 27,454, 15,638 and 15,306 tokens. Excess over a figure: 4,000, 2,455 and 2,385 times, each of them gone when the token is restricted to the capabilities the limited one covers, which is the gap #341 documents (a token capability that only overlaps a limited capability, or is wider than it, is not bounded by it). No other excess. `sum` was not in the universe; it is combined as `calls` and `distinct` are, kind by kind.
- **The "not reached, fail closed" arm** of `narrow_with` (question 2). Each set in `also_checked()` is an earlier step of the ceiling or what a claim named, and `meet(a, b)` is within `a` and within `b`, so the final ceiling is within each; the narrowed request is within the final ceiling, and each later `attenuate_root` only lowers figures, which keeps it within. The only way left to `NotCovered` would be a coverage relation that is not transitive (`TooLarge` and `Empty` cannot occur: the narrowed set has no more capabilities or constraints than the request). The implication rules were read for that (path prefixes with and without a trailing `/`, `prefix` over `path_prefix`, one-value ranges against `equals` and `one_of`, `5` and `5.0`, empty `one_of` and inverted ranges as vacuous) and found transitive. A second generated test used those constraints, server `s` or `*`, tools `a`, `*` and `a*`, and limits of every kind on two arguments (so that conflicts occur): four runs of 400,000 inputs (about 21,400 tokens each; in the three with conflicting limits, 635 to 671 `limit_conflict_at_root`) never gave the arm's detail. Were it reached, the request would be refused, which is safe; its code, `scope_exceeds_id_jag`, would be right in substance and its detail is fixed text.
- **What a refusal names** (question 3). At the grant, `LimitSplit` and `LimitConflict` carry the requested capability as sent (`req.display()`). At the ceiling and at each later set, the refused capability carries limits copied from the grant or the ceiling, and `narrow_with` maps it back to the request by recomputing each requested capability through the same sets with `attenuate_root_each`, which gives for each capability what `attenuate_root` of the set gives (each capability is handled on its own; only the split check looks at several). A capability not found falls back to `SPLIT_OF_THE_CLAIMS` or `CONFLICT_OF_THE_CLAIMS`, which hold no figure and name no capability. The generated test of the previous item also checked every refusal's detail: every capability between backquotes was one of the requested capabilities as sent, over the 378,000 refusals of one run, and the fallbacks were never used in any of the four. The `limit_conflict_at_root` detail says the grant (or the claims) holds a limited capability over the request with a limit of the same kind on another argument; that is structure, not a figure, and the agent sees the limits of every capability it is granted in its own token.
- **Cost** (question 4). Debug build, the throwaway test, timing `fuzzing::narrow` (which includes `apply`): a root grant of 1,024 capabilities each with `calls` 10, a `resources` entry, a `scopes` token mapped to 1,024 capabilities with `calls` 1000, and an ID-JAG with all three claims, so that all six checks run (grant, final ceiling, two kept steps, two claims). The grant check alone, without a ceiling, took 0.27 s for 1,024 requested capabilities; `apply` alone 0.34 s; the whole narrowing 1.39 s for 1,024 requested capabilities that pass, and 2.69 s for a request refused at the last check (a limited `s:*` in `authorization_details`), whose refusal recomputes every requested capability through five sets to name two. The same inputs on the tree before #341 (`2f903d13`, with #336's kept steps) took 0.32 s, 0.38 s, 1.41 s and 2.60 s, so #341 and #342 did not change the worst case measurably: the extra checks cost about what the `meet` and the earlier checks already did. The worst case needs the operator to configure a 1,024-capability grant and `scopes` entry with per-capability limits; with an unlimited one-capability grant and the limits chosen by the agent in `authorization_details` (256 capabilities), 1,024 requested capabilities took 80 ms to refuse and 256 took 35 ms to pass. All of it runs inside one `AppState::blocking` call (`handle` hands `narrow` to the pool), under `[limits] max_in_flight`. Not measured in a release build, which this pass did not build.
- **Order** (question 5). The request, the root grant and each claim's capabilities are `BTreeSet`s, so the order of the request's JSON, the configuration file or a claim's entries cannot change an answer. `clamp_to_all` sets `calls` from every parent before the per-argument kinds, so the copy of a `calls_per` or `distinct` does not depend on the order of the parents, and two parents with one kind on two arguments conflict in either order; the core test `clamp_to_all_is_clamp_to_for_one_and_order_free_sr128` covers this. What does follow the canonical order is which parent `attenuate` tries first, and with it the code of SR-132's case, and which pair a `limit_split_at_root` names; neither is under the agent's control.
- **The exchange** (question 6). `routes/token.rs` is not in the diff; the exchange calls `attenuate_with` with the lease store's remainders (`clamp_to_remaining`), which #341 did not touch (`attenuate_indexed` and `attenuate_one` are unchanged; the new code is in `attenuate_root`, `attenuate_root_each`, `under_all` and `limited_over`, all hop 0). The callers of `attenuate_root` are `narrow_with` and `POST /admin/root-token` only.
- **The `fuzzing` feature** (#338, #339). It exposes `attenuo_server::fuzzing` (wrappers over `IdJagCeiling` and `narrow_with`, holding no logic and no state, hidden from the docs) and the existing `attenuo_proxy::fuzzing`. Only `fuzz/Cargo.toml` enables it, and `fuzz/` is excluded from the workspace; `cargo tree -e features -p attenuo-server -p attenuo-cli` shows no `fuzzing`, and the Docker image builds `-p attenuo-server -p attenuo-cli` without features. CI enables it only in the fuzz build and for `cargo deny check --all-features`; the local gate's `cargo clippy --all-features` builds it too. `attenuo-cli` takes `attenuo-proxy` with `testing` as a dev-dependency only, so that is not in the binary either. Nothing is reachable from a normal build.
- **Other things in the diffs** (question 7). `Applied::limited_claims` keeps the whole set a claim named, including capabilities of `scopes` tokens unrelated to the request; checking against them can only refuse more (a split under a limited capability the ceiling already reaches), never grant more. An `authorization_details` claim over its bounds names nothing, so its empty set is never recorded (`has_limits` is false) and the ceiling is empty. The error path of the later checks builds `shown` in the same order the forward pass used (grant, final ceiling, then `also[..k]`), and skips a capability refused earlier without shifting the others.
