## Findings

### SR-121: a limit at hop 0 is per requested capability, not per run (Medium, fixed)

- **Confirmed by reading and reproduced.** The run limits design says a limit on hop 0 is the run's budget, because every call is charged against every limited capability, in every hop, that matches it (`charges_for`). At an exchange that holds: a child's capabilities are clamped to the parent's limits, and each call is also charged against the parent hop's capability. At hop 0 there is no parent hop. The root grant, and since #326 the ceiling, is not a hop: `CapabilitySet::attenuate` copies the covering capability's limits into each requested capability (`Limits::clamp_to`), and the root token then holds several capabilities, each with the full figure, each charged only by the calls it matches. With the ceiling, the claim's limit takes the same path: `meet` keeps the claim's capability, and the request is attenuated against it.
- **Attacker.** The agent at hop 0 (A2), which chooses its request. With the ceiling, the figure was set by the IdP (an `authorization_details` budget, the "RAR amount mapping at hop 0" of the run limits design's open question 6); without it, by the operator in `[[root_grants]]`.
- **Reproduced.** Unit level, with the real `IdJagCeiling::apply` and `attenuate`: root grant `banking:*`, an ID-JAG whose `authorization_details` names `banking:send_money` with `sum: {arg: amount, max: 100}`. The ceiling is that one capability. A request for `send_money` three times, with `to` pinned to `alice`, `bob` and `carol`, passes both attenuations and gives a root token of three capabilities, each with `sum` 100, and a call `{to: alice, amount: 100}` matches one of them. The run can send 300. With the ceiling off and the limit in the root grant, `granted.attenuate` gives the same three capabilities. The same path splits `calls`, `calls_per` and `distinct`: two capabilities for a fetch tool, `url` under two prefixes, would each get `distinct: {arg: url, derive: host, max: 1}`, so the one-host rule allows two hosts (by reading the same code, not run). The agent needs an argument whose values it can tell apart with constraints; the recipient, the URL or an amount range will do.
- **Severity.** Medium: a run budget, a P2 control, is spent several times over by the party it limits, by a request shape alone, with nothing in the record to show it beyond the root hop's capabilities. Not higher: only hop 0, only limits set above the request (by the root grant or a claim), and run usage (`context.usage`, per tool, not per capability) still counts every call of a destructive tool for a policy that reads it.
- **Options.** (1) Refuse at hop 0, with a new code, a request in which two capabilities take their limits from the same limited capability of the grant or the ceiling. Simple and sound; changes the answer to requests that work today. (2) Keep the grant's (or ceiling's) limited capabilities as a budget of the root lease, charged like a hop's: sound without refusing anything, but a lease store and charge change, and the budget is then not in the token. (3) Document only. **Recommendation:** (1) now, since it is small and fails closed, then (2) if refusing turns out to cost real requests. This branch does (3): the configuration reference says so under `[[root_grants]]` and `[idps.id_jag_ceiling]`, and the board has a row.
- **Test.** None committed, since nothing is fixed; the reproduction above was a throwaway unit test against `idp::ceiling`.
- **Fixed after the pass** (#328), with option 1. `CapabilitySet::attenuate_root` (core) is `attenuate` plus one rule: two capabilities of the result may not take their limits from the same capability of the grant whose limits are not empty. The parent of each requested capability is the one the shared attenuation step clamps it to, which reports its index, so the check cannot pick another covering capability than `attenuate` does; requested capabilities that are equal after clamping are one capability and pass. Hop-0 intake uses it against the root grant and again against the ceiling, and `POST /admin/root-token` against the root grant; the exchange is unchanged. A refusal is `400 invalid_scope` / `limit_split_at_root`, naming the two capabilities as requested (at the ceiling, as the request had them, before the grant's limits were copied in), never the limits. A split is refused also when each part asks for a lower figure of its own (two halves of 50 under 100 would be sound for `sum` and `calls`, but the smaller rule is kept). This changes the answer to requests that worked before, among them two tools under a limited `github:*`; such a request is rewritten as one capability with a `one_of` or wider constraint or tool pattern. Reproduced before the fix through the whole server with `POST /admin/root-token` and a grant: three recipients under `sum` 100 sent 300, and two URL prefixes under `distinct: {arg: url, derive: host, max: 1}` reached two hosts. Tests: `a_limited_grant_capability_is_not_split_at_the_root_sr121` and `a_split_is_judged_by_the_parent_attenuate_picks_sr121` (core), `attenuate_root_is_attenuate_without_splits` (property), `a_root_grant_limit_is_not_split_across_capabilities_sr121`, `a_root_grant_host_limit_is_not_split_sr121` and `an_exchange_may_split_a_limited_parent_capability_sr121` (`tests/run_limits.rs`), `an_id_jag_budget_is_not_split_across_capabilities_sr121` and `a_root_grant_budget_is_not_split_at_intake_sr121` (`tests/oidc.rs`); the hop-0 server tests fail before the fix, the exchange test passes before and after.

### SR-122: an ID token gets past the ceiling (Low, fixed)

- **Confirmed by reading.** `[idps.id_jag_ceiling]` applies only when the credential is an ID-JAG (`(CredentialKind::IdJag, Some(ceiling))` in `intake::handle`), as the reference page says ("ID tokens are never affected"). The same `[[idps]]` entry accepts this issuer's ID tokens from an agent whose `client_ids` entry, or agent id, is the ID token's `aud`, and the same `[[root_grants]]` entry applies to them. In the draft's flow the client gets the ID-JAG by exchanging the user's ID token, whose `aud` is the client, at the IdP, so the agent the ceiling is meant to bound normally holds that ID token too.
- **Attacker.** The agent at hop 0 (A2), holding the user's ID token and an ID-JAG whose claims allow less than the root grant.
- **Reproduced.** `id_jag_ceiling_narrows_by_each_claim` in `tests/oidc.rs` (#326) already shows it: under the ceiling, an ID-JAG whose `resource` names only github is refused `slack:post_message` (`scope_exceeds_id_jag`), and the same user's ID token presented by the same agent is given `slack:post_message`.
- **Severity.** Low: the root token stays within the root grant, which is what the operator allowed before the option existed, and it needs this issuer's ID tokens to be accepted for that agent. Higher than Info because it undoes the option for exactly the party it is meant to bound, and nothing at start-up says so.
- **Options.** (1) With the ceiling on, refuse this issuer's ID tokens at intake (a new code). (2) A per-entry key naming which credentials the entry accepts, `credentials = ["id-jag"]`, default both. (3) Document. **Recommendation:** (2), with a start-up warning when the ceiling is on and ID tokens are accepted for an agent that has a root grant at that issuer; (1) is simpler but takes ID tokens away from agents the operator may want them for. This branch does (3): the reference page, the guide and `IdpConfig`'s doc comment say how to keep an agent from presenting ID tokens.
- **Fixed after the pass** (#330), with option 2, in the sense that the operator can now close it: the default is unchanged and still accepts both kinds, so an entry with the ceiling and no `credentials` key answers exactly as before and is still open to this. `[[idps]] credentials` lists what the entry accepts at hop 0, `"id_token"`, `"id-jag"` or both (the names of the audit record's `credential` member); the default is both. A credential of a kind not listed is refused with `400 invalid_grant` / `credential_type_not_accepted`, whose `detail` is the code alone, as for every other `invalid_grant` of the verifier (SR-17). It is refused in `IdpRegistry::verify_for` right after the issuer lookup, the step at which an unknown issuer is refused with `untrusted_issuer`: before the `alg` check, the key fetch and the signature, and so long before the credential is used once at issuance. For both a known issuer that does not accept the kind and an unknown issuer, nothing has been fetched or checked, so the refusal costs the same; the two codes differ, but `untrusted_issuer` against any later code already tells whether an issuer is listed, so this adds no issuer oracle. It does tell an authenticated agent, without a valid credential, which kinds a listed issuer accepts, which is configuration and not a secret. Rejected: checking after the signature, which would hide that from an agent with no valid credential at the cost of a key fetch for a credential that will be refused. An empty list or another name refuses to start. An entry with `[idps.id_jag_ceiling]` that accepts ID tokens starts, as it did before, with a warning that the ceiling does not apply to them and naming the key: a refusal would stop configurations that start today. The warning is for the entry, not for each agent that has a root grant at that issuer as the recommendation said, since the IdP registry is built without the root grants; an entry with a ceiling and no root grant warns needlessly. Approval ID tokens (`[approvals]`, ADR-0009) are verified by the same code and are not affected: they are not hop-0 credentials. Tests: `by_default_an_entry_accepts_both_credentials_sr122` (the reproduction above, unchanged by default), `an_id_jag_only_entry_refuses_id_tokens_sr122` (the same ID token refused, no key fetch and no replay marker, an unknown issuer still `untrusted_issuer`, ID-JAGs by both grant types accepted under the ceiling), `an_id_token_only_entry_refuses_id_jags_sr122` (an ID-JAG refused by both grant types, its `jti` not used up), `an_id_jag_only_entry_still_takes_approval_id_tokens_sr122` (`tests/approvals.rs`), `credentials_are_checked_at_start_sr122` (`idp/mod.rs`: the default, the names, an empty list, the warning's text and when it is given) and `a_ceiling_that_id_tokens_get_past_is_warned_about_at_start_sr122` (`tests/logging.rs`, the warning as logged at start). With the check in `verify_for` disabled, the two refusal tests fail (the credential is accepted) and the approval test passes; with the `Purpose` test removed, so the check also runs for approvals, the approval test fails.

### SR-123: the attenuation against the ceiling was unbounded (Low, fixed)

- **Confirmed by reading.** `intake::handle` attenuates the request against the root grant and then against the ceiling inline, on the request's async task, before anything reaches the blocking pool. `attenuate` looks for a covering capability for each requested one, so its cost is the product of the two sizes, and `ArgConstraint::implies` between two `one_of` lists is the product of their lengths. Before #326 the second side at intake was the root grant, which the operator writes. With the ceiling it is the claim's size: `meet` keeps up to one capability per capability the claim names, and nothing bounded how many it names. A CPU-bound handler does not yield, so `[limits] request_timeout_seconds` cannot stop it, and a refused request does not use the ID-JAG up, so one ID-JAG can be sent again and again.
- **Attacker.** The agent at hop 0, when the IdP signs the `authorization_details` the client asked for (the draft lets the client ask for them in its token exchange at the IdP), and its own request. The body limit (2 MiB) bounds both together.
- **Reproduced.** Debug build, unit level, grant of 20 `server:*` capabilities, a claim of `n` capabilities and a request of the same `n`: `apply` took 13 ms, 147 ms and 576 ms for `n` = 1,000, 10,000 and 50,000 (claim JSON 30 KB, 314 KB and 1.6 MB), and the request's attenuation against the result 54 ms, 5.4 s and 142 s. Two `one_of` lists of 5,000 values took 0.56 s to compare (2,000: 83 ms).
- **Severity.** Low: it needs an IdP that signs large client-chosen claims, and denial of service is outside the threat model's security properties; but it stalls a runtime worker per request with one reusable credential, as SR-57 stalled the store.
- **Fix.** `MAX_CLAIM_CAPABILITIES` = 256 in `idp/ceiling.rs`: an `authorization_details` claim whose `attenuo_capabilities` entries hold more capability objects names nothing (counted before they are parsed), so the request is refused with `id_jag_ceiling_empty`, and a warning is logged. The ceiling is then at most the grant plus 256 capabilities. The draft sets no size. 256 is the figure SR-57 chose for counted values, and a choice the maintainer may change: it is one constant.
- **What remains, proposed.** A request is still unbounded (a 2 MiB body holds about 50,000 capabilities), and so are `one_of` lists in a request, a claim and a root grant; at an exchange (on the blocking pool) the parent's size is what the previous hop asked for, so an agent can make a large root token and then a slow exchange from it without any IdP. Options: a bound on capabilities per request and per token, and on `one_of` lengths, with a new code (changes the answer to requests that work today); or running hop 0's attenuation on the blocking pool, as the exchange does (moves the cost, does not bound it). **Recommendation:** both bounds, at a figure well above any real request (1,024 capabilities, 1,024 values).
- **Test.** `a_claim_naming_too_many_capabilities_names_nothing_sr123` (`idp/ceiling.rs`): 256 capabilities over two entries (with an entry of another type between them) are all named, 257 name nothing. Failed before the fix (257 were named).
- **Bounds after the pass** (#328), as recommended. `MAX_CAPABILITIES` and `MAX_ONE_OF_VALUES` (1,024 each, core): `CapabilitySet::validate_size` is checked by `attenuate` (and so `attenuate_with` and `attenuate_root`) before anything is compared, and by `DelegationChain::root` and `extend`, so an exchange, hop-0 intake and `POST /admin/root-token` (with or without a root grant) refuse a larger request with `400 invalid_scope` / `too_many_capabilities` or `one_of_too_long`. A `[[root_grants]]` entry or a `scopes` entry over either bound refuses to start, and an `authorization_details` capability with a longer `one_of` names nothing. No bound existed before except the body (2 MiB at `POST /token`), which held about 50,000 capabilities or 500,000 short values. Measured in a release build (the `bounds` group of `attenuo-core`'s `attenuation` bench, worst cases where every comparison runs to the end): one implication between two `one_of` lists of 1,024 values, 23 ms; 1,024 requested capabilities against 1,024, each covered only by the last, 6 ms; a request of one capability with a 1,024-value `one_of` against a parent of one such capability, 50 ms, and against 400 (about what a 2 MiB body holds, so a root token can carry them), 17.7 s. The bound per list therefore does not bound the cost: it is the product of the values of both sides, and a request of many lists multiplies it again. What remains open: a bound on the total values of a request or token (at 1,024 in total the product is about 50 ms), or an implication between lists that does not cost the product of their lengths, and running hop 0's attenuation on the blocking pool. Tests: `requests_are_bounded_in_size_sr123` (core, `tests/run_limits.rs`), `an_intake_request_is_bounded_in_size_sr123` (`tests/oidc.rs`), `a_root_grant_over_the_bounds_does_not_start_sr123`, `a_claim_with_a_long_one_of_names_nothing_sr123` and `config_is_checked` (`idp/ceiling.rs`).
- **Fixed after the pass** (#329), by making each comparison cheap and bounding the number of comparisons, in that order. Profiled first: the 17.7 s was `ArgConstraint::implies` between two lists, every child value against every parent value through `jcs::value_eq` (which writes each number as a string), for each of the 400 parent capabilities, and up to three times per pair, since attenuation tried `covers`, then `covers_calls`, then `covers` again after clamping.
  - *Implication.* `jcs::value_key` writes a value's canonical bytes (what `jcs::to_vec` writes, checked on generated values), and two values are `value_eq` exactly when their keys are equal: numbers are written as `value_eq` compares them (`1`, `1.0` and `1e0` alike, `-0.0` as `0`, an integer above 2^53 with all its digits, so `2^53 + 1` is not the float `2^53`), strings byte for byte with no normalisation (`é` in NFC and NFD stay apart), arrays in order, objects by sorted member names, and each kind starts with a different byte. So no confirming `value_eq` is needed. For one attenuation or coverage check, each constraint is wrapped once (`capability/prepared.rs`) with, computed on first use, its values' keys as a hash set (a process-wide keyed hash, so a request cannot choose collisions), and for a child `one_of` what its values share: the longest common prefix when all are strings, the longest common run of segments when all are plain paths, the smallest and largest integer when a range can judge all of them. A list then implies a list in one lookup per child value, and a `prefix`, `path_prefix` or `range` in the size of that constraint. `equals` compares keys, hash first. The parent set is wrapped once per attenuation, the search for a covering parent is one pass, and the server's loops over single capabilities (`meet` in `idp/ceiling.rs`, the refusal details at intake) use `CapabilitySet::covered` and `attenuate_each`, which wrap the parent once. Sets of at most 64 pairs of small capabilities (8 constraints, lists of 8) are still compared pairwise, by the old code, which costs less there.
  - *Reading a request.* A `CapabilitySet` was built one `BTreeSet` insertion at a time, and each comparison wrote both constraints' canonical forms through a tree of nodes, so a 1.6 MB request of 400 lists took 0.74 s to read, before any bound is checked. Sets are now built by sorting keys written once per capability, and a constraint's canonical form is written directly: 73 ms. The same set results, including which of two equal capabilities written differently (`1` and `1.0`) is kept.
  - *What stayed a product.* With each comparison cheap, attenuation still compares each requested capability with every parent capability that matches its patterns, constraint by constraint and value by value, so its cost is the constraints or `one_of` values of one side times the capabilities of the other. Within the #328 bounds that was 0.96 s for 1,000 requested capabilities with 25 equal constraints against 1,000 such parents, and 7.7 s for 400 lists of 1,024 against 400. That cannot be made cheap without an index of the parent's values, so a request, and each hop of a token, now also holds at most 1,024 argument constraints (`MAX_CONSTRAINTS`) and 1,024 `one_of` values (`MAX_ONE_OF_VALUES_TOTAL`) over all its capabilities. `CapabilitySet::validate_size` checks them with the other bounds, before anything is compared, so an exchange, hop-0 intake and `POST /admin/root-token` refuse more with `400 invalid_scope` / `too_many_constraints` or `too_many_one_of_values`; a `[[root_grants]]` or `scopes` entry over them refuses to start, and an `authorization_details` claim whose capabilities exceed them names nothing. This refuses requests that worked before, if any was that large: 1,024 capabilities can still carry one constraint each, and one list can still hold 1,024 values.
  - *Measured*, release build, the `bounds` group of `attenuo-core`'s `attenuation` bench, before and after ([bench note](../design/bench/2026-11-14-vm-criterion-attenuation-sr123.txt)): two lists of 1,024, 25.6 ms to 0.19 ms; one list against one, 49.7 ms to 0.19 ms; one list against 400 (no longer a token any request can make), 19.8 s to about 70 ms; and within every bound now, 1,024 requested capabilities against 1,024 with one constraint each, the worst being 600-byte `equals` arrays (7.8 s to 51 ms), `path_prefix` against one-value lists (230 to 30 ms), `equals` (35 to 21 ms) and one-value lists (39 to 29 ms); 512 by 512 with two constraints, 1.79 s to 28 ms; 32 lists of 32 a side, 24.6 to 0.45 ms. The small sets of the `covers` group moved by 20 to 120 ns (64 against 44 ns for one capability, 211 against 92 ns for a rejected eight), and the `decide` stages within noise.
  - *Not changed.* Hop 0 still attenuates on the request's async task: an intake runs the grant, the ceiling's `meet` and the ceiling again, each now bounded by the figures above, so a worst-case request holds a runtime worker for tens of milliseconds, not seconds. Moving it to the blocking pool, as the exchange does, would cost one task hand-off per intake and keep even that off the workers; it is left as a suggestion.
  - *Done after the pass* (#330): intake's attenuation against the root grant, the ceiling's `meet`, the attenuation against the ceiling, both `limit_split_at_root` checks and the work of naming a refused capability run in one `AppState::blocking` call, the helper the exchange uses, so no runtime worker runs them. The helper is the same in both places: tokio's blocking pool (512 threads by default, its queue unbounded, no timeout of its own), and a panic in the closure is resumed on the request's task, so a saturated pool or a panic answers as it does at the exchange; the exchange has no saturation test, so none was added. The order of the checks and every answer are unchanged; the existing intake suites (`tests/oidc.rs`, `tests/id_token_intake.rs`, `tests/actor_token_hop0.rs`, `tests/private_key_jwt.rs`, the hop-0 cases of `tests/run_limits.rs`) pass as they are. `POST /admin/root-token` already attenuated inside its blocking call. Reading the request into a `CapabilitySet` still happens on the async task, as reading the body does at the exchange.

### SR-124: `scope_exceeds_id_jag` showed the grant's limits (Info, fixed)

- **Confirmed by reading and reproduced.** `handle` attenuates the request against the root grant first, which copies the grant's limits into each requested capability, and then attenuates that result against the ceiling. A refusal there named the capability from the result: with a root grant `github:*` with `calls: 7` and an ID-JAG whose `scope` maps to `github:read_file`, a request for `github:read_file github:create_issue` was refused with ``requested capability `github:create_issue limits={"calls":7}` is not covered``. `scope_exceeds_grant` names the capability as sent.
- **Attacker.** The agent at hop 0, learning the grant's figures for a capability its ID-JAG does not allow. It sees the figures of the capabilities it is given in its own token anyway, so this tells it little more.
- **Severity.** Info.
- **Fix.** On that refusal, the detail names the first requested capability, as the request has it, that does not pass both attenuations, with the same wording. The code, status and the token issued are unchanged.
- **Test.** `scope_exceeds_id_jag_does_not_show_the_grant_limits_sr124` (`tests/oidc.rs`): the detail names `github:create_issue` and holds no `limits`; a request within both still gets `github:read_file` with `calls: 7`. Failed before the fix with the detail above.

### SR-125: a `scopes` capability with bad limits passed the start-up check (Info, fixed)

- **Confirmed by reading and reproduced.** `IdJagCeiling::from_config` checked a `scopes` capability's names but not its limits, while an `authorization_details` capability with limits that `Limits::validate` refuses names nothing. `scopes = { s = [{ server = "github", tool = "*", limits = { sum = { arg = "", max = 1 } } }] }` started. An intake that kept such a capability in the ceiling then failed at mint with `invalid_capability`, for a request that asked for nothing wrong.
- **Severity.** Info: a configuration mistake, failing closed, found by the first user.
- **Fix.** `from_config` calls `validate_limits` on each `scopes` capability, so the server refuses to start, naming the scope token. `[[root_grants]]` capabilities have the same gap (their limits are checked at mint only); changing that would refuse configurations that start today, so it is left with SR-121's row.
- **Test.** `config_is_checked` (`idp/ceiling.rs`) gained an empty `arg` and a `derive` on a `sum`. Failed before the fix.
- **`[[root_grants]]` fixed after the pass** (#333). `Config::check_server_names`, the start-up check of root grant capabilities, calls `validate_limits` on each, the check every hop-0 mint makes, so a root grant capability whose limits no token may carry refuses to start, naming the entry by index, issuer, agent and subject, the capability and the reason. A configuration that started before and failed at mint with `invalid_capability` now stops at start. Root grants are read at start only, so no reload path needed the check. Test `root_grant_limits_no_token_may_carry_refuse_to_start` (`tests/hardening.rs`).

### SR-126: what the ceiling was is not recorded (Info, proposed)

- **Confirmed by reading.** The intake record adds `id_jag_ceiling`, the names of the claims that narrowed, to the arguments, of which the record keeps only the digest. The standards note says a readable field would be a schema change and was not made. So afterwards an operator can tell that a ceiling was applied only by recomputing the digest for each of the eight possible lists, and can never tell to what: the claim values (`resource`, `scope`, the `authorization_details` entries) are not in the record, the digest or a log line above debug, and the mapping in the configuration may have changed since. The root hop's capabilities, which the record does cover, are the result, not the ceiling. A refused intake (`id_jag_ceiling_empty`, `scope_exceeds_id_jag`) writes no record, as `scope_exceeds_grant` never did, so a run of refusals leaves only the info lines of the requests that succeeded.
- **Severity.** Info: nothing is allowed that should not be; it is about what an investigation can show.
- **Options.** (1) A readable `id_jag_ceiling` member in the record, holding the claim names and a digest of the claim values (a schema change). (2) The claim names, and the claim values Debug-formatted, on the info line "root token issued from IdP credential" (a log change only; the values are the IdP's, not secrets, but they can be long). (3) Leave it. **Recommendation:** (2) now and (1) with the next record schema change.
- **Option 2 done after the pass** (#328). When the ceiling was applied, the info line carries `id_jag_ceiling`, the names of the claims that narrowed (comma-separated, from the server's own list), and `id_jag_claims`, `name=<compact JSON>` for each, each value cut to 512 bytes at a character boundary with its full length noted, Debug-formatted as every caller-influenced log value is (SR-18), so a newline in a claim stays on the line. Without the ceiling, or for an ID token, the line is as before. The record is unchanged, and refusals still write no record. Test `ceiling_claim_values_are_capped_sr126` (`idp/intake.rs`); the line was also checked by eye in the output of `an_id_jag_budget_is_not_split_across_capabilities_sr121`, not by an automated capture. Option 1 stays open.

## Not confirmed

- **The result wider than the grant or a claim.** `the_result_is_within_the_grant_and_every_claim` (added here) takes every pair of 11 capabilities (`*:*`, `github:*`, `github:read_*`, `github:read_file`, prefix constraints on `repo`, and `calls`, `distinct` and `sum` limits) as grant and as claim, 66 sets each: in every case `meet` is covered by both sides, and every request of those 66 sets that passes both attenuations is covered by the grant, the claim and the ceiling. `covers` is the order every hop uses, so this holds the claim as the code defines it; SR-121 is where that order and run limits part.
- **Wildcards and the reserved server.** A claim of `*:*` keeps the grant as it is (`meet` keeps each grant capability it covers). A claim can name `attenuo:*` (only names are checked), and keeps it under a `*:*` grant, but no upstream can be called `attenuo` (SR-34). `resources` refuses `*`, globs and `attenuo`; `scopes` refuses `attenuo` and server globs other than `*`, as `[[root_grants]]` does.
- **Claims present but empty, or of another type.** `scope: ""`, `resource: []`, `authorization_details: []`, a number, an object, nested arrays: each names nothing, so the request is refused with `id_jag_ceiling_empty` (unit tests for several, the rest by reading `named_by_*`). A mixed `resource` array keeps its strings. `null` is treated as absent, as documented: an IdP that writes `"scope": null` puts no limit there. An IdP that puts its scopes in another claim (`scp`) gets no narrowing from them; the draft's claim is `scope`.
- **Unicode and case.** Every comparison is exact, and a value that does not match names nothing, so a trick can only narrow. Scope tokens are split on ASCII whitespace, and the configuration refuses a token with any Unicode whitespace, so `repo.read\u{a0}chat` is one unmapped token.
- **Duplicate JSON keys.** The payload is parsed once into a map by `jsonwebtoken::decode` (serde_json, the last value wins), and `map_id_jag`, the checks and the ceiling read that one map. The payload is signed by the IdP; the agent cannot add a key.
- **Strict reading of a claim's capabilities.** `CapabilityConfig`, `Limits` and `ArgLimit` refuse unknown members, so a misspelt `limits` member makes the capability name nothing rather than unlimited; a malformed `range` or `path_prefix` is refused at deserialisation.
- **The option off.** With no `[idps.id_jag_ceiling]`, `id_jag_ceiling` returns `None` and the match arm is the old value; `id_jag_claims_are_ignored_without_a_ceiling` checks the answer and the record digest. Issuers are unique (`from_config` refuses a second entry with the same `issuer`), so the ceiling cannot come from another entry than the one that verified the credential. ID tokens cannot pass as ID-JAGs or the reverse: the `typ` checks differ and the `aud` is the agent's client id for one and `[issuer] issuer` for the other.
- **`may_act`, TTL, DPoP, replay.** None of them read the ceiling's result or are read by it: `may_act` comes from the grant and the request, the TTL from the credential and the actor token, `cnf` from the proof and `cnf.jkt`, and the credential is spent only once the root token is issued, after every refusal above.
- **The refusal as an oracle.** A refused request does not use the ID-JAG up, so the agent can send it again with different requests and learn which capabilities are within the grant and the ceiling. It can read the claims in its own ID-JAG, `scope_exceeds_grant` already answers the grant half, and every answer is about a token it is entitled to. `id_jag_ceiling_empty`'s detail names the claims present (in the ID-JAG), the agent and the issuer, as `no_root_grant` does. The verifier's messages stay at debug (SR-17), and the new debug line holds claim names only. `[limits] token_requests_per_minute` bounds the rate when set.
- **A later hop regaining what the ceiling removed.** An exchange attenuates against the subject token's capabilities and charges every ancestor (`a_later_exchange_cannot_exceed_the_id_jag_ceiling`); a renewal only extends the lease and reads no grant; the development root mint (`POST /admin/root-token`) is an admin action that presents no ID-JAG, so the ceiling has nothing to read there. No other path mints a root token from an ID-JAG.
- **Config holes.** `scopes` may map to `*:*`: that token narrows nothing, which the guide says. A resource mapped to a server with no `[[upstreams]]` entry is accepted; it fails closed (the grant gives nothing there, or the proxy has no such route), and capabilities name servers that only AuthZEN callers enforce, so refusing it would refuse valid configurations. A resource identifier with surrounding whitespace is accepted and is never matched by a value without it.
- **#325.** `rename_current_span` renames the current OpenTelemetry span, the route span `trace_route` entered; with tracing off, or a sampled-out or remote parent, it acts on a span that records nothing. It takes a `&'static str`; no caller text reaches it. The live script keeps its secrets in a `0700` dir (`umask 077`), passes the admin token to curl in a header file, pins both images by digest and binds every listener its configurations set to `127.0.0.1`. The containers use `--network host`, so a listener an image opens by default and the configurations do not set would be on every interface; neither configuration was found to leave one, but the images were not run.
