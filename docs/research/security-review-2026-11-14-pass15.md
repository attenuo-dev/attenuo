## Findings

### SR-118: server and upstream text reached the terminal raw (Low, fixed)

- **Confirmed by reading.** `api_error` built a refusal's text from the body's `error`, the stable code (shown since #319 as ` (<code>)`), `detail` and `decision_id`, or the whole body when it is not an error object, and `main` prints it with `eprintln!`. None of it was escaped. The same held for what `attenuo call` and `attenuo tools` print without `--json`: a JSON-RPC error's `message`, a denial's `reason` and `decision_id`, an approval's fields, every tool result's text, and each tool's `name` and `description`; and for `budget refund`'s detail and the "no JSON-RPC response" and "non-JSON" errors, which quote the body. The CLI escapes control characters only where an agent chooses the text (limit and constraint names, SR-59 and SR-72; tool names in the lease tree; `may_act` names).
- **Attacker.** Mainly an upstream MCP server (A3). The proxy filters which tools `tools/list` shows, not what their descriptions say, relays tool results and JSON-RPC errors, and relays a non-2xx upstream answer with its status and its JSON body (after the list filter and labelling), which the CLI then reads as a refusal (`mcp` falls back to `api_error` for a body without `jsonrpc`). Escape sequences in a tool description are a known way to hide text from the person reading a tool list (an injected instruction drawn in the terminal's background colour, or a line erased and redrawn), and some terminals act on OSC 52, which writes the clipboard. Also whoever answers at the server URL, as in SR-112.
- **Reproduced.** `api_error(400, {"error":"invalid_grant\u001b[2J","code":"replayed\u001b]52;c;aGk=\u0007","detail":"used\nerror: FORGED\r\u009b31m","decision_id":"d-1\u001b[8m"})` gave a message with ESC, BEL, CSI (U+009B), CR and a second line `error: FORGED` as they came. A tool list entry whose description held `\u001b[8m ... \u001b[0m` (conceal) and a tool result holding OSC 52 printed them raw.
- **Severity.** Low, as SR-59 and SR-72: the terminal of the person running the CLI is rewritten or misled; nothing is allowed that should not be, and no token leaves. Higher than Info because an upstream reaches it without any credential of its own, through the proxy.
- **Fix.** `render::escape_controls` (now `pub(crate)`) on every such string, and `escape_controls_keep_lines`, which keeps line feeds and tabs, for a tool's text and a description; a carriage return is escaped in both, since it lets a line overwrite itself. The CLI's own line break before `decision` stays. `ApiError`'s `code` and `detail` keep the values as sent, since callers compare them; `refund_refusal` escapes the detail it prints. `call` and `tools` now build their text in `call_text` and `tools_text` and print it, with the same lines and exit outcome as before for text without control characters. `--json` is unchanged: JSON escapes control characters in strings.
- **Test.** `api_error_escapes_control_characters_sr118` (`client.rs`) and `upstream_text_is_printed_with_control_characters_escaped_sr118` (`main.rs`): every case above comes out with `\u{1b}`-style escapes and no control character except the kept line breaks and tabs. Both failed before the fix (with the escape turned off, they and `constraint_names_and_diagnostics_escape_control_characters_sr72` fail).

### SR-119: an S3 endpoint without a host sent the PUT to the bucket's name (Info, fixed)

- **Confirmed by reading.** `SinkSection::validate` checked an S3 `endpoint` as a string: it starts with `http://` or `https://`, and what follows has no `/` (after trailing ones), `?` or `#`. `endpoint = "http://"` passes. `deliver` builds the request URL as `<endpoint>/<bucket>/<key>`, here `http:///<bucket>/<key>`, and the WHATWG parser, which reqwest uses, skips the extra slashes of a special scheme and reads the bucket as the host. `signed_host` fell back to the raw string after `://` when the endpoint did not parse, `""`, so the request was signed for an empty host and sent with `Host: <bucket>`. A backslash is a `/` to the same parser, so `http://minio:9000\evil` passed the string check and was sent with the path `/evil/<bucket>/<key>`.
- **Attacker.** A sloppy operator config (A8): an endpoint left as a bare scheme, with a bucket that is also a resolvable name.
- **Reproduced.** In a unit test with a listener on `127.0.0.1:80`, `endpoint = "http://"`, `bucket = "localhost"` and STS credentials: `validate` answered `Ok`, and the listener received `PUT /attenuo/checkpoints/00000000000000000001-....json` with `host: localhost`, the SigV4 `authorization` header (access key id, signed headers, signature), `x-amz-security-token` with the session token, and the checkpoint body. `reqwest::Url::parse("http:///evil.example/attenuo/checkpoints/k.json")` has host `evil.example`. With a bucket holding `:` the URL does not parse (`uri_encode` writes `%3A`) and nothing is sent.
- **Severity.** Info. It needs a broken configuration, which would never have delivered to the intended store, so the operator would see `audit_sink_failures_total` and the `/readyz` `degraded` flag. What leaves is the access key id, a signature for an empty host that S3 would not accept for any request, the session token (useless without the secret key) and a checkpoint, which is meant to be shipped and is signed.
- **Fix.** `sink::check_s3_endpoint`, called by `validate` and by `S3Deliver::new`: the endpoint must hold no backslash, whitespace or control character (the parser reads `\` as `/` and drops tabs and line breaks, as for `derive = "host"`, SR-56), must parse, have a host, and have the path `/` and no query or fragment as parsed. The string check stays. Every endpoint that delivered before still passes (`http://127.0.0.1:9000/`, `http://[::1]:9000`, `https://S3.Example.com:443`).
- **Test.** `an_s3_endpoint_the_url_parser_reads_differently_is_refused_sr119` in `sink.rs`: `http://`, `https://`, `http:///`, a backslash path, a trailing backslash and a tab refuse at `validate` and at `S3Deliver::new`, and a plain endpoint still builds. Failed before the fix (`validate` answered `Ok`); `config_validation_names_missing_and_foreign_fields` gained the endpoints that must keep passing.

### SR-120: the live scripts left per-run credentials readable by other local users (Info, fixed)

- **Confirmed by reading.** `scripts/live-spire-smoke.sh` ran `chmod 755 "$WORK"` on its `mktemp -d` directory ("mounted read-only into the container"), and wrote into it with the caller's umask: `admin.token`, the attenuo configurations holding it, and, under `conf/` (also `0755`), the SPIRE agent's join token and the bundle endpoint's private key (`chmod 644`). Its header says these "stay in the temp dir". `live-minio-smoke.sh` passed the MinIO root password as `-e MINIO_ROOT_PASSWORD=<value>` on `docker run` (twice), and `live-keycloak-smoke.sh` the Keycloak admin password as `-e KC_BOOTSTRAP_ADMIN_PASSWORD=<value>`; a process's arguments are readable by every local user through `ps` or `/proc/<pid>/cmdline`. The collector, MinIO and Keycloak scripts keep their own temp dirs at `0700`.
- **Attacker.** Another local user on a shared machine where a contributor runs a live script, for the length of the run.
- **Reproduced.** The SPIRE script's lines with umask `022`: the directory is `0755` and `admin.token` `0644` (OpenSSL 3.0 writes `-keyout` files `0600`, so `ca.key` was not exposed; `be.key` is made `0644` by the script). Docker could not be run here, so the scripts themselves were not.
- **Severity.** Info: every credential is random per run and belongs to services bound to `127.0.0.1` that live only for the run (the test attenuo server's admin token, a throwaway SPIRE, MinIO and Keycloak); none is the contributor's own. During the run another user could have used the admin token on the test server or attested a node with the join token before the agent did.
- **Fix.** The SPIRE work dir keeps `mktemp`'s `0700`. Only `conf/` and `bin/` are mounted, and a bind mount is resolved by the daemon, so the container never walks through the parent; both stay `0755` with `be.key` `0644` for a container user other than the caller (user namespace remapping), and other local users cannot reach them through the `0700` parent. The MinIO and Keycloak passwords are set in the environment of the `docker run` command and passed as `-e NAME`, which docker copies from its own environment. Each header says what remains: `mc` and `kcadm.sh` run in the container with secrets as arguments (`mc alias set`, `mc admin user add`, `kcadm.sh config credentials --password`, `set-password`), and so does curl with `-u` in the Keycloak script, visible in `ps` while they run.
- **Test.** None automated (the scripts are not part of CI, and docker was not available here); `bash -n` passes on all three. The next live run is the check.

## Not confirmed

- **`ca_pem_path` roots reaching another entry.** Each entry with `ca_pem_path` gets a client of its own from `fetch_client`, which starts from `fetch_client_builder` (no redirects, `localhost` pinned to loopback, SR-107) and adds that file's roots; entries without one share a client with the built-in roots only. Each entry has its own `JwksCache` holding its client, and there is no cache keyed by URL: two entries with the same `jwks_url` and different CA files fetch and cache separately, and an `[[idps]]` and an `[[actor_trust]]` entry are in two registries that share nothing. The approval ID token path uses the `[[idps]]` caches. No other outbound client (sink, notifier, telemetry, proxy) is built from these. `the_hostname_check_and_the_redirect_refusal_stay` covers the redirect refusal over TLS with the extra roots.
- **What a CA file can hold.** Every `CERTIFICATE` block is a trust anchor. A self-signed leaf works as one (pinning, which the operator chose); a leaf issued by some CA does not verify a chain it is not the root of, so it fails closed. Webpki takes an anchor's subject and key and does not check its `basicConstraints`, so a non-CA certificate in the file is trusted as a root for that entry only; that is what the operator put there.
- **A FIFO, `/dev/zero` or a huge file as `ca_pem_path`.** With the real binary: a FIFO hangs start-up after the store is opened, with no log line (stopped at 10 s by `timeout`); `/dev/zero` under a 2 GB address-space limit fails at once with `cannot read the file (out of memory)`, and without a limit would grow until the allocator fails. Not a finding: every file the configuration names is read the same way (`std::fs::read_to_string` for the signing key, the schema, the policies, the catalog and the operators file), the operator who can set the path can point any of them there, and the threat model counts anyone who can edit the config as able to add an `admin` (A8). A relative path resolves against the working directory, as every other path in the file and as the reference page says; under a service manager that is its `WorkingDirectory`. The file holds public certificates, so its mode does not matter; symlinks are followed, as for every other path.
- **Log injection through the new fetch error text.** `error_chain` adds the TLS cause, which can hold names an attacker's certificate presents (rustls' `NotValidForNameContext`). Every reader of `JwksError::Unavailable` logs it with `Debug` (`detail = ?detail` in the `IntakeError` and `ActorTokenError` mappings; `detail = ?e.to_string()` for approvals), which escapes control characters, as SR-115 asked for. The HTTP answer stays the stable `jwks_unavailable` (SR-17). The text holds no response body (the JSON parse error names a position, not content), no token (a key fetch sends none), and no password (`url_for_log`); a query string in a configured `jwks_url` was logged before #321 too.
- **The S3 header set with a session token.** `x-amz-security-token` is in the headers, signed, and sent once; the canonical request lists the seven headers sorted and the test checks it byte for byte. A token holding a line break is refused by reqwest's header check (a `builder error`, whose text names no value). An endpoint with user info is sent by reqwest as `Authorization: Basic` next to the SigV4 header, so the request fails; nothing is sent elsewhere, and the user info is not logged (`without_url`). IPv6 endpoints sign `[::1]:9000`, which is what is sent. A bucket or prefix with `.` or `..` segments is normalised by the parser, so the signed and the sent path differ and S3 refuses: fails closed.
- **`signed_host` signing what is not sent.** After SR-119, the fallback is reached only for an endpoint that does not parse, which is refused at start and by `S3Deliver::new`; before it, the one case found was `http://`, which is SR-119.
- **The ID token on the command line.** `--subject-token <literal>` prints the existing argv warning, and the reference page's example passes the credential in `ATTENUO_TOKEN`, whose value a shell history records as `$ID_TOKEN`, not the token, and which only the same user can read from `/proc`. No error path quotes it: `resolve` names the source, not the content, and a refusal quotes the server's answer. `--print token` prints the root token the server issued, which is what it is for.
- **The credential sent to the wrong server.** The exchange goes through the CLI's one client (`http_client`, no redirects) and `send_dpop`, which calls `refuse_redirect` on every answer, the `use_dpop_nonce` retry included, so a `307` cannot take the ID token elsewhere (SR-112).
- **A hop-0 DPoP proof without `ath`.** `bind_new` verifies `htm`, `htu` (the server's own `/token` URL), `iat` within its window and the server nonce when required, and spends the proof's `jti` once. A captured proof cannot be used again, and one captured before its first use would bind a root token for the attacker's credential to the victim's key, which the attacker does not hold. For an ID-JAG with `cnf`, the proof's key must be that key. The proof is checked before the credential is redeemed, so a `use_dpop_nonce` retry does not spend it.
- **Rate limit keying (#315).** The key is the chain's root lease (`chain_id_of`), so children, deeper chains and a PEP's unsigned chain (each hop checked as issued before the count) all count against their run. A new bucket needs a new root token, which needs a fresh user credential (single use) or a dev mint. `chain_id_of` is `None` only for an empty chain, which `validate_at` refuses. The table is bounded by `rate_limit_max_keys` (default 10000); a full table refuses new runs with `429`, which needs that many runs searching within one minute.
- **Page tokens (#316).** The binding is digests of what the caller sends, not a MAC, so nothing about it needs to resist the caller: any caller can make a valid token for its own query, and the token only ever moves it within that query's candidates. The 8-byte truncation matters only for telling a changed query from the original one: a changed query keeps a token with probability 2^-64 per part, and finding a different context that keeps it on purpose is a 2^64 second-preimage search, which buys an offset the caller could send anyway. The `detail` names which part differs, which the caller knows from its own two requests; with a token taken from another caller it learns only whether its own chain, server or context digest matches. The offset is read as `u64`, converted to `usize` saturating, clamped to the candidate count, and the end is a saturating add then `min`, as pass 14 found; `decode_search` runs before authentication and reads only the token.
- **Span integers (#317).** `otel_int` saturates at `i64::MAX`; the values are chain depths, sequence numbers and status codes, none from a caller.
- **The live scripts otherwise.** The SPIRE release tarballs are checked against pinned SHA-256s before extraction, every image is pinned by digest, and nothing is piped to a shell. Each script removes its container and temp dir in a trap on `EXIT`, `INT` and `TERM` (`KEEP=1` keeps the dir, as documented). Every listen address the scripts set is on `127.0.0.1` (MinIO's API and console, SPIRE's server and bundle endpoint, the discovery provider, Keycloak's `--http-host`, the collector's receivers from the guide), and SPIRE's sockets are in the container's `/tmp`; ports the images open by default and the scripts do not set were not checked. Container names and ports are predictable or chosen with a race, which another user with access to the docker daemon could use, but such a user is root on the machine already.

## Checked and found sound

**#321**

- `read_ca_pem` refuses an empty file, a file that is not PEM and one with no certificate, without quoting the file; `entry_client` names the path with `Debug`. The file is read once at start, as the reference page says (`the_ca_file_is_read_at_start_only`).
- The checksum headers are computed from the same SHA-256 as `x-amz-content-sha256`, and both are signed.

**#318 and #319**

- `check_hop0` refuses the sign-off flags at hop 0 and requires `--client-assertion-audience` with `--client-key`, so the CLI never signs an assertion for the IdP's `iss`. Flags for hop n are unchanged.
- The stable code in the error text comes from the same `stable_code` as the machine field; with SR-118 the printed copy is escaped and the field is not.
