## Findings

### SR-115: a newline in an action search's `server` forged log lines (Low, fixed)

- **Confirmed by reading.** `search_actions` logs one `info` line per search with `server = %server` (`routes/authzen.rs` at `b345a05`, the `tracing::info!` before the answer). `server` is the request's `resource.properties.server`, or its `resource.id`; `search_server` checks only that it is a non-empty string and, for `resource.id`, holds no `/`. The line is written after authentication, and whether or not the server exists in the catalog. With `[logging] format = "text"`, the default, `Display` writes a newline as it is. SR-18 fixed the same class on the decision line (Debug, `?`), and the comment there says why; this line was added after it.
- **Attacker.** Any holder of a delegation token (or an authenticated PEP with an issued chain): one request per forged line, nothing else needed.
- **Reproduced.** A search with `resource.properties.server` = `gh` + newline + `FORGED-SR115 level=INFO decision`, through the HTTP route and the default text format: the log had `... AuthZEN action search chain_id="..." server=gh` and then a separate line `FORGED-SR115 level=INFO decision evaluated=0 permitted=0`. The answer was `200` with no results.
- **Severity.** Low, as SR-18: it misleads an operator reading the text log during an incident and can fake a `decision` line; the audit log is not affected, and JSON logs escape the value.
- **Fix.** `server = ?server`, as on the decision line. The other fields of the line are `chain_id` (a lease id the server generated) and two counts. No other log line added in #310 to #312 writes a caller string.
- **Test.** `a_newline_in_an_action_search_server_stays_on_one_log_line_sr115` in `hardening.rs`: exactly one captured line holds the marker, it is the search line, and it holds `server="gh\nFORGED-SR115`. Failed before the fix with the two lines above. The route runs on the blocking pool, so the test's capture writer gained a shared buffer for threads that have none of their own, read by marker.

### SR-116: action search counted the catalog through its paging (Info, fixed)

- **Confirmed by reading.** The candidates of a search were every tool `[policy] catalog` lists for the named server (`engine.catalog()` filtered by server), whatever the token's capabilities. `would_allow` answers `false` for a tool outside the capabilities, but the tool still took a place in the candidate list, so with `page.limit` 1 every candidate is one page, and `next_token` is set exactly while candidates remain. The position is an offset and the cursor has no integrity tag (`page.rs`), so a forged `page.token` asks "is there a candidate after offset n" in one request, and a binary search finds the count in about log2 of it.
- **What a caller learns.** How many tools the catalog lists for any server name, the ones its token does not name included, and where its own tools sort among them (how many catalogued names come before each). Evaluating one tool at a time does not tell this: outside the capabilities, a catalogued tool and an unknown one are both `capability_denied`, because the capability stage runs before the catalog. The reference page said a caller "learns no more than evaluating each candidate one at a time would tell it". A revoked or expired token (still verifying until its `exp`) could page the same way, with every page empty.
- **Reproduced.** Against the conformance harness (catalog `github`: `create_issue`, `delete_repo`, `pay`, `read_file`), a token with `github:read_file` only, `page.limit` 1: four pages, three empty with a `next_token`, then `read_file` with `""`. Evaluation of `pay` and of `not_catalogued` answered `capability_denied` both.
- **Severity.** Info: the catalog's size and order are configuration, not secrets the design names, and nothing is allowed that should not be. Recorded because it made the stated property false.
- **Fix.** The candidates are now the catalogued tools of the server that the chain's effective capabilities could permit by name pattern, `attenuo_proxy::filter::could_permit_tool`, the question the proxy's `tools/list` filter asks. A tool that is not a candidate now could not be a result before (the capability stage's `permits` needs the same pattern match), so results are unchanged; only the empty pages over other tools go. A server the token does not name has no candidates and answers one empty page with `next_token` `""`. Paging still shows how many catalogued tools the token's own patterns match, which a token with a wildcard such as `github:*` is also shown by the proxy's `tools/list`.
- **Test.** `action_search_pages_only_over_the_tools_the_capabilities_name_sr116` in `authzen_conformance.rs`: one page holding `read_file`, the two evaluations above, and a search of a server the token does not name. Failed before the fix (four pages). The fixtures and `action_search_agrees_with_evaluation` pass unchanged.

### SR-117: action search is an unaudited, unlimited oracle over chosen arguments (Info, proposed)

- **Confirmed by reading.** A search writes no audit record (by design, `would_allow` and the reference page). `context.input` and `context.session_id` come from the caller and apply to every candidate, so a search answers "which of my tools would be allowed with these arguments". No rate limit applies to the AuthZEN routes: `[limits] mcp_requests_per_minute` is checked in `ServerAuthorizer` for `/mcp/{server}` only, and `token_requests_per_minute` for `POST /token`; the AuthZEN routes get the global `max_in_flight` (default 1024 concurrent) and `request_timeout_seconds` (default 60) only. One request evaluates up to `[authzen] max_batch` candidates (default 64), each with up to three store reads (counters, user windows, span index) and one Cedar evaluation, no more than a batch evaluation of 64 entries over the same top-level context costs; the run lock is not taken.
- **Observation.** An agent can search for argument values that a policy lets through, a recipient domain, a path, an amount under a threshold, a repository pattern, as fast as the server answers, and each attempt leaves only the `info` log line (chain, server, counts; not the arguments), no record in the hash-chained log. The same probing through `POST /access/v1/evaluation` writes a `deny` record per attempt, which is what an operator would notice. The reference page justifies the missing record by the list screen and the admin dry run, but neither is this: the list screen takes no arguments from the caller (they are Cedar unknowns), and the dry run needs an admin token. It enforces nothing and lets nothing run: a call found this way is still decided, audited and charged when it is made.
- **Reproduced.** `action_search_agrees_with_evaluation` (results change with `context.input`, `alice/public-site` against `alice/private`) and `action_search_writes_nothing` (three searches, no audit record, no approval, no charge), run on this branch.
- **Severity.** Info: no enforcement changes, and the reference page names the missing record as a cost; recorded because the stated comparison understates it and nothing bounds it.
- **Options.** (1) Keep it, and say in the reference page and the threat model that a search lets the caller try arguments without a record, unlike the list screen. (2) Count searches in a per-run rate limit: share the `mcp_requests_per_minute` table (the root lease is the key there too) or add `[limits] authzen_search_requests_per_minute`, off by default like the other rate limits. (3) Write one audit record per search request (not per candidate), with a new tool such as `authzen.search`, the server, an input digest and the permitted count; this changes what the audit log holds and every reader of it. (4) Add a digest of `context.input` to the log line, which gives a trace without the log's integrity.
- **Recommendation.** (2), with a new key off by default and the documentation change of (1) now. A run limit bounds the rate without changing the audit format, the threat model already treats rates as `[limits]` business (ADR-0014), and a deployment that wants searches visible can lower it; (3) is the stronger answer if the maintainer wants every probe in the log, at the cost of a record format change. Left open; this branch changes neither behaviour nor wording of the trade-off beyond pointing to this finding.
- **Option 2 done after the pass** in #315 ([ADR-0014 update](../decisions/0014-request-limits.md#update-2026-11-14-a-per-run-rate-limit-on-authzen-action-search-sr-117)), with the documentation of option 1. `[limits] authzen_search_requests_per_minute`, off by default, counts searches per run (the root lease, of the bearer's chain or of a PEP's issued unsigned chain) in a table of its own, apart from `mcp_requests_per_minute`. It is checked after authentication and before any candidate is evaluated; over it the answer is `429` `rate_limited` with `Retry-After`, nothing is evaluated, no audit record is written, and `requests_rate_limited_total{limit="authzen_search"}` counts it. Evaluations are not counted. Unset, nothing bounds the rate as before, so the finding stays open: whether a search should also write an audit record (option 3) is the maintainer's decision. Tests `limits::tests::the_search_limit_is_per_run_and_apart_from_the_mcp_limit` and, in `tests/limits.rs`, `the_search_rate_limit_is_off_by_default`, `the_search_rate_limit_is_per_run` and `a_pep_search_with_an_unsigned_chain_counts_against_its_run`.

## Not confirmed

- **`would_allow` saying allow where a decision denies, without a state change.** Read stage by stage against `decide_inner`. Both take one policy snapshot, check leases (a dead lease is `false` for every candidate), read labels, counters, usage, user windows and span matches by the same functions with the same `now`, and evaluate the policy with the same `CallLabels` except `approval`, which search leaves empty. The stages only `decide` has: `take_approval` or `take_presented` (can only turn a deny into an allow), the run lock (orders concurrent decisions; it changes what is read only when another decision charges meanwhile, a state change), the charge (refuses only when a counter moved since the read: the view's `held + adds > max` check is the store's), a charge or append failure (a store fault, which also changes the decision of the next evaluation), and `request_approval` (after a deny). `to_chain_and_call` builds the same call for a search and for an evaluation of a result (the result's `properties.server` is the search's server, the `input` and `session_id` the same), and `dpop_bound` is kept. A store without per-user windows refuses window charges, but both stores in the tree keep them. No case found; `action_search_agrees_with_evaluation` covers the common ones.
- **Taint, budget, other users, approvals through search.** What search tells about these is what an evaluation's `decision` tells for the same call, with less (no `reason`, no `budget` or `usage` context, no diagnostics): a tool absent from the results may be absent for taint, a limit or a user window shared with the user's other runs, as an evaluation's `false` would be. No approval is looked up, so search says nothing about pending or granted approvals.
- **Request validation before authentication.** `page` and `resource` are checked before the bearer, so an unauthenticated caller gets `400 invalid_page`, `invalid_cursor` or `invalid_search_resource` instead of `401` for a malformed request. Those checks read nothing but the body (no store, no catalog), as `batch_too_large` does for batches, so they tell nothing about the server's state.
- **`page.limit` and offsets.** A `limit` of any size is clamped to `max_batch` (`u64` to `usize` saturates first); 0, negatives, floats and strings are `invalid_page`. A forged offset up to `u64::MAX` is clamped to the candidate count, and `end` is a saturating add then a `min`, so no overflow and no slice outside the list. A token from another server's search is an offset into this one's list, which the caller could ask for anyway.
- **DPoP `htu`.** `bearer_auth` is called with `SEARCH_ACTION_PATH`, so a proof made for `/access/v1/evaluation` is refused at the search (`action_search_needs_a_proof_for_its_own_url`); the proof's `jti` is spent once per HTTP request, as for batches.
- **Policy reload during a search.** One snapshot holds the catalog and the policy for the whole request; between pages a reload can repeat or skip a tool, as the reference page says. `X-Request-ID` is echoed by the shared middleware, as a validated `HeaderValue` copied from the request.
- **The PEP unsigned-chain path.** The search goes through `admit`, as the evaluations do: `pep_id` and `pep_secret` or a top-level client assertion, `validate_at`, then `check_issued` for every hop before anything is read, so a PEP cannot search a chain the server did not issue (`unsigned_authzen_chains_can_search_actions_from_a_pep`).
- **Lease-tree user windows across users or issuers.** The windows are read with the issuer and subject recorded for the run's root lease at issuance, from the chain the server itself signed (`register_issued` re-verifies the token it minted), so a request cannot attach another issuer. `register_issued` runs only for a lease id the issuer generated (`new_lease`, a random UUID), and `register` refuses an existing id before the subject is recorded, so `BindingConflict` at issuance needs a UUID collision. The route is `viewer` (`ROUTE_ROLES`); what it adds for a viewer, the user's window figures for the tools the run used, is in every decision record's `usage.user_window`, which a viewer can already read through `GET /admin/audit`.
- **Cost of the read.** At most `MAX_TREE_WINDOWS` tool and kind pairs, two counters each, read in one `window_used` call; the tools are the run's root-lease usage counters, which exist only for destructive tools it was allowed. `truncated` is set when the cap cuts the list.
- **Migration 4.** It runs inside the migration runner's `IMMEDIATE` transaction, which reads `user_version` again inside it, so a concurrent open waits and then finds the file current, and a failed `ALTER TABLE` leaves version 3. A build whose list ends at 3 refuses a version 4 file before reading or writing (`a_build_before_migration_4_refuses_a_migrated_file`). Leases from before it keep a `NULL` issuer, which is never filled in or guessed.
- **Console rendering.** `userWindowsPanel` builds every cell with `h` and `mono`, which append text nodes (`document.createTextNode`), never HTML; attributes pass `ALLOWED_ATTRS`. A tool name holding markup shows as text.

## Checked and found sound

**#311, SDK and CLI search clients**

- All three send the token only as the bearer (with a DPoP proof for the search URL), never in the body; every request goes through the client that follows no redirect (SR-112). Errors map to `ApiError` with the server's stable code, as for evaluation, and the Python and TypeScript error messages quote at most 200 characters of an unexpected body, which is the server's answer, not a credential.
- Paging: the `_iter` loops and `attenuo authzen search --all` stop on `next_token` `""` and refuse a token equal to the one just sent. A server that sends a new token forever, with empty pages, keeps them asking; that is what answers at the server URL withholding an end, as a hang would be, and each request is bounded by the client's timeout.
- The CLI prints result names from the server's catalog, whose names `PolicyEngine` validates against `attenuo_core::names` at load (no control characters); its lease-tree lines escape tool names with `escape_debug` already.

**#312**

- `run_user_windows` shows neither the user's digest nor the issuer; the subject is on the tree's nodes already. A lease recorded without an issuer answers `null` rather than reading windows under a configured issuer.
- The write-once rule: the same subject and issuer again is a no-op, a different subject or issuer is `BindingConflict`, and a row from before migration 4 accepts the same subject and stays without an issuer, in both stores.
