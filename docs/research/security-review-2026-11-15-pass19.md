## Scope and method

The two features merged on 2026-11-15, read without the authors' claims as a guide:

- #348, `attenuo stdio-bridge`: `crates/attenuo-cli/src/stdio_bridge.rs` whole, its arguments in `cli.rs`, the guide `docs/guides/stdio-servers.md`, the CLI reference section and the threat model sentence;
- #349, the agentgateway external authorization route: `crates/attenuo-proxy/src/proxy/ext_authz.rs` whole, `RequestAuth::url` in `auth.rs` and its use in the server's `authorizer.rs`, `[[ext_authz]]` in both config files and `Config::check_ext_authz`, the route mounting in `proxy.rs` and the server's `lib.rs` with the `[limits]` layers around it, `screen_message` and `handle_post_inner` as far as the adapter reuses them, the design note, the guide, the configuration and HTTP references and the threat model sentence.

The attackers: an agent holding a valid narrow token that sends what it likes (A2, prompt-injected); a network peer of the bridge or of the route; a malicious or buggy STDIO child or upstream; a misconfigured gateway. Every suspicion got a reproduction first: the real `attenuo` binary for the bridge, the `tests/ext_authz.rs` harness (its fake gateway) and the proxy's `tests/hardening.rs` harness for the route and the proxy, a throwaway unit test for the JSON edge cases, and a Go 1.24 program for how Go's `encoding/json` reads the bodies in question. Four findings, numbered from SR-133. Three are fixed on this branch with a test that fails before the fix (SR-133, SR-134) or with the documentation corrected (SR-136); SR-135 is left open with a recommendation, its documentation corrected.

## Findings

### SR-133: member names that differ only in case (High, fixed)

- **Confirmed by reproduction.** JSON member names are case-sensitive, and serde_json reads them so. Go's `encoding/json` does not: it matches an object's member to a struct field by exact name or, failing that, by a case-insensitive match (with Unicode simple folds, so `ſ` matches `s` and the Kelvin sign `K` matches `k`), and when several members match one field the last one wins. A Go 1.24 program decoding into the struct shape that Go MCP servers use (`Method string \`json:"method"\``, `Name string \`json:"name"\``) read `{"jsonrpc":"2.0","id":1,"METHOD":"tools/call",...}` and `{"method":"ping","Method":"tools/call"}` as `tools/call`, `{"name":"read_file","Name":"delete_repo"}` as `delete_repo`, and an argument struct with `path` from `{"path":"/ok","Path":"/etc/passwd"}` as `/etc/passwd`. `"method\u0000"` it kept apart.
- **At the proxy.** `screen_message` takes a message without a `method` member for a response to a server-initiated request and forwards it after a lease check only, re-encoded with every member it had. So `{"jsonrpc":"2.0","id":1,"Method":"tools/call","params":{"name":"delete_repo","arguments":{}}}` reached the upstream with no decision and no decision record (the new hardening test, run on the code before the fix: the upstream received it and answered). With `method` and `Method`, `ping` was screened and `tools/call` run; with `name` and `Name`, `read_file` was decided and `delete_repo` run; with `path` and `Path`, the policy and the constraints saw one argument and the tool read another. Re-encoding, the SR-01 fix, keeps both members because they are two members to serde_json.
- **At the adapter.** `check_unambiguous` compares member names after unescaping, byte for byte, so it missed the same shapes; the fake-gateway harness got 200 for the `Method` body (allowed after a lease check) before the fix.
- **Attacker.** An agent with any token whose lease is live (A2), against an upstream that decodes messages with Go's `encoding/json` into structs, or with any other decoder that ignores case. Which Go MCP libraries do was not checked in this pass (none was run or read here); decoding JSON-RPC into tagged structs with the standard library is the common Go way. The gain is every tool of that upstream with any arguments, without a decision, a run-limit charge, an approval or a decision record for the call.
- **Severity.** High: a complete bypass of the per-call decision, by the party the proxy bounds, for a common upstream stack. Upstreams in TypeScript, Python and Rust (case-sensitive by default) are not affected.
- **Fix.** `jsonrpc::member_case_conflict` finds an object anywhere in the message with two member names whose folded forms (upper then lower case) are equal, and a member of the message or of its `params` whose folded form is one of the names the proxy reads (`jsonrpc`, `id`, `method`, `params`, `result`, `error`; `name`, `arguments`, `uri`, `_meta`) in another case. The proxy answers such a request with `-32600` `invalid_request` and forwards nothing of it (a notification is dropped; in a batch only that entry is refused); the adapter refuses the body with 400 `ext_authz_ambiguous_body` before any decision. The fold also makes `ß` and `ss` one key, which can only refuse more. What changes: a client that writes envelope or `params` names in another case than the schema's, or sends an argument object with two names that differ only in case, is refused where it was forwarded.
- **Not covered by the fix.** A single argument name in another case than the tool's schema (`Path` alone) is passed as it is: the proxy cannot know the schema's case, and a capability constraint or a policy that reads `path` then sees no `path`. A constraint on a missing argument refuses, so the remaining case is a `forbid ... when { context.input has path && ... }` policy, which does not fire. The threat model's residual risks now name it.
- **Tests.** `member_names_that_differ_only_in_case_never_reach_the_upstream_sr133` (`crates/attenuo-proxy/tests/hardening.rs`, fails before the fix on its first body: the upstream's `{"result":{}}` came back), `member_names_that_differ_only_in_case_are_found_sr133` (`jsonrpc.rs`), `member_names_that_differ_only_in_case_are_ambiguous_sr133` (`ext_authz.rs`), and two bodies added to `bodies_that_are_not_whole_and_unambiguous_are_denied` (`crates/attenuo-server/tests/ext_authz.rs`).
- **The remainder, fixed after the pass** (this PR). A call whose top-level argument name differs only in case from a name the decision knows for the tool is denied by the policy engine with `argument_case_mismatch`, before the capability stage, so the proxy, AuthZEN and the gateway route refuse it alike and record it as a deny with its reason (SR-133's refusal of a message, which no decision can read one way, stays before the pipeline with no record). The names known: the tool's catalog entry (`inputs`, `amount`, `destination`, `outbound`), the constraints and run limits of every capability at any hop whose patterns match the tool, and every name a loaded policy reads under `context.input` or compares with `context.untrusted_args`, from Cedar's JSON form at load, for all policies whatever their action. The last is needed: a read of an undeclared name guarded by `has` loads (as an impossible policy, a warning) and runs, so the catalog does not bound what policies read. An exact name of the tool's own passes even when another tool's policy reads a variant; a name nothing reads passes in any case, which the proxy cannot close without the tool's schema. Nested names are not looked at, since no check reads one by name. Rejected: refusing every name the catalog does not declare (breaks optional undeclared arguments, which the type check passes today, with no closed-inputs setting to opt in, and does nothing for a tool with no entry), and renaming to the known case (the proxy forwards what it decided, SR-01; the tool's field name is unknown; the gateway forwards the agent's bytes). Checked while fixing it: a constraint of every operator refuses a missing or `null` argument, and `sum`, `calls_per` and `distinct` (with or without `#host`) refuse one as `limit_arg_invalid`, so no limit treated a missing argument as nothing to count. Tests: `crates/attenuo-policy/tests/argument_case.rs` (constraints of each operator, a `has` forbid with the name declared and undeclared, `untrusted_args` and `untrusted_outbound`, limits at two hops, `#host` and `amount`, the type check and `decimal`, `ſ` and the Kelvin sign, exact, unrelated, nested and unknown names, a reload), `an_argument_in_another_case_cannot_dodge_a_named_taint_rule`, `a_limited_argument_in_another_case_is_refused_and_not_charged`, `an_argument_in_another_case_is_refused_by_both_paths_sr133` (proxy and gateway route) and the AuthZEN fixture `evaluation-deny-argument-case.json`; each fails with the check disabled.

### SR-134: the STDIO child got the server's secrets (Low, fixed)

- **Confirmed by reproduction.** `stdio-bridge` removed `ATTENUO_ADMIN_TOKEN`, `ATTENUO_TOKEN`, `ATTENUO_CLIENT_SECRET` and `ATTENUO_DPOP_KEY` from the child's environment, the CLI's own names. The server reads other secrets from the environment: `ATTENUO_AUDIT_SINK_TOKEN`, `ATTENUO_APPROVAL_NOTIFY_SECRET` (or the variable `secret_env` names), and `ATTENUO__*` overrides, among them `ATTENUO__ADMIN__TOKEN` and `ATTENUO__AUDIT__SINK__BEARER_TOKEN`. The real binary, run with all of them set and `sh -c 'env'` as the child, passed the last four to it.
- **Attacker.** The STDIO server (third-party code started through `npx` or `uvx`, which the guide's example does), when the bridge runs in the server's environment (one container or unit environment file for both). With the admin token it has the admin API: deciding approvals, revoking leases, reading the audit log; with the notifier's secret it can sign approval notices the receiver trusts.
- **Severity.** Low. It needs the bridge started with the server's secrets in its environment, and a child running as the same user as the server can often read them another way (the server's configuration file, `/proc/<pid>/environ`). The documentation said the bridge removes "attenuo's own secrets".
- **Fix.** Every variable whose name starts with `ATTENUO_` is removed (`scrubbed_env`). Variables under names the operator chose (`[approvals.notify] secret_env` and `headers`) cannot be known and still pass; the guide says so.
- **Tests.** `every_attenuo_variable_is_scrubbed_sr134` (unit), `the_child_gets_no_attenuo_variable_sr134` (`crates/attenuo-cli/tests/stdio_bridge.rs`, runs the binary; fails before the fix listing the four variables).

### SR-135: a grandchild of the bridge outlives it (Info, open)

- **Confirmed by reproduction.** On SIGTERM the bridge closes the child's stdin, waits two seconds, and kills the child (`Child::kill`). With `sh -c 'sleep 4242 & wait'` as the child, `sleep` was reparented to init and kept running after the bridge exited 0. A launcher such as `npx` or `uvx` is the child and the real server its child; a server that exits on end of input (most do) stops, one that does not keeps running with the API keys it was given, no longer reachable through the bridge.
- **Severity.** Info: a process left behind, not a path around attenuo. The guide said the bridge "stops the bridge and the server with it".
- **Options.** (1) Start the child in its own process group (`process_group(0)`) and signal the group on stop; it needs a `kill(-pgid)` call, which is `unsafe` libc code (the crate denies `unsafe_code`) or a new dependency (`nix`, `rustix`), and it stops Ctrl-C at a terminal from reaching the child directly (the bridge passes it on as the stop). (2) Document. **Recommendation:** (1), with `rustix` if a dependency is acceptable. This branch does (2): the guide and the CLI reference say which process is killed and to start the server directly or under a supervisor that stops the whole group or cgroup.

### SR-136: claims about methods and limits on the gateway route (Info, fixed)

- **Confirmed by reading and by test.** The design note said any method but `POST`, `GET` and `DELETE` is "405 `ext_authz_method_not_allowed`"; no such code exists, and the answer is axum's 405 with no body. The HTTP reference said the same methods get 405; axum routes `HEAD` to the `GET` handler, so `HEAD` gets the lease check and 200, as `HEAD /mcp/{server}` does at the proxy (the existing test now sends it). The guide named `max_request_body_bytes` and `mcp_requests_per_minute` as shared with the proxy but not that the route, which is not under `/mcp/`, gets the other routes' 503 shape over `[limits] max_in_flight` (not `-32006` `overloaded`) and is bounded by `[limits] request_timeout_seconds`.
- **Severity.** Info: every one of these answers is non-2xx or is the proxy's own, so the gateway's behaviour is as intended; the pages were wrong or incomplete.
- **Fix.** The design note, the HTTP reference and the guide say what the code does.

## Tried and held

The gateway route:

- **The parity claim, by message shape.** The adapter answers 200 only when `screen_message` put the message in `forward` and wrote no reply, and otherwise the proxy's own body; `screen_message` is the proxy's, so every decided method, every passthrough method and the lease check are the same code. The one rewrite the proxy makes, removing the approval token from `params._meta`, is documented (the token reaches the upstream after it was used). With SR-133 fixed, no shape tried got 200 at the adapter and a refusal or a rewrite at the proxy.
- **JSON edge cases**, through `check_unambiguous` and the parse (throwaway test): a BOM, trailing bytes after the value, a comment, invalid UTF-8 and a lone surrogate escape are refused by the parse; nesting beyond 128 levels is refused (recursion limit); an escaped member name (`method`) is a duplicate after unescaping; `-0.0` and a surrogate pair read the same everywhere; `1e16` is refused as written differently. `"method\u0000"` is another name to serde_json and to Go; a parser that cuts strings at NUL was not tried. An integer between 2^53 and 2^64 passes and a JavaScript upstream reads it rounded; that is the same at the proxy, which writes the same digits.
- **`Content-Encoding`.** agentgateway includes the body before any decompression, so a compressed body is not JSON and is refused by the parse. A body that is both valid JSON and a valid encoded stream of another JSON text was not tried.
- **The secret.** Checked first after the entry lookup, as SHA-256 of the one header value compared in constant time; two values, a missing value and a malformed digest refuse. hyper trims surrounding whitespace before the value is read; header names are case-insensitive. Nothing before it reads the token, the proof or the body, so a request without it is not decided, charged or recorded, and burns no `jti`. The lookup answers `unknown_server` for a name without an entry before the secret, which tells a caller which names have entries; server names are not secret (`/mcp/{server}` answers the same).
- **`x-envoy-auth-partial-body`.** Exactly one value, exactly `false`; repeated, `False`, `true` or absent refuse. The agent cannot set it (the gateway sets it after copying the listed headers).
- **What a refused request costs.** A request refused after authentication (ambiguous body, batch, parse error) has spent its DPoP `jti` and counted against `mcp_requests_per_minute`, as at the proxy, and charged no run limit and wrote no record. A charge is made only by an allowed decision; one the gateway then does not forward is lost to the run, which fails closed. One the gateway forwards twice (a retry policy) or replays from `cache` is run twice for one charge and one approval; the guide and the threat model put both on the gateway.
- **The session.** The adapter puts no session in the `ToolCall`. Nothing in the pipeline but Cedar's `context.session_id` reads it; run limits and approvals are keyed by the run and the hop. `require_listed_tools` only knows the catalog here (documented).
- **Labelling across paths.** Results through the gateway are never seen, so they taint nothing; an agent can read untrusted output through the gateway and then call through either path without the gate a proxy-path read would have set. Documented in the design note, the guide and the threat model as the route's limit; not a finding.
- **DPoP.** `htu` is compared after `normalize_htu` (lowercase scheme and host, default port dropped, path exact), so a trailing slash or another path refuses; `htm` is the forwarded method; the replay cache is shared with the proxy, and a proof for one path's URL fails `htu` on the other. `dpop_url` comes from configuration only.
- **Configuration.** An entry without an upstream is allowed (the gateway's server need not be proxied); an upstream without an entry is not reachable on the route. Names go through `check_server_name`; a percent-encoded path segment decodes to the entry's name and still needs its secret.
- **Limits.** The route is on the main listener inside `limits::shed` and `limits::deadlines` (see SR-136 for the two answers that differ), uses `[proxy] max_request_body_bytes` (413 by `Content-Length` and while reading), and counts against `mcp_requests_per_minute` in `authenticate_request`.
- **Log lines.** The refusals log the code and a fixed detail; the server name and parse errors are Debug-formatted (SR-18); neither the secret, its digest nor the token is logged.

The STDIO bridge:

- **Ids.** Each request gets a fresh `u64` id; a child's response is delivered only to a pending id it names as a `u64` (a float, a string or a negative number matches nothing), once (a second response is unmatched), and a message with a `method` is never taken for a response. The pending entry is inserted before the write and removed by a guard on every exit.
- **`initialize`.** An error answer is not cached, so the next `initialize` is forwarded again; the cached answer is the child's result only, never the first caller's request. The shared session is documented.
- **Memory.** Pending entries are bounded by concurrent requests, which the proxy's `max_in_flight` bounds; lines from the child are held up to `--max-line-bytes`. A child that stops reading its stdin holds the write queue's 256 lines of at most `--max-request-bytes` each (1 GiB at the defaults) until it reads or exits; callers time out at `--timeout`. Bounded, and a buggy child's own denial of service.
- **Origin and `Content-Type`**, against the real binary: any `Origin` (including `null`) is 403; `text/plain` is 415; no `Content-Type` is accepted. Current browsers send `Origin` on every `POST`, cross-origin or not, so the request a page could make without `Content-Type` is refused by `Origin`. `GET` is 405.
- **Listen address**, against the real binary: `localhost:3001` is not an address (refused by the argument parser), `[::ffff:127.0.0.1]` is not loopback to `Ipv6Addr::is_loopback` (refused, fail closed), `127.1.2.3` is loopback (accepted).
- **Inherited descriptors and directory.** The child had only its three pipes and the shell's saved copy of one (`/proc/<pid>/fd`): the listening socket and the bridge's other descriptors are close-on-exec. It inherits the working directory, which holds no attenuo secret.
- **Exit paths.** The child's exit, its stdout closing, the listener failing and a signal all go through `stop_child`; `kill_on_drop` covers a panic. A bridge killed with SIGKILL leaves the child with end of input on its stdin. Grandchildren: SR-135.
- **stderr.** The child's stderr is the bridge's, unfiltered: a child can write terminal escape sequences, as it could to any terminal it runs in. The bridge's own lines print ids JSON-encoded; `--verbose` prints a child's method name as sent, which the child could equally write to stderr itself.

## Not covered

- No real agentgateway was run; the fake gateway sends what its source sends (as in #349's tests). No real Go MCP server was run behind the proxy: the Go program decoded the bodies with the struct shapes Go servers use, and the proxy test checked what reached a recording upstream.
- Decoders other than Go's `encoding/json` that ignore case (.NET with case-insensitive options, some Java configurations) were not tried; the fix refuses by shape, so it covers any of them that folds no wider than Unicode simple case folding.
- The bridge was run on Linux only; Windows was not tried.
- Fuzzing was not run; the live scripts were not run.
