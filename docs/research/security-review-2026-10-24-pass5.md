- Related: [pass 1 and 2](security-review-2026-10-22.md), [pass 3](security-review-2026-10-23.md), [pass 4](security-review-2026-10-23-pass4.md), [run limits design](../design/run-limits.md), [threat model](../spec/threat-model.md), [task board](../tasks/board.md)

## Scope and method

Everything that merged after pass 4 (`0ff8177..a02bc83`). Most of that range is the rename and work earlier passes already read; the new surface, read in full, is:

- run limits: `attenuo_core::limits` (`Limits`, `ArgLimit`, `Derive::Host`, `charges_for`, `usage_charges`, narrowing and clamping per hop), the counters in `attenuo-audit/src/budget.rs` and the SQLite and memory lease stores (`plan`, `distinct` value rows, `IMMEDIATE` charge and refund transactions, `hop_limits`), the pipeline's `budget_view`, `budget_exhausted` before Cedar, `context.budget` and `context.usage`, soft limits, argument-level taint, and the usage write elision (`PolicyEngine::tracks_usage`, `attenuo-policy/src/usage.rs`);
- approvals: the approval store, `POST`/`GET /approvals/{id}`, the operator grant on both listeners, the signed approval token (`attenuo-token/src/approval.rs`), `attenuo approval verify`, the offline verifiers and approval helpers in both SDKs;
- audit: the checkpointer-thread presyncs (`CHECKPOINT_PRESYNC_LEAD`, `nears_checkpoint`, `WalMsg::SyncWal`, the database-file sync before a locked pass);
- `attenuo budget refund`, budgets in `attenuo lease tree`, the console's budgets and usage pages, typed limits in both SDKs, `scripts/release-check.sh` and the crate, wheel, sdist and npm packaging.

The attacker was taken as each of: (a) the holder of a valid child token, (b) a compromised sub-agent with its own credentials, (c) a thief holding a copied bound token but not its key, (d) a network position between client and server, (e) an upstream MCP server, and (f) whoever controls a call's arguments through prompt injection, trying to get past or exhaust a budget. For (f) the review tried value canonicalisation for `distinct` and `calls_per` (case, Unicode, trailing dots, userinfo, ports, IDNs, IPv6 literals, URL parser differentials), integer, negative and float amounts for `sum`, list-valued arguments, refunds, charged-then-failed calls, races between charge and revoke and between the budget Cedar sees and the charge, approval-token replay across leases and calls, and growth of the value rows. Parser differentials were checked against Python's `urllib` and `httpx` in the SDK's virtual environment; the SQLite lock behaviour was checked against the system SQLite 3.45 and the bundled one.

Every finding fixed here has a regression test that fails on the base commit and passes on this branch (each was run against the unfixed code first). Findings are numbered from SR-55.

The three Medium findings are all in run limits, and all reachable by an attacker who only controls arguments (f):

- **SR-55.** Policies over `context.usage` and `context.budget` were evaluated on figures read before the call was charged, and nothing re-checked them. Two concurrent payments of one run both passed the shipped "hard" cap `run_spend_cap_2000`, and every soft rule that asks on the second call. Fixed: a per-run lock from the read to the charge.
  Measured: with 32 clients on one run, calls wait 18 to 22 ms for the lock instead of queueing for the store's write gate, throughput fell by a median of 6 to 9.5 percent (22 percent in the worst of four passes), and runs with clients of their own do not wait on each other; no change made ([performance](../design/performance.md#the-sr-55-run-lock-under-concurrent-clients-2026-10-24)).
- **SR-56.** `"derive": "host"` used the WHATWG parser, which reads `https://a.example\@b.example/` as host `a.example`; Python's `urllib` and `httpx` fetch `b.example`. A host already counted could carry calls to any other host past a `distinct` limit and past `ask_on_a_new_site`. Fixed: such values have no host.
- **SR-57.** A list argument under `calls_per`, `distinct` or a usage `destination` wrote one counter row and one charge-log row per element in the charge's `IMMEDIATE` transaction, with a quadratic scan in `plan`. One 4 MiB request could hold the store's write lock (and so every decision) for a long time and grow the store by hundreds of MB. Fixed: at most 256 values per limit and call.

The Low findings fixed here:

- the database-file sync before a locked WAL pass closed a descriptor of the database file, which drops the process's SQLite locks on it (SR-58)
- control characters and `#` in a limit's `arg`, which a child chooses freely and the CLI printed raw (SR-59)
- `GET /approvals/{id}` answered tokens of revoked or expired hops (SR-60)
- the Python sdist packed any untracked file under `sdk/python` (SR-61)

Fixed later on `fix/security-pass5-open`, after the maintainer chose each approach: a `distinct` refund that freed a value a later call used (SR-62), hostless destinations that shared one usage value (SR-63), and the default approval audience (SR-64). Each has a regression test that failed on the code before its fix (SR-64's needs the new configuration key, so it was checked by reading the startup path instead).

## Verified fixed from earlier passes

- **SR-48, SR-50.** Every commit that writes a signed checkpoint, and every `sum` charge, still syncs at `FULL` or rides a synced append; the presyncs added since are extra syncs that no commit relies on. The database-file presync had the side effect in SR-58, now fixed.
- **SR-01.** The proxy still forwards a re-encoding of the screened messages, now after it removes `params._meta["dev.attenuo/approval"]`, so the new `_meta` member gives no way to send upstream something other than what was decided.

## Checked and found sound

- **Charges.** Every charge of a call is re-checked and applied in one `IMMEDIATE` transaction, all or nothing, keyed by a decision id that may charge once. Counters use `checked_add` and refuse figures above `i64::MAX`; usage saturates instead. A `sum` amount must be a non-negative integer up to `i64::MAX`, or an integral float up to 2^53: strings, fractions, negatives (including `-1` as an integer) and larger floats are `limit_arg_invalid`, and in usage add 0 while the policy sees the raw input (where a type error is `policy_error`, not a skipped forbid). Two concurrent calls with new `distinct` values cannot both take the last slot, and value rows per `distinct` limit are bounded by its `max`. Denied calls are never charged; an allowed call that fails upstream stays charged by design, and only the admin token can refund, once per decision, audited.
- **Narrowing.** A child under a limited parent carries the same limit with a `max` no larger (or `calls` for `calls_per` and `distinct`); `sum` takes no `derive`; ancestors are charged on every call through any of their matching capabilities, so a child cannot reset a budget by delegating or by finding an unlimited capability that also covers it.
- **Order.** `budget_exhausted`, `budget_error` and `limit_arg_invalid` come before Cedar, so no policy or approval passes them, and a run out of budget is never asked anything.
- **Usage elision.** The walk of Cedar's JSON form counts `context.usage`, `context["usage"]`, `context has usage` and any other use of `context` than one named attribute, and a set that cannot be rendered counts as reading. No form found that reads usage without being counted.
- **Approval tokens.** EdDSA by `kid`, `typ` checked in both directions (a delegation token is not an approval token and the reverse), `iss`, `aud`, `exp`; bound to the run, the calling hop's lease, the canonical call hash and the hop's `cnf.jkt` exactly; consumed by id in one transaction that re-checks the hop's lease, and given back when the call is not allowed or not recorded. Replays across hops, calls, runs and keys are refused (tests in `approvals.rs`). The SDKs' offline verifiers check `alg`, `typ` and `exp` and say they prove a grant, not single use. (The TypeScript verifier would read an `exp` beyond `Date`'s range as not expired, but only the issuer can sign one.)
- **Approval decisions.** `POST /approvals/{id}` takes only an ID token of the run's originating user, used once, and refuses delegation tokens; the operator grant needs the admin token, and on the console listener `allow_write = true`.
- **Console.** Every node is built with `createElement`, `textContent` and an attribute allowlist; links may only be hash routes or `/admin/` paths; ids in API paths are percent-encoded; Trusted Types is enforced by the CSP. The budgets and usage pages add no HTML sink.
- **CLI.** `approval show` prints arguments as JSON, so control characters arrive escaped; `budget refund` requires `--reason` and the admin token.
- **Packaging.** No key, token or database file is tracked. Crates are packaged from committed files unless `ALLOW_DIRTY=1`; npm packs `dist`, `README.md` and `LICENSE` only.

## Not covered

- The evaluation suite and its frozen policies (unchanged; the test split was not opened), the bench crate and the fuzz targets (not re-run).
- Typed limits in the SDKs beyond reading them: the server refuses unknown members, so a malformed SDK limit fails closed.
- Deployments with more than one server process on one store: the SR-55 lock and the replay caches are per process, and that is not a supported deployment.
- The dry-run and AuthZEN paths beyond `budget_view` itself, the signed checkpoint export (read, not exercised), and the documentation site build.
- Upstream parsers other than Python's `urllib` and `httpx` for SR-56 (Go's `net/url`, Node's `URL`, curl): the fix refuses the characters rather than relying on any one of them.
