## Scope and method

The code merged on 2026-11-15 and 2026-11-16, in this order, and nothing else:

1. #351, `crates/attenuo-policy/src/arg_names.rs` and its call in `PolicyEngine::authorize_labelled`: the rule that a call is denied with `argument_case_mismatch` when a top-level argument name differs only in case from a name the decision reads for the tool. Its two inputs were checked for completeness: the names collected from the loaded Cedar policies, and the fold that decides "differs only in case". Then the claim that an exactly named argument is never refused by the rule outside the documented case.
2. #350, `jsonrpc::member_case_conflict` and its two callers (`screen_message` in the proxy, `check_unambiguous` in the agentgateway adapter): the same fold questions.
3. #353 and #356, `crates/attenuo-cli/src/out.rs`: whether `audit verify`, `policy test`, `policy lint` and `health` keep their documented exit status when stdout or stderr is closed.
4. #354, `crates/attenuo-server/src/admin_ui.rs`: whether the new 404 for `POST /admin/approvals/{id}` on a console listener without `allow_write` comes only after the admin bearer check and changes no state.

The attacker for 1 and 2 is an agent with a valid narrow token (A2, prompt-injected) calling an upstream that decodes arguments with Go's `encoding/json`. Each question got a unit or integration test against this repository's own crates and binary. For the fold, a Go 1.24.7 toolchain installed on the review machine (no network) was used twice: a program printed Go's `foldName` key for every Unicode scalar value, and a program decoded a few bodies into a tagged struct. The Go standard library source that ships with that toolchain (`src/encoding/json/fold.go`, `decode.go`) was read for the matching rule. Two findings, numbered from SR-137. SR-137 is fixed on this branch with tests that fail before the fix. SR-138 is accepted: the limit it describes is now written in the threat model and the module documentation.

## Findings

### SR-137: the fold kept `ß` and `ẞ` apart (Low, fixed)

- **What Go does, from its source.** `decode.go` looks a member up by exact name first, then by `foldName(key)`. Go 1.24's `fold.go` defines `foldName` like this: an ASCII letter is upper-cased, and any other rune is replaced by the smallest rune of its `unicode.SimpleFold` orbit. The comment says the result equals `bytes.EqualFold`. So two names match one field when they are equal rune by rune under Unicode simple case folding. No full case mapping is used, so `ß` never becomes `ss`, and there is no special case for Turkish `İ` or `ı`.
- **What we did.** Both folds were `to_uppercase().to_lowercase()`, which uses full case mapping. That gives `ß` the key `ss`, but `ẞ` (U+1E9E) is already upper case and lower-cases to `ß`, so its key is `ß`. Go's orbit {`ß`, `ẞ`} got two keys.
- **Confirmed by reproduction.** The Go program printed Go's key for all 1,112,063 scalar values (Unicode tables 15.0.0), and the old fold was grouped against it. Exactly one Go orbit got more than one key: {U+00DF, U+1E9E}. A second Go program decoded `{"straẞe":"x"}` and `{"STRAẞE":"x"}` into `struct { S string \`json:"straße"\` }` and filled `S` both times. Before the fix, an engine whose catalog declared `straße` allowed `{"straẞe": "x"}` (`the_capital_sharp_s_is_refused_sr137` failed with `policy_allow`), and `member_case_conflict` passed `{"straße": "a", "straẞe": "b"}` (the added body failed).
- **Attacker and effect.** An agent (A2) facing a Go upstream whose argument (or JSON-RPC member) name contains `ß`. The effect is SR-133's, only for such names: a `forbid ... when { context.input has straße && ... }` does not fire, or two members reach the upstream and the last one wins. The proxy's own envelope and `params` names are ASCII, so `Method`-style shapes were never affected.
- **Severity.** Low. It is a gap in a High fix, but it needs an argument name with `ß` that the decision reads, which few tool schemas have.
- **Fix.** Both functions now compute `to_lowercase().to_uppercase().to_lowercase()`. Lower-casing first maps `ẞ` to `ß`, and from there both take the same path to `ss`. With the same Go key table, no Go orbit now has two keys. A second check built 200,000 random strings of one to five runes, each pair drawn from the same Go orbits (Greek final and medial sigma among them, to exercise Rust's context rule for `Σ`). The old fold split 232 of these pairs and the new one splits none. Across all scalar values, the only character whose key changed is U+1E9E, and the groups the new fold joins and Go keeps apart are the same as the old fold's. What changes for clients: an argument spelled with `ẞ` where the decision knows `ß` (or the reverse) is refused.
- **Tests.** `the_fold_joins_every_name_go_joins_sr137` (unit, `arg_names.rs`) takes fifteen Go orbits or names built from them and checks each gets one key: `ß`/`ẞ`, `ſ`, Kelvin and Ångström signs, Ohm, the three sigmas (alone and at the end of a word), the `Ǆ` digraphs, `ᾳ`/`ᾼ`, the four thetas, the iotas with U+0345, micro, `ẛ` and Cyrillic `ᲀ`. It also pins the over-joins listed below and that `İd` stays apart from `id`, as in Go. `the_capital_sharp_s_is_refused_sr137` (`tests/argument_case.rs`) covers the same through the engine. A `straße`/`straẞe` body is added to `member_names_that_differ_only_in_case_are_found_sr133` (`jsonrpc.rs`). The first two failed before the fix, and so did the third on its new body.
- **What the fold still joins that Go does not.** Full case mapping joins `ß` with `ss`, `ﬁ` with `fi`, and `ΐ` with its other code point. It also joins the dotless `ı` with `i`. Each of these can only refuse more. In the per-scalar comparison there were 59 such groups. Four involve only Unicode 15 characters; the rest are characters that Rust 1.99's Unicode tables have and Go 1.24's 15.0 tables do not. If a later Go carries a newer Unicode than the Rust toolchain does, a new orbit could be missed; the threat model says so.

### SR-138: reads the collector cannot see (Info, accepted)

- **Checked by a table test.** `every_expression_form_is_collected_or_named_as_a_limit_sr138` loads one policy for each form that can read `context.input` or `context.untrusted_args` and asserts which names are collected. Collected: attribute access, `has` with an identifier or a string, index with a string (on `context.input` and on `context` itself), `context has input.path`, negated `has`, `like`, `in`, `contains`, `containsAll` and `containsAny` on a member, an extension call (`decimal`, `ip`), member against member, and `if/then/else` around the read. The same holds for templates, linked or not. For `context.untrusted_args`: `==`, `!=` (either side), `contains`, `containsAll`, `containsAny` (both ways round), `in`, and a conditional literal (`contains(if ... then "path" else "url")` collects both). `isEmpty()` names none.
- **Not collected.** Four forms are not collected. (1) A whole-record comparison (`context.input == {"path": ...}`); the threat model already named this one. (2) A read through an expression that yields the record (`(if ... then context.input else context.input) has path`, `{"r": context.input}.r has path`). (3) The same for the set (`(if ... then context.untrusted_args else []).contains("path")`). (4) A name computed at evaluation time (`context.untrusted_args.contains(principal.watched_arg)`). `a_read_through_a_conditional_is_not_collected_sr138` shows that such a policy loads and runs: it refuses `path`, and `Path` is allowed.
- **Is the rule weaker than documented?** For (1), no. A `forbid` that compares the whole record can be passed by adding any argument, with or without a case trick, so the case rule adds nothing there. For (2) to (4), yes, slightly. The module docs and the threat model said "every name a loaded policy reads under `context.input`". These forms read such a name and are not collected. The text cannot say which name (4) reads, and (2) and (3) need the collector to follow values through expressions.
- **Severity.** Info. The policy author has to write a read in an unusual form, and the name has to be absent from the tool's catalog entry and capabilities (a name declared there is known whatever the policy says).
- **Why documented rather than fixed.** Following (2) and (3) means tracking which context paths each conditional, record literal and attribute step can yield: about thirty lines in `collect`, for forms no example, guide or test policy uses. (4) cannot be closed from the text. A conservative shortcut (collect every literal near any read of the record) would refuse argument names that are really values in the policy. The threat model now lists the forms and says to write reads directly or to declare the name in the catalog. The module docs of `arg_names.rs` say the same.

## Tried and held

The argument name rule (#351):

- **Every top-level name is checked once per call, before the capability stage.** Stage 0a runs after the name check and before any other stage, on `authorize_labelled`, which every decision path calls. Checked, holds: the existing `argument_case.rs` cases, all passing on this branch.
- **An exact name is not refused outside the documented case.** `a_tool_with_no_catalog_entry_keeps_its_exact_names` uses `unknown_tools = "allow"` and a tool with no entry. With nothing of the tool's own and a policy for another tool reading `path`, these pass: `{}`, `path`, `path` with an unrelated name and a nested `Path`, and `mode` under a capability that constrains it. A name in another case than one a policy reads (`Path`, `PATH`) or one a capability constrains (`Mode`) is refused. That is the documented case: nothing of the tool's own says which spelling it uses. A capability that constrains `Path` makes `Path` the tool's own spelling, so `Path` passes and `path` is refused. With two policies reading `path` and `PATH` and nothing of the tool's own, both spellings are refused; the rule's definition says so. Under the default `unknown_tools = "deny"`, exact names are refused as `tool_not_in_catalog`, never as `argument_case_mismatch`. Checked, holds. With a catalog entry, `own_exact_names_win_over_other_tools_names` and `exact_unrelated_nested_and_unknown_names_pass` already covered the same.
- **The diagnostic** names the two names and never a value (`a_forbid_behind_has_cannot_be_dodged_by_case`). Checked, holds.

`member_case_conflict` (#350):

- **The fold.** It is the same function as SR-137's, fixed there. Go folds `ſ` onto an ASCII letter, so a JSON-RPC or MCP name that contains one is a variant: `jſonrpc` and `argumentſ` are refused. Both bodies are added to `member_names_that_differ_only_in_case_are_found_sr133`. Checked, holds.
- **The callers.** `screen_message` checks before it reads anything, the approval token included; a request gets `invalid_request`, a notification is dropped, and a batch entry is refused alone. `check_unambiguous` checks after the duplicate and number checks and before any decision. Neither path can reach the upstream with a message the check refused. Checked, holds, by reading and by the pass 19 tests, which pass here.
- **The envelope comparison.** `variant_of` compares the folded member name with the raw list. The list names are lower-case ASCII, each its own fold, so comparing with the raw list is correct. Checked, holds.

The CLI's closed output (#353, #356):

- **Exit status with the reader already gone.** `tests/closed_output.rs` closes the read end before the command starts, so the first write of any size fails. It runs each command three ways (stdout closed, stderr closed, both), in text and with `--json`. A panic would exit 101. Results: `audit verify` gives 0 for an intact chain, 2 for a broken one and 1 for a 500 (`audit_verify_keeps_its_status_when_output_is_closed`). `policy test` gives 0 for a passing case, 2 for a failing case and 1 for a missing file (`policy_test_keeps_its_status_when_output_is_closed`). `policy lint` gives 0 for a clean file and 2 for a bare action (`policy_lint_keeps_its_status_when_output_is_closed`). `health` gives 0 healthy, 0 ready, 1 not ready and 1 for nothing listening (`health_keeps_its_status_when_output_is_closed`). `audit verify --file` with `--checkpoints` gives 0 for the genuine export and 2 for the re-signed one, all three ways and in both formats (added to `audit_verify_cross_checks_shipped_checkpoints_sr21`). Checked, holds. Each status is computed before anything is printed, so the output cannot change it. A closed stdout makes every `out!` a no-op that returns `Ok`, and `err!` never returns an error.

The read-only console listener (#354):

- **Bearer first, then 415 or 404, nothing changed.** `a_decision_on_a_read_only_console_is_404_after_the_bearer_and_changes_nothing` creates a real pending approval through the proxy. On a console listener without `allow_write` it sends `grant` and `decline` to that approval and to an unknown id. No bearer gives 401, and so does the agent's own token as the bearer. With the admin bearer, a body without a JSON `Content-Type` gives 415 and a JSON decision gives 404, the same for both ids, so the answer does not show whether an approval exists. Afterwards the approval is still `pending` with no approver, no audit record was added, the operator decision counters are 0, the call is still gated by the same approval, the user can still grant it and the call then runs, and the chain verifies. Checked, holds. In `router`, `require_admin` is the outermost route layer over every API route, the 404 route included; `require_json` sits inside it. The fallback 404 for an unknown path is outside the bearer check, as before #354; it names no route and changes nothing.

## Not covered

- Go's behaviour was taken from the Go 1.24.7 source and binary on the review machine, not from Go's online documentation, which was not reachable. Other Go versions were not run. Go releases before 1.21 matched names through a different function (`foldFunc`), which was neither read nor run here; that they match the same names was assumed.
- Decoders other than Go's `encoding/json` (for example `encoding/json/v2` with case-insensitive options, .NET or Java mappers) were not tried. A decoder that folds wider than simple case folding (full folding, `ß` with `ss`) is still covered, because our fold also joins those pairs. One that applies Turkish rules (`İ` with `i`) is not.
- The CLI tests close the pipe before the command starts. Closing mid-output is `tests/broken_pipe.rs`'s and `tests/broken_pipe_stderr.rs`'s, which were not changed. Windows was not tried.
- No fuzzing was run. The injection suite was not run and none of its numbers change: the argument rule gains only `ẞ` names, and the suite uses none.
