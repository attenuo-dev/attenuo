## Where attenuo fits

As of November 2026, narrowing delegation with a check on every call is not something only attenuo does. Tenuo, an Apache-2.0 project, implements an IETF individual draft in which holders narrow agent tokens offline. Commercial products (Aembit's MCP Identity Gateway, Mintive, Descope Envoy, Kihan Inktomi) and vendor-native controls (AWS AgentCore Policy, Microsoft's announced Dynamic Permissions) cover much of the enterprise side. Research prototypes (AgentCap or AgentGate, DelegateGuard) and that draft cover the core idea; see [their notes](#open-source-projects-research-prototypes-and-drafts) and [related work](research/related-work.md#where-attenuo-sits). attenuo is an open-source, self-hosted, standards-based implementation of it: RFC 8693 token exchange, ID-JAG or OIDC at hop 0, Cedar policy over call arguments, an AuthZEN decision endpoint, chains across identity providers and services, revocation that reaches running agents, a decision log anyone can verify offline, and an [evaluation](report/attenuo-2026-11.md) that states its own limits.

Most of these are not competitors. A gateway, a policy engine, an IdP and a workload identity system each do a different job, and several of them fit together with attenuo. The last section says how.

## Reading the columns

**OAuth scopes alone.** MCP's authorization model is OAuth 2.1, and attenuo keeps it: it uses RFC 8693 token exchange and your IdP for login. What scopes lack is a slot for the human across hops, argument-level control, and a way to pull back a token mid-run. See the [FAQ](faq.md#why-not-just-use-oauth-scopes).

**Gateways.** A gateway authenticates and routes, and the MCP-aware ones now also allow or deny individual tools by name. Envoy's `ext_authz`, and AgentGateway's Envoy-compatible version of it, let the gateway ask an external authorizer per request, so a gateway can enforce what attenuo decides. attenuo speaks AuthZEN, not the `ext_authz` protocol, so an adapter would be needed and has not been built or tried. None of the open-source gateways we checked documents per-hop narrowing or argument-level rules in its own policy language. AWS's AgentCore Policy does evaluate Cedar on tool arguments, which is the closest overlap with attenuo's policy stage; see its note below.

**Policy engines.** Cedar, OPA, Cerbos and the relationship stores OpenFGA and SpiceDB answer "may this happen". attenuo uses Cedar for that step. They do not issue delegation tokens, check attenuation, hold leases or sit in the request path, and attenuo adds those.

**IdP agent features.** Okta ships ID-JAG as Cross App Access, and Auth0 for AI Agents is generally available. Microsoft Entra Agent ID is generally available and documents an on-behalf-of flow for agents; its current docs do not mention ID-JAG. These products issue and manage agent identities. We could not confirm what any of them enforce per tool call or how they revoke mid-run. attenuo accepts an ID-JAG or an OIDC ID token as the first credential in a chain, and has been run only against assertions its own tests sign.

**Workload and machine identity.** SPIFFE and SPIRE give each workload a verifiable identity. Teleport gives bots short-lived access to MCP servers with per-tool allow lists, and is beta-testing delegated identities for agents. They say who the caller is and which tools it may reach; none documents a narrowing chain from a human through several agents with argument-level checks. v0 takes an agent's `actor` from a client secret; an actor token from a SPIFFE issuer is supported but not exercised in the demo.

## Product notes

Each note says what the product does, its licence and hosting, where it overlaps or differs from attenuo, and the primary page we read on 2026-10-24.

**AgentGateway.** A Linux Foundation MCP and A2A proxy written in Rust, created by Solo.io. Apache-2.0, self-hosted. Its MCP authorization rules are CEL over the tool, prompt or resource name, the target and JWT claims; the docs state that `mcp.tool.arguments` is "not set in `mcpAuthorization` rules". It can exchange the caller's token for a backend-scoped one (RFC 8693, with an optional actor token) and call an external authorizer that is "API-compatible with the Envoy External Authorization gRPC service", optionally with the request body. Overlap: per-tool policy and a single delegation hop. Gap relative to attenuo: no documented multi-hop chain, narrowing check, argument-level rules in its own policy, leases or tamper-evident log. Whether token exchange is in the open-source build or only in Solo's enterprise edition: (unverified, 2026-10-24). Sources: [MCP authorization](https://agentgateway.dev/docs/standalone/latest/configuration/security/mcp-authz/), [external authorization](https://agentgateway.dev/docs/standalone/latest/configuration/security/external-authz/), [MCP token exchange](https://agentgateway.dev/docs/kubernetes/main/documentation/security/backend-authn/token-exchange/mcp/), [repository](https://github.com/agentgateway/agentgateway) (all checked 2026-10-24).

**Pomerium.** An identity-aware proxy that fronts MCP servers, handles upstream OAuth for them, and keeps upstream tokens away from clients. Apache-2.0 and self-hosted, with a hosted control plane (Pomerium Zero) offered separately. Its `mcp_tool` policy criterion "allows policy enforcement at the individual tool level" by matching tool names; authorization logs can include the tool parameters. Service accounts and `mcp: client` routes let agents call tools on a user's behalf. Overlap: per-tool policy, per-call logging of arguments, and agents acting for users. Gap: policy matches the tool name, not argument values; no documented chain across several agents, narrowing, run-scoped revocation or tamper evidence. Which MCP features need a paid edition: (unverified, 2026-10-24). Sources: [MCP overview](https://www.pomerium.com/docs/capabilities/mcp), [MCP reference](https://www.pomerium.com/docs/capabilities/mcp/reference), [repository](https://github.com/pomerium/pomerium) (checked 2026-10-24).

**Envoy.** A general-purpose proxy. Apache-2.0, self-hosted. `ext_authz` calls an external authorizer per request and, over gRPC, can include the body. A newer MCP filter parses MCP messages into metadata that RBAC or `ext_authz` can use, for example to match a tool name; the docs say it is "actively under development" and do not say whether arguments are exposed. Overlap: a per-call enforcement point. Gap: no delegation, attenuation or audit of its own. Sources: [ext_authz](https://envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/ext_authz_filter), [MCP filter](https://envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/mcp_filter) (checked 2026-10-24).

**Kong.** An API gateway. Its AI MCP Proxy plugin "is only available as part of our AI Gateway Enterprise offering", so the MCP part is paid even where Kong Gateway itself is self-hosted. The plugin has default and per-tool ACLs by consumer and consumer group. Gap: no documented argument checks, delegation chain or tamper-evident log. Source: [AI MCP Proxy](https://developer.konghq.com/plugins/ai-mcp-proxy/) (checked 2026-10-24).

**Amazon Bedrock AgentCore Policy.** A hosted AWS service that attaches Cedar policies to AgentCore Gateway. Policies are evaluated on every tool call, default-deny and forbid-wins, and conditions can read the call's arguments, as in `context.input.amount < 500`. Principals come from the OAuth `sub` claim or an IAM identity. Overlap: this is the same model as attenuo's policy stage, Cedar over tool-call arguments at a gateway, so attenuo should not describe that stage as unique. Gap: AWS-hosted only; the docs we read show no multi-hop delegation chain, attenuation check, leases or tamper-evident log. Source: [policy conditions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-conditions.html) (checked 2026-10-24).

**Cedar.** A policy language and evaluator from AWS. Apache-2.0. attenuo uses it for its policy stage. Source: [repository](https://github.com/cedar-policy/cedar) (checked 2026-10-24).

**OPA.** A general policy engine (Rego), CNCF graduated, Apache-2.0, self-hosted. Decision logs support masking; the docs describe no signing or chaining. Gap: no tokens, attenuation or leases; you build the enforcement point. Sources: [repository](https://github.com/open-policy-agent/opa), [decision logs](https://openpolicyagent.org/docs/management-decision-logs) (checked 2026-10-24).

**Cerbos.** A policy decision point, Apache-2.0, self-hosted, with a paid Cerbos Hub. It ships a FastMCP middleware that "enforces authorization on every tool call and resource access"; whether arguments reach the policy is not stated. Audit backends are file, Hub, Kafka and a local store, with no tamper evidence described. Overlap: per-tool-call authorization for MCP servers built on FastMCP. Gap: no delegation tokens, attenuation or leases. Sources: [repository](https://github.com/cerbos/cerbos), [FastMCP integration](https://www.cerbos.dev/ecosystem/fastmcp), [audit configuration](https://docs.cerbos.dev/cerbos/latest/configuration/audit) (checked 2026-10-24).

**OpenFGA and SpiceDB.** Relationship-based (Zanzibar-style) authorization stores, both Apache-2.0 and self-hosted. A deleted relationship applies at the next check. They are a source of facts for attenuo's plans, not a delegation layer. Sources: [OpenFGA](https://github.com/openfga/openfga), [SpiceDB](https://github.com/authzed/spicedb) (checked 2026-10-24).

**Okta Cross App Access (ID-JAG).** An admin-managed flow in which the IdP exchanges a user's ID assertion for an ID-JAG that a requesting app redeems at a resource app; connections are configured per pair of requesting app and resource app. Hosted. ID-JAG is the basis of MCP's Enterprise-Managed Authorization extension, whose specification is published under `specification/stable`. Gap: one hop, IdP-level policy at token issue, nothing per tool call. Okta's help page does not state GA or Early Access: (unverified, 2026-10-24). Sources: [Okta help](https://help.okta.com/oie/en-us/content/Topics/apps/apps-cross-app-access.htm), [MCP extension](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization) (checked 2026-10-24).

**Auth0 for AI Agents.** Hosted. Generally available since 19 November 2025, made of user authentication, Token Vault, asynchronous (CIBA) approval and fine-grained authorization for RAG. Cross App Access support in Auth0 was announced for August 2026; whether it shipped: (unverified, 2026-10-24). Overlap: human approval before an agent gets a token. Gap: no documented per-tool-call policy over arguments, multi-hop narrowing or tamper-evident log. Sources: [GA announcement](https://auth0.com/blog/auth0-for-ai-agents-generally-available/), [XAA post](https://auth0.com/blog/xaa-protocol-auth0-ai-agents.md) (checked 2026-10-24).

**Microsoft Entra Agent ID.** Hosted, part of Entra. Generally available, with some parts (blueprints, agent identity creation) still labelled Preview. Agents can act for signed-in users "using standard OAuth 2.0 On-Behalf-Of flows with agent-specific impersonation", and Conditional Access has agent-specific templates. Gap: the docs describe one OBO hop, no per-hop narrowing, nothing per tool call, and no ID-JAG. Sources: [agent OBO flow](https://learn.microsoft.com/en-us/entra/agent-id/agent-on-behalf-of-oauth-flow), [what's new](https://learn.microsoft.com/en-us/entra/agent-id/whats-new-agent-id) (checked 2026-10-24).

**Teleport (MCP Access, Machine & Workload Identity, Beams).** An access platform for infrastructure. MCP Access proxies MCP servers; roles list allowed tools as "a literal string, a glob pattern, or a regular expression", and no tools are allowed unless listed. Machine & Workload Identity gives bots short-lived identity files for MCP servers. MCP traffic is recorded as `mcp.session.*` audit events, and an example shows a denied `tools/call` with its arguments. Delegated Identity, in the Beams public beta announced 16 June 2026, gives each agent "a delegated identity with scoped privileges". Licence: source AGPLv3; Community Edition binaries are free only for companies with fewer than 100 employees and under $10M annual revenue. Overlap: per-tool allow lists, MCP audit, and delegated agent identity, the last of which comes closest to attenuo's delegation claim. Gap, as documented: no argument-level policy, no stated rule that a delegated identity is a subset of the delegator's, nothing on multi-hop chains or mid-run revocation, no tamper evidence. Delegated Identity details beyond the press release: (unverified, 2026-10-24). Sources: [MCP access controls](https://goteleport.com/docs/enroll-resources/mcp-access/rbac/), [MWI with MCP](https://goteleport.com/docs/machine-workload-identity/access-guides/mcp/), [MCP audit events](https://goteleport.com/docs/reference/audit-events/mcp-sessions/), [Beams press release](https://goteleport.com/about/newsroom/press-releases/beams-llm-proxy-delegated-identity/), [licence](https://goteleport.com/blog/teleport-community-license) (checked 2026-10-24).

**SPIFFE and SPIRE.** A workload identity standard and its runtime, CNCF graduated, Apache-2.0, self-hosted. SPIRE issues short-lived SVIDs to workloads. It says who the caller is, not whom it acts for, and can supply the `actor` identity: attenuo accepts a JWT-SVID as the exchange's `actor_token` ([ADR-0007](decisions/0007-actor-authentication.md)). Source: [repository](https://github.com/spiffe/spire) (checked 2026-10-24).

### Open-source projects, research prototypes and drafts

Added 2026-11-13. Each note says only what the project's own repository, the paper's abstract page or the draft's text says, read on that date. We have not run any of them.

**Tenuo.** An Apache-2.0 authorization layer for AI agents with a Rust core and Python and TypeScript SDKs (TypeScript in beta); version 0.3.7 on PyPI, 12 November 2026. A warrant is a signed grant that lists the tools an agent may call, constraints on their arguments, a holder key, an expiry and a maximum delegation depth. A warrant can only narrow when passed to another agent, and it is verified in the caller's process without a network call; middleware for MCP servers (the official SDK and FastMCP) checks it before a tool runs. Self-hosted deployments check signed revocation lists locally, and an optional hosted service (Tenuo Cloud) distributes them and manages warrants and approvals. Signed decision receipts are opt-in. Its site calls it the reference implementation of the IETF attenuating agent tokens draft below. Overlap: this is the closest open-source project to attenuo we found: narrowing delegation with argument constraints, checked at MCP tool servers. Difference: Tenuo derives and verifies offline, attenuo issues each hop through a server exchange (RFC 8693) that registers a lease, so revoking a lease refuses the next call of every descendant, and attenuo adds a Cedar stage and a hash-chained log with signed checkpoints. Whether Tenuo's receipts are chained, and which identity providers it starts from: not verified. Sources: [repository](https://github.com/tenuo-ai/tenuo), [PyPI](https://pypi.org/project/tenuo/), [site](https://tenuo.ai) (read 2026-11-13).

**Attenuating agent tokens (IETF draft).** `draft-niyikiza-oauth-attenuating-agent-tokens-02`, 26 October 2026, an individual Internet-Draft with no IETF endorsement. A holder derives a narrower child token offline, signed with the parent's holder key and linked by hash; tools, argument constraints (exact, range, value lists, containment, wildcard, and/or), depth and lifetime can only stay equal or narrow, and unknown constraint types deny. Each call needs a proof-of-possession JWT over the tool and arguments. It leaves revocation to deployments. Source: [datatracker](https://datatracker.ietf.org/doc/html/draft-niyikiza-oauth-attenuating-agent-tokens-02) (read 2026-11-13). attenuo's relation to it is in [related work](research/related-work.md#online-versus-offline-attenuation).

**AgentGate and AgentCap (research).** Two titles by the same two authors, A. K. Kabbinamakki Suresh and P. Gao: AgentGate, a poster at the NeurIPS 2026 workshop "The Third Workshop on Agents in the Wild", and AgentCap, arXiv:2611.00729 (31 October 2026), whose comment says it was accepted at the same non-archival workshop. Both abstracts describe an MCP wrapper that checks each tool call's declared intent against policy, including where sensitive arguments came from, short-lived budget-limited capability tokens, and session-bound child agents that can only receive equal or narrower permissions, with zero attack success on AgentDojo and InjecAgent with GPT-5.4. AgentGate's abstract adds a Dafny model with seven proven properties; AgentCap's does not mention Dafny. We cannot tell from the abstract pages whether they are one paper under two names. Research code, not a product: licence and availability not verified. Sources: [NeurIPS page](https://neurips.cc/virtual/2026/168219), [arXiv](https://arxiv.org/abs/2611.00729) (read 2026-11-13).

**DelegateGuard (research).** arXiv:2610.16005, 12 October 2026, by P. T. Tran-Truong and four co-authors. A reference monitor outside the model turns the user's authorization into capabilities that can only narrow over purpose, data labels, operations, sinks and depth, mediates every data-moving action, cascades revocation through the delegation graph, and states when attenuation alone is enough (its Proposition 1). It carries purpose and data labels on the capability, which attenuo does not. Licence and availability not verified. Source: [arXiv](https://arxiv.org/abs/2610.16005) (read 2026-11-13).

## How they fit together

- Keep your IdP and OAuth. attenuo starts from the ID token or ID-JAG it issues.
- Keep your gateway. Put attenuo behind it as the decision point over AuthZEN once someone writes the adapter, or use attenuo's own proxy where there is no gateway. A gateway's per-tool allow list and attenuo's checks can both apply.
- Your existing policy engine does not carry over: attenuo's policy stage is Cedar and nothing else today.
- Add workload identity to prove which agent is calling.
