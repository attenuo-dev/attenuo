# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, minor versions may contain breaking changes; each one is called out under **Changed** or **Removed** with a `BREAKING:` prefix.

Entries are written by hand. `git cliff --unreleased` (see `cliff.toml`) produces a draft from conventional commits that is edited into this file before a release. Security fixes always go under **Security**, with the advisory identifier once one exists.

## [Unreleased]

### Added

- Server: `ca_pem_path` on `[[idps]]` and `[[actor_trust]]` entries (#321), a PEM file of CA certificates that the entry's key fetches (OIDC discovery, the JWKS or SPIFFE bundle, the refetch on an unknown `kid`) trust in addition to the built-in web PKI roots. An IdP or a SPIRE bundle endpoint (`https_web` profile with `serving_cert_file`) whose certificate a private CA issued could not be used before: every request that needed its keys failed with `503 jwks_unavailable` (#320). The roots are added, never substituted, and belong to that entry alone (another entry, and the server's other outbound connections, keep the built-in roots); the hostname check, the `https://` rule and the refusal of redirects are unchanged, and nothing can turn verification off. A file that is missing, unreadable, empty or without a usable certificate refuses to start; the file is read once at start (no reload re-reads it). SPIRE's `https_spiffe` profile (an X.509-SVID checked against the SPIFFE bundle) is still not supported. Test-only dev-dependencies of `attenuo-server`: `rcgen` 0.13 (with `yasna`, the only crates new to `Cargo.lock`), and `rustls` and `tokio-rustls`, already in the lock through reqwest.
- Per-user windows shown to the operator (run limits phase 3 step 2, #312). `GET /admin/leases/{id}/tree` answers `user_windows`: the current hour and day windows of the run's originating user (issuer and subject) for each tool in the run's root-lease usage and each kind a loaded policy reads, `{tool, kind, start, calls, amount}` with `start` in UTC, capped at the tree's 10000 entries with `truncated`. They count every run of that user. The member is `null` for a run issued before this version, because the store had no issuer for it; the server does not guess one. The console's lease page has a **User windows** panel, and `attenuo lease tree` prints `window <kind> <start> <tool>: <calls> calls, amount <amount>` lines under the root lease. The SDKs give `LeaseTree.user_windows` (Python `LeaseUserWindows` / `LeaseUserWindow`) and `LeaseTree.userWindows` (TypeScript). Read only: same `viewer` role as the rest of the tree; no new route, no error code, no way to reset a window, and charging and decisions are unchanged. Neither the issuer nor the store's keyed user digest is shown. The free-standing `GET /admin/users/windows?issuer=&subject=` of the design note is not built. The console browser smoke test adds a rule that reads the day window and checks that the panel shows the same rows as `attenuo lease tree`.
- Server: the AuthZEN Action Search API, `POST /access/v1/search/action` (AuthZEN 1.0 section 8, #310). Given `subject`, `resource` (the MCP server, as `resource.properties.server` or a `resource.id` without `/`) and an optional `context`, it answers the `[policy] catalog` tools of that server that the pipeline would allow now, as `{"page": {"next_token", "count"}, "results": [{"name", "properties": {"server"}}]}`. It runs the stages `POST /access/v1/evaluation` runs (lease check, run labels, run-limit counters, run usage and per-user windows read from the store, argument taint, capability stage, Cedar; `Pipeline::would_allow`) and writes nothing: no audit record, no charge, no approval taken or requested, like the admin dry run and the list screen; one `info` log line per search. Same authentication as evaluation (bearer delegation token, DPoP for a bound one, or a `[[peps]]` entry with `allow_unsigned_chain`); no reasons or diagnostics in the answer, so a caller learns only what evaluating each tool would tell it. Approval-gated tools are never results, and `context.approval_token` is refused. At most `[authzen] max_batch` candidates are evaluated per page; `page.limit` above it is clamped, `page.token` / `page.next_token` page through the rest. New stable codes `invalid_page`, `invalid_search_resource` and `approval_token_not_accepted`; a foreign `page.token` is `invalid_cursor`. Discovery now publishes `search_action_endpoint`. Subject and resource search, discovery `capabilities` and `signed_metadata` stay unserved, and the error-body difference from the specification's table is written up as an open decision; reasons in [AuthZEN conformance](docs/reference/authzen.md). The SDKs and the CLI have no call for it yet.
- SDKs and CLI: calls for AuthZEN action search (#311). Python `Client.authzen_search_action(token, server, arguments=None, *, page_token=None, limit=None)` returns one `AuthzenActionPage` (`actions`, `next_token`, `None` after the last page) and `authzen_search_action_iter` follows the pages, on `AsyncClient` too; TypeScript `authzenSearchAction(token, server, args?, { pageToken?, limit? })` and `authzenSearchActionIter`. They authenticate, sign DPoP proofs, retry and refuse redirects as the evaluation calls do. `AuthzenConfiguration` gains `search_action_endpoint` / `searchActionEndpoint`. The CLI gains `attenuo authzen search --upstream NAME [--arg k=v] [--limit N] [--page-token T | --all]`, beside `authzen eval`. A server test covers action search from a `[[peps]]` entry with an unsigned chain under `[authzen] allow_unsigned_chain`: accepted for an issued chain, refused without or with wrong PEP credentials and for chains the server did not issue, with no audit record either way.
- Lean proof of the covering rule ([`proofs/lean/`](proofs/lean/README.md), [design page](docs/design/lean-proof.md)). A Lean 4 model of argument constraints, name patterns, capabilities, capability sets, `covers`, `permits`, `attenuate` and the covering check of `validate_at`, with machine-checked proofs that `covers` and `implies` are sound against `permits` and `satisfied_by`, that both are reflexive and transitive, that in a valid chain every hop permits what the last hop permits, and that a successful `attenuate` returns a set its parent covers. No `sorry`; only Lean's standard axioms. The Rust code is not verified against the model; the README maps each Lean definition to the Rust item it models and lists what the model assumes and leaves out. `scripts/check-lean.sh` builds it and checks for `sorry` and axioms (`scripts/dev.sh lean`, which skips without Lean; `just lean`; a CI job `lean` on changes under `proofs/lean/`). RFC-0001 section 2 now says that this one part of P2 has a proof on a model and the other properties are tested only. Writing the model found no case where the Rust `covers` accepts a child that permits a call its parent does not.
- Differential test of the Lean model against the Rust code (`scripts/check-lean-differential.sh`, [proofs/lean/README.md](proofs/lean/README.md#differential-test)). `proofs/lean/Attenuo/Concrete.lean` instantiates the model on concrete JSON scalars (strings, `i64`/`u64` integers, floats with `1` equal to `1.0`, booleans, `null`) and on limits holding only `calls`, with every class law proven; the Lean executable `differential` evaluates the model on cases that `crates/attenuo-core/tests/lean_differential.rs` draws with a fixed seed and answers with the Rust functions. All 31,500 cases agree (`satisfied_by`, `implies`, `pattern_matches`, pattern covering, `Capability::permits` and `covers`, `CapabilitySet::permits`, `covers` and `attenuate`). The Rust test runs in `cargo test --workspace` without Lean; the comparison runs in `scripts/dev.sh lean`, `just lean` and the CI job `lean`, which now also installs Rust and runs on changes under `crates/attenuo-core/`. The property tests' shared strategies moved to `crates/attenuo-core/tests/strategies/mod.rs`. Making the model executable showed that its assumption `asLong (ofLong n) = some n` holds in Rust only for `n` in `i64`, which is all the model uses it for.
- Console browser smoke test: the role scenarios of [ADR-0016](docs/decisions/0016-admin-operators.md) in a real browser (`tests/console/roles.test.cjs`, run by `scripts/console-smoke.sh` after the page tour). The script adds four `[[admin.operators]]` to the main server's config (viewer, operator, operator with a future `expires_at`, expired viewer; digests from `attenuo admin operator hash`) and logs in as each and as `[admin] token` in a fresh page: the header reads `admin · admin`, `<name> · <role>` or `... · expires <date>`; a viewer's revoke, grant, decline and reload buttons are disabled, an operator's revoke and approval buttons are enabled (it grants one, recorded as `urn:attenuo:admin:otto`) and its reload button is disabled; an expired token gets "That token has expired." and an unknown one "That token was refused.". Each scenario fails on any console error, failed request or CSP violation other than the refused login's 401, checks contrast in both themes and takes one screenshot at device scale factor 2. No CI change: the `console-browser` job runs the script as before.
- Server: `private_key_jwt` client authentication (RFC 7523 §2.2, [ADR-0017](docs/decisions/0017-private-key-jwt.md), proposed) for `[[agents]]` and `[[peps]]`. An entry may hold `jwks`, a public JWK Set of up to 8 keys (RSA of at least 2048 bits, P-256, Ed25519), instead of or next to `secret_sha256`; startup refuses private members, symmetric keys, other curves and algorithms, a `use` other than `sig`, and duplicate or missing `kid`s in a set of several. Every endpoint that takes client credentials (`POST /token` at hop 0 and later hops, the AuthZEN evaluation and batch endpoints) accepts `client_assertion_type` / `client_assertion`. The assertion must have `iss` = `sub` = the client id, `aud` = `[issuer] issuer` only (the token endpoint URL is not accepted), a signature by the key its `kid` names, an `exp` at most `[token] client_assertion_max_lifetime_seconds` (new, default 300) ahead with `[token] client_assertion_clock_skew_seconds` (new, default 60) of leeway, and a `jti`, which is used once and kept in the replay store across restarts. Twelve new stable codes, `client_assertion_*`; a secret and an assertion together are `multiple_client_auth`. `[token] actor_auth = "secret"` now means client credentials of either kind. The method is recorded in the exchange and intake audit arguments (`private_key_jwt`, `actor_token+private_key_jwt`); no audit format change. Secrets work as before. CLI: `attenuo key gen --client <PATH> [--kid KID]` writes a client key and prints the `jwks` line, and `token exchange --client-key PATH [--client-assertion-audience ISSUER]` authenticates with it. SDKs: Python `DpopKey.client_assertion()` and `exchange(..., client_assertion=...)`, TypeScript `DpopKey.clientAssertion()` and the `clientAssertion` exchange option.
- Server: per-operator admin credentials with roles (audit S-2, [ADR-0016](docs/decisions/0016-admin-operators.md), proposed). `[[admin.operators]]` entries hold a `name`, the SHA-256 of the operator's token (`token_sha256`) and a `role`: `viewer` (read-only admin routes, the audit export and the policy dry run included), `operator` (also revokes leases and decides approvals) or `admin` (everything). The least role of every admin route is in one table (`attenuo_server::operators::ROUTE_ROLES`); a route missing from it needs `admin`, and a test fails when a mounted route has no entry. A role too low is 403 with the new code `admin_role_insufficient`. The bearer is hashed and compared with every credential in constant time. Admin audit records and operator approvals name the operator as `urn:attenuo:admin:<name>`. `[admin] token` keeps working unchanged as the operator `admin` with role `admin` and still records `urn:attenuo:admin`, so existing records, chains and checkpoints are unaffected and no schema changes. Startup refuses bad or repeated names, the reserved name `admin`, malformed digests, two operators with one digest and an operator with the digest of `[admin] token`; off loopback, operators alone satisfy the admin-credential check and a set `[admin] token` must still be strong. Operators are read from the file at startup only and cannot be set from the environment. New `GET /admin/whoami` (`{name, role}`), in the SDKs as `AdminClient.whoami()`. The console logs in with it, shows the operator and role in its header and disables buttons the role cannot use. CLI: `attenuo admin operator new --name <n> --role <r>` prints a new 256-bit token once and the config entry, and `attenuo admin operator hash` digests a token from stdin; both run offline. The threat model gains attacker A8, the careless or malicious operator.
- Server: admin operator expiry and reload without a restart ([ADR-0016](docs/decisions/0016-admin-operators.md#update-2026-11-13-expiry-and-reload), proposed). An `[[admin.operators]]` entry may carry `expires_at` (RFC 3339 with an offset); after it its token is answered 401 with the new code `admin_credential_expired` (same `WWW-Authenticate` challenge). The digest is compared with every credential first, the expiry only on the match. An entry already expired at startup is accepted with a warning naming it; a timestamp that does not parse refuses the file. New `POST /admin/operators/reload` (role `admin`, also on the console listener with `allow_write`): re-reads only `[[admin.operators]]` from the config file the server was started with, checks it with the startup rules against the `[admin] token` in force (which is not reloaded), and swaps the set in one step; it answers the operator names `added`, `removed` and `changed` (never a digest) and appends an `admin.operators.reload` audit record naming the caller. On a refusal nothing changes: 422 `operators_invalid` (not TOML, or a rule broken), 422 `operators_no_admin` (no unexpired `admin` credential would be left), 409 `reload_unavailable` (no config file), 500 `config_unreadable`; the 422s are audited as `deny`. The caller may remove or demote itself; requests admitted before the swap complete. `GET /admin/whoami` adds `expires_at` (null when none), and the console shows `expires <date>` after the role. CLI: `attenuo admin operator new --expires-in <90d|12h|...>` / `--expires-at <RFC 3339>` writes `expires_at` into the entry, and `attenuo admin operator reload` calls the endpoint and prints the changes. SDKs: `AdminClient.operators_reload()` (Python) / `operatorsReload()` (TypeScript), and `whoami()` returns `expires_at` / `expiresAt`. Threat model A8: a stolen operator token can now be withdrawn without a restart, and can be given a lifetime.

- Client tests against a real server for a `private_key_jwt` client assertion across the retries that send it again (the part of SR-108 and SR-111 that security review pass 12 did not verify). With `[token] dpop_nonce = "required"`, a fresh client's exchange authenticated by an assertion is refused `use_dpop_nonce`, sends the same assertion again with a proof carrying the nonce, and gets a DPoP-bound token; a later exchange by the same client carries the nonce at once and takes one request. With `[limits] token_requests_per_minute = 1`, the SDKs' load retry after a real `429` sends the same assertion and is accepted; the tests restart the server in place of waiting out the minute, with the issuer key and the store of spent credentials in files, so an assertion the 429 had spent would be refused after the restart. - SDKs: the stable error code on JSON-RPC errors. `RpcError.code` is the JSON-RPC number, so the server's stable code was reachable only as `data["code"]`; Python `RpcError.stable_code` and TypeScript `RpcError.stableCode` now carry it: `data.code`, or `data.reason` for a server older than `code`, else `None` / `undefined`. `Denied` / `DeniedError` (and `ApprovalRequired`) carry it too, the same string as `reason`, and `ApiError` exposes it as an alias of `code`, so `Unauthorized`, `Unavailable` and `RateLimited` have it as well and one name reads the stable code on every error the server answers with. `Unavailable` and `RateLimited` from the proxy take `code` from `data.code` when the proxy sends one. `code` keeps its meaning on every class. The integration suites check the codes of a denial, a stream cut and an unknown session against the real server.
- ID-JAG: `[[idps]] tenant`, optional. For a multi-tenant issuer it names the one tenant the entry trusts; an ID-JAG must then carry a `tenant` claim equal to it, else `400 invalid_grant` with `missing_claim` or the new code `tenant_mismatch` (draft-ietf-oauth-identity-assertion-authz-grant-06 §4.4.1). ID tokens are not affected; unset, nothing changes.
- ID-JAG: the header `typ` `application/oauth-id-jag+jwt` is accepted as `oauth-id-jag+jwt` is (RFC 7515 §4.1.9), and an actor token whose `typ` names another token type with the `application/` prefix is refused as it is without one.

- Every error body carries a stable `code` (audit K-8), and every code is in one table, `attenuo_core::error_codes::ERROR_CODES`, with its HTTP statuses, its `error` members, its JSON-RPC numbers and whether it is also a deny `reason`. REST bodies (the AuthZEN routes and the console listener included) add `"code"`: the `error_description` sub-code when the answer has one, `error` otherwise (`{"error": "invalid_grant", "code": "audience_mismatch", ...}`). The proxy's own JSON-RPC errors add `data.code`, equal to `data.reason` where that is present; errors that had no `data` (`-32700`, `-32600`, `-32602`, `-32004`, and the `-32005` answers to an upstream reply the proxy cannot filter or label) now have `data: {"code": ...}`, with the new codes `parse_error`, `invalid_request`, `invalid_params`, `unknown_server`, `session_unknown` and `upstream_invalid_response`. An AuthZEN batch entry's `context.error.code` is the same stable code. Nothing is removed or renamed: `error`, `detail`, `error_description`, `message` and `data.reason` keep their values, and deny reasons are unchanged. `docs/reference/http-api.md` has a new "Errors" section listing every code, generated from the table; tests fail when the page, or a code named in the sources, differs from it, and debug builds check every answer against it. The CLI, the console and both SDKs read `code` (falling back to the old fields for an older server); Python `ApiError.code` and TypeScript `ApiError.code` are new, on every subclass too.

- CLI: `--admin-server URL` (environment `ATTENUO_ADMIN_SERVER`), the base URL of the admin API for a server with `[admin] listen`. Every request to `/admin/*` goes there and every other request (tokens, AuthZEN, the proxy, `health`, the JWKS) to `--server`, so admin and agent commands share one setting instead of switching `--server` per command. Unset or empty, `/admin/*` goes to `--server` as before. The choice is made by path in the CLI's HTTP client, in one place. See the [CLI reference](docs/reference/cli.md#global-options).
- SDKs: the server's load refusals (`[limits]`) are typed errors. Python `Unavailable` and TypeScript `UnavailableError` for a 503 the server sends itself (REST `temporarily_unavailable`, or the proxy's JSON-RPC `-32006`), Python `RateLimited` and TypeScript `RateLimitedError` for a 429 (REST `rate_limited`, or the proxy's `-32007`). Both are `ApiError` subclasses with `reason` (`overloaded`, `request_timeout`, `rate_limited`, `too_many_sessions`, ...), `retry_after` / `retryAfter` (the `Retry-After` header in whole seconds; `None` / undefined when it is missing or not a number) and the proxy's JSON-RPC `data`. Neither is a denial, so code that catches `Denied` / `DeniedError` or `Unauthorized` / `UnauthorizedError` does not catch them. On `/mcp/{server}` a `-32006` or `-32007` counts as the proxy's only with `Retry-After`, which the proxy never relays from an upstream. A `408` `request_timeout` stays a plain `ApiError`. New opt-in client options, off by default: Python `Client(..., max_retries=N, max_retry_delay=10.0)` (and `AsyncClient`), TypeScript `new AttenuoClient(url, { maxRetries, maxRetryDelayMs })`, retry only `overloaded` and `rate_limited` (refused before any work), waiting `Retry-After` (1 s without one) plus up to 20 % jitter, never a `Retry-After` over the cap, with new DPoP proofs on each retry; a streamed call only before its stream starts and within its deadline. `request_timeout`, denials, 401s and transport errors are never retried. `AdminClient` raises the typed errors and does not retry.
- Server: configuration overrides from the environment (audit O-5). `ATTENUO__<SECTION>__<KEY>=value`, with nested sections as more `__` segments (`ATTENUO__SERVER__LISTEN`, `ATTENUO__TELEMETRY__TRACES__SAMPLE_RATIO`), sets one scalar key over the file's value, so a container can change its addresses and paths without a file of its own. The overrides are applied to the parsed file before it becomes a config, so every startup check sees the final value. The value takes the key's type (bool, integer, float, string); section and key match without regard to case. Strict: a variable that names no key, a list, a table of names, an `[[...]]` entry or an optional section the file lacks, has an empty value or one of the wrong type, sets a key another variable sets, or names any `[dev]` key stops the server with one error that lists every such variable by name and none of their values. Setting `ATTENUO__ADMIN__TOKEN` with `ATTENUO_ADMIN_TOKEN`, or `ATTENUO__LOGGING__FORMAT` with `ATTENUO_LOG_FORMAT`, refuses to start; each older variable alone works as before, and single-underscore variables (`ATTENUO_SERVER`, `ATTENUO_TOKEN`, ...) are never read as overrides. The server logs the overridden keys and variables at `info`, never their values. `Config::from_toml_with_env` and `Config::load_with_env` take the environment as a parameter. See [environment overrides](docs/reference/config.md#environment-overrides).

It never exits 2, which Docker reserves for health checks, and needs no token (audit O-7).

### Changed

- CLI: a refusal from a REST route names the server's stable error code (#319). The message was `error: server answered <status>: <error>: <detail>`, which left out the `code` the docs, the SDKs and operators key on; it is now `<error> (<code>): <detail>`, for example `invalid_grant (replayed): this credential was already used; present a fresh one` for a second use of one ID token, `invalid_scope (scope_exceeds_parent)` for a widening exchange and `invalid_request (actor_not_permitted)` for an actor outside `may_act`. The code is left out when it is the `error` itself or the whole `detail` (`unauthorized: token_expired`, `not_found: ...`), so nothing is said twice. Exit statuses are unchanged, and so is `--json`, under which an error is still this text on stderr. A script that matched `<error>: <detail>` in the CLI's output must match the new text; `scripts/live-keycloak-smoke.sh` is updated. See [exit status](docs/reference/cli.md#exit-status).
- Server: an AuthZEN action search `page.token` is bound to the query it was issued for (AuthZEN 1.0 section 8.2, #316). Besides its offset, the token now carries truncated SHA-256 digests of the delegation chain, the resolved MCP server and the RFC 8785 canonical `context` (digests only, no request data; not a MAC, since the server recomputes them from the presented request). A token sent with another chain (another run's, for one), another server or another `context` is 400 `invalid_cursor`, whose `detail` names which differs; that code's description now reads "another list, order or query". `page.limit` is not bound and may change between pages, and a policy or catalog reload between pages is still allowed. Tokens are longer (47 characters instead of 15), and an offset-only token issued before this change is refused as `invalid_cursor`: start again from the first page (tokens are short-lived and the endpoint is unreleased). Admin list cursors (`/admin/audit`, `/admin/audit/checkpoints`, `/admin/approvals`) are unchanged. The SDK iterators and `attenuo authzen search --all` resend the same query and page as before. See [AuthZEN conformance](docs/reference/authzen.md#action-search).
- Store: schema version 4 (#312). Migration 4 adds a nullable `issuer` column to `lease_subjects`, which the server now writes with the subject for every lease it issues, so the admin lease tree can find the run's per-user windows. Existing rows keep their subject with no issuer, and nothing fills one in later. The upgrade runs once at the first start, in one transaction. After it, a build older than this one refuses the file (`SchemaTooNew`, "reads schema versions up to 3"), as for every migration: restore the backup taken before upgrading to go back.

### Security

- Scripts: the live smoke scripts keep their per-run credentials from other local users (SR-120, Info, [security review pass 15](docs/research/security-review-2026-11-14-pass15.md), #322). `scripts/live-spire-smoke.sh` made its temp dir `0755`, so the attenuo admin token, the attenuo configurations and, under `conf/`, the SPIRE join token and the bundle endpoint's private key were readable by every user on the machine for the length of the run; the dir is now `0700` (`conf/` and `bin/` stay readable for the container, which mounts them directly). `scripts/live-minio-smoke.sh` and `scripts/live-keycloak-smoke.sh` passed the MinIO root and Keycloak admin passwords on `docker run`'s command line, which `ps` shows to everyone; they now reach docker through its environment (`-e NAME`). What remains is said in each script's header: `mc` and `kcadm.sh` in the container, and curl, still take some secrets as arguments.
- Server: an `[audit.sink]` S3 `endpoint` is checked as the HTTP client parses it (SR-119, Info, [security review pass 15](docs/research/security-review-2026-11-14-pass15.md), #322). `endpoint = "http://"` passed the start-up check, and the request URL `http:///<bucket>/<key>` parses with the bucket as its host, so the PUT went to whatever host the bucket named, with its SigV4 `Authorization` header, the STS session token if any and the checkpoint, signed for an empty host; a backslash, which the parser reads as `/`, slipped a path past the check. An endpoint without a host, with a path, query or fragment as parsed, or holding a backslash, whitespace or a control character now refuses to start. Configurations that delivered are unaffected.
- CLI: text from the server, or from an upstream MCP server through the proxy, no longer reaches the terminal with control characters in it (SR-118, Low, [security review pass 15](docs/research/security-review-2026-11-14-pass15.md), #322). A refusal's `error`, `code` (shown since #319), `detail` and `decision_id`, a body that is not an error object, a JSON-RPC error message, the fields of a denial or approval, `tools`' names and descriptions and `call`'s tool text were printed raw, so an upstream could put escape sequences in a tool description that hide text from the reader (or, in some terminals, write the clipboard), or rewrite the screen through an error. - Server: a per-run rate limit on AuthZEN action search, `[limits] authzen_search_requests_per_minute`, off by default (SR-117 option 2, Info, [security review pass 14](docs/research/security-review-2026-11-14-pass14.md), [ADR-0014 update](docs/decisions/0014-request-limits.md#update-2026-11-14-a-per-run-rate-limit-on-authzen-action-search-sr-117), #315). A search writes no audit record and the caller chooses `context.input`, so a run could try argument values against the policy as fast as the server answered. The new key counts `POST /access/v1/search/action` per run (the chain's root lease, from the bearer or from a `[[peps]]` entry's issued unsigned chain) in a table of its own, so searches and `/mcp` requests do not use up each other's minute; it is counted after authentication and before any candidate is evaluated. Over it: `429` `rate_limited` with `Retry-After`, the existing code and body of the other REST rate limits; nothing is evaluated or audited, and `requests_rate_limited_total` gains the label `limit="authzen_search"`. Evaluation and batch evaluation are not counted (they are audited). Same range checks as the sibling keys (0 to 1000000). The SDKs raise the refusal as `RateLimited` / `RateLimitedError` and retry it under `max_retries` / `maxRetries`, as for the other rate limits (new unit tests for this route); the CLI reports it and does not retry (new test). The deploy guide recommends setting it. Whether a search should also write an audit record stays open (SR-117).
- Server: a newline in an AuthZEN action search's `resource.properties.server` (or `resource.id`) no longer forges log lines (SR-115, Low, [security review pass 14](docs/research/security-review-2026-11-14-pass14.md), #314). The `AuthZEN action search` line wrote the caller's server name with `Display`, so with the default text log format a token holder could add a line of its choosing, as SR-18 once allowed on the decision line; it is Debug-formatted now. Test `a_newline_in_an_action_search_server_stays_on_one_log_line_sr115`.
- Server: AuthZEN action search no longer pages over catalogued tools the token's capabilities do not name (SR-116, Info, [security review pass 14](docs/research/security-review-2026-11-14-pass14.md), #314). Such a tool could never be a result, but it took a place in the candidate list, so the pages of `page.limit` 1 (or a forged offset in `page.token`) told the caller how many tools the catalog lists for any server, which evaluating one tool at a time does not (`capability_denied` either way). The candidates are now the catalogued tools the capabilities could permit by name, the proxy's `tools/list` filter; results are unchanged, and a server the token does not name answers one empty page. Test `action_search_pages_only_over_the_tools_the_capabilities_name_sr116`. Open from the same pass: searches are neither audited nor rate-limited, so an agent can try argument values against the policy without a record (SR-117, Info, a design choice for the maintainer).
- CLI and TypeScript SDK: a `307` or `308` from the server URL no longer takes the request body to another origin (SR-112, Low, [security review pass 13](docs/research/security-review-2026-11-13-pass13.md)). Both followed redirects by default (reqwest's policy, `fetch`'s `redirect: "follow"`) and sent the body again to wherever `Location` named: on `POST /token` the agent's client secret or client assertion, its actor token, the subject token and a DPoP proof the server had not seen, which the receiver could replay; only `Authorization` was dropped. Tests `test_assertion_expiry_of_a_payload_it_cannot_use_is_none_sr113` and `test_an_exchange_with_an_unusable_assertion_exp_gets_the_servers_answer_sr113`.

- Server: with `[limits] token_unauthenticated_requests_per_minute` on, a full per-peer table no longer refuses agents that authenticate (SR-109, Info, security review pass 12, option 2; [ADR-0014 update](docs/decisions/0014-request-limits.md#update-2026-11-13-a-full-peer-table-lets-agents-authenticate-sr-109)). Requests that authenticate an agent never enter that table, so one unauthenticated `POST /token` from each of `rate_limit_max_keys` addresses within a minute made every agent's token request `429` (`table_full`) before it could authenticate, for as long as the flood went on. Now a request from an address not in a full table runs when it carries client credentials (a secret, HTTP Basic or a client assertion) and no actor token: an agent that authenticates is served and not counted, and anything else gets the same `429` as before, with the same body and `Retry-After`, counted as `table_full`. A request without client credentials, or with an actor token (whose verification may fetch its issuer's keys), from such an address is still refused before any work, so an agent that sends an actor token is still refused during such a flood. A peer in the table over its limit is still refused before the handler runs. The trade-off: on a full table an address not in it can cost one client authentication per request (a digest compare or one signature verification), bounded in concurrency by `max_in_flight`, not in rate. Tests `a_full_peer_table_still_serves_an_authenticated_agent_sr109` (replacing the test that pinned the old behaviour) and `a_full_peer_table_lets_agents_authenticate_sr109`.
- Server: a refused `private_key_jwt` client assertion no longer tells a caller without credentials which client ids have keys (SR-110, Info, security review pass 12, option 1; [ADR-0017 update](docs/decisions/0017-private-key-jwt.md#update-2026-11-13-one-answer-until-the-signature-verifies-sr-110)). An unknown id or one with a secret only was refused `client_authentication_failed`, and an id with keys `client_assertion_bad_signature` or `client_assertion_unknown_kid`, which also said whether it had one key or several. A refusal that has no key of the client to verify with (unknown id, no keys, unknown `kid`, a key of another algorithm) verifies the assertion against a fixed decoy public key of its `alg`, as the secret path compares against a dummy digest, so an unknown id costs a signature verification too. Not constant time: the decoy RSA key is 2048 bits, so an RS256 probe against a larger RSA key is slower. Tests `an_assertion_refusal_does_not_tell_which_client_ids_have_keys_sr110` and `refusals_after_the_signature_keep_their_codes_sr110`.
- Server: a `private_key_jwt` client assertion is no longer used up by a refusal the client is told to retry. `POST /token` recorded the assertion's `jti` before it checked the agent's `[limits] token_requests_per_minute`, so an agent over its limit still wrote one replay marker per request, into the store every single-use credential shares, and a client that sent the same request again after `Retry-After` was refused `client_assertion_replayed`. The limit is now checked first, without counting (SR-108, Low, [security review pass 12](docs/research/security-review-2026-11-13-pass12.md)).
- Server: with `[token] dpop_nonce = "required"`, the `use_dpop_nonce` retry of a `POST /token` that authenticates with a client assertion works. - Server: single-use credentials stay used across a restart (hop-0 hardening, step 1 of [multi-replica readiness](docs/design/multi-replica.md)). An ID token or ID-JAG, an actor token, a `(parent jti, actor)` exchange or an approver's ID token redeemed before a restart could be redeemed again after it, until it expired, because the replay cache was a map in the process. Its markers are now rows of a `used_credentials` table in the server's SQLite file (the SHA-256 of the replay key and the expiry; no issuer, subject or agent id is stored), through the new `attenuo_audit::ReplayStore` trait. The `INSERT` is the first-use decision, in one `BEGIN IMMEDIATE` transaction for every key of the request, so two simultaneous redemptions cannot both succeed, and the credential is acted on only after that commit. Each redemption deletes up to 64 expired markers; the bound (100 000) and `replay_cache_full` are unchanged. One-way database upgrade: schema migration 3 adds the table (no other table changes), and a build that reads only schema version 2 refuses the file afterwards; back it up first ([the database schema](docs/guides/deploying.md#the-database-schema)). Credentials redeemed by the old binary are not in the new table, so the upgrade restart is the last one that forgets them.

- Core: a host limit (`"derive": "host"`) no longer derives a host from a value whose host, as written, holds an IDNA deviation character (`ß`, `ς`, ZWJ, ZWNJ) or `ẞ` (U+1E9E): the `url` crate maps `faß.example` to `xn--fa-hia.example` while Python's stdlib connects to `fass.example`, so such a URL could pass as an already-seen host. The limit answers `limit_arg_invalid` and run usage counts the value as itself; punycode spellings are unchanged (SR-100, [pass 10](docs/research/security-review-2026-11-06-pass10.md)).
- Server: security review pass 10 ([report](docs/research/security-review-2026-11-06-pass10.md)). After a restart the approval notifier reads its outbox backlog half a queue at a time, so notices that arrive while a batch is delivered no longer push backlog notices out of a full queue unsent, and `/readyz` no longer reads full while the backlog drains (SR-98); the `arg_probes` doc says that arguments past `MAX_ARG_PROBES` are still fingerprinted (SR-99). SR-100 (Info, IDNA deviation characters in a derived host) and SR-101 (Info, the bare-host reading of #201 assumes a client that adds `http://`) are reported with proposed patches, not changed; SR-97 is fixed below.
- Proxy: an answer to an earlier allowed call that an upstream puts in the body of a later `POST` of the same session and run (a `ping`, a list request or another call) is now recorded and labelled before it is relayed, like an answer on the listen stream; clients route a response by its id whatever body it arrives in. A `POST` that forwards a request while calls of its scope are awaited has its answer read for this, and one the proxy cannot read is answered `502` (SR-85).
- Proxy: when the map of calls awaited for the listen stream is full, the run holding the most entries gives up its oldest, so one run can no longer push out every other run's awaited calls (SR-86).
- Server: a repeated form `scope` on `POST /token` is refused like any other repeated parameter, instead of keeping the last one (SR-88).
- Proxy: a list request (`tools/list`, `resources/list`, `resources/templates/list`, `prompts/list`) that the upstream answers with `202` and then answers in the body of a later `POST` of the same session and run is now filtered there (and screened under `[proxy] list_filter = "policy"`), like an answer in its own body. The proxy remembers list requests next to awaited calls, with the same bounds and ten-minute expiry; a `POST` that forwards a request while one of its scope is awaited has its answer read for this, and one the proxy cannot read is answered `502` (SR-87).
- Server and proxy: the `request` span of every `TraceLayer` (API router, proxy router, console listener) records the route template (`MatchedPath`, or `unmatched`) instead of the full URI, so a query string such as `/admin/audit?subject=...` no longer reaches the log at `tower_http=debug` (SR-90).
- SR-92, SR-93: a delegation run has at most 32 approvals pending at once; a further distinct gated call is still answered `-32008` (`approval_required`) and recorded, but with no approval to grant and the diagnostic `too many pending approvals for this run`, so one run can no longer flood the `[approvals.notify]` queue and push out other runs' notices (SR-92). After a restart the notifier delivers every notice left open, reading the outbox `queue_capacity` at a time as the queue empties, instead of giving up those beyond the queue's capacity without an attempt (SR-93). [Pass 9](docs/research/security-review-2026-11-06-pass9.md).

SR-91 (Medium, unbounded argument fingerprint lookups per call) and SR-92 (Low, notice queue flooding by one run) are reported with proposed patches, not changed.
- Server: SR-91: argument matching is bounded per call. A fingerprint that several arguments carry is looked up once and reported for each of them; a call whose arguments carry more than 8,000 fingerprints in all (`MAX_ARG_PROBES`) is not looked up and every unpinned argument with a fingerprint counts as untrusted with kind `unreadable`, with the diagnostic `arguments carry more than 8000 fingerprints; unpinned arguments treated as untrusted`; and both lease stores return at most 8 results per fingerprint, lowest `seq` first (`MAX_SEQS_PER_PROBE`). ### Fixed

- Telemetry: a root token minted from an IdP credential at `POST /token` is exported as `attenuo.token.root`, as documented, not `attenuo.token.exchange` (#325). The handler renamed the span by recording `otel.name`, which `tracing-opentelemetry` applies only before a span starts, and the route span had started; found by the first run with a tracing backend. Test `an_idp_credential_at_post_token_is_an_attenuo_token_root_span`.
- Checkpoint sink, S3: every PutObject carries `x-amz-sdk-checksum-algorithm: SHA256` and `x-amz-checksum-sha256` (standard base64 of the SHA-256 the sink already computes), both signed with SigV4 (#321). AWS's PutObject reference and its Object Lock guide say that an upload into a bucket with an Object Lock retention period needs `Content-MD5` or `x-amz-sdk-checksum-algorithm`, which must come with its `x-amz-checksum-<algorithm>` value; the sink sent neither, so on AWS the recommended setup (PutObject-only keys, Object Lock with a default retention) was documented to fail (#320). Run against MinIO: every upload accepted, the stored checksum is the object's SHA-256, and a wrong checksum is refused. Not run against AWS S3.
- Server: a failed key fetch (`[[idps]]` discovery or JWKS, `[[actor_trust]]` JWKS or SPIFFE bundle) is logged with its cause (#321). The WARN line said only `error sending request` (seen in #320's SPIRE run); it now walks the error's `source()` chain, for example `error sending request: client error (Connect): invalid peer certificate: UnknownIssuer`, or `certificate not valid for name "localhost"` for a hostname mismatch, so an operator can tell a private CA from a wrong host or a refused connection. reqwest's second copy of the URL is left out, and a password in a key URL's user info is masked. The HTTP answer is unchanged: `503 temporarily_unavailable` / `jwks_unavailable` with the same body, never the cause.
- Checkpoint sink, S3: an `endpoint` with an explicit default port (`http://minio:80`, `https://s3.eu-west-1.amazonaws.com:443`) or with upper-case letters in the host now works (#320). SigV4 signed the host as written while the HTTP client sends it lowercased and without the default port, so S3 answered `403 Forbidden` to every PUT and the checkpoints never left the host; found by the first run against a real MinIO. The signed host is now the one sent.
- Telemetry: `http.response.status_code`, `attenuo.chain_depth` and `attenuo.audit.seq` reach an OpenTelemetry collector as integers, not strings (#317). `tracing` handed the `u64` fields to the OpenTelemetry layer as debug strings, so a collector saw `Str(200)` where the semantic conventions have an int; found by the first run against a real collector. They are recorded as `i64` now, and the OpenTelemetry tests check the types.
- SDKs: the opt-in load retry (`max_retries`, `maxRetries`) no longer sends a `private_key_jwt` client assertion that will have expired. An exchange sends the same `client_assertion` on every retry, which the server allows since a `429 rate_limited` or `503 overloaded` leaves it unused (SR-108), but the waits (a `Retry-After` of up to a minute per retry, up to `max_retries * max_retry_delay` in all) can outlast the assertion (60 s from `DpopKey.client_assertion()` / `clientAssertion()` by default, at most `[token] client_assertion_max_lifetime_seconds`), and once past its `exp` and the server's clock skew leeway the retry was refused `client_assertion_expired` (a 401, raised; nothing looped). Now a wait that would reach the assertion's `exp` (read from the assertion, by the client's clock, without the server's leeway, which the client does not know) is not made, and the 429 or 503 is raised at once as `RateLimited` / `RateLimitedError` (`Unavailable` / `UnavailableError`); the caller mints a new assertion and calls again, or mints with a `lifetime` that covers the waits. An assertion whose `exp` cannot be read, and every other request, is retried as before. Python and TypeScript behave the same; documented in both SDK READMEs and the identity-providers guide. Python's `_retry` and TypeScript's `retryHooks` gain an injectable clock for tests.

- `[[idps]] tenant = ""` (or only spaces) is refused at startup. It looked set but could match no real ID-JAG, so every ID-JAG from that issuer was refused at request time with no hint in the configuration.

- Approvals: a position in the SQLite lease store is never given twice, so `GET /admin/approvals` paging cannot meet a new approval below a cursor a client holds. The position was the implicit `rowid`, which SQLite reuses once the newest rows are deleted, and approvals are deleted: `remove_approval` drops the newest one when its request cannot be written to the audit log, and the run-state prune (`[leases] run_state_retention_seconds`) deletes old ones, so an emptied table started again at 1; `VACUUM` could also renumber it. Schema migration 2 rebuilds `approvals` with `position INTEGER PRIMARY KEY AUTOINCREMENT` from each row's rowid, keeping every row, its order, `approvals_call_idx` and the uniqueness of `id`. A file at version 2 is refused by a build that reads only version 1 (no downgrade; back the file up first). A position freed before the migration ran can still be given once more. The memory store's counter was already never lowered.
- Server: approval notices of one approval no longer go out of order after a restart. A notice stored while the restart's outbox backlog was still being delivered was queued at once and could overtake that backlog, so a webhook could get `approval.expired` (or `approval.decided`) before the `approval.pending` of the same approval; the integration test for an approval that expired while the server was down failed about one run in a hundred for that reason. Such a notice now waits in the outbox and is read behind every row stored before it, until the backlog is through; then notices are queued as they are stored again. Each notice is still delivered once (the outbox is read or the notice is queued, never both).
- Server: a graceful stop now lets go of the database before `serve` returns, so the next server on the same file (started by a supervisor, or in the same process by an embedder) no longer meets the single-writer fence of the one that just stopped. Before, `serve` aborted the checkpoint timer, lease maintenance and the console and metrics listeners without waiting for them, and each of these held the server state, and with it the fence, until the runtime got round to dropping it. They now stop between ticks or drain like the main listener, and are awaited. `serve` returns once the state is dropped and logs `single-writer fence released`; only a request still running after the 10 s drain can keep the database fenced, which is logged. New `attenuo_server::run` (what `serve` runs after binding, with the caller's shutdown future), `AppState::released` and `RELEASE_GRACE`. Two `approval_notifier` tests that failed about one run in three with "another process holds ...audit.sqlite.lock" now stop their server through `run`, as do the `dpop` tests, whose helper used to retry the lock until it was free.
- Server: a query string, path parameter or body that axum cannot read is answered in the JSON error shape instead of axum's `text/plain` (audit K-10, confirmed by test before the fix). A query parameter that does not parse (`/admin/audit?from=abc`, `?preview=maybe`) or a path parameter that does not parse or is not UTF-8 (`/admin/audit/entries/abc`, `/approvals/%FF`) is 400 `invalid_request`, and a body over 2 MiB on any REST or AuthZEN route is 413 `request_too_large` (it was 413 `text/plain`). `detail` names the parameter and its type and no longer quotes the value sent. The console listener answers the same way. At the MCP proxy a server name that is not UTF-8 is 400 with JSON-RPC `-32600`. Statuses are unchanged. Malformed JSON bodies already answered `invalid_request` and still do. Adds `serde_path_to_error` 0.1 and `form_urlencoded` 1 as direct dependencies of `attenuo-server`; both were already in the lock.
- Audit log: `GET /admin/audit/verify`, the export, the filtered search and every other query of a file-backed log no longer hold the connection lock appends commit on (audit finding A-1). They run on a separate read-only WAL connection, and verify walks a snapshot (the newest seq and the checkpoints read together) in pages of 1,000 rows, so an append during the walk cannot show as a break. Measured with the new `audit_reads` bench on a 50,000-entry log: verifies run back to back held one append for 27 and 95 s, and a filtered search pushed append p99 to 0.5 to 0.7 s; after the change append p99 stays at 0.3 to 4 ms in every case ([performance](docs/design/performance.md#long-audit-reads-and-the-append-path-2026-11-12)).
- Policy reload compiles the new policy set on the blocking pool with no lock held and swaps the engine in whole (A-7), and each decision, dry run and list screen uses one snapshot of the engine for all its stages, so a reload can no longer mix two policy sets in one decision (A-8). `PolicyEngine::with_policies_reloaded` builds the new engine; `Pipeline::evaluate_policy`, `budget_view`, `budget_view_from`, `add_user_windows` and `arg_taint` take the engine as an argument, and `Pipeline::policy()` returns the new `SharedPolicy`.
- `/readyz` is not ready while audit appends fail (A-12): a new `checks.audit_append` is `"error"` after a failed append until the next one succeeds, or for at most 30 s when nothing appends after it. A full disk used to leave the server "ready" while it denied every call. No write probe is made.
- Unknown keys in nested config tables are refused at start-up, as the config reference says: `[[upstreams]]` entries, `[policy.catalog.<server>.<tool>]` tables and the JSON of `catalog_path` (also in `attenuo policy test` and `lint`), and the table form of `[[root_grants]] capabilities`. A misspelt key used to be ignored, and two cases failed open: `sensitve = true` left the tool not sensitive, `constraint = {...}` left the grant unconstrained. A config with such a key no longer loads; the error names the key. A capability object in the body of the dev root mint (`POST /admin/root-token`) is read the same strict way, as the rest of that body already was. The token format is unchanged: a delegation token's capabilities still ignore unknown members.
- `POST /approvals/{id}` and `GET /approvals/{id}` no longer return the ID-token verifier's message in the `detail` of a 401 `invalid_token`; `detail` is now the stable sub-code, the same as `error_description`, and the message is logged at debug level (SR-17).
- `attenuo` exits 1, not 2, on a command line it cannot parse (an unknown flag, a missing argument, a bad value), so 2 means only "the answer was no". `--help` and `--version` still exit 0.
- `POST /token` no longer returns the verifier's message in the `detail` of a refused IdP credential (400 `invalid_grant`) or a refused `actor_token` (400 `invalid_request`), which named the expected audience, the issuer, the client ids or the SPIFFE id; `detail` is now the stable sub-code, the same as `error_description` (`audience_mismatch`, `unknown_kid`, `actor_token_audience_mismatch`, ...), and the message is logged at debug level (SR-17).
- A float `exp`, `iat`, `nbf` or `auth_time` in an ID token, ID-JAG or actor token is rounded down to the whole second, and one outside the `i64` range of seconds (`1e300`) is treated as absent, so a required claim is refused with `missing_claim`; before, it saturated, and an `exp` of `1e300` never expired. The Cedar translation and the declared-type check read floats through one checked conversion (a whole number of magnitude at most 922337203685477 is a `Long`; unchanged). `attenuo-server` and `attenuo-policy` warn on `cast_possible_truncation`, `cast_sign_loss` and `cast_possible_wrap`.
- Run limits: a `"derive": "host"` limit (`calls_per`, `distinct`) and a catalog `destination = "url#host"` read a URL with no scheme as `http://` followed by the value, so a bare host such as `www.example.com/x` or `localhost:8080` counts as its host instead of being refused with `limit_arg_invalid` (under a limit) or counted as a raw string (in run usage). The injection suite's host entities are unchanged.
- Python and TypeScript SDKs: the retry after a `use_dpop_nonce` refusal no longer fails now and then with `httpx.RemoteProtocolError` (Python) or `TypeError: fetch failed` / "other side closed" (TypeScript). The Python SDK's `NonceCache.update` now shuts the refused connection's socket down so the pool opens a new one (`attenuo.dpop.drop_connection`); the TypeScript SDK sends the retry once more, with the same headers and so the same DPoP proof, when `fetch` fails at the network level (`resendOnce`). - Server: an HTTP/1 answer sent before the request body was read to its end (401 for a missing or bad token on `/mcp/{server}`, `use_dpop_nonce` included, 413 for a declared body over the limit, 401 from the admin routes and the console) carries `Connection: close`. The reason is taken from an HTTP 401 answer only: a `-32001` inside a 200 answer can be an upstream's own error and keeps `reason == "unauthorized"`. The READMEs said a proof-less `call_tool` was `Unauthorized` with `error == "dpop_required"`, which held only for REST routes; they now say `reason == "dpop_required"`, which holds for both, and the integration tests assert it.
- Python and TypeScript SDKs: transport failures no longer escape the SDK's error hierarchy: an `httpx` transport error, or a `fetch` `TypeError` or timeout of the client's own `timeoutMs`, is raised as `TransportError`, also while a body or a stream is read. When an `/admin/*` request gets a 404 without an error code (the main listener's answer to a path it does not serve) and neither `--admin-server` nor `ATTENUO_ADMIN_SERVER` was given, a second line says the server may serve its admin API on a separate listener and to pass `--admin-server URL` (or set `ATTENUO_ADMIN_SERVER`). ## [0.1.0] - Unreleased

Prepared on 2026-10-24 and not yet tagged. The date is set when `v0.1.0` is tagged.

### Highlights

Attenuo is an authorization layer for AI agents that call tools over MCP. A user's authority reaches an agent, and every sub-agent it hands work to, as a signed delegation chain that can only narrow at each hop (RFC 8693 token exchange), and an enforcing proxy checks every `tools/call` against that chain and Cedar policies before anything reaches the upstream server.

0.1.0 is the first release. It ships one server process with token exchange, an AuthZEN decision endpoint, the MCP proxy and a hash-chained audit log with signed checkpoints. Leases revoke a delegation and everything below it, including calls and streams already in flight. Tokens can be bound to the agent's key with DPoP. Output labelling marks untrusted tool results and sends later risky calls to an operator for approval. Run limits cap call counts, amounts and destinations per delegation. The `attenuo` CLI, an admin console and Python and TypeScript SDKs cover the same API.

The injection-suite figures in the docs come from synthetic, model-free cases written alongside the policies they test, so they show what the mechanisms can block, not how a real agent under attack fares.
### Added
- SDKs: streamed `tools/call` answers. Python `Client.call_tool_stream(...)` (an iterator) and `AsyncClient.call_tool_stream(...)` (an async iterator), TypeScript `AttenuoClient.callToolStream(...)` (an `AsyncIterable`), with the arguments of `call_tool` / `callTool`, yield a `StreamEvent` for each JSON-RPC message as it arrives: notifications such as `notifications/progress`, server requests, then the response, whose event carries the `ToolResult` (`result`, `is_final` / `isFinal`). Each event keeps the SSE last event id (`last_event_id` / `lastEventId`) and the proxy's decision id. A denial raises `Denied` / `DeniedError` before anything is yielded. When the proxy cuts the stream for a lease or token reason, its final `-32001` event (`id: null`) raises the same `Denied` / `DeniedError` with `reason` (`lease_revoked`, `lease_expired`, `lease_unknown`, `token_expired`) and the `decision_id` of the `stream.end` record. A plain JSON answer is yielded as the one final event. An event over `max_event_bytes` / `maxEventBytes` (default 16 MiB, the proxy's `max_upstream_body_bytes` default; `DEFAULT_MAX_EVENT_BYTES`) is refused. The request is the one `call_tool` sends (MCP `Accept`, session id, approval token, DPoP proof with one nonce retry); `call_tool` and `callTool` are unchanged. In TypeScript the client's `timeoutMs` restarts on every read of a stream and `signal` aborts it. `fake_mcp` takes `--sse` (answers streamed as a `notifications/message` event, then the response with an `id:`), and with it a `tools/call` argument `hold_ms` delays the response, which both SDK integration suites use to have the real proxy cut a stream on revocation.
- SDKs: an optional total deadline on a streamed call (SR-82, part 2). Python `call_tool_stream(..., deadline=)` (seconds) and TypeScript `callToolStream(..., { deadlineMs })` bound the whole call from the request's start, so an upstream that sends only keep-alive comments, which restart the idle timer, can no longer hold a call open with no event; on expiry the stream ends with `AttenuoError` naming the deadline and the response is closed (the fetch aborted in TypeScript). A non-positive deadline is refused at the call (`ValueError` / `RangeError`). Default unchanged: no deadline.
- AuthZEN discovery reference (OpenID AuthZEN 1.0 section 9): the [AuthZEN conformance](docs/reference/authzen.md#discovery) page and the HTTP API reference now say what `GET /.well-known/authzen-configuration` holds (`policy_decision_point`, `access_evaluation_endpoint`, `access_evaluations_endpoint`; no search endpoints, `capabilities` or `signed_metadata`) and why it is public: no credential is needed and an `Authorization` header is ignored, since the document holds only the base URL and endpoint paths. The `metadata.json` fixture now also checks `Content-Type: application/json` and that an invalid bearer gets the same document. The endpoint itself is unchanged.
- AuthZEN batch semantics (OpenID AuthZEN 1.0 section 7.1.2.1): `POST /access/v1/evaluations` accepts `options.evaluations_semantic` of `deny_on_first_deny` and `permit_on_first_permit` besides `execute_all`; both were 400 `invalid_request`. Entries are decided in order and the batch stops after the first deny (an entry that cannot be evaluated counts as one) or the first permit. As in the specification's examples, the answer holds only the entries that were decided, so `evaluations` is shorter than the request; the entries after the stop are not decided, charged or audited. Another value, or one that is not a string, is still 400 (it used to be ignored when not a string). Fixtures `evaluations-deny-on-first-deny.json` and `evaluations-permit-on-first-permit.json`, and the test `stopped_batch_audits_only_what_it_ran`; see [batch semantics](docs/reference/authzen.md#batch-semantics).
- `[proxy] record_window_seconds` (default 60, 1 to 3600) and `record_window_max_keys` (default 10000, 100 to 1000000) set the window that bounds repeated audit records of one condition, and how many (delegation chain, tool, reason) windows are kept open. One pair covers both bounded kinds: the `stream.end` records of `GET` listen streams and the lease refusals of requests without a per-call decision (`initialize`, the list methods, notifications, `GET`, `DELETE`). Both were constants (`STREAM_END_RECORD_WINDOW`, `LEASE_REFUSAL_RECORD_WINDOW`, `RECORD_WINDOW_MAX_KEYS`), now `attenuo_proxy::records::DEFAULT_RECORD_WINDOW` and `DEFAULT_RECORD_WINDOW_MAX_KEYS`, and the defaults are unchanged. - Numeric `range` argument constraint (RFC-0001 section 3): `{"op": "range", "value": {"min": 0, "max": 2000}}`, both bounds inclusive, either one (not both) optional, `min <= max`. An argument satisfies it when it is a Cedar `long` in the bounds (a JSON integer, or a float with no fractional part such as `5.0`); a fraction, a numeric string or a number beyond `i64` does not. Checked in the capability stage, before the catalog type check and Cedar, so a call outside the range is `capability_denied` whatever the policy says. A child's range must sit inside its parent's, so an exchange that raises `max`, lowers `min` or drops a bound is refused as `exchange_widening`; `equals` and `one_of` children are covered when every value is an integer in the range, and a range covers an `equals` or `one_of` only when it holds a single integer. A malformed range (no bound, inverted, a non-integer bound, a member other than `min` and `max`, a repeated member) is refused on deserialization, in tokens, exchange requests, `--cap` and policy test files alike. API: `ArgConstraint::Range`, `ArgConstraint::range`, `RangeError`, `attenuo_core::as_long`. CLI: `--cap` takes the JSON form and `token inspect` prints `0 <= amount <= 2000`. SDKs: Python `Range(min, max)`, TypeScript `range({ min, max })` and the `RangeBounds` type. Time-range constraints stay deferred; RFC-0001 section 3.1 says why.

### Changed
- SDKs: a streamed call reads the proxy's stream-end event (`id: null`, `-32001`) as a cut only when `data.reason` is one the proxy sends (`token_expired`, `lease_revoked`, `lease_expired`, `lease_unknown`, `lease_error`, `unauthorized`) and `data.decision_id` is absent or a UUID; anything else of that shape now raises `RpcError` (code `-32001`) instead of `Denied` / `DeniedError`. Belt-and-braces: the proxy already rewrites any upstream message of that shape to `-32005` `upstream_stream_end_shape`.
- `POST /admin/budgets/refund` tells a pruned charge from no charge. When the charge log has no entry for the decision, the server reads its audit record (the audit log keeps every decision): a record carrying `budget` (an allowed call that charged run-limit counters) answers 410 with the new error code `charge_pruned`, naming the decision and `[leases] run_state_retention_seconds`; a decision that charged nothing stays 404 `not_found` with the detail "decision `<id>` charged nothing", one that charged run usage only says so (run usage also goes when the run is revoked), and an id no record has is 404 "unknown decision". Before, all of these were the same 404. Nothing new is audited for a refused refund. `attenuo budget refund` prints the server's 404 detail (exit 2, as before) and, for 410, "the charge of decision <id> was pruned ...; it can no longer be refunded" with exit status 4. The SDKs have no refund helper, so nothing changes there ([HTTP API](docs/reference/http-api.md#budget-refund)).
- Lease retention passes are bounded for wide runs. A pass of `LeaseStore::prune_leases` now touches at most `[leases] maintenance_batch_rows` lease rows, counting the leases its window looks at, the leases it reads to decide a run (new `LeasePrune::walked`) and the leases it deletes; before, it also read and deleted the whole subtree of every prunable run in its window in one transaction, so one run of 50,000 leases held the store for about 0.3 s. A run that does not fit is carried over: read to the end first, then deleted children before parents and the root last, over several passes. Which runs go is unchanged (whole runs, once every lease ended longer ago than `retention_seconds`), and so is what a token of such a run gets: refused all along, as `lease_unknown` once its rows are gone. A renewal or re-registration of a lease of a run being deleted is refused as unknown; a revocation, renewal or new child while the run is still being read makes the pass decide it again later. A pass of 1,000 rows now deletes about 400 leases of two-lease runs instead of 1,000, so a backlog takes more passes.
- The admin dry run (`POST /admin/policies/evaluate`) refuses an `approval` block with a member other than `by` (400 `invalid_request`, "`approval`: unknown member `approved_by`"), where it used to ignore it, so a misspelt member no longer quietly means "no approval" next to a valid `by`. A block without `by`, or with `by: null`, says that `by` is required; `session` now names an unknown member before a malformed known one, as `usage` and `budget` already did. The SDKs send only `by` and are unaffected.
- Lease refusals of requests without a per-call decision (`initialize`, `ping`, the list methods, `resources/unsubscribe`, `logging/setLevel`, notifications and client replies, `GET`, `DELETE`) are bounded like listen-stream ends: the first refusal per delegation chain (by digest), tool and reason in 60 s (`attenuo_proxy::records::LEASE_REFUSAL_RECORD_WINDOW`) is a `deny` record, and a retry within the window is still a 401 with the same reason but writes no record. Its `X-Attenuo-Decision-Id` and `data.decision_id` name the window's first record (both are left out in the moment before a concurrent first record is written), and it is counted in `audit_records_suppressed_total{tool,reason}`, whose `tool` label now also takes these eleven fixed names (a series appears once counted). Before, a client retrying on a revoked, expired or unknown lease added one record per request until its token expired. Refused token exchanges and renewals and `tools/call` denials are recorded every time, as before. ### Security

- Fuzzing round 2, FZ2-2 (low): `"derive": "host"` and `destination = "url#host"` took the host of any URL scheme, and a non-special scheme (`ssh://`, `git://`) has an opaque host that WHATWG neither percent-decodes nor maps through IDNA, so `ssh://a.ex%61mple/` and `ssh://a.example/` counted as two hosts (a `calls_per` budget each, a fresh `destination_seen`). Only `http`, `https`, `ws`, `wss`, `ftp` and `file` URLs have a host now; any other URL has none, so a limit refuses it with `limit_arg_invalid` and run usage counts it raw. A behaviour change for tools that take `ssh://` URLs under `#host`.
- Fuzzing round 2, FZ2-1 (low): `"derive": "host"` stripped one trailing dot, so `https://a.example../` counted as host `a.example.`, apart from `a.example`, and got a `calls_per` budget of its own (and a fresh `destination_seen` in run usage). Every trailing dot is stripped now, and a host left with an IPv4 spelling (`0x7f.1..`) is parsed again so it counts as the address.
- Fuzzing round 2, FZ2-3 and FZ2-4 (low): a refund of run usage subtracted what the decision logged, although a usage counter saturates at `MAX_LIMIT`, so after a call with an amount near `MAX_LIMIT` a refund could leave `context.usage.amount` below what the remaining calls had charged; a usage counter is now recomputed from the unrefunded charges. The SQLite refund also no longer sums a decision's rows with an integer `SUM` that could overflow and fail the refund.
- SR-55 (medium): concurrent calls of one run could all pass a policy over `context.usage` or `context.budget` (the shipped `run_spend_cap_2000`, every ask-on-repeat rule), because each read the figures before any was charged; a per-run lock now covers the read through the charge.
- SR-56 (medium): a `"derive": "host"` limit or `destination = "url#host"` counted `https://a.example\@b.example/` as `a.example`, which Python's `urllib` and `httpx` fetch as `b.example`; a URL with a backslash, whitespace or a control character now has no host (`limit_arg_invalid` under a limit).
- SR-57 (medium): a list argument under `calls_per`, `distinct` or a usage `destination` wrote two rows per element while holding the store's write lock; a call may now count at most 256 values per limit (more is `limit_arg_invalid`; in usage the list is one destination).
- SR-58 (low): the WAL checkpointer's database-file sync closed a descriptor of the file, which drops the process's SQLite locks, so another process could delete the WAL of the live store; the descriptor is now kept open.
- SR-59 (low): a limit's `arg` may not contain control characters or `#`, and `attenuo lease tree` escapes it, so a sub-agent cannot write terminal escapes into an operator's screen.
- SR-60 (low): `GET /approvals/{id}` answers 404 to a delegation token whose lease was revoked or has expired.
- SR-61 (low): the Python sdist lists its files, and `scripts/release-check.sh` refuses untracked files under `sdk/python`, so a stray local file is not published.
- SR-62 (low): refunding the decision that first used a `distinct` value made the value new again although a later, unrefunded call had also used it. A call that uses a seen value now logs a zero-amount charge row, and a refund frees a value only when no other unrefunded decision logged it, in both lease stores. A decision whose values were all seen can now be refunded (once).
- SR-63 (low): in run usage every value with no host (`destination = "url#host"`) counted as one destination, `null`, so after one such fetch `ask_on_a_new_site` never asked for another. A hostless value now counts as itself, wrapped as `{"raw": value}` so it never equals a host.
- SR-64 (low): with `[approvals] client_id` unset, an ID token for the root agent's own OAuth client approves its gated calls. When a loaded policy carries `@obligation("approval")` and `client_id` is unset, the server now logs a warning at startup and after each policy reload, and refuses to start when `[server] listen` is not loopback.
- SR-21: signed audit checkpoints can leave the host as soon as they are signed. New `[audit.sink]` with `kind = "webhook"` (`POST`, optional bearer token, any 2xx), `"file"` (append one JSON line and `fsync`, for a file on another mount that your own agent ships) or `"s3"` (`PUT` to an S3-compatible bucket, AWS Signature Version 4 implemented in the server on `ring`; no new dependency). Each delivery is the canonical JSON object `attenuo-shipped-checkpoint-v1`: the checkpoint, its `kid` and `signature`, `public_url` and `checkpoint_sha256`. The log's hook only queues; a background thread delivers in order with retries and jittered exponential backoff (`initial_backoff_ms`, `max_backoff_seconds`). The queue is bounded (`queue_capacity`, default 1024) and drops the oldest when full. New metrics `attenuo_audit_sink_{delivered,failures,dropped}_total`, `attenuo_audit_sink_queue_depth`, `attenuo_audit_sink_oldest_undelivered_timestamp_seconds`; `/readyz` adds `degraded` and `checks.checkpoint_sink` when a sink is configured (degraded when the queue is full or lags more than `max_lag_seconds`; 503 only with `fail_readiness = true`). `attenuo audit verify --file <export> --checkpoints <shipped.jsonl>` cross-checks an export against the shipped copies and exits 2 for a checkpoint signed again after shipping (same seq, different hash or signature), one deleted from the export, an entry that no longer hashes to the shipped `head_hash`, two different shipped checkpoints for one seq, or a shipped copy that does not verify. New `attenuo_audit::{ShippedCheckpoint, parse_shipped, cross_check, checkpoint_sha256}`.
- SR-40: a DPoP exchange sign-off (`subject_token_dpop`) is consent to one delegation only. BREAKING: the sign-off must carry `child_jkt` (the thumbprint of the key in the exchange's `DPoP` header) and `child_actor` (the request's `actor`), or the exchange is 401 `invalid_dpop_proof`; a plain proof by the parent's key is no longer accepted. The parent's holder can now make the sign-off in its own process and hand over only the result: `attenuo token sign-off --dpop-key parent.jwk --child-jkt <jkt> --actor <agent>` and `token exchange --subject-token-dpop-file`, `DpopKey.sign_off` and `exchange(..., subject_token_dpop=...)` in Python, `DpopKey.signOff` and `subjectTokenDpop` in TypeScript. `subject_dpop_key` / `subjectDpopKey` / `--subject-dpop-key` still work for a process that holds both keys.
- SR-41: a DPoP proof's `jti` is recorded only after the proof matched the token's key, so proofs by a wrong key (a thief holding a bound token) can no longer fill `[token] dpop_replay_capacity` and turn every bound request into a 503. An exchange's header proof and sign-off are recorded together or not at all.
- SR-42: without `[server] public_url`, DPoP `htu` is checked against `http://<Host>` only for a loopback `Host`; any other `Host` is treated as `localhost`, so a proof made for another server cannot be replayed here by sending its host name.

- SR-44: an exchange's replay check and its `actor_token` are consumed together, so an exchange refused as a replay no longer burns the caller's actor token.
- SR-45: `POST /token` refuses the reserved agent id `attenuo` as the exchange `actor` (400 `invalid_request`, `reserved_agent`), whether it came from `require_actor_auth = false` or an `[[actor_trust]]` mapping.
- SR-46: the verified-token cache no longer stores tokens over 16 KiB (they are verified on every request instead), so its memory is bounded by bytes as well as by count.
- SR-47: the proxy answers a full DPoP replay cache with HTTP 503 (JSON-RPC `-32006`, `data.reason` `dpop_replay_cache_full`, `Retry-After`) instead of 401 `invalid_dpop_proof`, so clients retry instead of treating their key as bad.
- SR-48: the RFC (P4) and the threat model now say that `[audit] durability = "normal"` can lose the newest records, including those of forwarded calls, on a power failure.
- SR-49: one principal (the chain's root lease) can hold at most `[proxy] max_sessions_per_principal` (default 64) live `Mcp-Session-Id` bindings; one more gets HTTP 429, JSON-RPC `-32007` (new, `attenuo_proxy::jsonrpc::CODE_TOO_MANY`), `data.reason` `too_many_sessions`, `Retry-After: 30`, and other users keep opening sessions. Before, one user could fill all `max_sessions` slots and leave everyone else with 503 until the TTL. - SR-53: the LangChain and Claude Agent SDK examples count a `-32003` as attenuo's denial only when its `data.decision_id` is in the proxy's `X-Attenuo-Decision-Id` response header (collected with an `httpx` response hook on the `mcp` client), as the SDKs do since SR-32; any other `-32003` is shown as an upstream error. The Claude Agent SDK example's README notes that its live mode cannot make this check.
- SR-20: everything attenuo hashes or signs as JSON is RFC 8785 (JCS) canonical JSON (new `attenuo_core::jcs`): members sorted by UTF-16 code units, the RFC's string escaping, numbers as ECMAScript writes the double; integers beyond ±2^53 keep all their digits instead of being rounded. Before, the bytes were `serde_json` output, and `serde_json`'s `preserve_order` feature (switched on workspace-wide by a dependency) kept nested objects in insertion order, so a verifier built without it, or in another language, computed different bytes. This covers the chain digest (and the lease bindings that the AuthZEN `chain_not_issued` check compares), the argument digest, `ou_sig`, audit entry hashes and checkpoint signatures. Argument constraints now compare JSON values the same way (`1` equals `1.0`, member order ignored) in `Eq`, `Ord`, `satisfied_by` and `implies`, so equality agrees with ordering and with the digest. `serde_json` parses with `float_roundtrip`. BREAKING: `ou_sig` is version 3 (context `attenuo-ou-v3`, claim `ou_sig_v: 3`); v2 tokens are refused with `UnsupportedOuSig(2)` and must be re-issued from the root. BREAKING: the audit entry hash is SHA-256 over `JCS(["attenuo-audit-entry-v2", seq, prev_hash, record])` (`attenuo_audit::ENTRY_HASH_VERSION`), `record_json` is stored canonically, and the construction is recorded in a new `audit_meta` table; an audit database written by an earlier build is refused at startup with an error that says to move it aside and start a new log. There is no migration: no logs were released in the old form. BREAKING: exports are format `attenuo-audit-export-v2` with canonical lines; `v1` exports are refused with a message that says why. The checkpoint signing input is unchanged byte for byte (context `attenuo-checkpoint-v1`).
- Fuzzing F5: `attenuo audit verify --file` and `attenuo_audit::verify_export` are strict. An export must have a header (it declares `from..=to`), and it fails if it holds entries outside that range (`outside_range`, new) or entries after its last valid checkpoint (`unsigned_tail_rejected`, new). Before, a signed export of `1..=5` with a forged entry 6 appended (chained and hashed) verified `ok` with `unsigned_tail = 1`. BREAKING for exports that end after their last checkpoint: pass `--allow-unsigned-tail` (or `verify_export_with(.., VerifyOptions { allow_unsigned_tail: true })`) to accept them, or sign the head (`GET /admin/audit/checkpoint`) before exporting. Entries outside the range fail either way.
- Fuzzing F4: an audit entry with `seq` = 2^64 - 1 and a correct hash no longer overflows the chain walk (a panic with overflow checks on, a wrap to 0 without); it is a bad entry, and `audit verify --file` reports it.
- SR-50: a commit that writes a signed audit checkpoint runs with `synchronous=FULL` at any `[audit] durability`, before the checkpoint reaches the `on_created` hook (the way checkpoints get shipped off the host). At `normal`, a power failure could take back entries that a shipped checkpoint already covered, and `audit verify` against that checkpoint would then report tampering that did not happen. A batch that turns out to cross a checkpoint is rolled back before inserting anything and committed again at `FULL` (SQLite cannot change `synchronous` inside a transaction): one extra transaction per checkpoint.
- SR-51: `SqliteLeaseStore::revoke` returns the revocation's result; if setting `synchronous` back afterwards fails, that is logged and the connection stays at `FULL`, instead of reporting a failed revocation that took effect.
- Fuzzing fixes (see `docs/design/fuzzing.md`). DPoP: a proof's `iat` far from the server clock overflowed the freshness check, a panic in debug builds and, in release builds, a proof with `iat = now - 2^63` passed as fresh; `iat` is now compared with `abs_diff`. Proxy: a list answer whose numeric `id` came back spelled differently (`1.0` sent, `1` answered by a JavaScript upstream, or a large or fractional id re-printed) skipped the list filter, so the client saw tools its chain cannot call; numeric ids now match by value. - SR-24: delegation tokens can be sender-constrained with DPoP (RFC 9449), so a leaked token is useless without the agent's key. A `DPoP` proof (Ed25519 or P-256) on `POST /token` or `POST /admin/root-token` binds the new token to the key (`cnf.jkt`, `token_type: "DPoP"`); a bound token is then accepted only with a fresh proof by that key (`htm`, `htu`, `ath`, `iat` within `[token] dpop_max_age_seconds`, unseen `jti`) by the proxy, `/token/renew`, the AuthZEN endpoints and `/token` as the parent of an exchange. The child of a bound token is always bound; binding it to another key needs the parent key's consent in `subject_token_dpop`. Failures are 401 `dpop_required` / `invalid_dpop_proof` with `WWW-Authenticate: DPoP` (JSON-RPC `-32001` in the proxy). Opt-in and backward compatible: `[token] dpop = "optional"` by default; `"required"` refuses unbound tokens. Audit records carry `dpop_bound: true` when it applies (omitted otherwise, so existing hashes are unchanged).
- SR-14: the detached originating-user signature is bound to the issuer and the root hop. BREAKING: `ou_sig` is now version 2, Ed25519 over `"attenuo-ou-v2" || iss || canonical(originating_user) || canonical(hop 0 {agent, capabilities, issued_at, lease})` (each field length-prefixed), carried with new claims `ou_sig_v: 2` and `ou_kid` (the key that made it) and checked under that key only. Tokens without `ou_sig_v` (version 1) are refused with `TokenError::UnsupportedOuSig`; re-issue them from the root. Nothing was deployed with v1. A user's `ou_sig` lifted from one chain no longer verifies in a chain with another root hop or issuer, even when the outer JWT is re-signed by a trusted key (rotation, multi-issuer). `DetachedSigner::sign` refuses the reserved `attenuo-ou-` contexts. New `attenuo_token::claims::{ou_sig_payload, ou_sig_message}`, `OU_SIG_VERSION`, `OU_SIG_CONTEXT`.
- SR-13: Cedar actions are server-scoped. BREAKING: the action of a call is `Action::"<server>/<tool>"` (still a member of `Action::"invoke"`), so a permit for `github`'s `read_file` no longer matches `read_file` on another upstream. Rewrite `Action::"read_file"` as `Action::"github/read_file"`; `attenuo policy lint` reports every bare action with its line (stage `actions`). `[policy] legacy_bare_actions = true` (deprecated, default `false`, warned at start) keeps the old ids while a policy set is rewritten; policy test files take `legacy_bare_actions` too. `/` is refused in server names and in tool names (except the MCP method names the proxy authorizes, such as `resources/read`) in capabilities, chains, the catalog and the engine, which denies such a call with `invalid_name`.
- SR-25: server and tool names are 1 to 128 ASCII `[A-Za-z0-9_.-]` characters (method names: such segments joined by `/`), compared case-sensitively, never normalized (`attenuo_core::names`). The proxy denies a `tools/call` with any other name (`invalid_name`) and, with `[proxy] require_listed_tools` (default `true`), one whose exact name the upstream never listed in `tools/list` and the catalog does not know (`tool_not_listed`), so an upstream that resolves `Delete_Repo` to `delete_repo` cannot step around a rule on `delete_repo`. Both are audited. BREAKING: capabilities, catalog entries and grants with other characters (spaces, `:`, non-ASCII) are refused.
- SR-36: the proxy's session registry no longer evicts other users' live sessions when full: expired bindings are reclaimed oldest first without a scan, and a new session beyond `[proxy] max_sessions` (default 100000) gets 503 `session_registry_full` (`-32006`, `Retry-After: 30`). Buffered upstream bodies are capped by `[proxy] max_upstream_body_bytes` (default 16 MiB, 502 `upstream_body_too_large`; also the SSE event limit) and request bodies by `max_request_body_bytes` (default 4 MiB, 413 `request_too_large`, read after authentication). `session_ttl_seconds` (3600) is configurable.
- SR-33: declared `originating_user.attributes` types (the built-in `mfa`, `roles`, `tenant`, `email` and `[policy] user_attributes`) are enforced before Cedar runs. A value of another type is denied with reason `attribute_type_mismatch` and audited, so `attributes.status != "suspended"` no longer permits `["suspended"]`. Nothing is coerced.
- SR-37: an ID token is bound to the agent that presents it. BREAKING: `[[idps]] audience` is ignored for ID tokens; `aud` must contain the agent's client id from the new `[[idps]] client_ids` table (default: the agent id), and `azp` must name it when `aud` has several values or `azp` is present. A token for agent A presented by agent B is refused with `credential_audience_mismatch`. The server warns at startup for each agent without an entry.

BREAKING: the old `status` field and the per-check `{ok,error}` objects are gone. A `[metrics] listen` off loopback is refused at startup unless `[metrics] allow_public = true`, and logs a warning when it is set.
- SR-17: client-facing errors carry stable reason codes only; the details go to the server log at debug. BREAKING: every 401 from the server is `{"error":"unauthorized","detail":<reason>,"error_description":<reason>}` with the reason `missing_token`, `invalid_token` or `token_expired` (the last only for a token that otherwise verified), instead of the verifier's message. The proxy's JSON-RPC 401 is `-32001` with message `attenuo: unauthorized: <reason>` and `data.reason`; an unreachable upstream is 502 `-32005` with message `attenuo: upstream unreachable` and `data.reason = "upstream_unreachable"`, without the `reqwest` text or the upstream URL. A JWKS fetch failure answers a fixed detail and logs the cause. BREAKING: AuthZEN `context.diagnostics` are returned only as the new `[authzen] diagnostics = "always" | "peps" | "never"` allows; the default `peps` returns them only to callers that authenticate as a `[[peps]]` client (`pep_secret`, now accepted together with a bearer token instead of 400).

### Performance

- The Python SDK's SSE parser reads a long line in linear time (SR-82, part 1): `SseParser.feed` searches each read for line ends once and keeps the unfinished line as a list of chunks joined once per line, as the TypeScript parser does, instead of appending to one buffer and searching it again from the start on every read. A 1 MiB `data:` line in 1 KiB reads took about 4 s and now takes about 10 ms. Behaviour is unchanged (checked against the old parser on 300,000 random bodies and splits); new test `test_parser_reads_a_long_line_in_small_reads_in_linear_time_sr82`.
- Measured the list filter on the `GET` listen stream ([performance](docs/design/performance.md#listen-stream-list-filter-2026-10-24)): parsing and re-serializing every JSON event adds 1.5 us to a 173-byte notification (1.7 against 0.16 us to frame it) and 0.6 to 0.7 ms to an 85 KB, 200-tool `tools/list` answer; end to end the small-event cost does not show against a relay floor of about 40 us per event. Not changed. The harness is the `#[ignore]` test `crates/attenuo-proxy/tests/listen_stream_cost.rs`.
- The proxy's check for upstream events in the shape of its stream-end event no longer parses every event on an SSE stream without a list filter: a byte scan first looks for a JSON number whose significant digits could make `-32001` (any spelling, `-3.2001e4` and rounded decimals included), and only events that pass are parsed; a chunk with none is relayed without a copy. Per event in the SSE stage, 0.95 to 0.06 us for a 173-byte notification and 653 to 27 us for an 85 KB tool result ([performance](docs/design/performance.md#stream-end-shape-check-on-the-unfiltered-sse-path-2026-10-25)). New `#[ignore]` test `disown` in `crates/attenuo-proxy/tests/listen_stream_cost.rs`.
- Measured token verification on a verified-token cache miss ([performance](docs/design/performance.md#token-verification-on-a-cache-miss-2026-10-24)): `Verifier::verify` is 116 us at 1 hop and 126 us at 3 in process, 107 us of it the two Ed25519 checks, and the proxy's `token_verify_miss` is 170 us p50 against 8.8 us for a hit. No change to the verifier or the token format: `ou_kid` has named the `ou_sig` key since `ou_sig` version 2 and the verifier already uses that one key (a missing or unknown `ou_kid` fails, never a try-every-key fallback; now also tested with the claim removed), and the chain clone is about 1 percent. New `cargo bench -p attenuo-token --bench verify` and `attenuo-bench hot-path --rotate-tokens` (every client cycles through the `--tokens`, which may then exceed `--clients`, so more tokens than the cache's 4,096 make every call a miss).
- Measured the SR-55 per-run lock under concurrent clients ([performance](docs/design/performance.md#the-sr-55-run-lock-under-concurrent-clients-2026-10-24)), file store, 2-hop token, against the build before SR-55: with 32 clients on one run, calls with a limit or kept usage wait 18 to 22 ms for the lock instead of queueing for the store's write gate, and throughput fell by a median of 6 to 9.5 percent (22 percent in the worst pass); runs with clients of their own show no lock wait. Taking the lock later (after the label read and approval take) was measured and not kept, since it moved the wait without raising throughput. `attenuo-bench hot-path` takes `--tokens N` to spread its clients over N runs. No server change.
- Measured the per-value run-limit kinds ([performance](docs/design/performance.md#limit-kinds-callsper-and-distinct-2026-10-24)), one client, file store, 2-hop token: a `calls_per` limit adds about 100 to 170 us at the client p50, the same as `calls`, with a new or a repeated value; a `distinct` limit adds about 190 to 240 us when the value is new (four counter writes, raw value or URL host alike) and nothing measurable when it was seen (no write; its charge transaction is about 25 us). The URL parse of a `derive: host` limit is 0.3 to 1.1 us per URL, under 1 percent of the limit's cost. `attenuo-bench hot-path` has six new configurations (`calls_per_new`, `calls_per_same`, `distinct_new`, `distinct_same`, `host_new`, `host_same`), a `--cells` option, a per-call sequence number in the body, client p90 and the first charge's `used_after` in its check; the `decide` bench has `charge_*/{calls_per,distinct,host}_{new,same}`, `charges_for/*` and `derive_host/*` cells. No server change.
- Fewer long pauses for a single client on the file store ([performance](docs/design/performance.md#single-client-outliers-2026-10-24)). The background WAL checkpointer now syncs the database file before its locked pass, which held appends 10 to 23 ms (median) and now about 3 ms, and syncs the WAL 32 entries ahead of each signed audit checkpoint, whose `FULL` commit took 13 to 16 ms p50 and now 3.4 to 3.9 ms. No commit syncs less or at another level; each change is one more sync on the checkpointer's thread. End to end, one client's calls over 10 ms fell from 0.27 to 0.29 % to 0.08 to 0.09 %; the share over 3 ms (about 1 % at load below 2) is the shared host's scheduling and is unchanged. `attenuo-bench hot-path` now reports requests over 3, 5 and 10 ms at the client and per server stage, and takes `--audit-set key=value`.
- Run usage (`context.usage`) is kept only when something can read it: a loaded policy references `context.usage`, the catalog names `amount` or `destination` for some tool, or `[policy] track_usage = true`. Decided at load and on every policy reload. Otherwise an allowed call to a destructive tool with no token limit makes no lease-store write and its decision record carries no `usage`. That write cost about 0.1 ms per such call from one client on the file store (+86 to +108 us decision mean, +98 to +144 us client p50, `attenuo-bench hot-path` new configuration `usage`), and about 0.7 to 0.9 ms at `durability = "full"` in process ([performance](docs/design/performance.md#run-usage-write-2026-10-24)).
- The lease store and the audit log no longer fight over SQLite's write lock when they share a file (the server's default). Every store of the process on one file now shares an in-process write gate, a FIFO lock held across each write transaction, so writers queue and are woken in turn instead of SQLite's busy handler sleeping 1, 2, 5 ms and so on; reads do not take it, and the lease check no longer waits behind a lease write. A new probe (`crates/attenuo-audit/tests/write_contention.rs`) counted 0.1 to 1.3 busy-handler sleeps per call at 4 and 8 threads before and none after; in process the p99 at 4 and 8 threads fell from 13 to 64 ms to 5 to 17 ms and throughput rose 1.3 to 1.9 times. End to end with a `calls` limit, 4 clients get about 1.3 times the requests per second and the lease-check stage fell from 0.6 to 2.3 ms to about 0.1 ms; with a `sum` limit the change is within noise (one `fsync` per call). Durability is unchanged, and in-memory stores and stores in separate files are not affected. Details in `docs/design/performance.md`.
- A `sum` charge no longer syncs its own commit when the lease store shares the audit log's file (the server's default): it commits at the store's level and the decision append commits with `synchronous=FULL`, one `fsync` that makes both durable before the call is answered or forwarded and that concurrent calls share through group commit (`LeaseStore::charge_sync_deferred`, `AuditSink::append_synced`). Profiling showed the `synchronous` switch costs about 2 us and every `sum` charge makes exactly one `fsync` of the call's 25 to 40 WAL pages, which the durability rule requires. So the change is within noise from one client end to end (about 80 us in process), and gives 1.3 to 1.8 times the throughput of concurrent `sum` charges plus appends in process. Under concurrency SQLite's busy-handler sleeps between the two connections dominated; the write-gate entry above removes them. New `decide` bench cell `decide_limited_*`. Details in `docs/design/performance.md`.
- Measured what output labelling and run limits add to one proxied call (new `attenuo-bench hot-path`, file store, one client, 2-hop token, 5 interleaved runs): an untrusted-output label adds nothing measurable at the client (about 15 us server-side for the run-label write; the `tool_result` append of about 140 us is paid by every allowed call since #42); a `calls` limit adds about 120 to 190 us at p50; a `sum` limit adds about 0.8 to 1.0 ms and halves single-client throughput, because its charge commits with `synchronous=FULL`; an approval round (gated call, operator grant, retry) is about 3.3 ms at p50. New `decide` bench cells for the counter read and the charge. Details in `docs/design/performance.md`.
- Measured the output-labelling cost: a `tool_result` append plus the run label is about 150 us on the file store at `normal` durability, about the same as the decision append, so an allowed call spends about twice as long in the audit log. Details in `docs/design/performance.md`.
- Investigated the proxy's upstream round trip and the `blocking_pool` stage (`perf/proxy-upstream-hop`); no code change. The upstream client already shares one keep-alive pooled `reqwest::Client` and sends each request in one write; the gap to a direct call is CPU wake-up latency between calls on the test VM. Running decisions inline removed the blocking-pool hop but moved the time into the `upstream` stage and cut 8-client throughput, so decisions stay on the blocking pool. Details in `docs/design/performance.md`.
- File-backed audit and lease stores run SQLite in WAL mode with `synchronous=NORMAL`, a busy timeout and a prepared-statement cache. New `[audit] durability = "normal" | "full"` (default `normal`): at `normal` a power failure or kernel crash can lose the newest decisions, never tear one, and the chain still verifies with an earlier head; `full` syncs every commit. Lease revocations always sync. The database now has `-wal` and `-shm` companion files.
- Group commit: audit appends go through one writer thread that commits every queued record in one transaction (up to 256) and answers each caller with its entry; a failed batch is retried record by record, so only a refused record is denied with `audit_error`.
- The proxy caches verified delegation tokens by SHA-256 of the token (4,096 entries), rechecking expiry on every hit, so an agent's repeated calls skip the two Ed25519 verifications (about 100 us). The audit append reads only the head's `seq` and hash instead of decoding the head row, serializes each record once, and the lease check reads a chain's leases with one query.
- Measured on a shared 4 vCPU container (one-hop allow call, 8 and 32 clients): file-backed log from about 460 to 490 calls per second to 3,100 to 4,500; in memory from about 4,300 to 5,300 to 5,000 to 6,600; single-client added latency with a file log from 2.1 ms to 0.85 ms. Details and caveats in `docs/design/performance.md`; results in `docs/design/bench/2026-10-23-vm-audit-write-path.md`.
- `attenuo-bench` gains audit mode `file_full`; new stage bench `cargo bench -p attenuo-server --bench decide`.
- The policy engine caches the chain-to-Cedar translation (entity store, principal, action, resource, and the `originating_user` and `chain` context records) per chain and tool, 4,096 entries, matched on every input it was built from and emptied on a policy reload; a call builds only `context.input`, `session_id` and `now_unix`. Cedar parsing that JSON was about 95 percent of the stage: `PolicyEngine::authorize` went from about 120 / 200 us to 11 / 13 us at 1 / 3 hops (cache hit; a miss costs what every call cost before). Decisions are unchanged; a test holds the cached request equal to the old one-pass translation. New bench `cargo bench -p attenuo-policy --bench policy_stage`, `PolicyEngine::cached_requests()`.
- WAL checkpoints moved off the audit writer. New `[audit] wal_checkpoint_seconds` (default 5; 0 restores SQLite's checkpoints on the writer): the writer connection runs with `wal_autocheckpoint=0` and a background thread checkpoints (`PASSIVE`) every interval or 256 commits, truncates the WAL when idle, and once more at shutdown (`SqliteAudit::with_wal_checkpoints`, `checkpoint_wal`, `SqliteLeaseStore::without_wal_autocheckpoint`). Under continuous load a round that finds the WAL past 64 MB pauses appends briefly so the WAL starts over; the `-wal` file peaks around 100 MB. At `durability = "normal"` the power-failure window is now up to one interval (or 256 commits) of decisions instead of about 1,000 pages. Same binary, file store, 8 clients: p99 21 to 23 ms down to 4 to 8 ms and throughput up 35 to 95 percent; at 32 clients p99 34 to 41 ms down to 11 to 23 ms.
- An append that finds the audit writer idle commits on the caller's thread, skipping the hand-off (about 20 to 40 us).
- End to end on the shared container (one-hop allow call, 1 / 8 / 32 clients): file-backed log 962 / 3,110 / 4,526 to 1,252 / 4,049 / 6,254 req/s with p99 at 8 and 32 clients from 15.5 and 23.8 ms to 5.4 and 13.0 ms; single-client added p50 with a file log 851 to 631 us, in memory 697 to 425 us. Results in `docs/design/bench/2026-10-23-vm-policy-stage.md`.
