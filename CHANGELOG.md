# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, minor versions may contain breaking changes; each one is called out under **Changed** or **Removed** with a `BREAKING:` prefix.

Entries are written by hand. `git cliff --unreleased` (see `cliff.toml`) produces a draft from conventional commits that is edited into this file before a release. Security fixes always go under **Security**, with the advisory identifier once one exists.

## [Unreleased]

### Performance

- Investigated the proxy's upstream round trip and the `blocking_pool` stage (`perf/proxy-upstream-hop`); no code change. The upstream client already shares one keep-alive pooled `reqwest::Client` and sends each request in one write; the gap to a direct call is CPU wake-up latency between calls on the test VM. Running decisions inline removed the blocking-pool hop but moved the time into the `upstream` stage and cut 8-client throughput, so decisions stay on the blocking pool. Details in `docs/design/performance.md`.

### Added

- `onbehalf-bench exchange` (token-exchange throughput with a fresh actor per request, 1 or 3 hops, memory or file audit store), `onbehalf-bench lease-renew` (M live leases renewing at interval T, renewal latency, server CPU, and the revoke-cascade time for a depth-3 tree with 100 descendants) and `--open-loop RATE` (Poisson arrivals, latency from the scheduled arrival) on the proxied call and on `exchange`. Every cell reports the server's CPU from `/proc`. Results in `docs/design/bench/2026-10-23-vm-exchange-lease.md`.
- Audit records have a top-level `kind` (`decision`, `exchange`, `root_token`, `lease_renew`, `lease_revoke`, `admin`) and, where there is a delegation chain, a `chain_id` (the lease id of the chain's first hop, stable as hops are added). Both are part of the hashed record and are indexed, cross-checked columns in SQLite. They went into entry hash v2, which was introduced this release cycle and never shipped, so v2 did not change; an audit database created with the earlier v2 shape (no `kind`/`chain_id` columns) is refused at open like the v1 ones, with a message to start a new log. `GET /admin/audit/export` takes `?kind=` and `?chain_id=` (400 for an unknown kind or an empty id), and so does `onbehalf audit export --kind --chain-id`; a filtered export's header carries `filter`, and offline verification refuses it because its chain has gaps. New `onbehalf_core::{RecordKind, chain_id_of}`, `onbehalf_audit::{RecordFilter, SqliteAudit::range_filtered}`, `AuditEntry.kind`/`.chain_id` (Python) and `kind`/`chainId` (TypeScript), and `kind`/`chain_id` (`chainId`) arguments on `audit_export` / `auditExport`.
- Offline export verification in both SDKs, with the same strictness as `onbehalf audit verify --file`: `onbehalf.audit.verify_export(path_or_lines, *, checkpoint_public_keys, allow_unsigned_tail=False)` in Python (new dependency `rfc8785==0.1.4`; the Ed25519 check needs the `verify` extra) and `verifyExport(source, { checkpointPublicKeys, allowUnsignedTail })` in TypeScript (with a small RFC 8785 implementation, tested against the RFC's vectors). They re-check the SHA-256 chain over canonical JSON, the header's range and the checkpoint signatures, return a report with `first_bad_seq`, and raise `ExportError` for a file that is not a verifiable export (no header, wrong format, filtered). A cross-language integration test exports from a real server, flips one byte and checks that the Rust CLI, Python and TypeScript name the same `seq`.
- Token refresh in both SDKs. Python: `TokenRefresher` (a context manager running a thread) and `AsyncTokenRefresher` (an `asyncio` task), plus `RefreshError`. TypeScript: `TokenRefresher` with `start()` returning a disposer, `provider` and `fetch()` for the MCP transport (the per-request token hook, on top of `mcpFetch`), plus `RefreshError`. Each renews the lease at a third of the lease interval, calls a caller-supplied `exchange` function before `exp` (margin default 20% of the lifetime, at least 5 s), exposes the current token with a change callback, retries with jittered backoff, and stops with a terminal error callback on `lease_revoked`, a permanent refusal or expiry. A replacement token must carry the same DPoP `cnf.jkt` as the one it replaces. Tokens are never logged. The exchange function must bring a fresh subject token each time, because a parent delegates to a given actor once.
- DPoP server nonces (RFC 9449 §8): `[token] dpop_nonce = "off" | "required"` (default `off`). When required, every response to a request with a `DPoP` header, and every `WWW-Authenticate: DPoP` challenge, carries `DPoP-Nonce`, and every `DPoP` header proof must carry a current nonce or is refused with 401 `use_dpop_nonce` (`WWW-Authenticate: DPoP error="use_dpop_nonce"`; JSON-RPC `-32001` with `data.reason` `use_dpop_nonce` at the proxy). Nonces need no storage: an HMAC of a `dpop_max_age_seconds`-wide time bucket under a key derived from the issuer's signing key, with the previous bucket also accepted. The exchange sign-off needs no nonce. New: `onbehalf_token::dpop::DpopKey::proof_with_nonce`, `VerifiedProof::nonce`, `onbehalf_proxy::AuthError::UseDpopNonce`. Both SDKs (`Client`/`AsyncClient`/`OnbehalfClient`, `AdminClient` dev mint, `TokenAuth`, `mcpFetch`) keep the latest `DPoP-Nonce`, put it in each proof (`DpopKey.proof(..., nonce=...)` / `{ nonce }`), and retry a request once on `use_dpop_nonce`. The CLI does not handle nonces yet.

### Fixed

- Flaky test `security_low::a_newline_in_a_tool_name_stays_on_one_log_line` (test-only change). Under parallel load it sometimes captured no log line: `tracing` caches each callsite's interest process-wide, and a callsite first reached by another test thread with no subscriber active could be cached as disabled before the test's scoped subscriber was installed. The test now relies on one global subscriber that writes to a per-thread buffer.
- `onbehalf policy lint` without `--config` no longer reports a correct server-scoped policy as an error. It declares the tools from the policy's own `<server>/<tool>` action names and prints a `note:` (and a `notes` array with `--json`) saying that tool attributes, input types and user attributes were not checked. New `onbehalf_policy::policy_action_names`.
- `onbehalf policy lint` without `--config` no longer warns that a policy using `context.input has repo` is impossible: it drops "impossible policy" warnings for policies that read `context.input` or user attributes, which the schema cannot declare without a catalog (`LintOptions::undeclared_catalog`), and the note says so. A policy that is impossible for other reasons (`when { false }`) still warns.
- The injection suite (`evaluation/injection-suite`) ignores `ONBEHALF_*` variables exported from another deployment (`ONBEHALF_ADMIN_TOKEN`, `ONBEHALF_SERVER`, ...), with one warning, instead of failing with 401. `ONBEHALF_BIN_DIR` and `ONBEHALF_INTEGRATION` still apply.

### Security

- SR-40: a DPoP exchange sign-off (`subject_token_dpop`) is consent to one delegation only. BREAKING: the sign-off must carry `child_jkt` (the thumbprint of the key in the exchange's `DPoP` header) and `child_actor` (the request's `actor`), or the exchange is 401 `invalid_dpop_proof`; a plain proof by the parent's key is no longer accepted. The parent's holder can now make the sign-off in its own process and hand over only the result: `onbehalf token sign-off --dpop-key parent.jwk --child-jkt <jkt> --actor <agent>` and `token exchange --subject-token-dpop-file`, `DpopKey.sign_off` and `exchange(..., subject_token_dpop=...)` in Python, `DpopKey.signOff` and `subjectTokenDpop` in TypeScript. `subject_dpop_key` / `subjectDpopKey` / `--subject-dpop-key` still work for a process that holds both keys.
- SR-41: a DPoP proof's `jti` is recorded only after the proof matched the token's key, so proofs by a wrong key (a thief holding a bound token) can no longer fill `[token] dpop_replay_capacity` and turn every bound request into a 503. An exchange's header proof and sign-off are recorded together or not at all.
- SR-42: without `[server] public_url`, DPoP `htu` is checked against `http://<Host>` only for a loopback `Host`; any other `Host` is treated as `localhost`, so a proof made for another server cannot be replayed here by sending its host name.
- SR-43: a 500 says `"detail": "internal error; the details are in the server log"`. Storage and I/O errors (SQLite messages, file paths) used to be returned in `detail`, including the lease-store error of a failed exchange.
- SR-44: an exchange's replay check and its `actor_token` are consumed together, so an exchange refused as a replay no longer burns the caller's actor token.
- SR-45: `POST /token` refuses the reserved agent id `onbehalf` as the exchange `actor` (400 `invalid_request`, `reserved_agent`), whether it came from `require_actor_auth = false` or an `[[actor_trust]]` mapping.
- SR-46: the verified-token cache no longer stores tokens over 16 KiB (they are verified on every request instead), so its memory is bounded by bytes as well as by count.
- SR-47: the proxy answers a full DPoP replay cache with HTTP 503 (JSON-RPC `-32006`, `data.reason` `dpop_replay_cache_full`, `Retry-After`) instead of 401 `invalid_dpop_proof`, so clients retry instead of treating their key as bad.
- SR-48: the RFC (P4) and the threat model now say that `[audit] durability = "normal"` can lose the newest records, including those of forwarded calls, on a power failure.
- SR-49: one principal (the chain's root lease) can hold at most `[proxy] max_sessions_per_principal` (default 64) live `Mcp-Session-Id` bindings; one more gets HTTP 429, JSON-RPC `-32007` (new, `onbehalf_proxy::jsonrpc::CODE_TOO_MANY`), `data.reason` `too_many_sessions`, `Retry-After: 30`, and other users keep opening sessions. Before, one user could fill all `max_sessions` slots and leave everyone else with 503 until the TTL. When the proxy refuses a session (this cap or `session_registry_full`), it now sends the upstream an MCP `DELETE` for the session the upstream just created, best effort, instead of leaving it open there. `BindOutcome` gains `PrincipalFull`; `ProxyConfig::max_sessions_per_principal`, `with_max_sessions_per_principal`, `SessionRegistry::with_max_per_principal`, `REASON_TOO_MANY_SESSIONS`, and the test doubles `FakeMcpServer::with_fresh_session_ids`, `sessions_opened` and `deleted_sessions` (it now answers `DELETE`) are new.
- SR-53: the LangChain and Claude Agent SDK examples count a `-32003` as onbehalf's denial only when its `data.decision_id` is in the proxy's `X-Onbehalf-Decision-Id` response header (collected with an `httpx` response hook on the `mcp` client), as the SDKs do since SR-32; any other `-32003` is shown as an upstream error. The Claude Agent SDK example's README notes that its live mode cannot make this check.
- SR-20: everything onbehalf hashes or signs as JSON is RFC 8785 (JCS) canonical JSON (new `onbehalf_core::jcs`): members sorted by UTF-16 code units, the RFC's string escaping, numbers as ECMAScript writes the double; integers beyond ±2^53 keep all their digits instead of being rounded. Before, the bytes were `serde_json` output, and `serde_json`'s `preserve_order` feature (switched on workspace-wide by a dependency) kept nested objects in insertion order, so a verifier built without it, or in another language, computed different bytes. This covers the chain digest (and the lease bindings that the AuthZEN `chain_not_issued` check compares), the argument digest, `ou_sig`, audit entry hashes and checkpoint signatures. Argument constraints now compare JSON values the same way (`1` equals `1.0`, member order ignored) in `Eq`, `Ord`, `satisfied_by` and `implies`, so equality agrees with ordering and with the digest. `serde_json` parses with `float_roundtrip`. BREAKING: `ou_sig` is version 3 (context `onbehalf-ou-v3`, claim `ou_sig_v: 3`); v2 tokens are refused with `UnsupportedOuSig(2)` and must be re-issued from the root. BREAKING: the audit entry hash is SHA-256 over `JCS(["onbehalf-audit-entry-v2", seq, prev_hash, record])` (`onbehalf_audit::ENTRY_HASH_VERSION`), `record_json` is stored canonically, and the construction is recorded in a new `audit_meta` table; an audit database written by an earlier build is refused at startup with an error that says to move it aside and start a new log. There is no migration: no logs were released in the old form. BREAKING: exports are format `onbehalf-audit-export-v2` with canonical lines; `v1` exports are refused with a message that says why. The checkpoint signing input is unchanged byte for byte (context `onbehalf-checkpoint-v1`).
- Fuzzing F5: `onbehalf audit verify --file` and `onbehalf_audit::verify_export` are strict. An export must have a header (it declares `from..=to`), and it fails if it holds entries outside that range (`outside_range`, new) or entries after its last valid checkpoint (`unsigned_tail_rejected`, new). Before, a signed export of `1..=5` with a forged entry 6 appended (chained and hashed) verified `ok` with `unsigned_tail = 1`. BREAKING for exports that end after their last checkpoint: pass `--allow-unsigned-tail` (or `verify_export_with(.., VerifyOptions { allow_unsigned_tail: true })`) to accept them, or sign the head (`GET /admin/audit/checkpoint`) before exporting. Entries outside the range fail either way.
- Fuzzing F4: an audit entry with `seq` = 2^64 - 1 and a correct hash no longer overflows the chain walk (a panic with overflow checks on, a wrap to 0 without); it is a bad entry, and `audit verify --file` reports it.
- SR-50: a commit that writes a signed audit checkpoint runs with `synchronous=FULL` at any `[audit] durability`, before the checkpoint reaches the `on_created` hook (the way checkpoints get shipped off the host). At `normal`, a power failure could take back entries that a shipped checkpoint already covered, and `audit verify` against that checkpoint would then report tampering that did not happen. A batch that turns out to cross a checkpoint is rolled back before inserting anything and committed again at `FULL` (SQLite cannot change `synchronous` inside a transaction): one extra transaction per checkpoint.
- SR-51: `SqliteLeaseStore::revoke` returns the revocation's result; if setting `synchronous` back afterwards fails, that is logged and the connection stays at `FULL`, instead of reporting a failed revocation that took effect.

- Fuzzing fixes (see `docs/design/fuzzing.md`). DPoP: a proof's `iat` far from the server clock overflowed the freshness check, a panic in debug builds and, in release builds, a proof with `iat = now - 2^63` passed as fresh; `iat` is now compared with `abs_diff`. Proxy: a list answer whose numeric `id` came back spelled differently (`1.0` sent, `1` answered by a JavaScript upstream, or a large or fractional id re-printed) skipped the list filter, so the client saw tools its chain cannot call; numeric ids now match by value. Token: `Issuer::issue_root` refuses (`TokenError::Malformed`) a user block or root hop with a time RFC 3339 cannot write (before year 0, such as an IdP `auth_time` of -1e11), which used to panic in the `ou_sig` encoding.
- SR-24: delegation tokens can be sender-constrained with DPoP (RFC 9449), so a leaked token is useless without the agent's key. A `DPoP` proof (Ed25519 or P-256) on `POST /token` or `POST /admin/root-token` binds the new token to the key (`cnf.jkt`, `token_type: "DPoP"`); a bound token is then accepted only with a fresh proof by that key (`htm`, `htu`, `ath`, `iat` within `[token] dpop_max_age_seconds`, unseen `jti`) by the proxy, `/token/renew`, the AuthZEN endpoints and `/token` as the parent of an exchange. The child of a bound token is always bound; binding it to another key needs the parent key's consent in `subject_token_dpop`. Failures are 401 `dpop_required` / `invalid_dpop_proof` with `WWW-Authenticate: DPoP` (JSON-RPC `-32001` in the proxy). Opt-in and backward compatible: `[token] dpop = "optional"` by default; `"required"` refuses unbound tokens. Audit records carry `dpop_bound: true` when it applies (omitted otherwise, so existing hashes are unchanged).

- SR-14: the detached originating-user signature is bound to the issuer and the root hop. BREAKING: `ou_sig` is now version 2, Ed25519 over `"onbehalf-ou-v2" || iss || canonical(originating_user) || canonical(hop 0 {agent, capabilities, issued_at, lease})` (each field length-prefixed), carried with new claims `ou_sig_v: 2` and `ou_kid` (the key that made it) and checked under that key only. Tokens without `ou_sig_v` (version 1) are refused with `TokenError::UnsupportedOuSig`; re-issue them from the root. Nothing was deployed with v1. A user's `ou_sig` lifted from one chain no longer verifies in a chain with another root hop or issuer, even when the outer JWT is re-signed by a trusted key (rotation, multi-issuer). `DetachedSigner::sign` refuses the reserved `onbehalf-ou-` contexts. New `onbehalf_token::claims::{ou_sig_payload, ou_sig_message}`, `OU_SIG_VERSION`, `OU_SIG_CONTEXT`.
- SR-13: Cedar actions are server-scoped. BREAKING: the action of a call is `Action::"<server>/<tool>"` (still a member of `Action::"invoke"`), so a permit for `github`'s `read_file` no longer matches `read_file` on another upstream. Rewrite `Action::"read_file"` as `Action::"github/read_file"`; `onbehalf policy lint` reports every bare action with its line (stage `actions`). `[policy] legacy_bare_actions = true` (deprecated, default `false`, warned at start) keeps the old ids while a policy set is rewritten; policy test files take `legacy_bare_actions` too. `/` is refused in server names and in tool names (except the MCP method names the proxy authorizes, such as `resources/read`) in capabilities, chains, the catalog and the engine, which denies such a call with `invalid_name`.
- SR-25: server and tool names are 1 to 128 ASCII `[A-Za-z0-9_.-]` characters (method names: such segments joined by `/`), compared case-sensitively, never normalized (`onbehalf_core::names`). The proxy denies a `tools/call` with any other name (`invalid_name`) and, with `[proxy] require_listed_tools` (default `true`), one whose exact name the upstream never listed in `tools/list` and the catalog does not know (`tool_not_listed`), so an upstream that resolves `Delete_Repo` to `delete_repo` cannot step around a rule on `delete_repo`. Both are audited. BREAKING: capabilities, catalog entries and grants with other characters (spaces, `:`, non-ASCII) are refused.
- SR-36: the proxy's session registry no longer evicts other users' live sessions when full: expired bindings are reclaimed oldest first without a scan, and a new session beyond `[proxy] max_sessions` (default 100000) gets 503 `session_registry_full` (`-32006`, `Retry-After: 30`). Buffered upstream bodies are capped by `[proxy] max_upstream_body_bytes` (default 16 MiB, 502 `upstream_body_too_large`; also the SSE event limit) and request bodies by `max_request_body_bytes` (default 4 MiB, 413 `request_too_large`, read after authentication). `session_ttl_seconds` (3600) is configurable.

- SR-33: declared `originating_user.attributes` types (the built-in `mfa`, `roles`, `tenant`, `email` and `[policy] user_attributes`) are enforced before Cedar runs. A value of another type is denied with reason `attribute_type_mismatch` and audited, so `attributes.status != "suspended"` no longer permits `["suspended"]`. Nothing is coerced.
- SR-37: an ID token is bound to the agent that presents it. BREAKING: `[[idps]] audience` is ignored for ID tokens; `aud` must contain the agent's client id from the new `[[idps]] client_ids` table (default: the agent id), and `azp` must name it when `aud` has several values or `azp` is present. A token for agent A presented by agent B is refused with `credential_audience_mismatch`. The server warns at startup for each agent without an entry.
- SR-38: `GET /readyz` returns a fixed shape, `{"ready":false,"checks":{"audit":"error","leases":"ok"}}`, with the storage error in the server log only. BREAKING: the old `status` field and the per-check `{ok,error}` objects are gone. A `[metrics] listen` off loopback is refused at startup unless `[metrics] allow_public = true`, and logs a warning when it is set.
- SR-17: client-facing errors carry stable reason codes only; the details go to the server log at debug. BREAKING: every 401 from the server is `{"error":"unauthorized","detail":<reason>,"error_description":<reason>}` with the reason `missing_token`, `invalid_token` or `token_expired` (the last only for a token that otherwise verified), instead of the verifier's message. The proxy's JSON-RPC 401 is `-32001` with message `onbehalf: unauthorized: <reason>` and `data.reason`; an unreachable upstream is 502 `-32005` with message `onbehalf: upstream unreachable` and `data.reason = "upstream_unreachable"`, without the `reqwest` text or the upstream URL. A JWKS fetch failure answers a fixed detail and logs the cause. BREAKING: AuthZEN `context.diagnostics` are returned only as the new `[authzen] diagnostics = "always" | "peps" | "never"` allows; the default `peps` returns them only to callers that authenticate as a `[[peps]]` client (`pep_secret`, now accepted together with a bearer token instead of 400).
- SR-18: caller-controlled strings (tool, server, method, agent, subject, reason, issuer, content type, client id, lease revoke reason) are logged with `Debug` formatting in the server and the proxy, so a newline in a tool name cannot forge a log line.
- SR-19: BREAKING: the server refuses to start with a non-loopback `listen` and no `[server] public_url`; `public_url` must be an `http(s)` URL with a host and no query or fragment. With `public_url` set, `/.well-known/authzen-configuration` is built from it alone; without it (loopback only) the `Host` header must be `localhost`, `127.0.0.1` or `[::1]` with an optional port, otherwise 400 `invalid_host`.
- SR-34: BREAKING: admin actions are audited with `originating_subject = "urn:onbehalf:admin"` instead of `"admin"`. The `urn:onbehalf:` subject prefix is reserved: IdP intake refuses an ID token whose `sub` starts with it (400 `invalid_grant`, `reserved_subject`) and so does the dev root mint (400 `reserved_subject`). The agent id `onbehalf` is refused in `[[agents]]`, `[[peps]]` and `[[root_grants]]` at startup and by the dev root mint (`reserved_agent`), next to the server name `onbehalf`, which already was. Filters on the old `admin` subject need updating; existing audit entries keep their subject and still verify.
- SR-35: `--token` and `--subject-token` take `-` to read the token from stdin, and `--token-file` / `--subject-token-file` read it from a file. A literal token on the command line still works but prints a one-line warning, as `--admin-token` and `--client-secret` already did.

### Performance

- File-backed audit and lease stores run SQLite in WAL mode with `synchronous=NORMAL`, a busy timeout and a prepared-statement cache. New `[audit] durability = "normal" | "full"` (default `normal`): at `normal` a power failure or kernel crash can lose the newest decisions, never tear one, and the chain still verifies with an earlier head; `full` syncs every commit. Lease revocations always sync. The database now has `-wal` and `-shm` companion files.
- Group commit: audit appends go through one writer thread that commits every queued record in one transaction (up to 256) and answers each caller with its entry; a failed batch is retried record by record, so only a refused record is denied with `audit_error`.
- The proxy caches verified delegation tokens by SHA-256 of the token (4,096 entries), rechecking expiry on every hit, so an agent's repeated calls skip the two Ed25519 verifications (about 100 us). The audit append reads only the head's `seq` and hash instead of decoding the head row, serializes each record once, and the lease check reads a chain's leases with one query.
- Measured on a shared 4 vCPU container (one-hop allow call, 8 and 32 clients): file-backed log from about 460 to 490 calls per second to 3,100 to 4,500; in memory from about 4,300 to 5,300 to 5,000 to 6,600; single-client added latency with a file log from 2.1 ms to 0.85 ms. Details and caveats in `docs/design/performance.md`; results in `docs/design/bench/2026-10-23-vm-audit-write-path.md`.
- `onbehalf-bench` gains audit mode `file_full`; new stage bench `cargo bench -p onbehalf-server --bench decide`.
- The policy engine caches the chain-to-Cedar translation (entity store, principal, action, resource, and the `originating_user` and `chain` context records) per chain and tool, 4,096 entries, matched on every input it was built from and emptied on a policy reload; a call builds only `context.input`, `session_id` and `now_unix`. Cedar parsing that JSON was about 95 percent of the stage: `PolicyEngine::authorize` went from about 120 / 200 us to 11 / 13 us at 1 / 3 hops (cache hit; a miss costs what every call cost before). Decisions are unchanged; a test holds the cached request equal to the old one-pass translation. New bench `cargo bench -p onbehalf-policy --bench policy_stage`, `PolicyEngine::cached_requests()`.
- WAL checkpoints moved off the audit writer. New `[audit] wal_checkpoint_seconds` (default 5; 0 restores SQLite's checkpoints on the writer): the writer connection runs with `wal_autocheckpoint=0` and a background thread checkpoints (`PASSIVE`) every interval or 256 commits, truncates the WAL when idle, and once more at shutdown (`SqliteAudit::with_wal_checkpoints`, `checkpoint_wal`, `SqliteLeaseStore::without_wal_autocheckpoint`). Under continuous load a round that finds the WAL past 64 MB pauses appends briefly so the WAL starts over; the `-wal` file peaks around 100 MB. At `durability = "normal"` the power-failure window is now up to one interval (or 256 commits) of decisions instead of about 1,000 pages. Same binary, file store, 8 clients: p99 21 to 23 ms down to 4 to 8 ms and throughput up 35 to 95 percent; at 32 clients p99 34 to 41 ms down to 11 to 23 ms.
- An append that finds the audit writer idle commits on the caller's thread, skipping the hand-off (about 20 to 40 us).
- End to end on the shared container (one-hop allow call, 1 / 8 / 32 clients): file-backed log 962 / 3,110 / 4,526 to 1,252 / 4,049 / 6,254 req/s with p99 at 8 and 32 clients from 15.5 and 23.8 ms to 5.4 and 13.0 ms; single-client added p50 with a file log 851 to 631 us, in memory 697 to 425 us. Results in `docs/design/bench/2026-10-23-vm-policy-stage.md`.

### Added

- Per-stage timing of proxied calls: histogram `onbehalf_proxy_stage_seconds{stage=...}` on `/metrics` (`token_verify_hit`, `token_verify_miss`, `lease_check`, `policy`, `audit_append`, `blocking_pool`, `upstream`, `response`, `total`; buckets from 1 us to 1 s) and the same figures as `tracing` debug fields. `onbehalf_proxy::Stage` and `Authorizer::observe_stage` (default no-op) let the proxy report its own stages. `onbehalf-bench` enables `/metrics` on the server it starts, reads the histograms around each measured window and prints a per-stage table (`--metrics-url` for an external server, `--metrics-port` for `--print-config`). First run in `docs/design/bench/2026-10-23-vm-proxy-stages.md`.
- Fuzz targets (`fuzz/`, cargo-fuzz on nightly, outside the workspace) for token and DPoP verification, `ou_sig`, delegation chains, names, capability attenuation (differential: an attenuated set never permits a call its parent does not), the proxy's JSON-RPC, session-header, body-limit and SSE handling, policy context building and AuthZEN, and audit export verification. ### Security

- SR-32: the Python and TypeScript SDKs raise `Denied` / `DeniedError` for a JSON-RPC `-32003` only when the response carries `X-Onbehalf-Decision-Id` and `data.decision_id` is one of the ids in it; an upstream's own `-32003` is an `RpcError`.
- SR-35: `onbehalf --admin-token` and `--client-secret` print a warning to stderr (arguments show up in `ps` and shell history); docs, README and the leak demo use the environment or stdin. `--token` and `--subject-token` are unchanged (`ONBEHALF_TOKEN`).
- SR-22 (info): store I/O no longer blocks tokio workers, and AuthZEN batches are bounded by `[authzen] max_batch`. SR-21 (info, partial): audit checkpoints are signed by the issuer key and verified against the JWKS; shipping them off the host is still up to the operator.
- SR-08 (high): AuthZEN evaluated unsigned chains from unauthenticated callers, so anyone who had seen a lease id could get decisions and write audit records for a forged user. The bearer is now required by default; body chains need a PEP credential, and every hop's lease must be bound (at issuance, write-once) to the digest of the chain prefix that created it.
- SR-10 (high): the `actor` of a token exchange was asserted, not authenticated, so any token holder could mint a child naming any agent. The actor now authenticates with its `[[agents]]` secret and must match `actor`; an agent already in the chain is refused (`duplicate_actor`).
- SR-11 (medium): `Mcp-Session-Id` was not bound to the caller, so another user's token could use, listen on or end a session. Session ids are bound to the originating user and root lease; mismatches get 403 `session_mismatch` and an audit record. Logs, policy context and audit records carry a hash prefix of the id, never the id.
- SR-12 (medium): tools missing from the catalog were evaluated as not `sensitive`, so `forbid ... when { resource.sensitive }` failed open for them. They are now denied with `tool_not_in_catalog` unless `[policy] unknown_tools` says otherwise.
- SR-15 (medium): the example config's fixed admin token was accepted on any bind address. Weak or placeholder admin tokens now stop the server off loopback, and admin actions (lease revocation, policy reload, dev root mint) are written to the audit log.
- SR-16 (low): `DelegationChain::validate_at` now rejects empty agent and lease ids, `issued_at` at or after `expires_at` or before the parent's, and repeated leases or agents.
- SR-24 (info, partial): each OIDC ID token or ID-JAG mints at most one root token, a parent token delegates to a given actor at most once (in-memory replay cache, `invalid_grant` / `replayed`), and a root token never outlives the credential it came from.
- Proxy: `tools/list` results delivered over SSE were passed through unfiltered (SR-23). List results are now filtered in JSON bodies, JSON-RPC batches and `text/event-stream` bodies. A list request answered with an unparseable body, or a content type that is neither JSON nor SSE, gets `502` instead of an unfiltered result.
- SR-29 (medium): an ECDSA-signed ID token without `jti` could be redeemed for a second root token by re-encoding its signature (`s` to `n - s`), because the replay cache hashed the whole credential. It now hashes the JWS signing input.
- SR-30 (medium, completed): the release workflow, which can push and sign images and create releases, ran third-party actions from mutable tags and restored a shared cargo cache. Every action in `release.yml` is pinned to a commit SHA and the release build starts without a cache. The Dockerfile base images (`rust:1-bookworm`, `debian:bookworm-slim`) are pinned by digest, `actions/checkout` and `dtolnay/rust-toolchain@stable` are pinned by SHA in the other workflows, and Dependabot now also tracks the `docker` ecosystem. Some actions in `ci.yml`, `docs.yml` and `sdk-*.yml` are still on tags.
- SR-31 (low): the Python SDK put server names and lease ids into URL paths unencoded, so `..`, `?` or `/` in them sent the request (with the admin or delegation bearer) to another endpoint. They are now percent-encoded, and `.` and `..` are refused.
- SR-34 (low): an upstream named `onbehalf` could write tool-call audit records that look like the server's own issuance, renewal and admin records. The name is now reserved.
- SR-39 (info): an IdP credential with a float `exp` was refused as expired.
- SR-27 (medium): the proxy's session check read only the first `Mcp-Session-Id` header (none if it was not visible ASCII) but forwarded every one, so a caller could slip another principal's session id past the SR-11 binding. `POST`, `GET` and `DELETE` now answer 400 to more than one `Mcp-Session-Id` or a value outside visible ASCII, forward only the checked value, and drop session headers from an upstream response that carries more than one.
- SR-28 (medium): a `GET` listen stream or a `tools/call` answered over SSE was lease-checked only when it opened, so revocation and token expiry did not end it. Streamed responses are now re-checked every `[proxy] stream_recheck_seconds` (new, default 2) and ended at the first failure, after a final SSE event with JSON-RPC error `-32001` and `data.reason` (`lease_revoked`, `token_expired`, ...). SSE bodies are relayed event by event; a final event without its terminating blank line is dropped.
