## [0.1.0] - 2026-10-24

### Highlights

Attenuo is an authorization layer for AI agents that call tools over MCP. A user's authority reaches an agent, and every sub-agent it hands work to, as a signed delegation chain that can only narrow at each hop (RFC 8693 token exchange), and an enforcing proxy checks every `tools/call` against that chain and Cedar policies before anything reaches the upstream server.

0.1.0 is the first release. It ships one server process with token exchange, an AuthZEN decision endpoint, the MCP proxy and a hash-chained audit log with signed checkpoints. Leases revoke a delegation and everything below it, including calls and streams already in flight. Tokens can be bound to the agent's key with DPoP. Output labelling marks untrusted tool results and sends later risky calls to an operator for approval. Run limits cap call counts, amounts and destinations per delegation. The `attenuo` CLI, an admin console and Python and TypeScript SDKs cover the same API.

The injection-suite figures in the docs come from synthetic, model-free cases written alongside the policies they test, so they show what the mechanisms can block, not how a real agent under attack fares.
### Added
- A response stream the proxy ends because its leases are no longer live or its token expired (the SR-28 re-check of a `GET` listen stream or a streamed `POST` answer) is now a `deny` audit record: tool `stream.end`, the reason (`lease_revoked`, `lease_expired`, `lease_unknown`, `lease_error`, `token_expired`), the token's chain, the proxied server and the session's hash tag, counted in `decisions_total{decision="deny",reason}`. The stream's final `-32001` event carries the record id in `data.decision_id`. One record per stream at most, and only for a token that verified when the stream opened (SR-18). A stream the client drops or the upstream ends is an `info` or `debug` log line, not a record. `attenuo_proxy::guard` gains `STREAM_END_TOOL`, `StreamRecord`, `StreamGuard::recording` and `end_event_recorded`; the test double `FakeMcpServer` can serve a `GET` listen stream (`with_listen_stream`) and replay given messages on `Last-Event-ID` (`with_replay`, `last_event_ids`); by default `GET` still answers `405`, so the examples and their audit counts are unchanged.
- New deny reason `input_type_mismatch`: a call argument the catalog declares a type for (`[policy.catalog.<server>.<tool>] inputs`) is checked before Cedar, and a present, non-null value of another type (a number where `repo` is a `string`, a string or `2.5` where a `long` is declared, a single value where a set is) is denied with that reason and the argument named in the diagnostics. Before, it reached Cedar: a policy that read it raised a type error (`policy_error`), and if no policy read it the call went through to the upstream. Integral numbers (`5.0`) count as `long`, as Cedar sees them; undeclared arguments, and tools evaluated under `unknown_tools = "sensitive"` or `"allow"`, are not checked. Works the same through the MCP proxy, AuthZEN, the admin dry run and `attenuo policy test`; the console explains the reason.

- `examples/multi-hop-demo`: delegation narrowing over three hops (alice, a planner, a coder, the GitHub MCP tools of the fake upstream), played by `run.sh` with the CLI. The planner's root token holds four tools under `acme/` with `may_act: [coder]`; the coder's exchange narrows `repo` to `acme/api`, adds a `distinct` limit of 1 on `repo`, drops `list_issues` and `create_issue`, and sets `may_act: []` (`attenuo token exchange --no-delegation`). The run shows a refused widening exchange, a refused further delegation, an allowed read, a write to `main` refused by policy, `create_issue` refused by capability, a second repository refused with `budget_exhausted`, the chain revoked by `chain_id` (`lease revoke --chain-id`, preview first) and `lease_revoked` on the coder's next call, then `audit verify` (14 entries, the two refused exchanges among them, checked) and `audit show --id` of the refused write. `policy_test.yaml` has 14 cases and exercises all five policies. CI runs the demo in the `demo` job and its tests in `policy-tests`; `scripts/dev.sh`, the justfile and `scripts/release-check.sh` run them too.
- Revoke by user or chain: `POST /admin/leases/revoke` (admin) with `{"user": "<sub>"}` or `{"chain_id": "<first-hop lease>"}`, exactly one, and an optional `reason` revokes every unrevoked lease of that originating user or delegation chain (expired ones included, since a renewal could revive them), each with the descendant cascade, in one transaction, and answers `{selector, preview, matched, revoked, matched_count, revoked_count, truncated, reason, audit_id}`. `?preview=true` is a dry run that writes nothing. One `admin.lease.revoke` record per call names the first 256 revoked leases, with the selector, reason and count in its digested arguments. The server now records each issued lease's originating subject (`LeaseStore::record_subject`, SQLite table `lease_subjects` created at open); leases registered by an older server have none and are matched only by `chain_id`. CLI: `attenuo lease revoke --user SUB | --chain-id ID [--preview]` ([HTTP API](docs/reference/http-api.md#revoke-by-user-or-chain)).
- Revoke by MCP session: `POST /admin/leases/revoke` also takes `{"session": "<Mcp-Session-Id>"}`. When the proxy binds a new session for a verified token, the server records the session id's SHA-256 (the audit tag is its first 12 characters), the upstream server and the caller's chain id (`LeaseStore::record_session`, write-once per session and server; SQLite table `lease_sessions`, created at open on older stores). The selector hashes the given id, resolves it to the chains recorded for it and revokes or previews them as `chain_id` would. The answer and the `admin.lease.revoke` record's digested arguments show `{"session_tag", "chain_ids"}`, never the raw id; an unknown session is a 200 with empty lists. The proxy gains `Authorizer::record_session` (default: nothing) and `session::session_digest`. CLI: `attenuo lease revoke --session ID [--preview]`, exclusive with a lease id, `--user` and `--chain-id`. The console has no session action ([HTTP API](docs/reference/http-api.md#revoke-by-session)).
- Admin console: revoke a whole chain or every lease of a user from the lease page. `GET /admin/leases/{id}/tree` now gives each node and ancestor `chain_id` (the chain's first-hop lease) and `subject` (the originating user recorded at issue, `null` for leases registered before subjects were recorded), read for the whole tree with one `LeaseStore::subjects` call. The lease page shows the originating user and has "Revoke chain…" and, when the lease has a subject, "Revoke all for <subject>…". Both open a dialog that previews `POST /admin/leases/revoke?preview=true` (counts, first ids, `truncated`), asks for a reason and a typed confirmation, and then shows the result with a link to the audit record. - Run limits, phase 2 second slice ([design](docs/design/run-limits.md#as-built-distinct-and-derived-destinations)). A capability's `limits` may carry `distinct: {arg, max}`: at most `max` distinct values of `arg` across the run's allowed calls, each list element counted, charged against every hop like the other kinds and stored as keyed hashes plus a count, so a repeat of a seen value costs nothing. A child's `distinct` must be on the same argument with `max` no larger, or implied by `calls: m` with `m <= max`. `calls_per` and `distinct` take `"derive": "host"` to count the host of a URL argument (WHATWG parse, lowercased, no port, user info or trailing dot); records, `data.limit` and the console name it `url#host`, and a value with no host is `limit_arg_invalid`. The catalog's `destination` accepts `"<input>#host"` for run usage, where values without a host count as one destination. `context.budget.destination_new`, the decision `budget` member, the refund and AuthZEN cover `distinct`. Servers older than this refuse tokens that use either. `GET /admin/leases/{id}/tree` gives every node a `budget` (its limits as issued, now kept per hop in the lease store for display, with `used` and `remaining`, and the run's usage on the root lease); the console's lease page shows a run-limits table and the decision view shows the record's `budget` and `usage`. `attenuo` prints `distinct` and derived limits. SDKs: Python `ArgLimit`, `Limits`, `Capability.with_limits(..., distinct=...)` and `Capability.typed_limits`; TypeScript `distinct` and `derive` on `Limits` / `ArgLimit`, `argLimit()` and `countedArg()`; both read the tree's `budget`. `config/policies/run-usage.cedar` adds a per-site soft rule (`ask_on_a_new_site`). The frozen injection-suite rules are unchanged; nothing here has been run on the suite yet.
- Run limits, phase 2 first slice: run usage as a policy input ([design](docs/design/run-limits.md#as-built-run-usage-and-soft-limits)). For every tool the catalog marks destructive, the server keeps per run, across every hop, the allowed calls of the tool, the sum of the catalog's new optional `amount` input and keyed hashes of its new optional `destination` input, and Cedar sees them as `context.usage.calls`, `.amount` and `.destination_seen` (always present; zero and false for other tools). Usage is charged with the run-limit counters after the policy allows, refunded with the decision, never refuses by itself, and is deleted when the run's root lease is revoked. A soft limit is a `forbid` with `@obligation("approval")` over `context.usage`, settled by the existing approval flow; no token change. The decision record gains `usage` (omitted for other tools), the `-32008` / `-32003` error data and AuthZEN answers carry it, and the admin dry run and `attenuo policy test` take it as input. Example policies with tests: `config/policies/run-usage.cedar`. An allowed destructive call now makes one lease-store write; with no limit matching, unreadable usage is the worst case for the policy instead of a denial.
- Output labelling, phase 2: argument-level taint (ADR-0009, design section 3.4). The proxy fingerprints every untrusted result before relaying it (`attenuo_core::fingerprint`: JSON string leaves of 8 characters or more, entities such as URLs and hosts, e-mail addresses, IBAN-shaped strings, runs of 6 or more digits and paths, and winnowed 24-character k-grams of text of 31 characters or more, after NFKC, lower-casing and whitespace collapsing; at most 2,000 from the first 1 MiB) and keeps them, HMAC-SHA-256 keyed per store, in a per-run span index (`LeaseStore::{add_spans, find_spans}`, new SQLite table `run_spans`, created in place; at most 20,000 hashes per run, oldest whole results evicted; deleted when the root lease is revoked). The `tool_result` record's `fingerprints` is now the count stored (0 for a trusted result); a failed index write is a `label_error`. For a destructive call (or one not in the catalog) on a tainted run, every argument not pinned by an `equals` or `one_of` constraint of a hop that permits the call is looked up: Cedar sees `context.args_contain_untrusted` and `context.untrusted_args`; an unreadable index makes every unpinned argument untrusted (kind `unreadable`). Decision records carry `labels.untrusted_args: [{arg, seq, kind}]` (at most 64, omitted when empty, so other records hash as before); `-32008` and `-32003` data, AuthZEN `context`, pending approvals (new `approvals.untrusted_args` column) and approval answers carry `untrusted_args` when non-empty. The dry run and `attenuo policy test` take `session.untrusted_args` and `session.args_contain_untrusted`. `config/policies/output-labels.cedar` adds `confirm_destructive_with_untrusted_args`. The console's decision view shows `tainted_by` and the matched arguments; the approval page shows the matched arguments. Injection suite: arm `attenuo_labels_args` with `policies/labels-args.cedar` (hashed under `added_later`), skipped on servers without phase 2. API: `attenuo_policy::{ArgLabels, CallLabels::args}`, `AuthDecision::untrusted_args`, `RecordLabels::untrusted_args`, `UntrustedArg`, `UntrustedKind`; `Pipeline::record_result` and the `jsonrpc` error builders take new parameters.
- Signed approval token (output labelling section 3.7, ADR-0009). Every answer about a granted, unexpired approval carries `approval_token`, a JWT signed with the issuer key (header `typ: attenuo-approval+jwt`, same `kid` and JWKS as delegation tokens) whose claims bind it to the run (`chain_id`), the calling hop (`lease`), the call hash (`ch`), the approval (`jti`) and, for a DPoP-bound hop, its key (`cnf.jkt`). A retry presents it in `params._meta["dev.attenuo/approval"]` (AuthZEN: `context.approval_token`); the proxy removes the key before the upstream and before the call hash. The server verifies it, checks the binding and consumes the named approval once through the lease store; any failure denies with the new reason `approval_invalid`. The decision record adds `approval.presented: "token"`. SQLite `approvals` gains a `jkt` column (migrated in place). Offline verification: `attenuo approval verify`, Python `verify_approval_token` and `call_hash`, TypeScript `verifyApprovalToken` and `callHash`; `call_tool_with_approval` / `callToolWithApproval` retry with the token, and `call_tool(..., approval_token=...)` / `callTool(..., { approvalToken })` send one.
- SDKs: operator approval calls on the admin clients. Python `AdminClient` and `AsyncAdminClient` `approvals(chain_id=None, *, state=None, limit=None)`, `approval(id)`, `grant_approval(id)` and `decline_approval(id)`; TypeScript `AdminClient` `approvals({ chainId, state, limit })`, `approval(id)`, `grantApproval(id)` and `declineApproval(id)` (new type `ApprovalQuery`). They call `GET /admin/approvals`, `GET /admin/approvals/{id}` and `POST /admin/approvals/{id}` and return the existing `Approval` type; fields it does not name are in `raw`. A 409 (`approval_not_pending`, `approval_expired`, `lease_revoked`) or 404 is an `ApiError` as everywhere else.
- Run limits, phase 1 (ADR-0010, [design](docs/design/run-limits.md)). A capability may carry `limits`: `calls`, `sum: {arg, max}` (a total over one non-negative integer argument) and `calls_per: {arg, max}`; a child's limits must narrow its parent's (`covers`, `validate_at`), and `/token` fills in missing limits and clamps a child's `calls` and `sum` to what the parent hop has left. Every allowed call is charged against every matching limited capability in every hop (hop 0's lease is the run), in one `IMMEDIATE` lease-store transaction after the policy decision and before the audit append, refunded if the append fails; `calls_per` values are stored as HMAC-SHA-256, and `sum` charges commit with `synchronous=FULL`. A call over a limit is denied in the capability stage before Cedar with `budget_exhausted` (`-32003` with `data.limit: {hop, kind, arg, max, used}`), unreadable counters with `budget_error`, an uncountable argument with `limit_arg_invalid`; no approval passes them. Cedar sees `context.budget.{limited, calls_remaining, amount_remaining, destination_new}`, always present; decision records of charged calls carry `budget.charged` (other records hash as before); AuthZEN answers carry `context.budget`, `context.limit` and `context.charged`; the dry run reads counters without charging. `POST /admin/budgets/refund {decision_id, reason}` refunds one decision once (`admin.budget.refund`). Example policy `config/policies/run-limits.cedar` with tests; `attenuo` shows and accepts limits; Python `Capability.with_limits` and TypeScript `withLimits`. Injection suite: arms `attenuo_limits` and `attenuo_labels_limits` with the frozen rule `policies/limits-rule.json` (`calls: 1` on every non-read capability, hashed under `added_later`), skipped on servers without limits; the combined arm settles approvals through the runner's labels-arm path, so a granted retry is charged. Not yet run on the corpus. `distinct`, `context.usage` and windows are later phases.
- Injection suite, preparation for output labelling: a per-call `output:` in the case format (the text the fake upstream returns; at most 600 characters), written for all 46 reads in `cases/dev/`; `fake_mcp` takes `POST /script` with `{"outputs": {"<tool>": ["text", ...]}}` and returns each text once, as a second content item after the echo; the runner checks that every allowed call with an `output:` got it back. New arm `attenuo_labels` (the `attenuo` arm plus `policies/labels.cedar`, the two `@obligation("approval")` policies of the output-labelling design, hashed in `cases/test/POLICY_HASHES.json` under `added_later`) with a scripted approver and a `gated` outcome for JSON-RPC `-32008` `approval_required`. The arm is skipped with a message on a server that rejects `labels.cedar` or does not answer a probe with `-32008`, which is the case on main. `cases/test/PROPOSED-READS-2026-10-24.md` proposes reads and outputs for the test split; the test cases themselves are unchanged. Numbers of the five existing arms are unchanged (dev: attenuo allows 10/60 attack calls, denies 3/69 benign; test: 7/38 and 3/29).
- Approvals for calls gated with `@obligation("approval")` (output labelling, phase 1, ADR-0009). A gated call opens an approval in the lease store (SQLite table `approvals`, and the memory store) bound to the run's `chain_id`, the calling hop's lease and the call's `call_hash`, with the call, the run's labels, and `expires_at` = the earliest of now plus `[approvals] ttl_seconds` (default 120), the hop's token expiry and its lease expiry; a repeated gated call reuses the pending one. `-32008` now carries `approval_id` and `expires_at`. The run's originating user decides with `POST /approvals/{id}` and an OIDC ID token verified as at hop 0 (`aud` = `[approvals] client_id`, else the root agent's client id; same `sub` and `iss`; used once through the intake replay cache); a delegation token is refused (403 `agent_token_refused`). The operator decides with `POST /admin/approvals/{id}`. `GET /approvals/{id}` (the user, or an agent of the same run), `GET /admin/approvals?chain_id&state&limit` and `GET /admin/approvals/{id}` read them. A granted approval is used by the identical retry from the same hop, once: Cedar sees `context.approval.present` and `by` (`user` or `operator`), and the decision record carries `approval: {id, by}`. Revoking the lease ends its approvals. New audit kinds `approval_request` and `approval_grant`; records without an approval hash exactly as before (a golden test pins both). AuthZEN answers carry `approval_id`, `expires_at` and, when a grant was used, `approval`. The policy dry run takes `approval: {"by": ...}`, and `attenuo policy test` cases take `approval: { by: user }`.
- `attenuo approval list|show|grant|decline` (operator), and `attenuo call` prints `APPROVAL REQUIRED` with the approval id and exits 2 for a gated call. Console page `#/approvals` and `#/approval/<id>` with **Grant** and **Decline** (with `[admin_ui] allow_write`).
- SDKs: Python `ApprovalRequired` (a `Denied` with `approval_id`, `expires_at`, `call_hash`) for a proxy-vouched `-32008`, `ApprovalNotGranted`, `Approval`, and `Client.get_approval`, `wait_for_approval` and `call_tool_with_approval` (sync and async); TypeScript `ApprovalRequiredError`, `ApprovalNotGrantedError`, `Approval`, and `getApproval`, `waitForApproval` and `callToolWithApproval`. - Output labelling, phase 1 (ADR-0009). The catalog takes `destructive` (default: not `readonly`) and `output` (`"untrusted"`, the default, or `"trusted"`), and `[policy] import_annotations = "never" | "narrowing"` (default `never`) lets MCP `readOnlyHint: false` and `destructiveHint: true` restrict a catalog tool, never loosen one. After every allowed `tools/call`, `resources/read`, `prompts/get` and `completion/complete`, the proxy reports the upstream's answer (JSON, or SSE event by event, upstream JSON-RPC errors included) before relaying it, and the server appends a new `tool_result` audit record (the call's `decision_id`, SHA-256 and size of the RFC 8785 JSON of the result, label, fingerprint count; no content). An untrusted result labels the delegation run, keyed by `chain_id`, in a new `run_labels` table (first label per source; a memory store equivalent). If the record cannot be written, the answer is withheld and the agent gets `-32003` with reason `label_error`. Cedar sees `resource.destructive`, `context.session.tainted`, `context.session.tainted_by`, `context.args_contain_untrusted` (always `false`), `context.untrusted_args` (empty), `context.approval.present` (always `false`) and `context.approval.by` (`""`), all always present. A `forbid` annotated `@obligation("approval")` gives the new reason `approval_required` when every applicable forbid carries it and a permit would otherwise allow the call; the proxy answers JSON-RPC `-32008` with `data: {reason, decision_id, call_hash}` and does not forward the call, and AuthZEN answers add `call_hash` to `context`. Decision records of calls on a tainted run carry `labels: {tainted_by: [seq]}`; the new record fields are omitted when empty, so existing entry hashes do not change. `POST /admin/policies/evaluate` takes an optional `session` and echoes the labels it used. - Audit query API for the admin console (read-only). `GET /admin/audit` takes optional exact-match filters `kind` (comma-separated), `decision`, `reason`, `subject`, `agent`, `lease`, `server`, `tool`, `chain_id`, `since` and `until` (RFC 3339, `[since, until)`), and pages newest first with `order=desc&before=N` (the answer adds `prev`); without the new parameters it answers exactly as before. `%` and `_` in a value are literal and `agent=l1` does not match `l10`. ### Security

- Fuzzing round 2, FZ2-2 (low): `"derive": "host"` and `destination = "url#host"` took the host of any URL scheme, and a non-special scheme (`ssh://`, `git://`) has an opaque host that WHATWG neither percent-decodes nor maps through IDNA, so `ssh://a.ex%61mple/` and `ssh://a.example/` counted as two hosts (a `calls_per` budget each, a fresh `destination_seen`). Only `http`, `https`, `ws`, `wss`, `ftp` and `file` URLs have a host now; any other URL has none, so a limit refuses it with `limit_arg_invalid` and run usage counts it raw. A behaviour change for tools that take `ssh://` URLs under `#host`.
- Fuzzing round 2, FZ2-1 (low): `"derive": "host"` stripped one trailing dot, so `https://a.example../` counted as host `a.example.`, apart from `a.example`, and got a `calls_per` budget of its own (and a fresh `destination_seen` in run usage). Every trailing dot is stripped now, and a host left with an IPv4 spelling (`0x7f.1..`) is parsed again so it counts as the address.
- Fuzzing round 2, FZ2-3 and FZ2-4 (low): a refund of run usage subtracted what the decision logged, although a usage counter saturates at `MAX_LIMIT`, so after a call with an amount near `MAX_LIMIT` a refund could leave `context.usage.amount` below what the remaining calls had charged; a usage counter is now recomputed from the unrefunded charges. The SQLite refund also no longer sums a decision's rows with an integer `SUM` that could overflow and fail the refund.
- SR-55 (medium): concurrent calls of one run could all pass a policy over `context.usage` or `context.budget` (the shipped `run_spend_cap_2000`, every ask-on-repeat rule), because each read the figures before any was charged; a per-run lock now covers the read through the charge.
- SR-56 (medium): a `"derive": "host"` limit or `destination = "url#host"` counted `https://a.example\@b.example/` as `a.example`, which Python's `urllib` and `httpx` fetch as `b.example`; a URL with a backslash, whitespace or a control character now has no host (`limit_arg_invalid` under a limit).
- SR-57 (medium): a list argument under `calls_per`, `distinct` or a usage `destination` wrote two rows per element while holding the store's write lock; a call may now count at most 256 values per limit (more is `limit_arg_invalid`; in usage the list is one destination).
- SR-58 (low): the WAL checkpointer's database-file sync closed a descriptor of the file, which drops the process's SQLite locks, so another process could delete the WAL of the live store; the descriptor is now kept open.
- SR-59 (low): a limit's `arg` may not contain control characters or `#`, and `attenuo lease tree` escapes it, so a sub-agent cannot write terminal escapes into an operator's screen.
- SR-60 (low): `GET /approvals/{id}` answers 404 to a delegation token whose lease was revoked or has expired.
- SR-61 (low): the Python sdist lists its files, and `scripts/release-check.sh` refuses untracked files under `sdk/python`, so a stray local file is not published.
- SR-62 (low): refunding the decision that first used a `distinct` value made the value new again although a later, unrefunded call had also used it. A call that uses a seen value now logs a zero-amount charge row, and a refund frees a value only when no other unrefunded decision logged it, in both lease stores. A decision whose values were all seen can now be refunded (once).
- SR-63 (low): in run usage every value with no host (`destination = "url#host"`) counted as one destination, `null`, so after one such fetch `ask_on_a_new_site` never asked for another. A hostless value now counts as itself, wrapped as `{"raw": value}` so it never equals a host.
- SR-64 (low): with `[approvals] client_id` unset, an ID token for the root agent's own OAuth client approves its gated calls. When a loaded policy carries `@obligation("approval")` and `client_id` is unset, the server now logs a warning at startup and after each policy reload, and refuses to start when `[server] listen` is not loopback.
- SR-21: signed audit checkpoints can leave the host as soon as they are signed. New `[audit.sink]` with `kind = "webhook"` (`POST`, optional bearer token, any 2xx), `"file"` (append one JSON line and `fsync`, for a file on another mount that your own agent ships) or `"s3"` (`PUT` to an S3-compatible bucket, AWS Signature Version 4 implemented in the server on `ring`; no new dependency). Each delivery is the canonical JSON object `attenuo-shipped-checkpoint-v1`: the checkpoint, its `kid` and `signature`, `public_url` and `checkpoint_sha256`. The log's hook only queues; a background thread delivers in order with retries and jittered exponential backoff (`initial_backoff_ms`, `max_backoff_seconds`). The queue is bounded (`queue_capacity`, default 1024) and drops the oldest when full. New metrics `attenuo_audit_sink_{delivered,failures,dropped}_total`, `attenuo_audit_sink_queue_depth`, `attenuo_audit_sink_oldest_undelivered_timestamp_seconds`; `/readyz` adds `degraded` and `checks.checkpoint_sink` when a sink is configured (degraded when the queue is full or lags more than `max_lag_seconds`; 503 only with `fail_readiness = true`). `attenuo audit verify --file <export> --checkpoints <shipped.jsonl>` cross-checks an export against the shipped copies and exits 2 for a checkpoint signed again after shipping (same seq, different hash or signature), one deleted from the export, an entry that no longer hashes to the shipped `head_hash`, two different shipped checkpoints for one seq, or a shipped copy that does not verify. New `attenuo_audit::{ShippedCheckpoint, parse_shipped, cross_check, checkpoint_sha256}`.
- SR-40: a DPoP exchange sign-off (`subject_token_dpop`) is consent to one delegation only. BREAKING: the sign-off must carry `child_jkt` (the thumbprint of the key in the exchange's `DPoP` header) and `child_actor` (the request's `actor`), or the exchange is 401 `invalid_dpop_proof`; a plain proof by the parent's key is no longer accepted. - SR-41: a DPoP proof's `jti` is recorded only after the proof matched the token's key, so proofs by a wrong key (a thief holding a bound token) can no longer fill `[token] dpop_replay_capacity` and turn every bound request into a 503. An exchange's header proof and sign-off are recorded together or not at all.
- SR-42: without `[server] public_url`, DPoP `htu` is checked against `http://<Host>` only for a loopback `Host`; any other `Host` is treated as `localhost`, so a proof made for another server cannot be replayed here by sending its host name.

- SR-44: an exchange's replay check and its `actor_token` are consumed together, so an exchange refused as a replay no longer burns the caller's actor token.
- SR-45: `POST /token` refuses the reserved agent id `attenuo` as the exchange `actor` (400 `invalid_request`, `reserved_agent`), whether it came from `require_actor_auth = false` or an `[[actor_trust]]` mapping.
- SR-46: the verified-token cache no longer stores tokens over 16 KiB (they are verified on every request instead), so its memory is bounded by bytes as well as by count.
- SR-47: the proxy answers a full DPoP replay cache with HTTP 503 (JSON-RPC `-32006`, `data.reason` `dpop_replay_cache_full`, `Retry-After`) instead of 401 `invalid_dpop_proof`, so clients retry instead of treating their key as bad.
- SR-48: the RFC (P4) and the threat model now say that `[audit] durability = "normal"` can lose the newest records, including those of forwarded calls, on a power failure.
- SR-49: one principal (the chain's root lease) can hold at most `[proxy] max_sessions_per_principal` (default 64) live `Mcp-Session-Id` bindings; one more gets HTTP 429, JSON-RPC `-32007` (new, `attenuo_proxy::jsonrpc::CODE_TOO_MANY`), `data.reason` `too_many_sessions`, `Retry-After: 30`, and other users keep opening sessions. Before, one user could fill all `max_sessions` slots and leave everyone else with 503 until the TTL. When the proxy refuses a session (this cap or `session_registry_full`), it now sends the upstream an MCP `DELETE` for the session the upstream just created, best effort, instead of leaving it open there. `BindOutcome` gains `PrincipalFull`; `ProxyConfig::max_sessions_per_principal`, `with_max_sessions_per_principal`, `SessionRegistry::with_max_per_principal`, `REASON_TOO_MANY_SESSIONS`, and the test doubles `FakeMcpServer::with_fresh_session_ids`, `sessions_opened` and `deleted_sessions` (it now answers `DELETE`) are new.
- SR-53: the LangChain and Claude Agent SDK examples count a `-32003` as attenuo's denial only when its `data.decision_id` is in the proxy's `X-Attenuo-Decision-Id` response header (collected with an `httpx` response hook on the `mcp` client), as the SDKs do since SR-32; any other `-32003` is shown as an upstream error. The Claude Agent SDK example's README notes that its live mode cannot make this check.
- SR-20: everything attenuo hashes or signs as JSON is RFC 8785 (JCS) canonical JSON (new `attenuo_core::jcs`): members sorted by UTF-16 code units, the RFC's string escaping, numbers as ECMAScript writes the double; integers beyond ±2^53 keep all their digits instead of being rounded. Before, the bytes were `serde_json` output, and `serde_json`'s `preserve_order` feature (switched on workspace-wide by a dependency) kept nested objects in insertion order, so a verifier built without it, or in another language, computed different bytes. This covers the chain digest (and the lease bindings that the AuthZEN `chain_not_issued` check compares), the argument digest, `ou_sig`, audit entry hashes and checkpoint signatures. Argument constraints now compare JSON values the same way (`1` equals `1.0`, member order ignored) in `Eq`, `Ord`, `satisfied_by` and `implies`, so equality agrees with ordering and with the digest. `serde_json` parses with `float_roundtrip`. BREAKING: `ou_sig` is version 3 (context `attenuo-ou-v3`, claim `ou_sig_v: 3`); v2 tokens are refused with `UnsupportedOuSig(2)` and must be re-issued from the root. BREAKING: the audit entry hash is SHA-256 over `JCS(["attenuo-audit-entry-v2", seq, prev_hash, record])` (`attenuo_audit::ENTRY_HASH_VERSION`), `record_json` is stored canonically, and the construction is recorded in a new `audit_meta` table; an audit database written by an earlier build is refused at startup with an error that says to move it aside and start a new log. There is no migration: no logs were released in the old form. BREAKING: exports are format `attenuo-audit-export-v2` with canonical lines; `v1` exports are refused with a message that says why. The checkpoint signing input is unchanged byte for byte (context `attenuo-checkpoint-v1`).
- Fuzzing F5: `attenuo audit verify --file` and `attenuo_audit::verify_export` are strict. An export must have a header (it declares `from..=to`), and it fails if it holds entries outside that range (`outside_range`, new) or entries after its last valid checkpoint (`unsigned_tail_rejected`, new). Before, a signed export of `1..=5` with a forged entry 6 appended (chained and hashed) verified `ok` with `unsigned_tail = 1`. BREAKING for exports that end after their last checkpoint: pass `--allow-unsigned-tail` (or `verify_export_with(.., VerifyOptions { allow_unsigned_tail: true })`) to accept them, or sign the head (`GET /admin/audit/checkpoint`) before exporting. Entries outside the range fail either way.
- Fuzzing F4: an audit entry with `seq` = 2^64 - 1 and a correct hash no longer overflows the chain walk (a panic with overflow checks on, a wrap to 0 without); it is a bad entry, and `audit verify --file` reports it.
- SR-50: a commit that writes a signed audit checkpoint runs with `synchronous=FULL` at any `[audit] durability`, before the checkpoint reaches the `on_created` hook (the way checkpoints get shipped off the host). At `normal`, a power failure could take back entries that a shipped checkpoint already covered, and `audit verify` against that checkpoint would then report tampering that did not happen. A batch that turns out to cross a checkpoint is rolled back before inserting anything and committed again at `FULL` (SQLite cannot change `synchronous` inside a transaction): one extra transaction per checkpoint.
- SR-51: `SqliteLeaseStore::revoke` returns the revocation's result; if setting `synchronous` back afterwards fails, that is logged and the connection stays at `FULL`, instead of reporting a failed revocation that took effect.
- Fuzzing fixes (see `docs/design/fuzzing.md`). DPoP: a proof's `iat` far from the server clock overflowed the freshness check, a panic in debug builds and, in release builds, a proof with `iat = now - 2^63` passed as fresh; `iat` is now compared with `abs_diff`. Proxy: a list answer whose numeric `id` came back spelled differently (`1.0` sent, `1` answered by a JavaScript upstream, or a large or fractional id re-printed) skipped the list filter, so the client saw tools its chain cannot call; numeric ids now match by value. Token: `Issuer::issue_root` refuses (`TokenError::Malformed`) a user block or root hop with a time RFC 3339 cannot write (before year 0, such as an IdP `auth_time` of -1e11), which used to panic in the `ou_sig` encoding.
- SR-24: delegation tokens can be sender-constrained with DPoP (RFC 9449), so a leaked token is useless without the agent's key. A `DPoP` proof (Ed25519 or P-256) on `POST /token` or `POST /admin/root-token` binds the new token to the key (`cnf.jkt`, `token_type: "DPoP"`); a bound token is then accepted only with a fresh proof by that key (`htm`, `htu`, `ath`, `iat` within `[token] dpop_max_age_seconds`, unseen `jti`) by the proxy, `/token/renew`, the AuthZEN endpoints and `/token` as the parent of an exchange. The child of a bound token is always bound; binding it to another key needs the parent key's consent in `subject_token_dpop`. Failures are 401 `dpop_required` / `invalid_dpop_proof` with `WWW-Authenticate: DPoP` (JSON-RPC `-32001` in the proxy). Opt-in and backward compatible: `[token] dpop = "optional"` by default; `"required"` refuses unbound tokens. Audit records carry `dpop_bound: true` when it applies (omitted otherwise, so existing hashes are unchanged).
- SR-14: the detached originating-user signature is bound to the issuer and the root hop. BREAKING: `ou_sig` is now version 2, Ed25519 over `"attenuo-ou-v2" || iss || canonical(originating_user) || canonical(hop 0 {agent, capabilities, issued_at, lease})` (each field length-prefixed), carried with new claims `ou_sig_v: 2` and `ou_kid` (the key that made it) and checked under that key only. Tokens without `ou_sig_v` (version 1) are refused with `TokenError::UnsupportedOuSig`; re-issue them from the root. Nothing was deployed with v1. A user's `ou_sig` lifted from one chain no longer verifies in a chain with another root hop or issuer, even when the outer JWT is re-signed by a trusted key (rotation, multi-issuer). `DetachedSigner::sign` refuses the reserved `attenuo-ou-` contexts. New `attenuo_token::claims::{ou_sig_payload, ou_sig_message}`, `OU_SIG_VERSION`, `OU_SIG_CONTEXT`.
- SR-13: Cedar actions are server-scoped. BREAKING: the action of a call is `Action::"<server>/<tool>"` (still a member of `Action::"invoke"`), so a permit for `github`'s `read_file` no longer matches `read_file` on another upstream. Rewrite `Action::"read_file"` as `Action::"github/read_file"`; `attenuo policy lint` reports every bare action with its line (stage `actions`). `[policy] legacy_bare_actions = true` (deprecated, default `false`, warned at start) keeps the old ids while a policy set is rewritten; policy test files take `legacy_bare_actions` too. `/` is refused in server names and in tool names (except the MCP method names the proxy authorizes, such as `resources/read`) in capabilities, chains, the catalog and the engine, which denies such a call with `invalid_name`.
- SR-25: server and tool names are 1 to 128 ASCII `[A-Za-z0-9_.-]` characters (method names: such segments joined by `/`), compared case-sensitively, never normalized (`attenuo_core::names`). The proxy denies a `tools/call` with any other name (`invalid_name`) and, with `[proxy] require_listed_tools` (default `true`), one whose exact name the upstream never listed in `tools/list` and the catalog does not know (`tool_not_listed`), so an upstream that resolves `Delete_Repo` to `delete_repo` cannot step around a rule on `delete_repo`. Both are audited. BREAKING: capabilities, catalog entries and grants with other characters (spaces, `:`, non-ASCII) are refused.
- SR-36: the proxy's session registry no longer evicts other users' live sessions when full: expired bindings are reclaimed oldest first without a scan, and a new session beyond `[proxy] max_sessions` (default 100000) gets 503 `session_registry_full` (`-32006`, `Retry-After: 30`). Buffered upstream bodies are capped by `[proxy] max_upstream_body_bytes` (default 16 MiB, 502 `upstream_body_too_large`; also the SSE event limit) and request bodies by `max_request_body_bytes` (default 4 MiB, 413 `request_too_large`, read after authentication). `session_ttl_seconds` (3600) is configurable.
- SR-33: declared `originating_user.attributes` types (the built-in `mfa`, `roles`, `tenant`, `email` and `[policy] user_attributes`) are enforced before Cedar runs. A value of another type is denied with reason `attribute_type_mismatch` and audited, so `attributes.status != "suspended"` no longer permits `["suspended"]`. Nothing is coerced.
- SR-37: an ID token is bound to the agent that presents it. BREAKING: `[[idps]] audience` is ignored for ID tokens; `aud` must contain the agent's client id from the new `[[idps]] client_ids` table (default: the agent id), and `azp` must name it when `aud` has several values or `azp` is present. A token for agent A presented by agent B is refused with `credential_audience_mismatch`. The server warns at startup for each agent without an entry.
- SR-38: `GET /readyz` returns a fixed shape, `{"ready":false,"checks":{"audit":"error","leases":"ok"}}`, with the storage error in the server log only. BREAKING: the old `status` field and the per-check `{ok,error}` objects are gone. A `[metrics] listen` off loopback is refused at startup unless `[metrics] allow_public = true`, and logs a warning when it is set.
- SR-17: client-facing errors carry stable reason codes only; the details go to the server log at debug. BREAKING: every 401 from the server is `{"error":"unauthorized","detail":<reason>,"error_description":<reason>}` with the reason `missing_token`, `invalid_token` or `token_expired` (the last only for a token that otherwise verified), instead of the verifier's message. The proxy's JSON-RPC 401 is `-32001` with message `attenuo: unauthorized: <reason>` and `data.reason`; an unreachable upstream is 502 `-32005` with message `attenuo: upstream unreachable` and `data.reason = "upstream_unreachable"`, without the `reqwest` text or the upstream URL. A JWKS fetch failure answers a fixed detail and logs the cause. BREAKING: AuthZEN `context.diagnostics` are returned only as the new `[authzen] diagnostics = "always" | "peps" | "never"` allows; the default `peps` returns them only to callers that authenticate as a `[[peps]]` client (`pep_secret`, now accepted together with a bearer token instead of 400).
- SR-18: caller-controlled strings (tool, server, method, agent, subject, reason, issuer, content type, client id, lease revoke reason) are logged with `Debug` formatting in the server and the proxy, so a newline in a tool name cannot forge a log line.
- SR-19: BREAKING: the server refuses to start with a non-loopback `listen` and no `[server] public_url`; `public_url` must be an `http(s)` URL with a host and no query or fragment. With `public_url` set, `/.well-known/authzen-configuration` is built from it alone; without it (loopback only) the `Host` header must be `localhost`, `127.0.0.1` or `[::1]` with an optional port, otherwise 400 `invalid_host`.

- SR-32: the Python and TypeScript SDKs raise `Denied` / `DeniedError` for a JSON-RPC `-32003` only when the response carries `X-Attenuo-Decision-Id` and `data.decision_id` is one of the ids in it; an upstream's own `-32003` is an `RpcError`.
- SR-35: `attenuo --admin-token` and `--client-secret` print a warning to stderr (arguments show up in `ps` and shell history); docs, README and the leak demo use the environment or stdin. `--token` and `--subject-token` are unchanged (`ATTENUO_TOKEN`).

- SR-08 (high): AuthZEN evaluated unsigned chains from unauthenticated callers, so anyone who had seen a lease id could get decisions and write audit records for a forged user. - SR-29 (medium): an ECDSA-signed ID token without `jti` could be redeemed for a second root token by re-encoding its signature (`s` to `n - s`), because the replay cache hashed the whole credential. It now hashes the JWS signing input.

- SR-34 (low): an upstream named `attenuo` could write tool-call audit records that look like the server's own issuance, renewal and admin records. The name is now reserved.
- SR-39 (info): an IdP credential with a float `exp` was refused as expired.
- SR-27 (medium): the proxy's session check read only the first `Mcp-Session-Id` header (none if it was not visible ASCII) but forwarded every one, so a caller could slip another principal's session id past the SR-11 binding. `POST`, `GET` and `DELETE` now answer 400 to more than one `Mcp-Session-Id` or a value outside visible ASCII, forward only the checked value, and drop session headers from an upstream response that carries more than one.

### Performance

- Measured token verification on a verified-token cache miss ([performance](docs/design/performance.md#token-verification-on-a-cache-miss-2026-10-24)): `Verifier::verify` is 116 us at 1 hop and 126 us at 3 in process, 107 us of it the two Ed25519 checks, and the proxy's `token_verify_miss` is 170 us p50 against 8.8 us for a hit. No change to the verifier or the token format: `ou_kid` has named the `ou_sig` key since `ou_sig` version 2 and the verifier already uses that one key (a missing or unknown `ou_kid` fails, never a try-every-key fallback; now also tested with the claim removed), and the chain clone is about 1 percent. New `cargo bench -p attenuo-token --bench verify` and `attenuo-bench hot-path --rotate-tokens` (every client cycles through the `--tokens`, which may then exceed `--clients`, so more tokens than the cache's 4,096 make every call a miss).
- Measured the SR-55 per-run lock under concurrent clients ([performance](docs/design/performance.md#the-sr-55-run-lock-under-concurrent-clients-2026-10-24)), file store, 2-hop token, against the build before SR-55: with 32 clients on one run, calls with a limit or kept usage wait 18 to 22 ms for the lock instead of queueing for the store's write gate, and throughput fell by a median of 6 to 9.5 percent (22 percent in the worst pass); runs with clients of their own show no lock wait. Taking the lock later (after the label read and approval take) was measured and not kept, since it moved the wait without raising throughput. `attenuo-bench hot-path` takes `--tokens N` to spread its clients over N runs. No server change.
- Measured the per-value run-limit kinds ([performance](docs/design/performance.md#limit-kinds-callsper-and-distinct-2026-10-24)), one client, file store, 2-hop token: a `calls_per` limit adds about 100 to 170 us at the client p50, the same as `calls`, with a new or a repeated value; a `distinct` limit adds about 190 to 240 us when the value is new (four counter writes, raw value or URL host alike) and nothing measurable when it was seen (no write; its charge transaction is about 25 us). The URL parse of a `derive: host` limit is 0.3 to 1.1 us per URL, under 1 percent of the limit's cost. `attenuo-bench hot-path` has six new configurations (`calls_per_new`, `calls_per_same`, `distinct_new`, `distinct_same`, `host_new`, `host_same`), a `--cells` option, a per-call sequence number in the body, client p90 and the first charge's `used_after` in its check; the `decide` bench has `charge_*/{calls_per,distinct,host}_{new,same}`, `charges_for/*` and `derive_host/*` cells. No server change.
- Fewer long pauses for a single client on the file store ([performance](docs/design/performance.md#single-client-outliers-2026-10-24)). The background WAL checkpointer now syncs the database file before its locked pass, which held appends 10 to 23 ms (median) and now about 3 ms, and syncs the WAL 32 entries ahead of each signed audit checkpoint, whose `FULL` commit took 13 to 16 ms p50 and now 3.4 to 3.9 ms. No commit syncs less or at another level; each change is one more sync on the checkpointer's thread. End to end, one client's calls over 10 ms fell from 0.27 to 0.29 % to 0.08 to 0.09 %; the share over 3 ms (about 1 % at load below 2) is the shared host's scheduling and is unchanged. `attenuo-bench hot-path` now reports requests over 3, 5 and 10 ms at the client and per server stage, and takes `--audit-set key=value`.
- Run usage (`context.usage`) is kept only when something can read it: a loaded policy references `context.usage`, the catalog names `amount` or `destination` for some tool, or `[policy] track_usage = true`. Decided at load and on every policy reload. Otherwise an allowed call to a destructive tool with no token limit makes no lease-store write and its decision record carries no `usage`. That write cost about 0.1 ms per such call from one client on the file store (+86 to +108 us decision mean, +98 to +144 us client p50, `attenuo-bench hot-path` new configuration `usage`), and about 0.7 to 0.9 ms at `durability = "full"` in process ([performance](docs/design/performance.md#run-usage-write-2026-10-24)).
- The lease store and the audit log no longer fight over SQLite's write lock when they share a file (the server's default). Every store of the process on one file now shares an in-process write gate, a FIFO lock held across each write transaction, so writers queue and are woken in turn instead of SQLite's busy handler sleeping 1, 2, 5 ms and so on; reads do not take it, and the lease check no longer waits behind a lease write. A new probe (`crates/attenuo-audit/tests/write_contention.rs`) counted 0.1 to 1.3 busy-handler sleeps per call at 4 and 8 threads before and none after; in process the p99 at 4 and 8 threads fell from 13 to 64 ms to 5 to 17 ms and throughput rose 1.3 to 1.9 times. End to end with a `calls` limit, 4 clients get about 1.3 times the requests per second and the lease-check stage fell from 0.6 to 2.3 ms to about 0.1 ms; with a `sum` limit the change is within noise (one `fsync` per call). Durability is unchanged, and in-memory stores and stores in separate files are not affected. Details in `docs/design/performance.md`.
- A `sum` charge no longer syncs its own commit when the lease store shares the audit log's file (the server's default): it commits at the store's level and the decision append commits with `synchronous=FULL`, one `fsync` that makes both durable before the call is answered or forwarded and that concurrent calls share through group commit (`LeaseStore::charge_sync_deferred`, `AuditSink::append_synced`). Profiling showed the `synchronous` switch costs about 2 us and every `sum` charge makes exactly one `fsync` of the call's 25 to 40 WAL pages, which the durability rule requires. So the change is within noise from one client end to end (about 80 us in process), and gives 1.3 to 1.8 times the throughput of concurrent `sum` charges plus appends in process. Under concurrency SQLite's busy-handler sleeps between the two connections dominated; the write-gate entry above removes them. New `decide` bench cell `decide_limited_*`. Details in `docs/design/performance.md`.
- Measured what output labelling and run limits add to one proxied call (new `attenuo-bench hot-path`, file store, one client, 2-hop token, 5 interleaved runs): an untrusted-output label adds nothing measurable at the client (about 15 us server-side for the run-label write; the `tool_result` append of about 140 us is paid by every allowed call since #42); a `calls` limit adds about 120 to 190 us at p50; a `sum` limit adds about 0.8 to 1.0 ms and halves single-client throughput, because its charge commits with `synchronous=FULL`; an approval round (gated call, operator grant, retry) is about 3.3 ms at p50. New `decide` bench cells for the counter read and the charge. Details in `docs/design/performance.md`.
- Measured the output-labelling cost: a `tool_result` append plus the run label is about 150 us on the file store at `normal` durability, about the same as the decision append, so an allowed call spends about twice as long in the audit log. Details in `docs/design/performance.md`.
- Investigated the proxy's upstream round trip and the `blocking_pool` stage (`perf/proxy-upstream-hop`); no code change. The upstream client already shares one keep-alive pooled `reqwest::Client` and sends each request in one write; the gap to a direct call is CPU wake-up latency between calls on the test VM. Running decisions inline removed the blocking-pool hop but moved the time into the `upstream` stage and cut 8-client throughput, so decisions stay on the blocking pool. Details in `docs/design/performance.md`.
- File-backed audit and lease stores run SQLite in WAL mode with `synchronous=NORMAL`, a busy timeout and a prepared-statement cache. New `[audit] durability = "normal" | "full"` (default `normal`): at `normal` a power failure or kernel crash can lose the newest decisions, never tear one, and the chain still verifies with an earlier head; `full` syncs every commit. Lease revocations always sync. The database now has `-wal` and `-shm` companion files.
- Group commit: audit appends go through one writer thread that commits every queued record in one transaction (up to 256) and answers each caller with its entry; a failed batch is retried record by record, so only a refused record is denied with `audit_error`.
- The proxy caches verified delegation tokens by SHA-256 of the token (4,096 entries), rechecking expiry on every hit, so an agent's repeated calls skip the two Ed25519 verifications (about 100 us). The audit append reads only the head's `seq` and hash instead of decoding the head row, serializes each record once, and the lease check reads a chain's leases with one query.
- Measured on a shared 4 vCPU container (one-hop allow call, 8 and 32 clients): file-backed log from about 460 to 490 calls per second to 3,100 to 4,500; in memory from about 4,300 to 5,300 to 5,000 to 6,600; single-client added latency with a file log from 2.1 ms to 0.85 ms. Details and caveats in `docs/design/performance.md`; results in `docs/design/bench/2026-10-23-vm-audit-write-path.md`.
- `attenuo-bench` gains audit mode `file_full`; new stage bench `cargo bench -p attenuo-server --bench decide`.
- The policy engine caches the chain-to-Cedar translation (entity store, principal, action, resource, and the `originating_user` and `chain` context records) per chain and tool, 4,096 entries, matched on every input it was built from and emptied on a policy reload; a call builds only `context.input`, `session_id` and `now_unix`. Cedar parsing that JSON was about 95 percent of the stage: `PolicyEngine::authorize` went from about 120 / 200 us to 11 / 13 us at 1 / 3 hops (cache hit; a miss costs what every call cost before). Decisions are unchanged; a test holds the cached request equal to the old one-pass translation. New bench `cargo bench -p attenuo-policy --bench policy_stage`, `PolicyEngine::cached_requests()`.
- WAL checkpoints moved off the audit writer. New `[audit] wal_checkpoint_seconds` (default 5; 0 restores SQLite's checkpoints on the writer): the writer connection runs with `wal_autocheckpoint=0` and a background thread checkpoints (`PASSIVE`) every interval or 256 commits, truncates the WAL when idle, and once more at shutdown (`SqliteAudit::with_wal_checkpoints`, `checkpoint_wal`, `SqliteLeaseStore::without_wal_autocheckpoint`). Under continuous load a round that finds the WAL past 64 MB pauses appends briefly so the WAL starts over; the `-wal` file peaks around 100 MB. At `durability = "normal"` the power-failure window is now up to one interval (or 256 commits) of decisions instead of about 1,000 pages. Same binary, file store, 8 clients: p99 21 to 23 ms down to 4 to 8 ms and throughput up 35 to 95 percent; at 32 clients p99 34 to 41 ms down to 11 to 23 ms.
- An append that finds the audit writer idle commits on the caller's thread, skipping the hand-off (about 20 to 40 us).
- End to end on the shared container (one-hop allow call, 1 / 8 / 32 clients): file-backed log 962 / 3,110 / 4,526 to 1,252 / 4,049 / 6,254 req/s with p99 at 8 and 32 clients from 15.5 and 23.8 ms to 5.4 and 13.0 ms; single-client added p50 with a file log 851 to 631 us, in memory 697 to 425 us. Results in `docs/design/bench/2026-10-23-vm-policy-stage.md`.
