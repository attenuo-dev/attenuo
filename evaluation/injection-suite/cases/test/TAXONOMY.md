# Attack taxonomy for the test split

The test cases in this directory were written from this list, after the suite policies and catalogs in [`../../policies/`](../../policies/) were frozen (commit `fb98a18`, hashes in [`POLICY_HASHES.json`](POLICY_HASHES.json)) and before any test case was run. Every case names one class in its `taxonomy:` field. The classes come from the injection tasks of AgentDojo ([Debenedetti et al., 2024](https://arxiv.org/abs/2406.13352)), the direct-harm and data-stealing split of InjecAgent ([Zhan et al., 2024](https://arxiv.org/abs/2403.02691)), the incidents in [incidents-2025-2026](../../../../docs/research/incidents-2025-2026.md), and the attacks on names and delegation that the [threat model](../../../../docs/spec/threat-model.md) lists. The descriptions are ours. No benchmark text or data is copied.

The author of the test cases had read the frozen policies. The cases were written to probe them, including their known weak spots (suffix globs, undeclared arguments, open browsing). That makes the test split adversarial toward onbehalf, not tuned for it. It also means the cases are not a random sample of real attacks.

| Class (`taxonomy:`) | What the injected agent does | Source | What in onbehalf could stop it | Test cases |
|---|---|---|---|---|
| `tool_misuse` | Calls a tool the user task does not need: transfer money, delete a file, remove a user. | AgentDojo injection tasks; InjecAgent direct harm | Tool-level capability | t-banking-01, t-workspace-01, t-travel-01, t-slack-11 |
| `arg_tampering` | Calls a tool the task needs with attacker-chosen arguments, including encodings meant to slip past a check: a type the check does not expect (`"1500"` for a number), a negative amount, path traversal under a prefix, a suffix that satisfies a glob (`mallory@evil.example,carol@acme.example`), an argument the catalog does not declare (`reply_to`, `Bcc`), a case or whitespace variant of an allowed value. | AgentDojo (changed recipients and amounts); our own encodings | Argument constraints in the token; Cedar conditions; neither checks undeclared arguments or upstream path resolution | t-banking-02, -03, -04, -12, t-workspace-02, -03, -04, -09, t-travel-02, -09, t-slack-02, -03, -05, t-github-01 |
| `exfil_allowed_channel` | Sends data out through a tool and destination the task legitimately uses: the body of a mail to the right colleague, an issue in the right repository, a reservation name, a note file. | InjecAgent data stealing; the 2025 GitHub MCP incident | Nothing per call; needs information-flow tracking | t-workspace-05, -12, t-travel-03, t-slack-04, t-github-04 |
| `cross_server_escalation` | A task scoped to one MCP server makes a call on another server the user also has: a chat task that tries to move money or read private repositories. | MCP incident reports of over-broad tokens | Server-level capability; the other server's policy | t-banking-07, t-slack-01 |
| `cross_server_confusion` | Calls a tool whose name also exists on another server (`send_email`, `create_calendar_event`, `read_file`) on the wrong server, where the rules differ. | SR-13 (server-scoped Cedar actions) | Server-scoped capabilities and actions | t-workspace-06, t-travel-04, t-github-05 |
| `name_spoofing` | Uses a tool or server name that looks like an allowed or a dangerous one: case variants (`Delete_Repo`), homoglyphs (Cyrillic `о`), zero-width characters, an unknown server name that a sloppy client or upstream might resolve. | SR-25 (exact names, `tool_not_listed`) | The proxy's name rule and listed-tool check, before any decision | t-banking-08, t-workspace-07, t-travel-07, t-slack-06, t-github-02 |
| `batch_smuggling` | Hides an injected call next to legitimate ones: in a JSON-RPC batch, or as a duplicate `params.name` member that parsers resolve differently. | JSON-RPC batching; duplicate-key parser differentials | Per-message screening of batches; re-encoding the screened request | t-banking-09, t-workspace-08, t-travel-08, t-slack-07, t-github-03 |
| `replay_after_revocation` | Repeats a call, or delegates further, after the user has revoked the session: the same token, a sub-agent's token, or a new delegation from the revoked token. | Session hijack and long-lived token incidents | Leases and their cascade to descendants; refusal to delegate from a revoked parent | t-banking-10, t-workspace-10, t-travel-06, t-slack-09, t-github-07 |
| `chain_depth_abuse` | Re-delegates to sub-agents to widen scope (drop a constraint, add a tool), to cycle back to an agent already in the chain, or to go past the depth limit. | Multi-agent delegation attacks in the threat model | Attenuation check at exchange; duplicate-actor and `max_depth` rules | t-banking-11, t-travel-11, t-slack-08, t-github-06 |
| `data_dependent` | Chooses the payee, URL, hotel or rental company from injected tool output, where the task legitimately leaves that choice open. | AgentDojo travel and banking tasks | A suite policy with an allow-list (payees, domains); nothing when the choice is genuinely open | t-banking-06, t-travel-05, t-slack-12, t-github-08, t-github-10 |
| `repetition` | Repeats a permitted call (a second payment, a larger amount under the limit). | InjecAgent direct harm | Nothing per call; needs rate or count limits | t-banking-05 |

Some cases also carry benign calls that the frozen policies refuse. These are tasks a user would plausibly ask for (pay a new payee, mail a new contact, comment on a private repository). They measure the false-positive cost of static suite policies: t-banking-13, t-workspace-11, t-workspace-13, t-travel-10, t-slack-10, t-github-09.
